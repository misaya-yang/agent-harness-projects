MODULE 01 · AGENT LOOP

Agent Loop 如何把一次请求推进到确定结束？

测试命令已经退出 0，终端为何仍显示运行中？提交层接收操作，Turn 调度后续工作，采样步骤向模型发请求。三个边界分别产生受理、工具结果和回合终态。

INCIDENT 01 · TEST PASSED, TURN STILL RUNNING

命令退出后，Turn 仍要交回执行结果并判断下一步。

一次采样步骤可以因传输失败重新尝试。采样结果成功返回后，Turn 判断模型是否需要跟进，或者输入队列是否还有待处理项。常规续跑条件为 needs_follow_up = model_needs_follow_up || has_pending_input。

  1. 看到命令退出码 0：只确认这次执行成功。
  2. 看到 tool output 回注：模型现在才拿到执行事实。
  3. 看到仍需跟进：模型或排队输入要求再跑一个 step。
  4. 看到 turn completed：整轮才真正结束。

模块目标：能从任意停点判断当前仍在 submission、Turn 还是 sampling step，并用续跑等式解释下一步为什么发生。

心智模型

一个 Turn 可以包含多次模型采样。模型选择工具后，执行结果先写入活跃历史，随后才有机会影响下一次模型判断。

当模型产生工具调用时，工具结果必须先回到历史，下一 step 才能据此判断；两者都为空时，内核进入收尾，还会运行适用的停止钩子。终态由 turn/completed 的 turn.status 报告。成功的 Item、完成的 sampling response 与完成的 Turn 是三个不同事实。

ROOT-CAUSE LENS

把故障归到拥有它的层：模型选错工具、策略拒绝权限、执行环境失败、还是结果没有正确回注。不要把所有失败都叫作“模型不行”。

  1. 提交：输入变成可追踪的操作。
  2. 推理：模型读取上下文并选择下一步。
  3. 行动：工具在权限与沙箱边界内执行。
  4. 回注：结果进入历史，驱动下一次判断。

MODULE 02 · STATE & INTERVENTION

Thread、Turn、Item 怎样承载状态，用户又怎样安全地改变在途任务？

测试仍在运行时，用户追加的限制应进入下一次采样，还是先取消当前工作？先判定在途工具的副作用能否接受，再选择 steer 或 interrupt。

先确定作用对象，再选择动作

状态层次：Thread 保存对话身份和运行设置，持久 Thread 还能恢复历史。Turn 跟踪一轮执行，Item 记录消息、命令、文件变更或工具调用。

Steer 要求 expectedTurnId 与活动 Turn 一致，接受表示输入进入处理队列。下一次模型请求才会采用新输入，某些配置还允许提前中止这一段采样流，以便更早处理输入。Interrupt 发出取消信号，内核尝试短暂收尾再终止任务。检查 turn/completed 及宿主实际状态，确认哪些操作已经发生。

同步 request_user_input 会等待客户端应答。异步交互工具产生带异步标记的消息 Item，立即返回 accepted。用户的回答之后作为新输入抵达。

  1. Thread：保存身份、历史、配置基线与多个 Turn。
  2. Turn：拥有活动任务、取消信号、等待表和 pending input。
  3. Item：通过适用的生命周期通知、增量或历史查询观察。
  4. 干预：steer 提交新输入，interrupt 请求取消，异步消息工具立即返回受理结果。

MODULE 03 · TOOL SYSTEM

工具怎样被发现、并行执行、取消并可靠回注？

工具明明装了，模型为什么没有调用？先查本次请求公布的定义，再查参数、授权和执行，最后确认结果是否进入下一次模型请求。

六个检查点，一条定位顺序

短 trace：可见？ → 参数对？ → 允许？ → 执行了？ → 输出完整？ → 回到历史？。先找第一个“否”，不要跨层猜原因。

DEBUG ORDER

工具未出现 → 查本 step 的可见工具；参数错 → 查 schema；执行被拒 → 查审批、规则与沙箱；命令成功但回答错 → 查输出截断和回注。

模型在每个 step 使用该步组装的工具视图。工具定义可直接发给模型，也可登记后等 tool_search 发现。有些工具只允许普通模型调用，有些只允许 Code Mode 程序嵌套调用。隐藏工具仍可保留在内部派发表。启用延迟发现时，模型可通过 tool_search 取得工具定义。调用是否能进入后续请求还要看回执配对与历史归一化。

另一个容易混淆的新变化：同步用户提问会挂起等待；异步用户提问或消息会立即返回“已接受”，答案以后续输入到达。看到“工具成功”时，先确认它承诺的是完成，还是仅仅送达。

  1. 发现：这个 step 里模型是否看得见。
  2. 校验：参数是否符合结构化契约。
  3. 授权：策略、规则与权限是否允许。
  4. 执行：在限定环境中启动并采集结果。
  5. 归一化：保留头尾诊断并声明截断。
  6. 回注：让模型基于事实继续。

    MODULE 05 · PROMPT & CONTEXT ENGINEERING

    Codex 每个 Step 实际把什么发给模型？

    工具结果明明在界面上，模型为什么没有提到它？把请求拆成基础指令、动态上下文、活跃历史、工具定义与输出格式，再寻找信息在哪一步被裁减。

    REQUEST SHAPEPrompt = Base Instructions + Active Input活跃输入包含已送达的用户输入、环境片段和投影后的历史。压缩检查点提供替换后的历史。工具定义和输出格式有独立字段。

    提示词工程首先是状态工程

    Step 快照：采样准备阶段捕获本步有效的模型设置、环境、权限和工具路由，并组装可用的项目指令及扩展上下文。生效范围取决于更新入口，运行中的采样可以沿用已捕获设置。

    World State 差分：项目指令、权限和环境等区块可以和上一次已知状态比较。知道前态时只注入需要变化的区块。缺少前态时重新提供必要上下文，代价是额外 token。

    稳定前缀：基础指令和稳定区块尽量保持顺序与身份稳定，帮助 prompt cache 命中；环境变化和工具结果随输入历史进入对应位置。具体缓存命中由供应商报告。

    1. Base Instructions：会话级行为基线，不随普通 compaction 被摘要替换。
    2. Dynamic Context：项目、环境、权限和扩展贡献的可差分状态。
    3. Active History：消息、推理项、工具调用与回执的模型工作集。
    4. Tool Specs：本 step 可调用能力的独立结构化字段。

    MODULE 06 · HARNESS ARCHITECTURE

    Core、App Server、客户端与执行环境怎样组成一个 Codex？

    为 IDE 接入人工审批时，哪个组件应等待用户、哪个组件应拦住命令？Core 组织会话，App Server 传请求与事件，客户端收集答案，执行宿主强制资源限制。

    MENTAL MODEL内核拥有会话 actor、Turn 循环、工具与历史语义。协议拥有请求顺序、双向交互、类型生成与多种传输。

    客户端、App Server 与 Core 如何分工

    短 trace：客户端 → App Server → 会话 actor → 工具与模型 → 事件返回客户端。进程内提交用操作队列和回复通道；跨进程接入用双向 JSON-RPC。Rust 类型单向生成客户端类型与 schema，减少多端接口漂移。

    App Server 可嵌入进程，独立服务也可监听 stdio、Unix socket 或 WebSocket。连接先发 initialize 并等待响应，再发 initialized。审批与 MCP 表单采用带 ID 的服务端反向请求，客户端用同一个 ID 应答。实际字段与可选能力见运行版本的 schema。

    更换客户端时，保留同一 Turn 状态语义和审批请求关联。展示方式可以独立替换。远端模型连接、App Server 连接和实际执行宿主也要分别确认。

    MODULE 07 · PERSISTENCE & RECOVERY

    Codex 怎样从追加日志恢复出与在线运行一致的状态？

    客户端断线后，界面怎样补齐漏掉的 Item，Core 又怎样恢复下一次请求的上下文？两条路径读取不同视图，分别由分页协议和检查点重建负责。

    01

    Thread

    拥有身份、设置和运行状态。持久 Thread 支持恢复、派生和归档，临时 Thread 只存在于运行时。

    02

    Turn

    一次请求与 Agent 工作；可 steer、interrupt，完成时发出明确 final status。

    03

    Item

    带标识的可观察记录，可通过生命周期通知、增量或历史查询获取。

    三层对应三种恢复问题

    短 trace：Thread 持有历史 → Turn 持有本次任务 → Item 记录可观察事实。Thread 可恢复、分叉与归档；Turn 可转向、中断并明确收尾；Item 则必须保持调用与输出配对。

    Core 从持久化 rollout 重建模型工作集，使用最新有效的 replacement history 检查点及后续记录，兼容旧日志中的 ThreadRolledBack 记录。客户端视图从另一条路径获取，先 thread/resume，再按需通过 thread/turns/list 与 thread/items/list 补齐历史，用对应 ID 合并实时通知。

    五套记忆，解决五种连续性问题

    Active History 服务下一次模型请求，可被 compaction 替换。Rollout 是每个 Thread 的追加式事实日志，用于恢复与审计，但不会每轮全量进入模型。

      MODULE 12 · RELIABILITY ENGINEERING

      工具失败、模型流断开或进程重启时，系统怎样确定性收口？

      流断开时，一次工具调用可能已经改变文件。先确定可见的最后事实，再决定返回工具错误、重试模型请求、等待用户或结束 Turn。

      失败先分类，再选择去处

      命令非零退出、权限拒绝或可恢复的工具错误通常进入工具结果。不能继续采样的错误会结束回合。诊断时同时比较模型收到的输出、客户端终态和宿主结果。

      采样失败后，错误分类决定能否重试，退避策略可采用服务端给出的时间。重试从当前活跃历史重建请求，部分路径会附加已采集的执行记录。只有实际落下的结果和记录可供重新读取，外部动作的幂等要由工具或业务系统保证。

      模型侧 WebSocket 遇到要求回退的错误或尝试预算耗尽时，可切到 HTTP 流。请求前的历史归一化会补齐部分缺失回执、移除孤儿输出。工具是否真的产生副作用仍应查执行记录。

      1. 分类：可重试、回给模型、终止 Turn 或等待用户。
      2. 收口：每个调用必须有真实或合成回执。
      3. 防重：记录已执行副作用，不假装具备事务。
      4. 验证：断言模型在 wire 上实际收到了什么。
      FIVE-STEP DEBUG LOOP

      定位容器 → 找最后事实 → 检查安全/环境边界 → 核对 active context 与回注 → 设计一个能推翻当前假设的最小实验。

      PROBLEM SET 01 · 架构设计题

      “流在工具执行后断开，重试为什么可能制造重复副作用？”

      展开答题骨架与解耦推演

      【先定位】 工具 Item 已执行，但模型流没有自然完成。重试粒度通常是重新发送从历史派生的请求，不是从断开的字节位置继续。

      【关键风险】 如果模型不知道调用已经执行，就可能再次触发同一命令。采样会从活跃历史重建，启用执行记录时可附上已保留的元数据。若崩溃发生在实际执行与持久记录之间，仍要由工具端判定动作是否已经生效。

      【最小验证】 检查第一次调用是否有稳定 call id、执行记录是否完整、重试请求是否带回已执行事实，以及外部动作本身能否设计为幂等。

      【答题结论】 Agent 重试的底线不是“绝不重复”，而是“重复前拥有足够事实，并让副作用尽量幂等”。

      PROBLEM SET 02 · 故障排查题

      “用户提交了 MCP 表单，为什么工具仍然超时？”

      展开答题骨架与排查路径

      【先定位】 分别验证服务器是否发出反向请求、客户端是否展示并回复、等待项是否收到结果。取消和超时也会清理等待项。

      【关键证据】 先匹配 App Server 反向请求 mcpServer/elicitation/request 的 JSON-RPC ID，再在 Core 侧核对 MCP server 和它自己的请求 ID。查看 action 与 content，再确认等待项是否已取消。turnId 可空，只用于关联回合。

      【避免误判】 MCP over HTTP 还需区分回复 POST 的 HTTP 状态与另一个待处理请求的 RPC 结果。追踪最后一个确认信号便能确定问题在客户端、App Server 桥接还是 MCP 传输。

      PROBLEM SET 03 · 安全攻防题

      “WorkspaceWrite 与 OnRequest 同时存在，跨工作区写入该怎么判？”

      展开答题骨架与权限决策

      【先分轴】 WorkspaceWrite 描述当前可写边界，OnRequest 描述何时允许询问。命令规则与企业约束还可能进一步收紧。

      【判断顺序】 先看规则是否禁止或要求询问，再看策略是否允许展示询问，最后由权限画像与系统沙箱执行。明确批准后的尝试可能保留强制限制，也可能在沙箱外执行，取决于调用方式与有效策略。查看该次执行实际采用的沙箱。

      【答题结论】 三轴是组合关系，不是二选一。要回答谁能放行，必须先指出当前拒绝来自哪一轴。

      速查术语

      Thread
      包含身份、运行设置和多个 Turn 的会话容器，可选择持久化。
      Turn
      一次用户请求及 Agent 随后完成的全部工作。
      Item
      消息、命令、文件变更或工具调用等最小输入输出单元。
      Base Instructions
      会话级模型行为基线，与动态上下文和活跃历史分层。
      Active History
      Agent Loop 为下一次模型请求维护的可替换工作集。
      Rollout
      每个 Thread 独立追加的持久化事实日志。
      Compaction
      生成 checkpoint 并替换 active history；不会把完整 transcript 改写成一个文件摘要。
      Memories
      跨 Thread 提取与整理的长期事实层，不替代精确 resume。
      PermissionProfile
      运行时有效的文件系统、网络与沙箱执行方式。
      AskForApproval
      决定哪些工具操作可以发起审批的策略。
      Hook
      在 Codex 生命周期节点运行的确定性脚本或 MCP 处理器。
