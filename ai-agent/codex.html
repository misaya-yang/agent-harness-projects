MODULE 01 · AGENT LOOP

Agent Loop 如何把一次请求推进到确定结束？

测试命令已经退出 0，终端为何仍显示运行中？提交层接收操作，Turn 调度后续工作，采样步骤向模型发请求。三个边界分别产生受理、工具结果和回合终态。

INCIDENT 01 · TEST PASSED, TURN STILL RUNNING

命令退出后，Turn 仍要交回执行结果并判断下一步。

一次采样步骤（sampling step）可以因网络传输波动而单独重试，这并不影响外部已生效的工具状态。采样响应成功返回后，宿主回合调度器（Turn）依据续跑判定式 needs_follow_up = model_needs_follow_up || has_pending_input 决定走向：若模型提出了新的工具调用，或者会话输入队列中仍有待处理的插话，调度器就必须驱动下一个 sampling step；只有两者皆为空时，Turn 才进入终止收尾。

  1. 看到命令退出码 0：只确认这次执行成功。
  2. 看到 tool output 回注：模型现在才拿到执行事实。
  3. 看到仍需跟进：模型或排队输入要求再跑一个 step。
  4. 看到 turn completed：整轮才真正结束。

模块目标：能从任意停点判断当前仍在 submission、Turn 还是 sampling step，并用续跑等式解释下一步为什么发生。

心智模型

在 Codex 的运行时架构中，一个 Turn 包含了一次或多次模型采样步（sampling step）。模型输出工具调用提议后，宿主先在受限执行环境中启动命令，并把规范化后的回注结果写入活跃历史（Active History），下一次模型请求才有依据展开后续推理。

当模型输出包含工具调用时，宿主必须先完成工具调度并把执行结果回注到活跃历史，下一次采样步才能据此判断；只有当模型不再产生工具调用、且当前回合没有待处理排队输入时，内核才正式进入收尾流程，并在触发注册的停止钩子后收束回合。终态由协议事件 turn/completed 中的 turn.status 正式宣告。在工程排障中，单个命令 Item 的执行成功、一次模型流式响应的接收完毕，与整个 Turn 的收敛完成，是三个处于不同控制层级的独立事实。

ROOT-CAUSE LENS

把故障归到拥有它的层：模型选错工具、策略拒绝权限、执行环境失败、还是结果没有正确回注。不要把所有失败都叫作“模型不行”。

  1. 提交：输入变成可追踪的操作。
  2. 推理：模型读取上下文并选择下一步。
  3. 行动：工具在权限与沙箱边界内执行。
  4. 回注：结果进入历史，驱动下一次判断。

MODULE 02 · STATE & INTERVENTION

Thread、Turn、Item 怎样承载状态，用户又怎样安全地改变在途任务？

测试仍在运行时，用户追加的限制应进入下一次采样，还是先取消当前工作？先判定在途工具的副作用能否接受，再选择 steer 或 interrupt。

先确定作用对象，再选择动作

状态层次：Thread 负责承载会话全局身份、配置基线与完整执行脉络，持久化的 Thread 还支持历史重放与状态分叉；Turn 负责调度单次用户请求引发的多步流转，维护当前的取消信号与输入排队区；Item 则是不可变的事实单元，精确记录单条消息、终端命令、文件改动或工具调用。

Steer 用于在任务执行途中注入新的指导约束。客户端调用该接口时必须显式传入与当前活动回合一致的 expectedTurnId；App Server 校验通过后返回受理响应，并将新输入置入当前 Turn 的待处理队列（pending input）。正在运行中的工具不会被暴力掐断，宿主在组装下一次模型采样时才将其并入上下文；若启用了快流截断开关，宿主也可主动中止当前未完的文本生成，以尽早消化该干预指令。Interrupt 则用于紧急刹车。App Server 向核心状态机广播取消信号，宿主停止后续任务排队并尽力对在途子进程做受限清理。注意中断操作无法回滚已经提交到磁盘的文件或网络调用，运维排查时必须结合 turn/completed 的终态以及执行宿主的物理状态，核验真实发生的修改边界。

人机协作的等待机制分为两种截然不同的协议契约：同步 request_user_input 会由 App Server 发起反向请求并阻塞挂起当前 Turn，直至用户在客户端界面完成表单并应答后，工具才产出结果继续推进；而异步交互工具（如 request_user_input_async）在将交互提议固化为带异步标识的消息 Item 后便直接返回 accepted，当前步正常收口，用户的答复将在未来作为全新的输入进入下一轮队列调度。

  1. Thread：保存身份、历史、配置基线与多个 Turn。
  2. Turn：拥有活动任务、取消信号、等待表和 pending input。
  3. Item：通过适用的生命周期通知、增量或历史查询观察。
  4. 干预：steer 提交新输入，interrupt 请求取消，异步消息工具立即返回受理结果。

MODULE 03 · TOOL SYSTEM

工具怎样被发现、并行执行、取消并可靠回注？

工具明明装了，模型为什么没有调用？先查本次请求公布的定义，再查参数、授权和执行，最后确认结果是否进入下一次模型请求。

六个检查点，一条定位顺序

短 trace：可见？ → 参数对？ → 允许？ → 执行了？ → 输出完整？ → 回到历史？。先找第一个“否”，不要跨层猜原因。

DEBUG ORDER

工具未出现 → 查本 step 的可见工具；参数错 → 查 schema；执行被拒 → 查审批、规则与沙箱；命令成功但回答错 → 查输出截断和回注。

在模型每次发起采样前，宿主都会为该 step 动态组装专用的工具定义集合（Tool Specs）。对于核心高频工具，其结构化契约直接序列化进入请求体；而对于规模庞大的扩展工具池，宿主可开启延迟发现机制，仅注入轻量索引，允许模型在推理中按需通过 tool_search 检索具体定义。此外，调用权限受运行时模式限制：基础工具面向模型的自由生成开放，而部分高危系统操作仅允许在 Code Mode 沙箱内由程序化脚本嵌套派发。

模型提出的工具调用能否合法闭环，取决于工具执行器与会话历史的严格对接：每一个生成的 tool_call 必须以稳定的 call_id 与执行环境返回的 tool_result 成对匹配，并在跨过输出长度预算（截断与归一化）后注入模型活跃工作集。看到日志中记录“工具成功”时，务必分清它代表的是命令已在宿主中运行结束，还是仅代表异步消息已成功递入目标系统的收件箱。

  1. 发现：这个 step 里模型是否看得见。
  2. 校验：参数是否符合结构化契约。
  3. 授权：策略、规则与权限是否允许。
  4. 执行：在限定环境中启动并采集结果。
  5. 归一化：保留头尾诊断并声明截断。
  6. 回注：让模型基于事实继续。

    把一次拒绝拆成三问

    短 trace：命令规则分类 → 是否允许询问 → 权限画像与沙箱执行。排查权限拦截时，必须依次核对三道防线：① 命令分类规则（Command Rules）针对操作签名、参数及路径，静态裁决该动作属于直接允许、需要人工介入还是禁止执行。细粒度策略（Granular Policies）还能分别控制沙箱提权、规则提问、Skill 脚本或 MCP 交互的开关，关闭某类权限后涉及该类的操作将直接被拒。② 审批路由机制（AskForApproval / Guardian）在规则要求询问时，决定是由自动化 Guardian 模型进行合规审查，还是经由 App Server 向终端用户弹出交互审批；若自动审查超时、执行出错或无法得出明确裁决，系统按安全保守原则一律判为拒绝。③ 宿主执行有效边界（PermissionProfile 与 SandboxPolicy）在获得放行后，底层进程能够触达的文件范围与网络出口，依然受到运行时有效权限画像（PermissionProfile）与操作系统沙箱机制的物理限制。沙箱未开放的宿主路径，任何应用层批准都无法直接穿透。

    受管网络还可以把出口收敛到代理，启用凭据 broker 时，沙箱进程只看到占位值，真实凭据在出口注入。当前有效边界由 PermissionProfile 表示，包含由 Codex 管理、由外部强制与停用外层沙箱三种形态。SandboxPolicy 仍用于兼容配置与协议。排查拒绝时同时核对命令规则、审批路由和执行宿主采用的权限。

    MODULE 05 · PROMPT & CONTEXT ENGINEERING

    Codex 每个 Step 实际把什么发给模型？

    工具结果明明在界面上，模型为什么没有提到它？把请求拆成基础指令、动态上下文、活跃历史、工具定义与输出格式，再寻找信息在哪一步被裁减。

    REQUEST SHAPEPrompt = Base Instructions + Active Input活跃输入包含已送达的用户输入、环境片段和投影后的历史。压缩检查点提供替换后的历史。工具定义和输出格式有独立字段。

    提示词工程首先是状态工程

    Step 快照冻结：在每次发起采样前，宿主都会对运行时状态拍摄原子快照，固化当前步生效的模型超参、工作目录环境、权限边界以及工具路由表。这确保了流式推理过程中即使客户端并发修改了偏好，当前采样也拥有不可变的上下文基线。

    World State 差分注入：项目全局规约、环境上下文与权限声明在内部维护状态版本。宿主在组装请求时与上一步的已知状态比较：仅对发生漂移的区块注入增量快照，而在状态未变时复用前态，避免浪费宝贵的输入 token。

    稳定前缀与缓存对齐：将会话级行为基线（Base Instructions）与固定结构置于请求最前列，保持字节与顺序确定性，最大化利用模型供应商的前缀缓存（Prompt Cache）；环境增量与交互历史作为活跃历史（Active History）追加于后，工具定义以 Tool Specs 独立传输，结构化要求绑定至 Output Schema。

    1. Base Instructions：会话级行为基线，不随普通 compaction 被摘要替换。
    2. Dynamic Context：项目、环境、权限和扩展贡献的可差分状态。
    3. Active History：消息、推理项、工具调用与回执的模型工作集。
    4. Tool Specs：本 step 可调用能力的独立结构化字段。

    MODULE 07 · PERSISTENCE & RECOVERY

    Codex 怎样从追加日志恢复出与在线运行一致的状态？

    客户端断线后，界面怎样补齐漏掉的 Item，Core 又怎样恢复下一次请求的上下文？两条路径读取不同视图，分别由分页协议和检查点重建负责。

    01

    Thread

    拥有身份、设置和运行状态。持久 Thread 支持恢复、派生和归档，临时 Thread 只存在于运行时。

    02

    Turn

    一次请求与 Agent 工作；可 steer、interrupt，完成时发出明确 final status。

    03

    Item

    带标识的可观察记录，可通过生命周期通知、增量或历史查询获取。

    三层对应三种恢复问题

    短 trace：Thread 持有历史 → Turn 持有本次任务 → Item 记录可观察事实。Thread 维系持久身份、配置基线与全量历史，支持恢复、派生与归档；Turn 维系活动执行周期，支持通过 steer 转向、interrupt 中断并保证确定性收束；Item 则保证每个工具调用的提议与回执严格配对。

    会话恢复分为内核重建与客户端追赶两条独立路径：Core 从持久化 Thread Rollout 重建模型工作集，以最新有效的 replacement history 检查点为基石向后重放未压缩事件，并兼容处理历史记录中的 ThreadRolledBack 标记；客户端视图则先调用 thread/resume，再按需通过 thread/turns/list 与 thread/items/list 补齐历史记录，并以稳定 ID 合并实时增量通知。

    对于长历史会话，客户端在 resume 时可配置 excludeTurns 避免全量加载阻塞，或借助 initialTurnsPage 快速拉取首屏；thread/items/list 支持以指定 Turn 内的 Item ID 作为游标稳定续页。客户端断线重连后，应先比对已持久化的历史事件与当前在途状态，防止误判在途任务已经终结。

    五套记忆，解决五种连续性问题

    Active History 服务下一次模型请求，维护当前推进所需的短期上下文与工具回执，可被随后的 compaction 整体替换。Thread Rollout 是每个 Thread 的追加式事实日志，采用 append-only 记录全量生命周期事件，专用于恢复、分支重建与审计，但不会每轮全量进入模型。

    Guardian Review History 保留授权判断所需的原始证据，专供安全审查与权限裁决，普通 compaction 不删除已有的授权证据。Verified Answers 保存少量由宿主验证的回答，保留条数与字节数受限，超出预算时审查上下文可能标记证据不全。

    Long-term Memories 跨 Thread 工作：具体写入与读取取决于 Thread 的记忆版本和配置，非完整聊天备份，而是蒸馏出的全局事实与偏好。实验接口 thread/memory/read 可读取已经加载的 Thread 对应版本的摘要，返回空值可能意味着禁用、缺失、不可读或内容为空。

    1. 工作记忆：当前模型需要继续任务的 active history。
    2. 事实日志：Thread 独立 rollout，追加发生过的事件。
    3. 授权证据：供 Guardian/审批判断，不依赖模型摘要。
    4. 长期记忆：跨会话的精选事实，不是完整 transcript。

    INCIDENT 08 · MODEL FORGOT, APPROVAL STILL VALID

    模型看不到旧信息，不代表授权证据已被删除。

    普通压缩后，审查证据和仍有效的验证回答按独立预算保留。分页线程 revert 则从留存的历史前缀重建，旧 rollout 中的历史回滚事件也会改变重放范围。按 Thread 恢复精确状态用 resume，跨 Thread 的 Memories 用于提供经过筛选的上下文。

    1. 继续当前任务：读 Active History。
    2. 恢复原 Thread：读最新 checkpoint 与 rollout 尾部。
    3. 判断授权：读审查证据与仍有效的 Verified Answers。
    4. 跨 Thread 延续偏好：检索 Long-term Memories。

    判断练习：“新 Thread 应该精确恢复上一 Thread 最后一条工具调用吗？”不应该；这是 resume 的责任。长期记忆只保存值得跨会话复用的事实与偏好。

      MODULE 12 · RELIABILITY ENGINEERING

      工具失败、模型流断开或进程重启时，系统怎样确定性收口？

      流断开时，一次工具调用可能已经改变文件。先确定可见的最后事实，再决定返回工具错误、重试模型请求、等待用户或结束 Turn。

      失败先分类，再选择去处

      面对运行异常，首要任务是将错误准确归因到负责层：命令非零退出码、权限拒绝或已知的工具环境异常，应格式化为结构化工具结果回注模型，驱动模型在下一步展开自纠；若遇到无法恢复的底层传输中断、模型配额耗尽或进程崩溃，应立即以明确状态终止当前 Turn 并通知客户端，严禁伪造假成功。诊断排查时，必须将模型在请求中看到的实际提示词、App Server 发出的终态事件与宿主保留的物理执行痕迹进行三方交叉比对。

      采样失败后，错误分类决定能否重试，退避策略可采用服务端给出的建议间隔。重试并非简单重复发送旧字节，而是以当前活跃历史为最新真理源重新组装模型请求，部分路径会附加已采集的执行记录。对于已经在执行宿主中落盘的文件写入或远程调用，工具本身必须具备幂等设计或具备状态探查能力，严禁因为上层盲目重试造成破坏性的重复副作用。

      模型侧 WebSocket 遇到要求降级的错误或尝试预算耗尽时，连接管理器可自动平滑回退至 HTTP 分块流式传输。请求前的历史归一化会补齐部分缺失回执、移除孤儿输出。工具是否真的产生物理改动，仍应探查执行宿主的实际状态。

      1. 分类：可重试、回给模型、终止 Turn 或等待用户。
      2. 收口：每个调用必须有真实或合成回执。
      3. 防重：记录已执行副作用，不假装具备事务。
      4. 验证：断言模型在 wire 上实际收到了什么。

      PROBLEM SET 01 · 架构设计题

      “流在工具执行后断开，重试为什么可能制造重复副作用？”

      展开答题骨架与解耦推演

      【先定位】 工具 Item 已执行，但模型流没有自然完成。重试粒度通常是重新发送从历史派生的请求，不是从断开的字节位置继续。

      【关键风险】 如果模型不知道调用已经执行，就可能再次触发同一命令。采样会从活跃历史重建，启用执行记录时可附上已保留的元数据。若崩溃发生在实际执行与持久记录之间，仍要由工具端判定动作是否已经生效。

      【最小验证】 检查第一次调用是否有稳定 call id、执行记录是否完整、重试请求是否带回已执行事实，以及外部动作本身能否设计为幂等。

      【答题结论】 Agent 重试的底线不是“绝不重复”，而是“重复前拥有足够事实，并让副作用尽量幂等”。

      PROBLEM SET 02 · 故障排查题

      “用户提交了 MCP 表单，为什么工具仍然超时？”

      展开答题骨架与排查路径

      【先定位】 分别验证服务器是否发出反向请求、客户端是否展示并回复、等待项是否收到结果。取消和超时也会清理等待项。

      【关键证据】 先匹配 App Server 反向请求 mcpServer/elicitation/request 的 JSON-RPC ID，再在 Core 侧核对 MCP server 和它自己的请求 ID。查看 action 与 content，再确认等待项是否已取消。turnId 可空，只用于关联回合。

      【避免误判】 MCP over HTTP 还需区分回复 POST 的 HTTP 状态与另一个待处理请求的 RPC 结果。追踪最后一个确认信号便能确定问题在客户端、App Server 桥接还是 MCP 传输。

      PROBLEM SET 03 · 安全攻防题

      “WorkspaceWrite 与 OnRequest 同时存在，跨工作区写入该怎么判？”

      展开答题骨架与权限决策

      【先分轴】 WorkspaceWrite 描述当前可写边界，OnRequest 描述何时允许询问。命令规则与企业约束还可能进一步收紧。

      【判断顺序】 先看规则是否禁止或要求询问，再看策略是否允许展示询问，最后由权限画像与系统沙箱执行。明确批准后的尝试可能保留强制限制，也可能在沙箱外执行，取决于调用方式与有效策略。查看该次执行实际采用的沙箱。

      【答题结论】 三轴是组合关系，不是二选一。要回答谁能放行，必须先指出当前拒绝来自哪一轴。
