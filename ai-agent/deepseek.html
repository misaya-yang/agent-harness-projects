EVENTS FIRST · RECOVERY BY DESIGN

DeepSeek Harness 如何在崩溃后重建会话并判断能否续做。

工具调用留下了记录，进程却在保存结果前崩溃。DeepSeek Harness 让插件围绕会话事件协作，从记录重建下一步模型可见的历史。能重建历史，不代表已经知道文件是否写入；这决定了恢复时哪些工具可以重试。

CHAPTER 01 · COMPOSITION

场景一：你改了“核心”，但真正生效的是另一棵插件树。

dsh 的循环、模型、工具、会话和持久化通过插件服务组合；有效组合树决定运行行为。

源码更新 · 插件装配

相同的插件配置在升级后可能被跳过。

启动时优先检查插件声明的 engines.dsh，缺省时才看 DSH peer 范围。不兼容的 bundle 会被跳过并报告；普通插件行也在加载前检查。版本豁免只对指定包版本和指定运行时版本生效。排查工具缺席时，先确认该行是否成功挂载，再查 Agent 的工具注册。

CHAPTER 02 · TURN / STEP / REQUEST

场景二：用户中途补充一句话，Agent 却提前宣布完成。

Turn 可以包含零个或多个 Step。Step 承载一次逻辑模型请求及其工具批次，失败重试可以在同一 Step 内发起多次实际调用。

Turn / Step 事件步进机idle
  1. turn/start
  2. 领取输入 · pre-step
  3. step/start
  4. system / user
  5. request/header
  6. 实时助手帧
  7. assistant/message
  8. tool/call → result
  9. step/end
  10. 下一 Step · 总结
  11. turn/end

观察哪些事件进入日志，哪些只发给当前连接。

短 trace：用户消息在步边界进入

steer 进入 next-step 并唤醒；followup 进入 next-turn 并唤醒；inject 进入 next-step 但不唤醒。要预测一条插话何时生效，先看投进了哪个队列。Turn 启动时会取走全部 next-step 输入和一个 next-turn prompt；同一 Turn 后续的 Step 只取 next-step。准备停止的钩子结束后会再检查收件箱。

判断法：看“欠下的工作”

工具结果可能要求再请求一次模型。触发收尾时，循环还要检查是否有新的 next-step 输入；next-turn 输入留给下一回合。

CHECKPOINT · TRACE

练习：同一 Step 的请求失败两次、第三次成功。应该有几个 Step，几个 Request？

查看答案

一个 Step、三次实际请求。重试复用该 Step 的模型选择、提示词装配和工具集合；已接纳的用户消息只记录一次，每次调用都从当前视图重建请求。

本章小结

相位负责“现在能不能跑”，日志负责“已经发生了什么”，收件箱负责“还欠什么”。

CHAPTER 03 · SESSION LOG & SURFACE

场景三：工具似乎已执行，崩溃后却没有结果记录。

Session Log 记录已提交的事件，Surface 提供当前模型历史。页面也能先收到实时流式帧。已结算的消息或失败尝试可以进入会话日志；内存提交后完成存储 flush 才跨过持久化检查点。

CRASH TAIL恢复时必须区分“没开始”和“结果未知”。日志中的工具提议若尚无调用记录，恢复时补 TOOL_NOT_STARTED。已有调用记录但缺结果则补 TOOL_OUTCOME_UNKNOWN，再次执行前先核对实际副作用。

短 trace：一次流只有一个结算事件

agent/assistant-stream 送实时帧。结算时，assistant/message 携带消息与紧凑流记录，assistant/attempt 仅保留尝试证据。依次点击三个按钮。每点一次，先看界面多了哪段文字，再核对日志多了哪条记录、模型计数有没有变化。

判断法：先找最后一个持久事实

持久化后端通过写句柄保存事件，flush 给出持久化检查点。发行组合使用 JSONL 写入 V4 格式。先点「模型提议 read」后直接恢复，再重置并加点「记录调用」后恢复。实验假设已记录的事件都已 flush；真实崩溃只读取实际留存的日志前缀。

CHECKPOINT · DECIDE

练习：一次写文件工具留下调用记录，日志却没有结果。恢复后先查什么？

查看答案

先检查目标文件和本次操作的记录。调用事件在工具执行前已写入，此时无法区分刚要执行、执行到一半或执行完成。

本章小结

日志是真相不代表日志永远完整；关键能力是让残缺也有类型、有修补顺序、有安全的下一步。

CHAPTER 04 · PROMPT & REQUEST

场景四：把每轮变化的状态塞进 System Prompt，缓存与审计一起失效。

静态规则放稳定的提示词片段；沙箱、审批、委派等动态状态作为带“取代旧快照”说明的 user 消息进入历史。

SYSTEM具名片段按顺序拼接

相同输入得到相同字节，给前缀缓存稳定基础。

RUNTIME变化时追加快照

旧状态可审计、可被压缩。

SURFACE从事件折叠消息

请求不维护第二份易漂移的消息数组。

HEADER记录实际生效配置

记录 Provider、模型配置和工具。提示词由 system/message 重建。

短 trace：一次请求的三层输入

装配 System 与 Tools → 固定 adapter → 记录 system、用户输入和变化的运行时提醒 → 按需记录 Header 与 Context → 从 Surface 派生消息并发送冻结请求。

判断法：易变内容离前缀越远越好

把身份放在稳定片段，把易变政策追加成运行时提醒。支持历史内更新的模型路由可在同一请求序列中追加新的系统提示；其他路由会从首个 system 节点重建。缓存命中可能降低重复输入成本，消息仍占上下文容量。

CHECKPOINT · CLASSIFY

练习：当前沙箱从只读变为可写，应该改 System Prompt 还是追加运行时快照？

查看答案

追加新的运行时快照，并明确取代此前快照。

本章小结

“模型看见什么”必须有可重放来源；“放在请求哪里”由稳定性和语义寿命决定。

CHAPTER 05 · TOOL PIPELINE

场景五：第二个工具先完成，模型下一步先读谁的结果？

原生执行器并行运行标为可并发的工具，按模型调用顺序提交结果。程序化工具调用（PTC）让模型通过 run_code 运行一段程序，程序中的子调用继续经过同一策略管线。

源码更新 · 工具生命周期

“准备中”是单独可观察的阶段。

客户端现在区分工具准备、开始和结果，并在持久历史重放时恢复这些展示状态。准备进度只显示模型在构造工具参数。判断副作用时要核对调用、结果及实际工作区。

面试追问：为什么 UI 的准备进度不能作为恢复时重试工具的依据？

工具失败定位器选择症状
FIRST EVIDENCE

选择一种失败

系统会指出最先查看的管线阶段。

  1. 记录调用：参数冻结，模型提出的内容先成为事实。
  2. 政策判断：调用前钩子可放行、拒绝、取消或请求审批。已经记录的参数保持原样。
  3. 单调守卫：审批放行后仍运行注册的守卫。守卫只能拒绝或放弃表态。
  4. 执行与后处理：执行包装层可加取消信号。工具返回后先规范化结果，再由后置策略调整模型可见输出，最后发送结果通知。
  5. 顺序提交：并行派发，按模型调用顺序提交结果。

并发判断：默认独占

只有并发分类器明确返回 true，调用才进入并发池。分类器缺失、抛错或结果不明确时，这次调用独占执行。默认池上限为 10。

取消判断：每个调用都要配对

取消时先排空已启动调用，未派发的调用补合成错误结果。调度器自身坏掉则不能伪造“已恢复”的结果。

CHECKPOINT · SCHEDULE

练习：调用 A 慢、B 快，二者都声明并发安全。结果先写谁？

查看答案

A、B 可以同时执行；A 的结果先提交。较快的 B 需要等待前面的结果，如果中间插入独占调用，还要等前一组工作结束。

本章小结

工具结果是下一步模型输入，所有政策、呈现与错误必须在唯一提交点前完成。

CHAPTER 06 · CAPABILITY SEAMS

场景六：换一个执行后端，却被迫改遍所有上层工具。

文件服务、进程服务各自定义调用契约；Provider 实现本地或远程操作，文件工具、Bash 和终端经同一契约调用。

01 / DEFINITION

定义

给出窄接口、失败词汇与生命周期，不绑定实现位置。

02 / PROVIDER

提供

本地沙箱或远程运行时实现同一契约，并声明哪些操作受支持。

03 / CONSUMER

消费

工具与表面只依赖接口，不出现后端名称分支。

CHECKPOINT · SEAM TEST

练习：怎样判断一个执行世界抽象真的切到位？

查看答案

替换 Provider 后，Consumer 不增加后端分支；不支持的能力在派发前暴露，而不是静默丢失。

本章小结

可替换性不是接口数量，而是差异是否被完整封在边界里。

收到 SANDBOX_UNAVAILABLE 时先查执行后端。若后端可用而写入仍被拒，依次核对当前目录、允许写入的目录和目标文件的系统权限。审批通过后，执行环境仍会检查文件权限。

CHECKPOINT · THREAT MODEL

练习：进入 worktree 后，要改原始项目的文件。一次审批怎样影响这次写入？

查看答案

如果原项目目录在 worktree 之外，也未列为额外可写根，原文件会被拦截。一次批准只改变该调用使用的文件策略，Session 后续调用仍用原策略。

本章小结

每道安全边界都要准确声明防谁、不防谁、失败时做什么。

CHAPTER 08 · PROFILE / BUNDLE / PRESET

场景八：改了一个 Agent 的工具集，却意外影响所有会话。

Profile 组装进程，bundle 提供能力集合，patch 覆盖插件行；Agent 作用域中的 preset 负责单个 Agent 的人格、工具限制与子组合。Web 等发行 Profile 通过 dsh-agent-preset 配置行声明 config.plugins。

判断法：先问生命周期

全进程共享能力放 Profile。Preset 注册表保留现有 Agent 已绑定的配置代际，子 Agent 可继承该代际。Session 打开过首个 Turn 后，公开的 preset 切换入口会拒绝变更。

设置为什么另有一套机制

设置面板只投影插件声明为可在线修改的字段，按配置行 ID 保存到当前 Profile 的 patch。修改时核对 revision；秘密字段会被保留，避免把遮盖后的值写回。

CHECKPOINT · SCOPE

练习：只让研究子代理看见三个只读工具，应改全局 Profile 还是子 Agent 作用域？

查看答案

改子 Agent 作用域的工具 restriction。全局 Profile 会扩大影响面。

本章小结

配置层级就是影响半径。能说清何时生效、影响谁、如何回滚，才算选对层。

CHAPTER 09 · CONTEXT & COMPACTION

场景九：摘要写得太长，下一轮仍没有回答空间。

压缩保留原始事件，并通过带锁的选区、摘要和替换提交改变模型可见视图。

源码更新 · 压缩预算

窗口上限必须给本次回答留空间。

三种触发不是一回事

每一步的边界都会检查上下文压力。估算阈值时既要看窗口的默认比例 0.8，也要给后续输出留出空间。请求错误链处理 Provider 确认的窗口溢出，空闲维护相位处理手动压缩。

两级瘦身各守一段时间

spill 在新结果产生时外置超大文本；prune 在压力检查时缩旧结果。二者失败都不能把成功工具改判为失败。

练习：摘要生成期间又来了新消息，能否直接提交旧摘要？

查看答案

自动压缩会检查整个 Surface 是否变化；手动压缩重新检查被选区间与其适用条件。检查失败时拒绝替换。

本章小结

压缩目标是用可追溯替换换取更小、仍可继续工作的模型视图。

CHAPTER 10 · EXTENSIONS & MULTI-AGENT

场景十：后台子代理还活着，宿主重启后却再也找不到它。

一次性 run 随结果结算。可续联 child 有身份和自己的 Inbox，能否冷恢复取决于 Session 持久化和 Provider。Workflow 复用子代理，Team 启用后在同一代理树上维护共享任务板。

ONE-SHOT一次性 run

失败折成停止原因，句柄结算后释放。

CONTINUABLE可续联 child

持久 descriptor + Session + Inbox，驻留实例可以丢。

WORKFLOW脚本 fan-out

执行 TypeScript 工作流的独立进程使用调用会话的文件策略；编排器管理子代理数量和并发。

TEAM共享任务板

根 Session 持有任务记录。成员沿同一子代理树发现、发消息和冷恢复。

短轨迹 · 子代理消息

选择目标 → 目标接收入箱 → 返回 messageId

运行中的目标在下一 Step 接收 Steer，未驻留的可续联目标先恢复。返回值确认入箱。历史 team/message/queued 与 team/message/delivered 仍可解码，当前投递由 subagent runtime 负责。

运行时扩展

查看插件能力与安装插件走不同入口。

Standard 和 Creator 使用 cordis_inspect 只读查询运行版本、有效配置与工具。plugin_manager 可改整个 Profile 的持久配置；它要求足够权限，安装的 Host 插件会在宿主进程运行。程序和浏览器仍可用 Host runner 管理进程内临时 Package。

从操作结果判断目标状态

用 list_agents 查看成员状态。send_message 成功说明消息已经入箱，子任务可能还在运行。wait_agent 等待调用者自己的 next-step 输入。发行组合默认关闭 interrupt_agent。

预算必须在协调者一侧

Subagent Provider 声明支持的能力，Workflow 限并发与子代理总数，Team 在任务板上限制任务数并用 revision 检查并发修改。

CHECKPOINT · RECOVER

练习：list_agents 显示一个成员是 inactive，能说明任务完成吗？

查看答案

inactive 仅表示没有正在执行的 Turn。向可续联成员调用 send_message；若成员已卸载，运行时先读历史并尝试恢复，返回的 messageId 只确认入箱。

本章小结

恢复需要可读取的历史、持久身份和支持续联的 Provider。入箱回执、目标回复与任务完成是三个独立的观察点。

短 trace：Web 有两条通道

一次请求一次响应的方法走 HTTP；流式 token 走带心跳的 WebSocket 多路复用。断线恢复时，持久会话历史与进行中的流分别处理。收到一次 HTTP 响应，仍需等待任务所需的会话事件。

CHAPTER 12 · ERROR, RECOVERY & PRACTICE

最后一题：面对“Agent 又做了一遍”，怎样用证据而不是猜测排障？

把整门课压成一套诊断法：确定有效组合，找最后持久事实，区分控制状态与模型视图，按错误码路由，再用可推翻假设的最小实验验证。

01 / ROUTE

错误码决定处理者

默认策略允许为限流、服务故障、超时、传输和空响应重试。窗口溢出走压缩恢复；配额与凭据错误默认不重试。

02 / CHECKPOINT

执行前的持久化检查点

发行 base 中的 checkpoint policy 在模型请求、顶层工具执行与下一 Step 前 flush。嵌套工具依赖外层调用的检查点。工具调用已落盘、结果未落盘时，副作用仍可能已经发生。

03 / REPLAY

恢复必须可重放

同一日志尾部得到同一修补；同一请求可从 Header 与 Surface 重建。

五步诊断卡

① 导出有效组合；② 确认 Agent 作用域和权限；③ 找实际留存的最后一个事件；④ 区分未开始、结果未知、可重试与终态；⑤ 写一个能让假设失败的最小回放或故障注入。

质量不是一句“有测试”

上游无密钥快照通过发行 Profile 重放模型流，并按场景比对持久事件、协议或 UI 输出。会改文件的用例另行比对完整工作区，检验日志与实际副作用是否一致。

PROBLEM SET 01 · 副作用未知

进程在工具体执行后、结果落盘前崩溃。恢复系统应该自动标成功、自动重试，还是保留未知？

展开答题骨架

保留“结果未知”，补齐合法的工具结果与回合边界。自动标成功是在编造事实，自动重试可能重复副作用。

PROBLEM SET 02 · 重试设计

为什么在同一个 Step 内重新构造下一次请求？

展开答题骨架

失败尝试可以单独结算，已接纳的用户输入只记一次。模型适配器的失败进入请求错误链，再选择重试、压缩或结束。

PROBLEM SET 03 · TEAM DELIVERY

send_message 已返回 messageId，能否据此判定共享任务做完？

展开答题骨架

这只确认目标接受了输入。任务是否完成看共享任务板的已提交状态，目标的回复和后续回合结果各有自己的记录。
