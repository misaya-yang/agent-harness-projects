CHAPTER 01 · OWNERSHIP BEFORE DEBUGGING

场景：界面显示“完成”，测试进程却还在跑。先查哪里？

先定位状态拥有者。一个生产级 Agent 把承载、会话、工具和执行世界分开，症状出现在哪一层，不等于根因属于哪一层。

为什么先找“拥有者”

同一个会话内核可以被终端、stdio、leader 和 headless 承载。Pager 把事件投影到界面。本地会话启动时获得专用线程和 Tokio LocalSet，SessionActor 编排回合，ChatStateActor 管理对话历史、用量和 prompt 索引。工具运行时派发调用，Workspace 管理文件、进程与 VCS 副作用。

MINI TRACE

界面完成 → 找对应 prompt 的终态 → 按 call ID 核对工具是返回退出结果，还是只返回后台句柄 → 用句柄查实际进程状态。需要分别确认三层结束。

  1. 承载层：输入、展示与连接生命周期。
  2. 会话层：单写者状态、队列与 turn 裁决。
  3. 工具层：schema、权限、派发与结果。
  4. 执行层：文件、进程、VCS 与远端代理。

CHAPTER 02 · THREE NESTED LOOPS

场景：模型已经不再调用工具，为什么任务仍没结束？

模型返回文本后，采样步已经结束。会话仍可能补待办提醒、消费插话，或由 Stop hook 与 goal 状态触发同一 prompt 的下一轮。

把一次工作拆成三种尺度

Session actor 串行接纳输入；round 决定 goal 或 Stop hook 是否让同一 prompt 再跑一轮；采样步 完成一次模型流与一批工具。自然结束、取消、步数耗尽和重复动作硬停分别进入不同的收尾分支。

DECISION TRACE

Response → 有工具：执行并回填 → 无工具时检查启用的待办提醒与排队插话，再将候选终态交给外层决定是否续跑。

  1. 普通输入进入会话队列；插话和「立即发送」走各自的准入与取消路径。
  2. 每步受独立步数上限、重复工具调用检测与容量检查约束。
  3. 工具完成后结果必须回到历史。
  4. 终态类型决定外层能否续跑。

CHAPTER 03 · PROTOCOL AS EVIDENCE

场景：用户按了取消，稍后却收到一条“成功完成”。哪一个状态尚未正式提交？

流式输出与可回卷状态并发时，“看见文本”不等于“响应已提交”。协议层要给每次请求一个可验证的结束边界。

01 / ACCEPT

请求进入谁的队列

ACP 的 session/prompt 提交内容，session/update 流式报告增量。Grok 扩展另有回退、压缩和待交互状态。

02 / STREAM

事件是否被消费

采样层等待终态事件被消费，使工具事件与模型输出保持可读顺序。等待超时仍可继续，取消或回退撤销请求归属时则丢弃结果。

03 / REVOKE

取消是否撤销所有权

取消或可改变对话的在途回退会撤销请求归属。临界点之后到达的旧响应，连同统计，都不能提交到恢复后的回合。

CHAPTER 04 · TOOL GATES

场景：同批三个工具调用，第二个被拒。第三个还会执行吗？

如果用户明确拒绝，后续调用在准备阶段得到取消结果。如果策略只拒绝这一条，后续调用仍可继续准备。

先建立三段式管线

准备依次做 JSON/schema、hook、计划模式和权限判断；用户拒绝、取消或插话可截断剩余准备。已经批准的调用仍进入执行阶段，执行阶段为能解析出相同路径且包含写入的调用分配批内互斥锁。独立工具仍可并行，外部进程和无法解析路径的工具需要各自判断。结果按完成顺序回填，靠 call ID 配对。

NEW MECHANISMS

StructuredOutput 被建模为合成工具，校验失败沿 tool_result 自纠；启用延迟发现的工具可经 search_tool → use_tool 暴露给模型，另有直接内联的工具定义。

  1. 解析、hook、权限：有序准备。
  2. 批准调用：并行执行。
  3. 可定位到同一路径且涉及写入的调用：在批内持锁执行。
  4. 每个 tool_use：必有 tool_result。

CHAPTER 05 · SIDE-EFFECT BOUNDARY

场景：工具结果写着“成功”，文件却没变。成功到底是谁的事实？

工具结果可能只证明启动成功。命令是否结束看退出结果，文件是否修改看实际路径与 diff。先用调用 ID 和工作目录对齐记录，后台命令再按任务句柄检查。

文件与 VCS

读写、状态和差异必须来自实际工作区，而不是模型的完成宣告。

进程与终端

命令的退出、被杀原因和输出终帧，才构成进程完成证据。

本地与代理

同一窄接口可在本机执行，也可通过类型化 RPC 交给远端 workspace。

按 prompt 回退

先预览跟踪到的文件与外部修改冲突。执行时可选只回对话、只回文件或两者；文件、Git 和 hunk 有各自的恢复结果。

CHAPTER 06 · PERMISSION × SANDBOX

场景：用户点了“允许”，为什么命令仍被系统拒绝？

审批回答“这次是否允许”，OS 沙箱回答“这个进程最多能做什么”。两者处理不同失效边界。

两道门，三个失败方向

权限规则和 Hooks 先于普通模式放行。dontAsk 会拒绝需要询问的调用，always-approve 跳过普通询问，auto 使用分类器。沙箱默认 off。启用且应用成功后才限制文件。子进程网络隔离只在 Linux 实施，macOS 上相同选项不阻断网络。

SECURITY TRACE

hook → plan gate → permission → OS boundary → child network。本次同步把 requirements.toml 解析为类型化配置。组织可以禁用 always-approve；相对文件规则同时考虑书写的工作目录和其解析后的物理路径。

  1. 可解释的风险：询问用户。
  2. 策略命中：明确拒绝。
  3. 保护无法施加：拒绝启动。
  4. 获批后仍受内核能力上限约束。
CHECKPOINT 06判断题：自动批准等于关闭沙箱吗？检查审批模式和启动日志。内置 profile 应用失败可能告警后继续，自定义 profile 应用失败可拒绝启动。权限确认后还需核对 OS 和实际生效的限制。
CHAPTER 07 · RECOVERABLE SESSION

场景：写目录切换记录时连接断了，能再追加一次吗？

先查这次追加在哪一步失败。切换工作目录使用同一个 generation 去重，错误类型区分未写入、已写但后续失败、无法确认。普通对话追加有自己的持久化路径。

三态比 success / failure 更诚实

NotCommitted 可用同一 generation 重试；Committed 表示写入已完成，之后同步可能失败，数据可能仍在页缓存。Indeterminate 时先找原 generation 并核对存储，再决定是否安全重试。updates.jsonl 追加记录事件，chat_history.jsonl 存在可重建的对话视图。

RECOVERY TRACE

锁 → generation 查重 → 追加 → 同步内容与目录项 → 返回三态。对话 rewind 追加 RewindMarker，重放时过滤已放弃的分支。文件 rewind 走 Workspace；压缩点保存另一份模型历史。

  1. 未提交：可以重放。
  2. 已提交：不可重复执行。
  3. 不确定：先对账，再决定。
  4. 坏行隔离，成对性修复。

CHAPTER 08 · CONTEXT ECONOMICS

场景：压缩成功了，Agent 却忘了约束、重复做事。摘要哪里不够？

Compaction 是替换历史后重建一个仍能工作的现场。真正困难的是：什么必须逐字保留、什么可以总结、什么运行态要重新注入。

源码更新 · 按配置启用的 Memory V2

Memory V2 把捕获与整理分开。

启用 V2 后，会话捕获先向 observations/_inbox 发布不可变观察。整理阶段维护 topics 和生成的 MEMORY.md。会话固定当前 rollout 阶段，捕获与批量整理分别受配置控制。观察可先发布，主题或汇总要等整理完成。

CHAPTER 09 · EXTENSION TRUST

场景：项目新加一个扩展，为什么 Agent 看见了能力却不执行？

“被发现”“对模型可见”“可被派发”“被目录信任”是四件事。扩展类型决定它做什么，来源决定它是否可信。

六类扩展，各改一层

Rules 给约束；Skills 给工作流；MCP 给外部工具；Plugins 打包多种能力；Hooks 做确定性裁决；Memory 提供跨会话证据。项目 Hooks、MCP 与插件按来源检查信任。项目插件启用后仍需信任该目录才会加载可执行能力。Claude 设置导入，先扫描可导入权限、环境和 MCP，再由用户选择迁移。

DISCOVERY TRACE

发现配置 → 核对来源信任 → 看工具注册与可见性 → 核对调用权限。任一步失败都不应统称为“插件坏了”。

  1. Rules / Skills：改变判断与流程。
  2. MCP：增加可调用能力。
  3. Plugins：组合与分发。
  4. Hooks：在明确时点拦截。

CHAPTER 10 · MULTI-AGENT GOVERNANCE

场景：子代理已经完成，父代理为什么既没收到结果，也没被重新唤醒？

后台完成不是一个返回值，而是带取消、已消费、可见性与父会话状态的事件。单写者协调 actor 管理整棵子任务树。

子代理是完整子会话

子会话复用会话引擎，拥有独立历史，默认在后台运行并共享工作目录。可申请 worktree；创建或恢复失败时可能回退共享目录。嵌套深度默认 1，普通会话并发上限回退默认 32，均可由配置调整。

WAKE TRACE

child complete → coordinator → 检查自动唤醒配置、后台标记、取消、显式 kill、等待者是否已收件、goal 与父通道 → 允许则提交合成 prompt。

  1. New：新会话与独立历史，可选择执行目录。
  2. Resume：从已完成子会话复制转录，启动新的执行实例。
  3. 完成：轮询面 + 事件面双通道。
  4. 血统：统一取消、计费与可见性。

CHAPTER 11 · ONE CORE, FOUR CARRIERS

场景：升级 CLI 后，旧后台进程仍在服务。谁应该退出？

会话内核可进程内嵌、通过 ACP stdio 或 WebSocket 接入、经本地 leader 共享，也可连接 headless relay。脚本入口 grok -p 提供 plain、JSON 和两种流式 JSON 格式；grok agent serve 另提供带 token 的 WebSocket。共享守护进程还必须解决锁、就绪、身份和单向版本收敛。

承载不同，状态机不能分叉

内嵌适合强沙箱边界；stdio 以输入输出流承载 ACP；leader 让多个客户端共享后台内核；headless relay 用 ping 和 liveness 超时治理半开连接。版本检查只在客户端与 leader 的版本均可解析、且客户端更新时触发替换。同版本或更老的客户端仍连接现有 leader。连接失效走独立的存活检测。

DAEMON TRACE

锁 → pid/socket 核验 → 有界登录 → ready → client_id|request_id 路由 → keepalive → 按版本判断是否替换。用锁持有者、进程版本和就绪握手验证是哪一层拒绝了连接。

  1. In-process：边界随当前进程。
  2. stdio：IDE 子进程承载。
  3. Leader：本机多客户端复用。
  4. Headless relay：远端连接与重连。

CHAPTER 12 · FAILURE BUDGETS & ENGINEERING

综合场景：同样是“请求太大”，为什么有时剥图，有时必须压缩？

恢复动作会改写请求，也可能损失信息。可靠系统先按“谁能修、要改什么”分类，再让每层消耗自己的预算。

五步故障判断法

① 找最后可靠事实；② 判断是模型可修、harness 可修还是必须交给用户；③ 区分瞬态与确定性；④ 选择不扩大损失的恢复动作；⑤ 用线级真实测试锁住协议、事件和用户所见。

ERROR TRACE

字节级超限 → 剥图一次；token 超窗 → compaction；可重试的 429 → 按 Retry-After 或退避策略等待；启用仅输出前重试且已输出 → 结束该请求；未知状态 → 不做破坏性恢复。

  1. 传输重试：独立预算。
  2. 生成循环重采样：独立预算。
  3. 截断续写：独立预算。
  4. 子代理等待限流：独立预算。

LAB 01 · 循环诊断

模型连续读取同一份内容，应该在哪一层止损？

展开判断骨架

先看动作签名：将工具名与规范化、排序后的参数组成签名。只读重复先提醒，达到阈值后返回不可被外层续跑的 stationarity 终态。

验证：相同调用乱序后仍应被识别；硬停后 goal 与 Stop hook 不应重新点火。

LAB 02 · 压缩诊断

压缩后规则还在，但 Agent 忘了后台子任务。缺了哪条链？

展开判断骨架

项目规则应逐字重插；后台任务属于运行态，应由 compaction 后的状态 reminder 重建。摘要负责较早语义历史，不承担全部现场恢复。

LAB 03 · 多代理诊断

子代理显示 cancelled，父会话空闲。单凭完成事件就能唤醒吗？

展开判断骨架

不要唤醒：子结果取消或记录到显式 kill 时不唤醒。仅取消父回合时，先确认该动作是否传播给这个子代理，再检查其他唤醒条件。

TurnOutcome
把自然结束、取消、预算耗尽与防循环硬停分开的终态词汇。
Stationarity
按规范化工具签名检测“动作没有进展”。
Full-replace
摘要旧历史，再显式重建约束、意图与运行态。
Wake gate
决定后台完成是否应重新启动父模型的纯函数闸门。
Three-state commit
把未提交、已提交和结果不确定分开表达。
