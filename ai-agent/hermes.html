CHAPTER 01 · ONE TURN

用户只补充一句话，不该因此杀掉正在写文件的工具。

在通用回合中，先准入一次，再反复请求模型和运行工具，最后统一收尾。用户在途改意时，要先确认当前卡在模型请求还是工具执行，再决定何时应用新指令。

INCIDENT → PLAIN LANGUAGE

三段式回合把一次性工作和重复工作分开。

序章取得跨进程回合租约、恢复冻结 prompt 与历史、检查是否需要压缩；循环重复“问模型—执行工具—回填结果”；尾声持久化、在需要时交代预算耗尽，并检查后台复盘能否派发。可交付的文本进入收尾。空输出、截断和丢失工具调用仍可继续尝试。

短 trace：lease → build → model → tools → model → finalize

STEER补充方向

当前工具继续执行，指引排到下一安全边界，以独立用户消息进入通用循环。适合“另外也检查测试”。

REDIRECT更换目标

通用循环中取消在途模型请求并提交修正。工具正在执行时改走 steer，并可请求支持交还的工具让出前台。

INTERRUPT立即硬停

通知活动回合和可取消的执行分支，记录中断。已经发生的副作用需要另行处理。

QUEUE下回合再说

当前回合完整收尾后，再把消息作为一个新回合处理。

CHAPTER 02 · MODEL & FAILURE

同一个 429，不一定该做同一件事；先分类，再恢复。

通用循环通过 transport 适配 Chat Completions、Anthropic Messages、Codex Responses 与 Bedrock Converse，再由错误分类和重试阶段选择恢复动作。显式启用 codex_app_server 时，Hermes 把整个回合交给 Codex 子进程，再把事件投影回自己的会话。只有非中断的限流、上游限流或计费失败，且能激活已配置的备用路由时，同一用户回合才会交由通用循环重试。

01 / INCIDENT

双重重试风暴

主 OpenAI 兼容与 Anthropic 客户端将 SDK 重试交给通用循环，让它统一遵守 Retry-After 和请求级配额。辅助调用或插件 transport 仍要核对各自的实现。

02 / TRACE

集中分类

error → reason → action bits → one retry owner。请求形状修复只改本次 API 副本，不回写规范转录。

03 / EXIT

错误去哪里

请求形状可在调用层修复，工具错误可随结果交还模型。耗尽配额、认证或策略拒绝可能直接成为可见终态。

凭据冷却
按失败语义定时长，不只看状态码；歧义会被单独标为“未确认”。
备用链
按真实后端身份去重，避免“名字不同、其实还是同一坏端点”。
成本守卫
长上下文出现确定性空响应时，缩短昂贵重试，不让每次沉默都重新付整段输入。
CHAPTER CHECK

你能做什么：为新 provider 错误补一个分类和恢复动作，而不是在调用点再堆一段字符串判断；还能解释为什么修复历史必须 copy-on-write。

CHAPTER 03 · TOOL EXECUTION

模型一次发来六个正确调用和一个空工具名，不该整批作废。

工具进入执行器前会先去重、纠正常见参数形状、标记非法调用，再按资源冲突切成并行段和屏障段。合法调用继续执行；非法项得到自己的错误结果，给保留的调用补齐配对结果。批次写入失败等整轮退出条件仍单独处理。

  1. 目录发现：工具按注册元数据进入统一注册表；发现结果可缓存，动态 schema 在给模型展示时才求值。
  2. 渐进披露：Tool Search 在有可延迟工具或已授予 Connections 时启用桥接。默认 5% 只限制嵌入目录大小，上限 4,000 token。模型查到工具后，调用仍需通过会话工具面与参数校验。
  3. 冲突调度：受支持的读写用实际路径判断冲突。重叠且含写入时另起一段，不相交的写仍可并行。无法确定作用域或声明必须串行的工具才构成屏障。
  4. 结果治理：大结果保留预览并溢写，重复大结果变引用桩，未信任的网页与外部工具结果加语义边界。

CHAPTER 04 · EXECUTION BOUNDARY

本地能执行命令，不等于本地有操作系统沙箱。

六个内置后端共用 terminal 执行接口：Local、Docker、SSH、Modal、Daytona 与 Vercel。Singularity / Apptainer 由官方插件提供。比较后端时要确认命令在哪执行、看得见哪些路径、工作现场如何延续。

SECRET先拿走秘密

支持过滤的后端会剥离供应商凭据。Docker 配置出口代理后可给代理所管服务下发替代 token，在代理端注入真凭据。显式环境转发另有边界。

DAMAGE再限制破坏

命令根据生效审批模式裁决。匹配硬阻断规则、自毁保护或用户拒绝规则时直接拒绝。文件工具另检查目标路径。

POLICY最后保护规则

会话作用域决定使用哪个 profile 的配置和凭据。容器挂载、网络和进程内插件各有独立边界，profile 归属本身不会隔离 OS 进程。

CHAPTER 05 · TRANSCRIPT & RECOVERY

调用已记录，结果来不及写入。重启后怎样判断工具有没有执行？

规范转录记录发生过什么，API sidecar 保存供模型回放的消息内容副本。profile 的存储由 persistence_assembly 装配，内置后端使用 SQLite state.db，历史可搜索。持久会话在运行可能有副作用的工具前先存调用块，写失败时中止这一批。

01 / CANONICAL

干净转录

保留用户、assistant、tool 的规范顺序。临时记忆和中断脚手架不应污染这里。

02 / SIDECAR

精确重放

消息可保存 API 内容副本，保留同一消息的已发送前缀。压缩或改写内容时失效对应旧副本。

03 / RECOVERY

按副作用清尾

纯读的未闭合调用能从模型回放中过滤。可能有副作用的调用保留，并补上 UNKNOWN 结果，让恢复回合先检查外部状态。

CHAPTER 06 · MEMORY LOOP

“记住这条经验”不能阻塞用户当前的回答。

Hermes 区分会话内的冻结快照、磁盘活状态和外部记忆 provider。记忆按符合条件的用户回合计数，技能按循环迭代计数，两个间隔默认都是 10。触发到期后，还要有最终回复、未被中断或 veto，并通过后台设置与作用域条件，才尝试派发复盘。

FROZEN会话内快照

系统提示绑定本会话的记忆快照。磁盘内容可以更新，已建好的提示等下一会话、压缩或其他明确的重建边界再刷新。

PREFETCH回合级召回

外部 provider 的召回内容进入 user 消息 API 副本，并带“素材而非新指令”的边界。

REVIEW后台自审

后台 fork 以回合快照和受限工具工作。进入下一前台回合时，可取消排队复盘或中断活动复盘。

DRIFT写入防漂移

读取失败不能当空文件；外部修改无法往返时拒绝覆盖，并留下可恢复副本。

CHAPTER 07 · EXTENSION SYSTEM

能观察发生了什么，不等于有权改变将要发生什么。

Hermes 把扩展权力分成三档：skill 是按需加载的知识包；observer hook 汇报生命周期；middleware 才能改写请求或包住执行。进程内 Python 扩展拥有宿主权限。平台对声明式扩展能力做具体授权，并记录申报集合的哈希；profile 下的 Gateway 事件 hook 则以操作者放置文件作为信任边界。

Skill
先把名字和摘要放进索引，正文用到时再读；适合可复用的操作知识，不占常驻上下文。
Observer
记录或轻量回应事件。坏插件不能拖垮错误分类，多个观察者可以依次运行。
Middleware
真正改变请求或执行，仅保留少数强制入口；输入先复制，避免共享可变对象被污染。
Capability
每项声明必须对应已经存在的强制 gate；升级新增能力后重新征得同意。

CHAPTER 08 · CACHE & COMPACTION

压缩后消息变少，不代表这次压缩有效。

系统提示按 stable、context、volatile 三层组装。回合级变化可以走 API sidecar。内置压缩配置起点为 50%。窗口小于 512,000 token 时，比例至少 75%，随后再应用输出预留与绝对限额。只有粗估时预检可能等一次真实 usage，provider 明确报溢出时进入独立恢复。

CACHE保护已发送字节

stable 前缀是缓存资产；时间、记忆与插件上下文不应在每回合重写它。

MEASURE粗估配真实回执

发送前的估算与响应后的真实 token 用量各有用途。下一次真实输入 usage 才能验证压缩效果。相关路由不返回 usage 时，系统仍可根据估算判断是否需要压缩。

GATES三道闸门

摘要服务失败进入 cooldown，结构上无可压内容暂缓，连续两次经 provider 确认无收益才触发 anti-thrash。观察期探针允许评估是否恢复自动压缩。

TXN提交像事务

会话锁、提交栅栏、防增长守卫和软归档共同保证“压坏了就不发布”。

SHORT TRACE

一次安全压缩的最短心智模型

pressure? → checkpoint → keep head/tail → summarize middle → validate size → commit or rollback

摘要失败也要分类：认证、网络、空内容或截断时保全原文；普通失败才允许确定性兜底。压缩结果保留用户原话、关键锚点和检索提示，让丢失变成延迟检索。

CHAPTER CHECK

你能做什么：说明为何逐回合微压缩默认关闭。开启后可逐步缩小历史，但也会反复改写 provider 已看到的前缀。比较同路由的输入与缓存计费，再判断净收益。

CHAPTER 09 · MULTI-HOST

CLI、桌面、消息网关可以长得不同，但不能各自拥有一套回合语义。

当前 classic CLI、Ink TUI 与桌面可连接共享网关。SessionAuthority 负责提交、订阅和活动执行，侧边客户端可以断开后从另一表面接续。消息适配器另按 platform session key 路由，多 profile 活动绑定自己的 home、凭据和执行环境。

场景 · 多客户端接续

关掉 TUI 后，用 Desktop 接手待审批回合。

prompt.submit 确认输入已准入。主动 detach 只撤销该订阅。连接丢失后，网关可按无订阅者的回收策略关闭会话。重连后，由已授权且已订阅的客户端携当前执行世代与审批 ID 响应。

01 / INPUT

输入仲裁器

02 / OUTPUT

事件多路复用

流式 token、步骤和工具生命周期通过同一事件面送往终端、WebSocket 或镜像观察者。

03 / WRITE

执行与写入所有权

提交回执只证明输入准入。订阅可以断开重接，审批还需匹配当前执行世代与提示 id。存储层回合租约隔离跨进程的会话写入。

传输失败
只把明确的“对端已死”当正常断开；本机磁盘、序列化等错误必须进入崩溃诊断。
工具面门控

配置恢复

CHAPTER 10 · ASYNC DELIVERY

后台任务完成时，父代理还在说话：结果不能直接写入当前消息序列。

异步委派可把完成事件入队，等父会话空闲再开启新回合。cron 有独立的到期、申领、执行与交付路径。一次性任务可显式 rearm，投递目标的配置与运行终态分别检查。

场景 · 可选投递镜像

发送成功的通知，是否要进入目标聊天历史？

Webhook 有按路由启用的镜像选项；成功送到聊天平台后，可把已发送内容写入目标聊天会话，使用户回复时 Agent 知道自己刚说过什么。该选项默认关闭，并受目标 profile 范围约束。

面试追问：为什么外部投递成功和会话历史已记录必须分别确认？

DISPATCH立即给句柄

后台工作不阻塞当前回合；若目标没有耐久消费者，则降级为同步，不发一个永远没人收的句柄。

CLAIM先认领再投递

耐久账本分别记录派发、完成与投递。claim 租约协调谁可交付；外部发送结果不明确时，仍要从回执核实。

REPLAY有界重放

耐久完成记录有最多 8 次交付尝试与 48 小时的启动重放窗口。在途子任务若已失去执行所有者，其执行结果可能是 UNKNOWN。

CHAPTER 11 · DELEGATION

多代理最难的不是“并发跑”，而是只把值得保留的内容带回来。

通常由宿主创建新的 AIAgent 子会话，在线程中执行，拥有独立转录、迭代预算与终端会话。工具面受委派策略裁剪，开启继续已有子会话时则延续原转录。父回合可收到任务句柄与结果摘要，子代理的完整转录单独留存。同步委派直接返回工具结果，异步委派可走完成队列。

BUDGET摘要聚合预算

有可用 usage 时，从父剩余窗口拨一部分按份分配，并受单份字符上限约束。超限保留头尾并尝试将全文存盘。

LIVENESS心跳与 stale 分档

无进展阈值在工具外为 450 秒、工具内为 1,200 秒。看门狗请求中断后可以放弃等待并返回超时；执行线程及既有副作用仍需核实。

PROOF自我报告不是证据

子说“已部署”只能算摘要；父必须用 URL、ID、提交或其他句柄亲自核验外部副作用。

CHAPTER 12 · OPERATING JUDGMENT

排查 Agent，不要先猜模块；先判断哪一层还有能力修复。

最终练习把前十一章压成五个问题：回合在哪一段？消息该走哪条干预通道？失败应交给机器、模型还是用户？状态是否已耐久？新结果能否在不改写前缀的情况下进入下一回合？

五步场景诊断

  1. 定范围：是单次模型请求、工具执行、整回合，还是宿主路由？先别把所有“卡住”都叫网络问题。
  2. 看退出原因：区分预算耗尽、中断、护栏、持久化失败、provider 失败与真正的正常回答。
  3. 查耐久边界：工具副作用发生前，调用块是否已经可恢复？后台完成是否已进入耐久账本？
  4. 核对缓存边界：谁改写了已发送前缀？易变内容是否错误地进入系统提示或规范转录？
  5. 验证恢复动作：重试是否只有一个 owner？压缩是否真的降到阈值下？子代理的完成是否有父侧验证句柄？

PROBLEM SET 01 · 干预选择

模型正在生成解释，用户改了最终输出格式；模型正在执行不可逆命令，用户说目标错了。两次分别选什么？

展开判断

前者用 redirect：取消在途模型请求并保留已经完成的上下文。后者用 interrupt：副作用目标错误，继续执行的代价更高。若工具正在做安全的长读且用户只是补充范围，用 steer。

PROBLEM SET 02 · 压缩设计

摘要后消息少了一半，但下一次真实输入仍高于阈值。算成功吗？下一步怎么做？

展开判断

一次真实采样仍超阈值只能说输入压力尚未解除。先区分摘要无效、下一请求新增内容和固定开销；连续两次确认无效才触发 anti-thrash。再检查是否该减少固定工具与提示。

PROBLEM SET 03 · 委派信任

三个子代理都说“修复完成”，父代理能直接向用户宣布成功吗？

展开判断

不能。摘要是自我报告。父应检查可核验句柄，运行与声明同等级的测试，并区分 implemented、tested、published 和 deployed。探针失败就报告 UNKNOWN。

回合
从一条用户输入进入，到尾声发布状态的完整单位；一次模型调用只是迭代。
sidecar
随消息持久化的 API 视图副本，不改规范正文。
checkpoint
压缩或副作用前确认外部状态可恢复的检查点。
