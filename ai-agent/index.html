01 / CONTROL FLOW运行循环一个任务为何继续、转向或结束？

一次用户交互回合（Turn）通常由宿主调度多次模型采样步（Step）构成。单个模型的流式回复结束、工具子进程的命令退出，以及整个回合的状态收敛，是三个处于不同控制边界的独立事件。

任务现场

测试子进程仍在后台执行，模型却已在终端输出“完成”。排查时应先核对模型文本、工具执行回执，还是宿主发布的 Turn 终态事件？

  1. 宿主接纳用户指令并分配回合标识（Turn ID），正式开启执行周期。
  2. 模型采样产生测试工具调用；宿主在执行环境中启动命令，并将退出码与输出标准化为回执注入下一次输入。
  3. 模型给出最终答复后，宿主评估后续工具需求、排队插话与停止条件，确认全部收敛后再发布回合终态。

继续追问用户插话在什么边界进入？工具失败应继续让模型修复，还是终止整个 Turn？

跨项目对照Codex 在同一回合里请求模型、执行工具，再将结果送回模型；OpenCode 先把请求写入收件箱，再唤醒该会话的执行循环。模型回复文字和宿主确认收束是两个时刻。

迁移练习为“测试失败后修复一次，再验证”写出最多两轮的停止条件与事件轨迹。

面试自测：如何设计不会误判完成的 Agent Loop？

退出码 0 仅证明单次工具执行成功。要向用户可靠报告任务完成，宿主必须确认所有必需的校验步骤均已交付，且活跃历史中不再有未处理的工具结果或待办插话。若因用户取消、超时或步数耗尽而提前终止，必须记录带明确原因的终态状态码（如 cancelled / budget_exhausted），禁止与正常收敛混淆。

02 / STATE状态协议UI、模型和日志看到的状态为何不同？

同一次运行会向不同受众投射出不同的状态视图（投影）。前端界面实时消费带格式的流式增量（展示视图），持久层追加已提交的不可变事件（审计与恢复视图），而宿主仅按预算组装经过过滤的模型工作集。当系统异常中断时，这三者往往停留在不同的时间水位上。

任务现场

用户界面已显示“工具执行成功”，进程重启后模型却重新尝试执行该工具。此时哪一层的状态事实未被持久化？

  1. 为每一次工具调用分配全局唯一的关联标识（Call ID）。
  2. 在架构中解耦客户端已接收的即时通知、本地存储已落盘的执行事实，以及下一次允许模型感知的上下文工作集。
  3. 若存储中仅见调用发起事件而缺失执行回执，应先探查物理环境；切勿直接假设操作失败而盲目重复派发。

继续追问流式 chunk 算正式消息吗？断线后应相信旧 UI 状态还是重新读取快照？

跨项目对照DeepSeek 区分实时输出帧和已结算的消息事件。OpenCode 的实时推送断线就可能漏收；重连可查询 SQLite 里的会话状态。逐条补读旧事件还取决于宿主是否保存事件正文，workerd 会启用该选项。

迁移练习设计“工具调用已落盘、结果未落盘”的恢复判定表。

面试自测：为什么原始日志不等于模型上下文？

同一条输出可以先出现在屏幕上，再被模型调用取消。重连后要从持久记录核对最后成功的步骤；界面重新订阅实时通知，模型按自己的规则重建上下文。

03 / TOOLS工具系统并行执行怎样保持结果有序、可取消？

并发调用能显著降低整体 I/O 等待延迟，但也打破了单调的时间先后。并发工具的结果必须通过唯一调用标识与原提议严格绑定，并在回填到模型历史时保持确定的时序约束，宿主才能组装出语义合规的模型请求。

任务现场

同一批次并发派发的两个读操作中，后发起的 B 比先发起的 A 先完成。回填给模型的上下文历史中，应该按物理完成顺序还是按模型提议顺序排列？

  1. 保持每个工具提议与其参数校验签名、全局唯一 Call ID 的严格映射。
  2. 调度执行时允许只读操作并发推进，对涉及相同文件路径的写操作施加互斥锁；前端可按完成先后流式展示。
  3. 归一化回填时遵循模型协议规范。Pi 的并发路径按发起顺序有序重排结果消息，避免乱序提交污染模型对话因果。

继续追问参数错误是可修复结果还是致命异常？取消时尚未启动的调用如何结算？

跨项目对照Pi 按工具批次组织结果；OpenCode 的模型步骤会启动工具任务并等待它们结算。跨项目比较时，分别看执行顺序、结果关联和取消边界。

迁移练习为两个并行读和一个写操作分别给出可以并行执行的操作和交给模型的结果顺序。

面试自测：工具并行完成，怎样保持历史正确？

界面可以先显示 B。准备下一次模型请求时，宿主要用编号匹配 A 和 B，并遵守提供方的消息顺序。若 A 中途取消，要保留取消或待核实状态，直接补上“成功”会污染后续判断。

04 / EFFECTS副作用安全用户批准后，为什么命令仍可能被拒？

修改工作区文件、触发网络请求或执行系统命令等改变外部持久环境的操作统称副作用。安全体系由三层协同防御：静态规则判定操作能否提议，审批策略裁决由谁确认授权，操作系统沙箱与进程凭据则在底层强制物理隔离。

任务现场

用户在前端弹窗中明确点击了“允许写入工作区外文件”，工具进程却依然抛出权限异常。这次审批究竟改变了什么、又受阻于什么？

  1. 规则引擎基于提议操作的命令签名、目标资源路径与环境配置，裁决为直接放行、要求审批或强制拒绝。
  2. 触发审批后将人工应答或 Guardian 决策与当前请求 ID 绑定，已授权的作用域仅在本次或当前回合有效。
  3. 宿主以有效权限画像（PermissionProfile）启动沙箱进程。即便用户授权放行，若宿主沙箱或操作系统内核策略限制了外层文件系统访问，底层系统调用仍将被物理拦截。

继续追问沙箱不可用时能否降级裸执行？“never ask”应该放行还是明确拒绝？

跨项目对照Codex 的有效权限配置、审批策略与执行策略共同约束工具。Grok 的工具审批与可独立配置的 OS 沙箱分工；OpenCode 的权限决定也不能代替宿主隔离。

迁移练习列出一次危险 shell 操作从提议到进程启动的所有裁决点。

面试自测：审批和沙箱分别防什么？

例如用户同意修改报告，但进程只获得了工作区的写权限，写工作区外的副本仍可能失败。应分别查看批准的目标和实际执行权限；关闭交互询问本身不会授予写权限。

05 / MODEL INPUT提示词与上下文下一次请求究竟给模型发了什么？

大语言模型是无状态的，每一步只能利用当前请求显式注入的信息。即便磁盘上记录着完整的交互历史，宿主仍必须在上下文窗口预算内，精确裁剪系统基础指令、动态项目规则、活跃对话工作集与工具契约。

任务现场

团队刚刚在仓库中更新了编码规范文件，下一步模型需要立即遵循新约定，但绝不能把过往数十轮的冗长执行日志全量重新塞入请求窗口。

  1. 捕获当前步有效的配置快照，提取最新适用的项目规范与可用工具集合。
  2. 将环境差分状态、保留近期轮次的工作集以及回注的工具结果拼装为合法请求，严格记录截断与压缩元数据。
  3. 在发送前核对请求各分层的结构与字节预算，排查关键约束是否因窗口超限被静默丢弃。

继续追问工具定义算历史消息吗？压缩会改写基础指令或授权证据吗？

跨项目对照Codex 先给单个工具输出分配预算，长会话另有本地或远端压缩。DeepSeek 从已结算事件投影模型可见历史，失败尝试可留档而不进入下一次模型请求。

迁移练习为一条模型请求标出稳定前缀与每步变化的输入。

面试自测：Agent 每个 step 发给模型什么？

模型忽略新规则时，先检查这条规则是否进了本次请求。缩短一个过长的工具结果、压缩整段历史、刷新项目规则，各自改变的输入不同。

06 / CONTINUITY记忆与恢复会话日志、摘要和长期记忆各管什么？

完整日志（Transcript）忠实记录已发生的一切事实，模型上下文（Active Context）决定当前步思考所需的临时工作集，而跨会话长期记忆（Memories）沉淀提炼出的跨回合偏好与结论。三者在写入频率、清理周期与检索路径上完全解耦。

任务现场

经过上下文压缩后，模型不再知晓早期的文件名与操作过程；此时磁盘上的会话日志依然完整。下一次模型请求是否会自动读取这份完整日志？

  1. 明确当前会话是否启用持久化日志，并定位最新检查点（Checkpoint）的物理存储路径。
  2. 在下一次模型请求中，基于替换历史（replacement history）装配摘要、近期未压缩消息与关键运行时状态。
  3. 若需要将本次任务经验沉淀给未来的新对话，必须经过显式的观察捕获、后台提炼整理与跨会话写入流程。

继续追问摘要会不会无限增长？已批准的操作证据是否跟着摘要消失？

跨项目对照Grok 的压缩检查点服务于当前会话恢复。Hermes 的后台 review 可以整理记忆和技能，文件变化在后续新建或重建提示时才对模型可见。

迁移练习画出同一 Thread 两次压缩后的日志、checkpoint 和当前模型请求。

面试自测：压缩后 transcript 与模型上下文怎样变化？

压缩后，旧消息可以仍在日志里，却不再逐条占用模型窗口。要恢复遗漏的文件名，应检查摘要保留了什么，以及宿主能否按需取回原记录。跨会话记忆还取决于是否启用以及何时读取。

07 / EXTENSION扩展机制规则、工作流、工具和钩子放在哪里？

设计 Agent 扩展点时，必须先理清是由模型自主选择触发，还是由宿主在关键生命周期强制执行。一段指导提示（Prompt/Skill）、一个外部能力接口（MCP/Tool），与一段在进程内拦截 I/O 的前置钩子（Hook），拥有完全不同的保证能力。

任务现场

团队要求在每一次写文件之前执行强制的代码风格与合规检查。这项能力应该实现为一段供模型阅读的 Skill 说明，还是宿主写路径上的确定性 Hook？

  1. 梳理扩展所需的系统数据、执行凭据以及由哪一层组件进行权限委托。
  2. 锚定触发时机：是模型在推理时按意图选配，还是由宿主内核在派发前沿确定性管道单调拦截？
  3. 分别构造正常通过、校验拦截以及插件卸载三种边界用例，验证扩展生效的严密性与回滚表现。

继续追问插件被发现就等于可调用吗？模型请求钩子能修改什么？

跨项目对照Pi 的进程内扩展与应用共享进程；通过 MCP 调用工具时，实际权限取决于工具服务在哪里、以谁的身份运行。DeepSeek 把只读检查与持久安装插件分成两个入口。

迁移练习把项目规范、外部数据库查询和写前检查分别放到合适的机制。

面试自测：何时选 Skill、MCP 或 Hook？

项目写作规范可用 Skill 提供；查询外部系统可接入 MCP 工具。若写入之前必须通过检查，需在实际写入路径强制执行，并验证检查失败时操作会停止。

08 / DELEGATION多代理编排子任务完成后，结果怎样安全回到父任务？

在多代理系统中，子任务被调度器受理、子代理在独立线程中执行完成，以及执行结论投递到父会话收件箱，是三个异步发生的离散阶段。父会话不能在刚拿到受理回执时便提前宣告任务结束。

任务现场

父代理调用派发工具后收到子任务调度器的 accepted 回执，随即在终端宣布完成；而此时子代理尚未开始实际执行。谁负责在真正的执行结果产生后唤醒父会话？

  1. 派发子任务时清晰定义独立目标、继承的上下文视图边界，以及所授予的文件与预算配额。
  2. 维护子任务句柄、执行状态机、专属收件箱以及向上传播的取消控制通道。
  3. 子代理执行结束后，将其结构化结论安全投递至父会话队列，由协调器触发合成输入唤醒父代理进行结果归纳。

继续追问父历史应继承多少？谁有权取消后代任务？

跨项目对照OpenCode 新建子会话时继承父会话的显式权限和元数据；OpenClaw 把子任务完成回执与通道投递分开，任务完成不等于对方已收到。

迁移练习为并行研究和最终综合写出任务树、交付点与取消规则。

面试自测：子代理怎样回报、取消和控制成本？

父任务收到 accepted 只能确认子任务已受理。只有拿到对应子任务的终态和结果，并确认父会话已消费它，才有依据做最终汇总。取消父任务时还要检查仍在运行的子任务。

09 / PRODUCT SURFACE客户端与宿主多个入口如何共享一套运行语义？

CLI 终端、IDE 插件与 Web 页面可以作为不同的客户端表面接入同一个 Agent 内核。为了防止多端接入时产生冲突或状态漂移，核心状态机的单写者权威、双向命令协议与断线追赶机制必须严格统一。

任务现场

开发者同时在本地 CLI 终端和浏览器 Web 界面中打开了同一个正在运行的会话。哪个客户端拥有命令写入权？断线重连后如何补齐已发生的增量？

  1. 客户端通过明确的握手协议与会话标识连接至宿主守护进程（App Server / Leader）。
  2. 掌控该会话的单写者服务负责请求的排队、校验与裁决，并通过标准事件流向各端广播进度。
  3. 客户端断线重连后，先通过分页接口拉取持久化的历史快照，再衔接实时增量通知并按 ID 完成去重。

继续追问前端能否自建第二个工具循环？不同宿主的权限是否天然相同？

跨项目对照Codex App Server 区分客户端请求、服务端反向请求和通知；Pi 提供 SDK 和子进程 JSONL RPC。接入新客户端时，要分别核对它们怎样提交输入、接收进度和恢复会话。

迁移练习画出 IDE 提交命令、收到更新和断线重连时的三条调用路径。

面试自测：同一 harness 如何支持多个客户端？

当网页关闭后任务仍在运行，新客户端应找到原会话及其控制者。它需要的最小能力是读取状态、订阅进度、提交允许的操作，并能处理“这次请求已过期”。

10 / OPERATIONS可靠性工程失败发生后，哪一层还有权重试？

重试的前提是明确知道上一次操作造成了什么副作用，以及谁具备验证该副作用的能力。网络通信超时仅意味着传输层未收到 ACK，绝不代表远程命令或写操作没有在目标环境中生效。

任务现场

文件修改工具在本地执行成功，但随后的模型流式传输因网络波动中断。如果直接将原请求全量重试，极易造成重复补丁或副作用雪崩；此时首先应该比对什么？

  1. 严格区分未派发、明确失败、确定完成以及因通信中断导致的「结果未知」四种状态。
  2. 对处于未知状态的非幂等写操作，优先核对磁盘文件指纹、事务日志或幂等键，严禁无条件重试。
  3. 由负责该层的故障分类器在有界预算内执行重试；若无法确证物理状态，必须将不确定的事实边界显式呈现给调用方。

继续追问HTTP 200 证明任务成功了吗？恢复测试为何必须验证调用与结果成对？

跨项目对照OpenClaw 把运行预算、供应商重试与会话恢复分别管理；Hermes 的持久回合租约让接手者识别正在执行的工作。先判断副作用是否已提交，再决定能否重试。

迁移练习为“工具成功、传输断开、进程重启”写一张不重复执行的恢复表。

面试自测：如何避免多层重试放大一次故障？

例如文件已写入、结果还没保存就断电，恢复后应先检查文件版本。重复发送同一请求只有在目标能去重或操作可安全重复时才合适；还要把内外两层的重试计入总预算。
