OPENCODE · DEV

从持久状态理解 OpenCode 的循环、审批与恢复。

当终端界面显示「已受理」（admitted）时，模型推理可能尚未真正启动。OpenCode 的核心设计是先将用户输入持久化写入会话收件箱（Inbox），随后由后台的会话协调器（Run Coordinator）择机推进执行。这种解耦让 HTTP 客户端能立即释放连接；但要确认任务真实进展，系统必须进一步追踪该输入何时被交付给模型 Runner，以及关联的工具何时完成执行与结算。

CHAPTER 01 · WHEN DOES THE SESSION ADVANCE?

请求已经发出，模型却还没开始。

输入受理阶段仅负责将请求写入持久收件箱并返回凭据。当会话协调器被唤醒后，Runner 必须推进到特定的安全调度边界，才能正式交付挂起的输入并发起下游模型调用。

受理、交付与运行各有边界

admit(input) → commit Inbox → wake(sessionID) atStepBoundary → promote pending input → load context runStep → stream one model request → settle local tools nextBoundary → check continuation, input and controls

复现：在步进机走到“流读完”，预判工具审批仍未回复时能否进入第二个 Step。

主循环步进机idle
  1. 受理输入
  2. 唤醒协调器
  3. 交付用户消息
  4. 重载上下文
  5. 开始模型 Step
  6. 发布本地工具调用
  7. 流读完并等待结算
  8. 工具返回与 Step 结算
  9. 新 Step 回注结果
  10. 无后续工作，结束执行

跟踪一次工具调用怎样驱动第二个模型 Step。

  1. 幂等受理与重试唤醒　具有相同 Session、相同消息类型与相同 Client ID 的重试请求，会直接复用已受理的持久记录；若传入 resume: false，则系统仅执行入队持久化而不立即唤醒协调器，后续可通过携带同一 ID 的请求显式唤醒推进。
  2. 输入交付与成批合并　标记为 steer 的纠偏插话可以在模型回合之间的 Step 边界被批量检出并交付给 Runner；而普通的 queue 消息则必须等待会话回到完全空闲边界（idle boundary），且每次仅按序交付一条。
  3. Step 结算与自动续跑　单个 Step 会完整消费模型 Provider 流，并挂起等待当前批次的所有本地工具执行完成；只要本轮产生了需要向模型回注的本地工具调用，协调器就会驱动开启下一个 Step，并在退出前检查是否有新的待处理输入与控制信号。

CHAPTER 03 · WHAT SURVIVES A CRASH?

断线丢了半句，重连后怎样补回来？

在线界面的实时打字效果来自无持久保证的 SSE 流式事件。客户端断线后应主动查询已提交至 SQLite 的消息投影，因为完整文本内容是在 session.text.ended 提交时原子落盘的。能否从实验日志接口完整补回原始事件帧，则严格取决于服务端是否配置了事件正文留存。

事件 → 状态投影台教学投影
持久类提交0
可补读正文0
已收实时帧0
服务器待审批0

对照两次实验：先断线、发送文本 delta 和终态、再重连。重置后先开启留存，再做一遍。终态两次都写入查询投影，只有第二次能从实验日志补读事件正文。

  1. 持久化事务与实体投影　持久类事件的全局自增序号（aggregate sequence）与实体投影必须在同一数据库事务中提交；例如输入交付事务会在原子操作中清空对应 Inbox 条目并将消息正式写入 message 表。而底层 event 表中的完整事件正文另由 events.persist 开关控制，默认关闭以节省空间。
  2. 瞬态流式帧与断线重连　流式文本增量（session.text.delta）与审批提醒（permission.asked/replied）属于无持久化保证的瞬态事件，仅用于在线 UI 即时渲染；客户端断线重连后，必须主动重新拉取已持久化的完整消息投影与当前挂起的待审批请求快照。
  3. 增量事件追赶与同步　若服务端启用了事件留存，实验性会话日志接口支持传入排他参数 after={seq} 进行增量追赶，并可追加 follow=true 保持长连接流式消费；当历史回放完毕并切入实时流时，服务端会发出 log.synced 同步标识；但受限于磁盘配额，已留存的报文正文仍可能被后台任务按策略裁剪。

CHAPTER 04 · THE TOOL THAT DISAPPEARED

工具已注册，模型为什么还看不到？

排查工具不可见时，首先核验本次模型请求装配的工具快照（tool snapshot）。模型特定政策可能替换具体的代码修改工具，全局性的 deny 规则可直接隐藏整类工具，而 Code Mode 模式还会将部分工具收敛至 execute 的下属执行目录中。

02 · edit 权限示例
等待选择
  1. 预判某个编辑工具能否看见，再判断调用能否访问目标文件。
  1. 模型差异化工具政策　根据模型命名规则，匹配特定前缀的 OpenAI GPT 系列模型会被自动切换为专用的 patch 差异更新工具，以发挥其补丁编辑特长；而其他模型则继续使用常规的 edit（精确行替换）与 write（全量覆盖）工具。
  2. 规则粒度决定可见性　权限系统在装配工具清单时会根据 Action 查找末条生效规则：若命中针对全部资源（resource: *）的全局 deny 规则，该工具会直接从本次模型的可用工具快照中剔除；而若规则只是拒绝访问特定路径（如 protected/*），工具依然对外暴露，拦截动作将延迟到模型发起具体调用时的执行现场。
  3. 运行时二次资源断言　工具最终能否执行，取决于工具自身的动态参数断言（resource assertion）与当前请求绑定的上下文定义；即使是通过 MCP 接入的第三方外部工具，在全局注册表中也同样受到统一的运行时安全断言约束。

CHAPTER 05 · APPROVAL WHILE THE MODEL WAITS

模型流已经结束，工具仍在等谁批准？

工具在执行前会向 Permission 模块提交 action 与具体 resource。若策略裁决为 ask，执行线程将在进程内挂起并等待 Deferred 结果。客户端既可订阅实时的审批提醒事件，也能随时通过 REST 接口主动查询当前挂起的待处理审批项。

审批裁决矩阵选择 5 个维度
01 · 请求资源
02 · Agent 规则
03 · Session 覆盖
04 · 项目历史审批
05 · 需要审批时的答复
等待选择
  1. 按 action 和 resource 检查规则。只有裁决为 ask 时才应用答复。
  1. 规则匹配优先级与短路　权限引擎会逐项校验工具请求的每项资源。在合并静态 Agent 规则与动态 Session 覆盖时，同 Action 的规则以最后一条为准；如果任一资源在规则链中最终裁决为 deny，系统会立即短路拒绝整次调用，根本不会再去查验项目持久化的历史批准（always）。
  2. 审批作用域与持久化生效　人工回复 once 仅单次放行当前工具调用；而选择 always 则在存在可持久化资源的前提下，将放行规则永久写入项目级权限配置，并立即触发重新评估当前工作区（Location）下所有处于挂起状态的同类审批请求。
  3. 拒绝联动与反馈透传　执行 reject 会连带影响同会话、同父消息触发的整批挂起审批。若用户拒绝时附带了文字反馈，系统会将反馈包装为模型可见的工具错误结果以协助其自我修正；若拒绝且不提供反馈，则直接中断当前 Step。底层的系统级隔离则严格依赖宿主进程或容器边界。

CHAPTER 06 · THE PROMPT CHANGED OVERNIGHT

项目规则改了一行，下一步的模型输入哪里变了？

在组装模型请求前，装配器会依次加载基础 system 提示词、指令基线、会话历史与当前可用工具。外部项目规则的变更可以作为增量更新记入历史，在触发上下文压缩后则以全新的指令基线接续。排查模型实际收到的请求时，还必须核验会话 Hook 是否在最后阶段就地改写了参数。

System 拼装台选择场景
观察点
沿基础 system、指令基线、增量与请求 hook 查看模型输入。
  1. 基础系统提示词组合　上下文装配器优先采用自定义 Agent 声明的 system 提示，缺失时回退到引擎内置模板；同时系统会根据当前请求公布的工具快照，动态注入针对 shell、write、edit 等工具的最佳实践使用规范。
  2. 确定性分层与缓存复用　指令组装严格遵循固定顺序：全局 Code Mode 规范、MCP 说明、项目引用与通用技能等静态通用资产置于最前，随后再追加动态发现的工作区规则（rules）与会话指令条目，最大化利用底层 Provider 的 KV 提示词缓存。
  3. 消息适配与 Hook 拦截　投影出的转录历史必须经过特定目标模型的 adapter 转换为 API 专有格式；在实际发送网络请求前的最后关头，注册的会话 Hook 仍拥有最高裁决权，能够就地审查或改写本次请求的 system 指令、消息列表及暴露工具。

CHAPTER 07 · WHEN THE WINDOW FILLS

换模型后，为什么输入突然变长？

换模型导致 Token 激增时，先核查当前上下文的 Token 预估值与目标模型的可用窗口，再评估新模型能否兼容原有的历史边界快照。系统为手动压缩命令、自动预检触发以及 Provider 报溢出时的应急恢复分别提供了入口。

  1. 手动触发与异步调度　用户发起的 compact 命令会作为一条控制消息先写入持久化收件箱，由会话协调器安排在当前 Step 执行完毕后的下一个安全调度边界处被检出执行。
  2. 自动预检与溢出恢复　自动压缩在每次请求前根据估算的 Token 总量与目标模型的最大窗口（减去安全预留）进行判断；若请求发出后模型直接返回请求体超长错误，会话 Runner 会启动容错逻辑，尝试执行一次基于溢出的应急压缩（overflow compaction）并重新组装请求重试。
  3. 多模型上下文兼容性　压缩生成的可移植结构化摘要会汇总早期历史并完整保留尾部的近期上下文；但某些 Provider 原生的紧凑会话窗口绑定了特定的模型 ID 与格式，若中途切换为不兼容的模型，新模型将无法解析这些原生快照，只能跳过快照重新展开未压缩的历史文本，导致输入 Token 骤增。

CHAPTER 08 · A CHILD REPORTS BACK

父代理收到子任务 ID，此时结果在哪？

委托工具会创建或复用带有 parentID 关联的子 Session，并启动专门的后台异步作业（Job）。父工具在调起后立即返回子任务句柄（child ID）；当子任务执行结算时，先将报告写入待交付队列，随后再以带有稳定通知 ID 的合成消息安全投递进父会话的收件箱。

子代理派生实验台选择 3 个维度
01 · 当前会话
02 · 深度预算
03 · 派生权限
等待选择
  1. 先看深度，再看父调用的 subagent 权限。
  1. 派生深度与委托权限　系统在派发前先递增计算当前层级深度（默认深度硬上限为 1，严防失控的递归嵌套），再将目标子 Agent 的标识作为受控资源，向权限系统发起 subagent 动作校验，未获授权则直接拒绝创建。
  2. 工作区继承与独立裁决　新建的子会话默认继承父会话的工作目录（Location）及显式授予的上下文权限；但在运行过程中，子会话拥有独立的会话实体与消息状态，工具的调用由子会话绑定的 Agent 规则独立裁决。
  3. 可靠通知与父收件箱交互　当子任务结算时，生成完成报告与写入待发队列在同一事务中持久化；系统以合成的系统通知消息将结果安全投递进父会话的 Inbox，直到父 Inbox 确认受理后才清空待发记录；即使父会话此时处于回滚或忙碌状态，通知依然安全入队，待唤醒后交付给父模型。

CHAPTER 09 · ONE RUNNER, DIFFERENT PROVIDERS

换了模型，为什么工具和故障方式都变了？

换模型导致行为异常时，先检查模型目录（catalog）中解析出的具体模型标识、变体配置（variant）与绑定的工具政策，再确认本次网络请求到底走了哪一条底层传输通道。

模型请求交换台选择请求场景
观察点
观察模型能力、编辑工具和传输分别在哪一层生效。
  1. 规范化流式抽象　会话 Runner 依赖底层统一的流式接口将各家模型的特有输出转换为标准的流式事件；每个逻辑 Step 封装一次完整的模型网络往返，当遭遇网络抖动或瞬态异常时，重试机制在当前 Step 内部独立收口。
  2. 双轨传输与降级锁定　模型连接支持可选的会话级 WebSocket；一旦 WebSocket 握手或通信失败，系统会自动降级并将当前会话强行固定到标准 HTTP 通道，直到服务重启或重新创建会话连接实例。此过程完全不影响面向前端 UI 的独立 /api/event SSE 事件流。
  3. 终态原因与输出续跑　流异常中断若为 unknown，系统将其归类为网络不完整流并触发重试；若模型因达到单次生成上限而返回 length 停止信号，Runner 则会自动启动专门的输出续写（continuation）机制，请求模型在下一个 Step 中无缝接续生成。

CHAPTER 10 · WHO OWNS THE EXTENSION?

加一个扩展，要改工具、提示词，还是执行边界？

接入外部扩展时应按职责选择扩展点：技能（Skill）与项目指令专职补充动态上下文，插件（Plugin）负责挂载会话 Hook 与执行工具，而 MCP 则负责把跨进程或远程服务的能力挂载进统一的工具目录中。

  1. 插件按需激活与生命周期　服务端的全局工具目录查询仅反映当前已完成初始化的内容，冷启动阶段允许部分条目暂缺；会话 Runner 与核心调度器在正式执行命令前，会进入专门的准备阶段，确保目标 Location 所需的本地插件完全激活。
  2. 提示词增强与命令分流　在组装 prompt 时，系统动态解析用户显式引用的技能内容并注入上下文；若用户输入的是注册的内部斜杠命令，则直接交由 Session 命令调度器分发；而底层的原生操作系统 Shell 命令则路由至专属的终端环境执行。
  3. 扩展工具的拦截契约　无论是本地插件引入的自定义工具还是远程 MCP 服务提供的工具，都必须统一挂载到全局工具注册表并受制于相同的权限边界；session.context 钩子用于动态控制本次请求中暴露给模型的工具快照，而 tool.execute.before 钩子则在工具真正调起前执行最后一道参数审计。

CHAPTER 11 · WHICH BUDGET WAS EXHAUSTED?

这次消耗的是模型预算、工具输出还是重试次数？

执行中断时，必须精细区分消耗的到底是模型回合步数、工具返回字符上限、网络重试预算还是进程恢复配额。准确定位到具体触发的资源瓶颈，才能制定正确的恢复方案。

  1. 回合步数硬顶与收口　当会话连续执行的 Step 步数触达 agent.steps 上限时，Runner 会在最后一次请求中强行注入收尾提示词并将模型参数设为 toolChoice: none；即使为了协议完整性仍携带了工具定义，本地执行器也会在底层坚决拦截任何后续工具调用。
  2. 多维恢复限制与熔断　针对 Provider 网络超时的重试会显式发布事件并消耗重试预算；输出续写机制若发现最近三条消息均为因 length 截断而续写的助手消息，会主动熔断判为失败以防无限死循环；而在服务器崩溃重启后，系统会检查并累计本地执行认领（claim）的尝试次数，防止故障任务被反复唤醒。
  3. 工具返回体积治理　工具输出的文本受到严格的尺寸限制（默认截断阈值为 2,000 行或 50 KiB）；向模型回填的结果仅保留截断后的摘要预览与外部完整日志的文件存储路径，防止超大日志瞬间击穿上下文窗口。

面试题 · 服务重启后，怎样交付可靠的工具会话？

请求已经受理，能否安全重试？

客户端复用相同的 Session ID 与用户输入 Client ID 发起重试，服务端的持久受理层将幂等返回首次受理记录，防止重复入队。在系统设计上，收件箱入队与 Runner 实际交付必须解耦为两个独立状态阶段；若工具执行具有外部副作用，调用本身必须自备业务幂等键或依赖提交事务回执。

前端断线，怎样恢复成正确的状态？

重连后前端应重新建立实时 SSE 订阅，并主动调用 REST 接口拉取最新的已提交会话消息与挂起的待审批快照，根据全局 Message ID 执行合并去重；对于启用了事件正文留存的服务端，可从本地已知最后处理的全局序号（aggregate sequence）开始增量补读事件；最终的文本状态始终以 session.text.ended 提交到 SQLite 的投影为准。

Provider 表示 stop，怎样验证会话为何继续？

首先检查当前 Step 是否记录了未结算的本地工具调用，工具是否正在执行或等待人工审批；其次检查 Inbox 中是否堆积了新的 steer 插话或待处理的 queue 消息。即使模型自身表明推理完毕（stopReason 正常），只要存在待回填结果或排队输入，协调器仍会依约推进开启后续 Step。

  1. 已受理，未交付　查 Inbox、delivery 模式、当前 Step 和执行状态。
  2. 已开始，无文本或终态　区分 SSE 断线、模型流未结束、工具仍执行或等待权限。逐层对照查询接口。
  3. 有结果，后续行为异常　比较历史压缩边界、本次工具快照、模型 variant 和请求 hook。
