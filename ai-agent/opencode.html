CHAPTER 01 · WHEN DOES THE SESSION ADVANCE?

请求已经发出，模型却还没开始。

受理把输入持久化。会话协调器唤醒后，Runner 到安全边界才能交付输入并发起模型调用。

受理、交付与运行各有边界

admit(input) → commit Inbox → wake(sessionID) atStepBoundary → promote pending input → load context runStep → stream one model request → settle local tools nextBoundary → check continuation, input and controls

复现：在步进机走到“流读完”，预判工具审批仍未回复时能否进入第二个 Step。

主循环步进机idle
  1. 受理输入
  2. 唤醒协调器
  3. 交付用户消息
  4. 重载上下文
  5. 开始模型 Step
  6. 发布本地工具调用
  7. 流读完并等待结算
  8. 工具返回与 Step 结算
  9. 新 Step 回注结果
  10. 无后续工作，结束执行

跟踪一次工具调用怎样驱动第二个模型 Step。

  1. 同一输入可重试　同 Session、同类型、同输入 ID 重试沿用首次受理。resume: false 只受理。
  2. 什么时候进入历史　默认 steer 可在 Step 间交付。queue 等空闲边界，一次交付一项。
  3. 什么时候续跑　Step 读完整条 Provider 流并等待本地工具结算。记录了需要回注的本地调用时会续跑，空闲前还会检查新输入与控制项。

CHAPTER 05 · APPROVAL WHILE THE MODEL WAITS

模型流已经结束，工具仍在等谁批准？

工具向 Permission 提交 action 和 resource。命中 ask 时等待进程内 Deferred。客户端可订阅实时审批提醒，也能主动查询当前待处理请求。

审批裁决矩阵选择 4 个维度
01 · 请求资源
02 · Agent 规则
03 · Session 覆盖
04 · 需要审批时的答复
等待选择
  1. 按 action 和 resource 检查规则。只有裁决为 ask 时才应用答复。
  1. 规则次序　同资源最后匹配的配置规则胜出。先检查合并的 agent/session deny，再应用项目已保存的 allow。
  2. 答复范围　once 只放行本次；always 在有可保存资源时持久写入项目规则并重评当前 Location 待批项。
  3. 拒绝与隔离　reject 影响同 Session、同来源消息的审批批次。有反馈时可形成模型可见的工具失败，无反馈可中断 Step。系统执行隔离由宿主边界提供。

CHAPTER 06 · THE PROMPT CHANGED OVERNIGHT

项目规则改了一行，为什么不必重写整段提示词？

执行前装载基础 system、指令基线、会话历史和工具。新版以指令状态保存基线与更新，变化进入历史更新，压缩完成时推进 epoch。

System 拼装台选择场景
观察点
沿基础 system、指令基线、增量与请求 hook 查看模型输入。
  1. 基础 system　优先用 agent 自带 system，缺省渲染内置文本。shell、write、edit 指导取决于所公布工具。
  2. 指令来源有顺序　Code Mode、MCP、引用、技能等通用来源在前，随后引入发现的规则和会话条目，使前缀可以复用。
  3. 请求完成前　投影历史需要经模型消息转换。会话 hook 还能修改本次请求的 system、消息与工具。

CHAPTER 07 · WHEN THE WINDOW FILLS

历史越长，新模型看到的内容越少吗？

先查当前上下文的估计和可用窗口，再看所选模型能使用哪种历史边界。手动压缩、自动预检和 Provider 溢出恢复分别有入口。

  1. 手动压缩　手动 compact 持久进入 Inbox，默认在下一安全边界处理。
  2. 自动压缩　按当前请求估计和模型窗口留出空间。模型在输出前拒绝过长请求时，运行器可尝试 overflow 压缩，再重建请求。
  3. 保留什么　本地摘要可缩并旧历史、保留近期上下文；支持的模型可存 native window。换模型后按兼容边界重建。

CHAPTER 08 · A CHILD REPORTS BACK

父代理收到子任务 ID，此时结果在哪？

工具创建或复用带 parentID 的子 Session，并启动专门的后台 Job。父调用先收到 child ID，完成报告随后经父 Inbox 回流。

等待选择

  1. 派生检查　先看当前嵌套深度和 agent 模式，再以目标 agent ID 为资源检查 subagent 权限。默认深度上限为 1。
  2. 继承边界　新 child 默认继承父 Session 的 Location 与显式会话权限。子会话用自己的 agent 和会话规则裁决工具。

CHAPTER 10 · WHO OWNS THE EXTENSION?

加一个扩展，要改工具、提示词，还是执行边界？

按责任选扩展点。技能与项目指令补上下文，插件可接入 Hook 和工具，MCP 把远端能力接入同一工具目录。

  1. 插件加载　服务器路由读当前已加载的目录。Runner 在模型执行准备边界可等待 Location 插件激活。
  2. 提示词与命令　prompt 准备解析显式技能选择。Session command 有独立入口，按命令的执行契约进入会话。
  3. 工具扩展　插件工具和 MCP 使用注册表和权限边界。session.context 与 tool.execute.before 分别对应本次视图和调用前。

CHAPTER 11 · WHICH BUDGET WAS EXHAUSTED?

这次消耗的是模型预算、工具输出还是重试次数？

步数、输出、网络重试和进程恢复处理不同的资源。定位到具体触发点，才能决定是否继续。

  1. 步数阈值　达到 agent.steps 时追加收尾提示并设置 toolChoice: none。工具定义仍随最终请求发送，本地执行器也会拒绝调用。
  2. 三类恢复　Provider 重试发布重试事件；连续三条 assistant 因 length 截断会失败；本地执行 claim 支持服务器崩溃后的有限恢复。
  3. 工具输出　文本按配置截断，默认 2,000 行或 50 KiB。返回预览与留存路径。

面试题 · 服务重启后，怎样交付可靠的工具会话？

请求已经受理，能否安全重试？

复用同一 Session 和用户输入 ID，受理层返回首次受理结果。把入队和交付分别建模。工具的外部副作用需有自己的幂等键或提交记录。

前端断线，怎样恢复成正确的状态？

先取会话与待审批快照。需要重放持久状态时，从上次收到的 Session aggregate 序号继续。文本 delta 用于实时展示，完整文本以文本终态和投影为准。

Provider 表示 stop，怎样验证会话为何继续？

确认 Step 有没有记录本地工具调用，工具是否结算。再检查 Inbox 中的 steer、queue 与控制项。模型无需续跑时，Runner 依然会检查边界上的新工作。

  1. 已受理，未交付　查 Inbox、delivery 模式、当前 Step 和执行状态。
  2. 已开始，无文本或终态　区分 SSE 断线、模型流未结束、工具仍执行或等待权限。逐层对照查询接口。
  3. 有结果，后续行为异常　比较历史压缩边界、本次工具快照、模型 variant 和请求 hook。
小结 · 30 秒自测

任选一个症状，写出观察到的最后边界、应出现的下一事件，以及能区分两条失败路径的证据。
