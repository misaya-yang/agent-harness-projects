CHAPTER 01 · FIND THE OWNER

场景：终端显示“完成”，会话里却没有最终消息。先定位状态拥有者。

同一个任务横跨模型适配、循环、会话壳和呈现层。只有找到“谁持有这份事实”，你才知道该查哪一种证据。

四层职责与事实拥有者

Pi AI 翻译各家模型请求；Agent Core 运行 turn、工具与队列；AgentSession 持久化、压缩、重试并托管扩展；TUI / RPC 只呈现或传输。屏幕结束，只能证明最后一层画完了。

SHORT TRACE

user → stream → message_end → session entry → render

若 message_end 已有而 entry 缺失，查会话壳；entry 已有而屏幕没更新，查呈现；stream 直接以 error 收口，问题更靠近模型适配。

事件与状态的关系

message_start/update 更新 streamingMessage，不会不断追加 transcript；message_end 才把完成消息推入公开状态。监听器按顺序等待，因此“结束事件发出”和“run 已闲置”不是同一时刻。

判断法

三种读点，三种承诺

画字读 partial；取最终答案读完成消息；安全开启下一项工作等 idle。不要在应用层再造一份“当前助手消息”。

学习检验：点更新、message_end、agent_end、监听器完成，指出哪一步追加消息，哪一步允许开启新 run。

CHAPTER 03 · ONE PROMPT, MANY TURNS

场景：用户只问一次，日志却出现五次模型请求。它不一定失控。

一次 prompt 可以包含多个 turn；每个 turn 是“一次助手响应 + 紧随其后的工具批次”。工具结果回填后，模型需要再开一轮才能继续推理。

先看事件顺序，再谈“任务完成”。

回合如何决定继续与结束

error/aborted 结束低层 run。只有整批结果都要求 terminate，才取消工具驱动的续跑，队列仍可能触发下一轮。宿主可用 finishTurn 要求结束或继续。低层循环的轮数预算由宿主接入。后续回合先走 prepareNextTurn，每次模型请求前还可以通过 prepareRequest 更新 context、模型和思考档位。

SHORT TRACE

toolUse → result → toolUse → result → stop

这是一条 prompt、三次 turn。看到 agent_end 只说明循环已停，不说明业务目标已达成。

CHAPTER 04 · STEER / FOLLOW-UP / ABORT

场景：工具正在写文件，用户说“停，改另一个方案”。消息该插在哪里？

Steer 纠正当前任务，Follow-up 排下一件事；二者都不会插进 tool call 与 tool result 之间。Abort 只是协作式信号，不能撤销已发生的副作用。

消息干预先保证协议配对

Steer 默认一次取最早一条，在当前批次落定后、下次模型调用前进入；Follow-up 只有任务自然收口后才续跑。Abort 会传给模型流、钩子和工具；已开始的执行体要主动响应。1.6.0 为批次中未开始的调用补 Operation aborted 错误结果，让历史保留调用与结果的配对。

练习

开始工具 → Steer → Follow-up → 结束 Turn

预期先消耗 Steer，Follow-up 仍排队。若先 Abort，只能断言信号发出，不能断言副作用回滚。

学习检验：能区分 Steer、Follow-up、Abort，并为 Abort 写出“工具必须配合”的验收条件。

CHAPTER 06 · TOOL BATCH

场景：快工具先完成，为什么不能先把它的结果塞回会话？

执行可以并行，历史必须确定。Pi 把一批工具拆成“按源序预备 → 并发执行 → 按源序回填”。

工具批次排序实验parallel

只要一个工具要求 sequential，整批都串行。

并行进度与源序提交

tool_execution_end 按真实完成先后发，UI 立即反馈；tool result 按模型原始调用顺序写入，确保重放、缓存与测试稳定。两者混用才会让结果对不上调用。

两道安全题

残缺参数与副作用冲突

助手因 length 被截断时整批不执行，只回喂错误让模型重发。参数校验与调用前钩子先串行完成；同文件修改也应串行化。

动态工具

tool_search 激活工具后，Agent 将 toolsAdded / toolsRemoved 写进 system 消息。Provider 适配层根据目标 API 提交工具定义，后续回合可从 transcript 重放当前工具。

学习检验：运行并行实验后，能解释为何 fast 先结束，而 transcript 仍先写 slow 的结果。

CHAPTER 07 · APPEND-ONLY SESSION TREE

场景：回到旧消息试另一条路，原分支会不会被覆盖？文件改动会不会一起回滚？

当前 Coding Agent 使用 v3 追加式条目树；移动 leaf 就能从历史点续写，旧分支仍在。但这是对话历史，不是工作区快照。

源码更新 · 规范上下文

历史保留，模型视图仍可以修订。

SessionManager 已成为后续模型请求上下文的权威来源。新的 context_edit 作为追加条目，可省略或替换一条消息在未来请求中的内容，却不改写原始会话树和 UI 历史。

CHAPTER 08 · CONTEXT COMPACTION

场景：上下文快满了，直接删最老消息却把 tool call 与 result 拆开。

压缩追加摘要、firstKeptEntryId 与 prompt/tool 检查点；下一次请求从检查点、摘要与近期路径重建。切点必须让位于工具配对完整性。

  1. 判压力：provider usage 为权威，新增内容保守估算；超过 window − reserve 才自动触发。
  2. 找切点：从后往前保留近期内容，不拆开工具配对。
  3. 生成摘要：旧对话转纯文本，每条工具结果截取 2000 字符并合并上一摘要；失败的摘要不落盘。
  4. 追加边界：原条目仍在树中，只有模型投影改变。

压缩改变模型视图，保留历史事实

Coding Agent 在新 prompt 前，以及工具结果已记录、准备下一回合时检查压力。可恢复的 overflow 或早期 length 可触发一次压缩重试；含 tool call 的截断响应会先记录合成失败结果并走普通调度。失败尝试可追加 context_edit 从模型视图省略。

压缩后怎样恢复工具集合？

压缩 entry 的 systemMessage 汇总保留段里的 prompt 和工具状态，替代该段原有的 system 消息。压缩后的 system 增量继续重放。reserveTokens 控制触发阈值，摘要输出上限取决于模型与可用空间。

同一个 MCP 工具，模型怎么找到它？

Coding Agent CLI 内置 MCP、Tool Search 与 Codemode，支持 stdio 与 Streamable HTTP。tool_search 用 BM25 发现并激活 deferred 工具。codemode 在 QuickJS 中运行脚本，可组合工具并缩减回传内容；脚本没有 Node API、文件或网络接口，宿主工具仍可执行真实操作并经过 tool_call 和 tool_result。SDK 使用者需显式装配这些内置扩展。

CHAPTER 10 · TUI IS A PROJECTION

场景：终端看起来卡住，实际只是没有变化的行无需重绘。

1.0 起默认 Fullscreen，使用 alternate screen 与应用管理的视口；Regular 使用主屏和终端 scrollback。两种模式都使用差分渲染和同步输出。

差分帧对比台等待帧

高亮行是本帧真正重写的内容；宽度变化会完整重绘。

TUI 只投影运行状态

流式文本只改一行就不重画整屏；窗口宽度变了，旧换行假设失效，必须完整重绘。组件必须遵守可见宽度约束。1.6.0 的 render() 返回 readonly string[]；Container 会复用缓存数组，扩展要先复制再修改。

判断法

状态证据不要取自截图

自动化应读完成事件、会话上下文或 RPC 状态。截图不能证明监听器已结算、消息已落盘或业务目标已满足。

CHAPTER 11 · SDK / RPC / DURABLE

场景：IDE 要知道何时结束，后台任务还要在重启后续跑。

Coding Agent 用同进程 SDK 或 stdin/stdout RPC 控制会话。独立的 Pi Durable 保存执行进度，p2 和 p3 通过 Chord 组织宿主、worker 与插件。

题目
IDE 何时能确认会话结束？后台任务重启时该重新提交，还是从原任务恢复？

RPC 的三个完成信号

prompt 响应的 data.disposition 表明启动、排队或已处理。agent_end 结束一次低层 run，之后仍可能重试、压缩或续跑。客户端应先订阅事件，再发送 prompt，用 agent_settled 判断会话层何时结束自动推进；handled 的 prompt 没有开启 run。

stdout 保留给协议记录，stderr 承载诊断。按 LF 分帧并容许 CRLF，JSON 字符串里的 U+2028 和 U+2029 属于内容。

Durable 恢复已提交的进度

conversation.commit() 可原子追加 entry、修改文档和创建任务。模型请求是 pi.generation 任务，它管理 pi.tool 子任务。任务可保存 checkpoint，也可 park 等待信号。重开存储后使用 resume()；相同 requestId 返回原 submission。工具还需为外部副作用实现自己的幂等策略。

Chord 负责跨进程对象

Chord 用 contract 描述对象，用可订阅引用反映状态，调用由链接绑定 principal。p2 是实验性的自托管 Durable UI，owner 可以在服务器和 worker 上运行 agent 与 shell。后继 p3 基于 Chord v2，此快照是 headless server，每个 session 有自己的 worker，加载后可恢复 Durable 任务。

CHAPTER 12 · TRIAGE & BUILD YOUR OWN

综合场景：模型重试、压缩重试和用户处理同时发生，成本开始失控。

按“模型能否修复”和“证据是否仍新鲜”分诊。工具错误回喂模型，瞬态网络错误退避，配额与未知错误交给用户；溢出单独走一次性压缩恢复。

看到什么正确出路验收证据
参数错 / 工具抛错写成 isError 结果，带现场与下一步动作下一轮能自纠
429 / 5xx / 断流只对白名单瞬态模式做可取消退避重试事件 + 终态
quota / billing / 未知不盲重试，交回用户无恢复风暴
context overflow排除普通重试；压缩后仅允许一次恢复尝试新边界 + 闩锁
用户 Abort终止不重试；检查执行体是否响应副作用实际停止

五步判断法

  1. 标入口：SDK、交互、print/json、RPC 或 Durable。
  2. 找最后一个已提交事实：终态消息、工具结果、会话条目或 Durable checkpoint。
  3. 按 owner 分层：Provider、Loop、Session、Extension、UI。
  4. 检查恢复：类型匹配吗？证据晚于最近压缩吗？预算只允许几次？
  5. 验证目标，不把 HTTP 成功、进程退出或截图当成任务完成。
BUILD CHECK

自己的 Agent 至少写下六条合同

事件何时提交；工具如何排序；截断参数是否执行；队列在哪里注入；失败去往模型、重试还是用户；持久历史怎样重建上下文。每条都要有反例测试。

恢复：确认溢出来自当前模型且晚于最近压缩；移除工作上下文里的失败助手消息，追加压缩边界，再 continue 一次。原始条目不删除，第二次仍溢出就交用户。

验收：工具调用与结果配对完整；历史保留场景，模型下一轮看不到失败残骸；恢复不超过一次。

课程边界会读事件，也会怀疑“已实现”。从 Coding Agent 读取会话投影与 agent_settled；从 Pi Durable 读取已提交的任务和 checkpoint。Chord 的远程访问边界由应用及部署决定。

课程完成：你现在可以从短 trace 判断 owner、顺序、恢复和证据等级，并把机制迁移成可测试合同。

Turn
一次助手响应及紧随的工具批次。
Transcript
发生过什么的事实记录，不等于每次模型请求看到的消息。
Steer
当前工具批次结束后、下一次模型调用前注入的纠偏消息。
Follow-up
当前任务自然收口后再处理的后续消息。
Checkpoint
Durable 任务提交的进度，进程重启后可从此继续。
Project Trust
项目资源加载门，不是操作系统沙箱。
