AGENT LOOP / SESSION TREE / DURABLE TASKS

Pi Agent 的事件循环如何决定继续、回注与停止。

在向 Pi 发起读取配置与修复代码的请求时，工具执行完成、会话条目落盘与终端界面呈现往往发生在完全不同的时刻。Coding Agent 依靠细粒度事件推进当前循环，采用追加式树形会话记录保留每一次历史分支；而在遭遇进程崩溃或需要跨重启接续任务时，则需引入独立的 Pi Durable 任务编排引擎。

  • 判断完成顺序和会话顺序为何不同
  • 解释压缩为何不删除历史，以及何时仅允许一次压缩恢复尝试
  • 判断该用同进程 SDK、子进程 RPC，还是可恢复任务的 Pi Durable

CHAPTER 01 · FIND THE OWNER

场景：终端显示“完成”，会话里却没有最终消息。先定位状态拥有者。

同一个任务横跨模型适配、循环、会话壳和呈现层。只有找到“谁持有这份事实”，你才知道该查哪一种证据。

四层职责与事实拥有者

Pi AI 负责统一适配各家 Provider 的请求构造与流式解析；Agent Core 负责调度 Turn 轮次、工具并发批次与输入队列；AgentSession 在会话层管控条目持久化、上下文压缩、重试策略并托管扩展；外层的 TUI / RPC 则专注于终端呈现或跨进程传输。例如当屏幕上已经流式打出文字时，底层模型可能刚输出局部增量；若此时发生中断并要核对真正的落盘记录，必须向 SessionManager 的会话历史寻证，而非采信屏幕呈现。

SHORT TRACE

user → stream → message_end → session entry → render

AgentSession 会先向事件总线分发事件，随后再将 message_end 对应的会话条目写入持久化文件。如果监听器刚收到事件就立即读取磁盘，极易因异步落盘时差而读到未更新状态；反之，若磁盘已存在条目但屏幕毫无反应，则应优先排查 TUI 的差分重绘逻辑。

事件与状态的关系

message_start 与 message_update 仅在内存中就地更新草稿对象 streamingMessage，不会污染或持续膨胀会话历史；直到 message_end 事件发出，完整的助手消息才会被原子追加至公开状态。由于事件总线会严格按序等待所有注册监听器执行完毕，因此「模型结束流式生成」与「当前 Run 完全回到闲置状态（idle）」之间存在明显的时差。

判断法

三种读点，三种承诺

界面打字时应消费增量 partial；助手消息生成完毕（message_end）后，必须第一时间检查是否发起了工具调用。若集成基础 Agent SDK，调用 waitForIdle() 必须等待全部后置监听器完成；若基于 Coding Agent 构建复杂会话，最终结算则以第 11 章的 agent_settled 为准。

CHAPTER 03 · ONE PROMPT, MANY TURNS

场景：用户只问一次，日志却出现五次模型请求。它不一定失控。

单个用户 prompt 往往包含多个交替演进的 turn；每个 turn 严格定义为「单次助手响应 + 紧随其后的工具并发批次」。工具返回结果回填至上下文后，必须驱动模型开启新一轮推理才能消化结果并继续推进。

回合如何决定继续与结束

底层循环的退出主要受四类信号驱动：遇到 error 或 aborted 时，当前低层 Run 会立即终止；当工具批次全部执行完毕且未中断时，若所有工具结果均显式声明了 terminate，内核才会取消由工具驱动的自动续跑，但此时输入队列中若有待处理消息仍可能触发下一轮；宿主层调用 finishTurn 则能显式结束当前 Run 并直接跳过队列读取。为防失控，低层循环必须由宿主注入轮数预算守卫。在进入后续回合前，内核先通过 prepareNextTurn 推进回合状态，并在每次向模型发起网络请求前，调用 prepareRequest 动态同步最新的上下文投影、目标模型与思考预算档位。

SHORT TRACE

toolUse → result → toolUse → result → stop

一条 prompt 经历三次 turn 演进。必须牢记：捕捉到 agent_end 仅代表当前回合执行循环停机，绝不代表实际业务目标已被验证达成。

CHAPTER 04 · STEER / FOLLOW-UP / ABORT

场景：工具正在写文件，用户说“停，改另一个方案”。消息该插在哪里？

Steer 在工具批次结算后进入下一次请求，Follow-up 要等当前任务自然停下。Abort 向工具发协作式取消信号，已经发生的副作用需单独核对。

消息干预先保证协议配对

Steer 消息默认按 FIFO 顺序每次取出最早的一条，在当前工具批次完全落定后、发起下一次模型请求前注入上下文；Follow-up 消息则必须等待当前任务的所有回合自然收口后才被取出并开启新任务。Abort 信号会同时向在途的模型流、扩展钩子以及运行中的工具广播；已经启动的执行体必须具备主动感知取消信号并退出的协作能力。为了避免模型在后续回合中因缺少工具输出而报错，1.6.0 运行时会自动为批次中尚未启动的工具调用补填 Operation aborted 错误结果，确保转录历史中每一项工具调用都严格拥有对应的返回条目。

练习

开始工具 → Steer → Follow-up → 完成工具批次

操作演练：点击「开始工具」模拟耗时执行，接着依次点击「+ Steer」与「+ Follow-up」注入插话。随后点击「完成工具批次」，观察调度器先弹出并消费 Steer 消息送入下一轮模型推理，而 Follow-up 依然在队列中挂起。只有当模型消化工具输出并给出终态回答（点击「模型答完，无新工具」）且无新工具调用时，整条任务自然收尾，Follow-up 才被调度启动。

学习检验：能区分 Steer、Follow-up、Abort，并为 Abort 写出“工具必须配合”的验收条件。

失败沿统一事件通道收口

所有 Provider 层的异常都必须规范化收口为统一的终止原因：模型服务报错或超限映射为 stopReason: error，主动取消则映射为 aborted。Agent 主循环仅依据这两个标准字段做出分支裁决；但在宿主回调函数或自定义事件监听器内部抛出的未捕获异常，依然会导致顶层 Promise 直接 reject，需要外层调用者单独捕获。

更新机制

缓存与思考档位也要可诊断

Anthropic Message Threads 机制会在每一轮对比上一轮的请求配置与消息历史前缀。只要上下文仅是在尾部追加新消息，系统就可以直接复用服务端的 Message Thread 缓存；一旦发生分支切换或执行了上下文压缩从而改变了前缀哈希，适配层便会自动降级发送全量请求。当把视觉模型切换为纯文本模型时，适配层会在本次请求中将图片对象替换为文本占位符，而存储中保留的原始图片条目依然完好，以便后续切回视觉模型时继续使用。

CHAPTER 06 · TOOL BATCH

场景：快工具先完成，为什么不能先把它的结果塞回会话？

并行模式先按模型列出的顺序校验和运行调用前钩子，再并发执行获准的工具，最后按原调用顺序写入结果。

工具批次排序实验parallel

试两种执行顺序，再切到截断响应，观察为何收到 start 事件也不能证明工具体已经运行。

并行进度与源序提交

tool_execution_end 事件在工具实际执行结束时立即发出，供前端界面及时更新每项任务的进度状态；但在将工具输出写入会话条目时，必须严格恢复为模型最初发起调用时的原始顺序。这样既能保证 UI 获得低延迟的流式反馈，又能确保历史回放、前缀缓存哈希以及回归测试的一致性。如果将两者次序混淆，会导致会话转录中的调用与返回错位。

两道安全题

残缺参数与副作用冲突

如果模型输出因达到最大输出上限（stopReason: length）而被截断，由于可能生成了残缺不全的 JSON 参数，Agent 会直接拒绝执行整批工具，而是将截断错误回填给模型要求重发。在并发控制上，所有工具的参数校验与调用前安全钩子会先按序串行执行；对于命中相同目标文件的写操作，也必须经过文件锁串行化排队，防止并发写入造成文件损坏。

动态工具

通过 tool_search 动态激活工具后，Agent 会将包含 toolsAdded 与 toolsRemoved 增量的 system 消息写入转录。Provider 适配层据此向目标 API 提交最新的工具定义清单，而在后续回合回放历史时，系统能沿转录精准重建当时的工具上下文。

学习检验：运行并行实验后，能解释为何 fast 先结束，而 transcript 仍先写 slow 的结果。

历史保留，模型视图仍可以修订。

追加记录与上下文重建

在追加式条目树中，每条 entry 都包含唯一的 id 与指向前驱的 parentId。当为模型重建请求上下文时，系统首先沿当前 leaf 节点向上回溯出有效分支链，截取最新的压缩保留段，随后再对这些条目叠加上最新的 context_edit 记录（如省略特定冗余消息）。这种机制让底层不可变的原始条目、上层动态的模型视图以及编辑指令的来源 ID 可以被独立审计。首条 system 消息声明了全局 prompt 结构与工具清单，后续的增量配置以独立的 system 消息追加，在恢复会话或切回旧分支时可沿分支路径精准重放。

SHORT TRACE

e1 ← e2 ← e3；回到 e1，再追加 e4

e2/e3 没被删，e4 成为新分支。模型只看 e1→e4；文件系统不会随 leaf 移动，代码试验仍需 Git 或隔离工作区。

  1. 判压力：使用仍对应当前投影的 provider usage，加上新增消息的估算。旧 usage 失效时重估。常规自动阈值是 window − reserve。

压缩改变模型视图，保留历史事实

Coding Agent 会在两个关键节点主动检查上下文压力：一是接收到新的用户 prompt 时，二是工具结果刚刚写入转录、正准备发起下一轮推理前。如果模型调用最终由于上下文超限（overflow）或特定截断（length）而失败，会话壳层允许触发一次上下文压缩恢复。当截断的助手消息中夹带了未闭合的工具调用时，循环会先为整批工具合成失败占位结果以闭合协议，随后进入压缩流程，将失败的助手消息及其配对结果从送给模型的上下文中一并省略，避免模型在下一轮看到自身的错误残骸。

压缩后怎样恢复工具集合？

压缩 entry 的 systemMessage 字段会汇总保留段之前的所有 prompt 规则与当前激活的工具定义，直接替代保留段原有的全局 system 声明；此后新发生的配置增量仍会按原样追加与重放。通过 reserveTokens 可以设置触发自动压缩的安全阈值，而每次生成的摘要长度上限则由模型能力与剩余上下文空间共同约束。

资源加载与执行隔离

一个搜索工具什么时候值得放进每次请求？

Coding Agent CLI 内置了对 MCP、Tool Search 与 Codemode 的集成，支持通过 stdio 与 Streamable HTTP 连接服务。对于高频核心工具可以直接暴露在提示词的 tool specs 中；而对于低频专业工具，则可声明为延迟加载，仅在模型通过 tool_search 明确检索并激活后，再将其 schema 注入下一轮请求，从而大幅节省默认上下文。借助 QuickJS 沙箱运行的 codemode 脚本，模型可以在沙箱内一次性组合串联多次搜索调用，仅向主上下文返回过滤后的精确结果。此时 QuickJS 仅约束脚本执行环境，当脚本调用宿主工具时，仍会受到工具各自的权限与安全钩子拦截。SDK 使用者需显式装配这些内置扩展。

差分帧对比台等待帧

高亮行是本帧真正重写的内容；宽度变化会完整重绘。

TUI 只投影运行状态

在终端渲染中，当流式输出仅导致单行文字变更时，TUI 只向终端输出该受影响行的差分指令；但当发生窗口缩放（resize）时，由于所有历史输出的折行与布局均发生变化，渲染器必须执行全量重新布局与整体重绘。所有 UI 组件的输出宽度都必须严格受到当前终端视口约束。在 1.6.0 版本中，组件的 render() 方法被收紧为返回 readonly string[]，而 Container 容器为了性能会复用内部缓存的字符串数组，任何扩展在修改布局时都必须先复制数组，切勿直接就地改写。

判断法

状态证据不要取自截图

排查故障或编写端到端自动化测试时，必须通过监听 agent_settled、检查会话 JSONL 或读取 RPC 状态来获取权威证据。绝对不能将终端截图或文字出现作为判定任务完成的标准，因为界面的字符渲染既无法证明后台监听器已经结算，也不能证明会话已经安全落盘，更不能代表业务逻辑已真正达成。

RPC 的三个完成信号

在通过 stdin/stdout 与子进程进行 RPC 通信时，发送 prompt 后收到的初始响应中，data.disposition 会指明该请求是立即被执行（started）、进入等待队列（queued）还是被扩展就地消费（handled）；若为 handled，则无需等待 Run 结算。低层的 agent_end 仅代表当前单次执行循环结束，随后系统可能因错误自动重试、触发上下文压缩或消费排队消息；客户端必须在发送 prompt 之前就提前建立事件监听，并以 agent_settled 事件作为整场会话完全停止自动推进的唯一权威凭证。

标准输出（stdout）严格保留给协议数据帧，诊断日志则全部由标准错误（stderr）承载。报文按 LF 分帧并兼容 CRLF，JSON 字符串内部的 U+2028 与 U+2029 视作普通文本内容。

Durable 恢复已提交的进度

在 Pi Durable 架构中，conversation.commit() 提供了原子保障，可在一个事务中同时追加条目、更新状态并创建任务。每一次模型生成都被抽象为 pi.generation 任务，并由其负责管理下辖的 pi.tool 子任务。任务不仅可以定期提交 checkpoint 固化中间进度，还能调用 park() 挂起自身以等待外部异步信号（例如在等待远程测试服务回调时释放执行进程）。当存储重新打开并执行 resume() 时，系统利用同一 conversation 下的幂等 requestId 精准寻回原始提交；对于意外中断的工具调用，只有显式标记了 replay: "safe" 的安全操作才会自动重做，其余具有外部副作用的操作仍需依赖业务本身的幂等设计。

Chord 负责跨进程对象

Chord 框架采用 contract 定义对象契约，通过可订阅的分布式引用实时同步状态，其 RPC 调用由链路凭证与 principal 严格鉴权。原型的 p2 是一个实验性的自托管 Durable Web 界面，允许所有者在服务器与工作节点上跨进程调度 Agent 与 Shell；而后续演进的 p3 则基于 Chord v2 构建，形态为无头服务集群，每个会话分配独立的 worker 进程，重启或迁移后可直接重新挂载并恢复 Durable 任务。

CHAPTER 12 · TRIAGE & BUILD YOUR OWN

综合场景：模型重试、压缩重试和用户处理同时发生，成本开始失控。

按“模型能否修复”和“证据是否仍新鲜”分诊。工具错误回喂模型，可识别的瞬态错误走退避，配额与未知错误交给用户。当前失败若满足 overflow 恢复条件，才尝试压缩和续跑。

看到什么正确出路验收证据
参数错 / 工具抛错写成 isError 结果，带现场与下一步动作下一轮能自纠
429 / 5xx / 断流只对白名单瞬态模式做可取消退避重试事件 + 终态
quota / billing / 未知不盲重试，交回用户无恢复风暴
context overflow排除普通重试；压缩后仅允许一次恢复尝试新边界 + 闩锁
用户 Abort终止不重试；检查执行体是否响应副作用实际停止

五步判断法

  1. 标明入口协议：明确是同进程 SDK、命令行交互、JSON 流、子进程 RPC 还是 Pi Durable。
  2. 寻访最后事实：找到最后一条已提交的助手消息、工具执行结果、JSONL 条目或 Durable checkpoint。
  3. 锁定责任归属：依序在 Provider、Loop、Session、Extension 与 UI 五层中定位根因。
  4. 核验恢复有效性：确认失败类型是否支持恢复、恢复证据是否晚于最新压缩检查点、以及恢复预算是否超限。
  5. 验证业务闭环：以可执行的验收测试或业务状态为凭据，绝不把 HTTP 200、进程正常退出或终端输出文字当成任务完成。

“两个并行工具完成顺序相反，随后上下文溢出。写出不破坏历史的 trace。”

展开参考答案

执行：按声明顺序预备，并发执行；进度按完成顺序发，结果按声明顺序回填。
