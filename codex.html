MODULE 01 · AGENT LOOP

Agent Loop 如何把一次请求推进到确定结束？

本模块建立课程的执行骨架：提交循环接收操作，Turn 循环组织工作，sampling step 与模型交互。后续所有工具、压缩、恢复与协作机制都挂在这三层上。

INCIDENT 01 · TEST PASSED, TURN STILL RUNNING

命令成功，只说明一个 Item 完成；它不代表整个 Turn 已收束。

把一次任务分成三层就不容易误判：提交循环接收操作，Turn 循环决定是否继续，单次 sampling step 只负责一次模型请求。每步结束都执行同一个裁决：needs_follow_up = model_needs_follow_up || has_pending_input。

  1. 看到命令退出码 0：只确认这次执行成功。
  2. 看到 tool output 回注：模型现在才拿到执行事实。
  3. 看到仍需跟进：模型或排队输入要求再跑一个 step。
  4. 看到 turn completed：整轮才真正结束。

模块目标：能从任意停点判断当前仍在 submission、Turn 还是 sampling step，并用续跑等式解释下一步为什么发生。

心智模型

一次回合不是一次模型调用。它从用户输入入队开始，经过上下文组装、流式响应、工具判定、受控执行与结果回注，直到模型不再请求工具、也没有排队输入才收敛。

当模型产生工具调用时，工具结果必须先回到历史，下一 step 才能据此判断；当模型不再要求跟进且输入队列为空时，Turn 才自然收束。成功的 Item、完成的 sampling response 与完成的 Turn 是三个不同事实。

ROOT-CAUSE LENS

把故障归到拥有它的层：模型选错工具、策略拒绝权限、执行环境失败、还是结果没有正确回注。不要把所有失败都叫作“模型不行”。

  1. 提交：输入变成可追踪的操作。
  2. 推理：模型读取上下文并选择下一步。
  3. 行动：工具在权限与沙箱边界内执行。
  4. 回注：结果进入历史，驱动下一次判断。

MODULE 02 · STATE & INTERVENTION

Thread、Turn、Item 怎样承载状态，用户又怎样安全地改变在途任务？

本模块把状态容器、事件生命周期和三种人机干预放到同一张时间线上：steer 改变下一步，interrupt 停止当前工作，异步消息只承诺送达。

先确定作用对象，再选择动作

状态层次：Thread 保存可恢复的长期容器；Turn 表示一次用户请求及其全部 Agent 工作；Item 是消息、命令、文件变更或工具调用等可观察事实。操作必须明确落在哪一层。

Steer 把新输入放进当前 Turn 的 pending queue，在下一个完整 step 边界进入历史，不抢断正在生成的 token。Interrupt 取消活动任务，先给约 100ms 收尾窗口，必要时硬终止，并留下 aborted 历史事实与工具取消回执。

同步 request_user_input 会登记等待项并阻塞对应工具；异步用户消息立即返回 accepted，回答以后续输入到达。accepted 表示送达，不表示用户已经回答。

  1. Thread：保存身份、历史、配置基线与多个 Turn。
  2. Turn：拥有活动任务、取消信号、等待表和 pending input。
  3. Item：必须有开始、完成或明确中止的生命周期。
  4. 干预：steer 排队，interrupt 取消，async message 只投递。

“测试正在运行，用户补充‘不要修改数据库’，应该 steer 还是 interrupt？”

展开判断与答案
若当前动作尚未触及数据库，可 steer，让约束在下一 step 生效；若危险副作用已经可能发生，应 interrupt，随后检查已启动工具的实际状态与取消回执。选择标准不是输入有多重要，而是继续当前 step 是否仍然安全。
反例

把所有新输入都实现成抢占会制造残缺 Item、孤儿工具调用和不可重放历史；把所有输入都排队又会让危险动作继续。干预语义必须与副作用风险绑定。

模块验收：给出一个在途任务，能指出状态位于 Thread、Turn 还是 Item，并选择 steer、interrupt、同步询问或异步消息。

MODULE 03 · TOOL SYSTEM

工具怎样被发现、并行执行、取消并可靠回注？

本模块覆盖工具的完整生命周期：step 快照、暴露档、延迟发现、参数校验、授权、并行门闩、输出截断与调用—回执配对。

六个检查点，一条定位顺序

短 trace：可见？ → 参数对？ → 允许？ → 执行了？ → 输出完整？ → 回到历史？。先找第一个“否”，不要跨层猜原因。

DEBUG ORDER

工具未出现 → 查本 step 的可见工具；参数错 → 查 schema；执行被拒 → 查审批、规则与沙箱；命令成功但回答错 → 查输出截断和回注。

当前机制会在每个 step 重建工具路由，因此 MCP、项目规则和动态工具的变化最迟下一步生效。工具还分直接、延迟、仅模型调用、仅 code mode 与隐藏等暴露方式；列表太大时由 tool_search 按需发现。取消也不能让调用凭空消失：每个已派发调用都必须得到真实或合成回执，历史才可重放。

另一个容易混淆的新变化：同步用户提问会挂起等待；异步用户提问或消息会立即返回“已接受”，答案以后续输入到达。看到“工具成功”时，先确认它承诺的是完成，还是仅仅送达。

  1. 发现：这个 step 里模型是否看得见。
  2. 校验：参数是否符合结构化契约。
  3. 授权：策略、规则与权限是否允许。
  4. 执行：在限定环境中启动并采集结果。
  5. 归一化：保留头尾诊断并声明截断。
  6. 回注：让模型基于事实继续。

MODULE 04 · SAFETY BOUNDARIES

Codex 怎样把模型意图变成受控的真实副作用？

本模块分开讲审批策略、权限画像、命令规则、OS 沙箱、Guardian、受管网络与凭据代理。核心不是“是否安全”，而是谁分类、谁授权、谁最终强制。

    把一次拒绝拆成三问

    短 trace：命令规则分类 → 是否允许询问 → 权限画像与沙箱执行。规则可给出允许、询问或禁止；Granular 还能分别开关沙箱升级、规则询问、Skill 脚本、权限申请和 MCP elicitation，关掉某类意味着自动拒绝，不是静默放行。

    当自动审查被启用且路由条件满足时，Guardian 可以代替用户裁决；它超时、执行失败或格式错误时都 fail-closed。受管网络还可以把出口收敛到代理，启用凭据 broker 时，沙箱进程只看到占位值，真实凭据在出口注入。

    判断法：先问“谁拒绝”，再问“这个拒绝能否通过审批改变”。沙箱硬边界、企业约束和禁止规则不是点一下按钮就会消失。

    “审批策略设成 never，是不是就没有安全边界了？”

    展开判断与答案
    不是。never 只表示系统绝不向用户升级询问，沙箱、权限画像与禁止规则仍然生效；越界结果会直接回给模型。审批是交互策略，沙箱才是执行强制。
    BOUNDARY

    实验台展示常见沙箱与审批组合；实际裁决还可能叠加 Granular 分类、企业 requirements、Guardian 与受管网络。不要从一个开关推断整条安全链。

    模块验收：面对一次拒绝，能按“规则分类 → 是否允许询问 → 权限画像 → OS 强制”找出首个收紧点，并说明批准为什么不等于关闭沙箱。

    MODULE 05 · PROMPT & CONTEXT ENGINEERING

    Codex 每个 Step 实际把什么发给模型？

    本模块不教“写一段更长的 Prompt”，而是拆开基础指令、动态世界状态、活跃历史、工具定义与输出约束，并解释它们怎样在 step 边界重新组装。

    REQUEST SHAPEPrompt = Base Instructions + Active InputActive Input 由动态上下文、活跃历史、当前输入与 compact checkpoint 组成；Tools 和 output schema 作为独立请求字段。

    提示词工程首先是状态工程

    Step 快照：每步开始时冻结模型设置、权限、环境、AGENTS.md、MCP runtime、Skills 与模型可见工具。运行中的更新只影响下一步，避免同一次请求看到互相矛盾的世界。

    World State 差分：项目指令、权限和环境被拆成有身份的区块。前态为 Known 时只发送替换或删除差分；前态为 Unknown 时全量重注入，宁可多花 token，也不假装模型已经知道。

    稳定前缀：基础指令和稳定区块尽量保持顺序与身份稳定，帮助 prompt cache 命中；动态区块、历史与工具结果放在后部。缓存优化不能改变语义边界。

    1. Base Instructions：会话级行为基线，不随普通 compaction 被摘要替换。
    2. Dynamic Context：项目、环境、权限和扩展贡献的可差分状态。
    3. Active History：消息、推理项、工具调用与回执的模型工作集。
    4. Tool Specs：本 step 可调用能力的独立结构化字段。

    “Compact 后，下一次 LLM 请求会重新读取完整 transcript 吗？”

    展开判断与答案
    默认不会。Agent Loop 从 replacement history 派生新的 active input；完整 transcript 继续作为持久化事实源。后续压缩读取当前 active history——上一 checkpoint 加新增消息——而不是重新加载最初全部历史。
    TEACHING SCALE

    100k 窗口、86% 阈值和摘要压缩率只用于展示状态变化；真实限额由模型、provider、feature 与压缩路径决定。实验必须保持“替换 checkpoint”，不能把摘要画成无限累加。

    MODULE 06 · HARNESS ARCHITECTURE

    Core、App Server、客户端与执行环境怎样组成一个 Codex？

    本模块建立平台拓扑：Core 拥有会话语义，App Server 负责跨进程协议，客户端负责投影与交互，执行宿主负责真正的文件、进程和网络边界。

    MENTAL MODEL内核拥有会话 actor、Turn 循环、工具与历史语义。协议拥有请求顺序、双向交互、类型生成与多种传输。

    一个内核，两套协议，两种部署形态

    短 trace：客户端 → App Server → 会话 actor → 工具与模型 → 事件返回客户端。进程内提交用操作队列和回复通道；跨进程接入用双向 JSON-RPC。Rust 类型单向生成客户端类型与 schema，减少多端接口漂移。

    TUI 可以内嵌 App Server，也可以通过 stdio、Unix socket 或 WebSocket 接入常驻服务。远程控制、daemon 和不同前端改变的是部署与传输，不改变 Thread / Turn / Item 的核心语义。

    判断所有权时问一句：这项逻辑是否影响“任何客户端都必须遵守的事实”？是，就放进内核或协议；只是呈现、租户接入或产品工作流，则留在外层。

    MODULE 07 · PERSISTENCE & RECOVERY

    Codex 怎样从追加日志恢复出与在线运行一致的状态？

    本模块覆盖 Thread、Turn、Item 的寿命，rollout 检查点、反向重放、resume、fork、interrupt 与 rollback。重点不是“保存消息”，而是恢复模型真正看见的状态。

    01

    Thread

    拥有身份、历史与运行状态；可 start、resume、fork、archive，并包含多个 Turn。

    02

    Turn

    一次请求与 Agent 工作；可 steer、interrupt，完成时发出明确 final status。

    03

    Item

    最小可观察单元；拥有 started / completed 生命周期并承载增量更新。

    三层对应三种恢复问题

    短 trace：Thread 持有历史 → Turn 持有本次任务 → Item 记录可观察事实。Thread 可恢复、分叉与归档；Turn 可转向、中断并明确收尾；Item 则必须保持调用与输出配对。

    会话记录采用追加日志与替换历史检查点。恢复时从日志尾部向前找到最近检查点，再正向重放尾部；回滚写成新的事实，而不是删除曾经发生的记录。这样在线视图与恢复视图可以由同一套重放语义生成。

    如果只保存消息列表，“命令已经执行但最终回答还没完成”就无法准确表达。三层模型能保住已提交 Item，同时把未完成 Turn 标成中断，而不是假装它从未发生。

    “Resume 会从 transcript 第一行重新回放全部历史吗？”

    展开判断与答案
    不会。恢复逻辑从日志尾部寻找最新存活的 replacement-history 检查点，以它作为完整基线，再正向重放之后的尾部；World State 的 full/patch、Turn 设置和窗口身份也在同一次重建中恢复。
    OPERATION BOUNDARY

    Compaction 替换模型工作历史；rollback 撤销指定用户轮及其上下文更新；fork 在稳定采样边界复制出新 Thread；interrupt 只终止当前在途 Turn。四者不能互换。

    模块验收：能画出“追加日志 → 最新检查点 → 尾部重放”的恢复链，并预测 compaction、rollback、fork、interrupt 各自改变哪本账。

    MODULE 08 · MEMORY MANAGEMENT

    Codex 说“记住”时，究竟写进了哪一套记忆？

    本模块把短期工作集、完整会话日志、授权审查证据、宿主验证事实和跨 Thread 的长期 Memories 分开。它们拥有不同寿命、写入者、读取方式和清理语义。

    源码更新 · 授权证据

    压缩后，谁还能证明用户授权？

    当前实现把 Guardian 的 Thread 上下文作为常开路径；授权审查所需证据由独立保留层协调。模型工作历史被 compact 替换，不等于批准事实被删除。

    面试追问：普通压缩和 rollback 对授权证据的影响为何不同？

    返回「记忆与恢复」主题 ↗

    五套记忆，解决五种连续性问题

    Active History 服务下一次模型请求，可被 compaction 替换。Rollout 是每个 Thread 的追加式事实日志，用于恢复与审计，但不会每轮全量进入模型。

    Guardian Review History 保留授权判断所需的原始证据，普通 compaction 不删除已有的授权证据。Verified Answers 保存少量由宿主验证的回答，当前快照最多 8 条、单条约 16 KiB、总量约 64 KiB。

    Long-term Memories 跨 Thread 工作：后台先从 rollout 提取候选事实，再由整理阶段合并到记忆文件；新会话只注入小摘要和检索入口，需要时再 list/read/search。外部上下文会标记污染，避免不可信内容被固化。

    1. 工作记忆：当前模型需要继续任务的 active history。
    2. 事实日志：Thread 独立 rollout，追加发生过的事件。
    3. 授权证据：供 Guardian/审批判断，不依赖模型摘要。
    4. 长期记忆：跨会话的精选事实，不是完整 transcript。

    INCIDENT 08 · MODEL FORGOT, APPROVAL STILL VALID

    模型看不到旧信息，不代表授权证据已被删除。

    Compaction 只替换模型工作历史；审查证据和仍有效的宿主验证回答走独立保留路径。Rollback 才表示用户要撤销某段历史，因此会同步调整工作历史与相应证据。长期 Memories 又是另一条异步管线，不能拿来恢复精确 Turn 状态。

    1. 继续当前任务：读 Active History。
    2. 恢复原 Thread：读最新 checkpoint 与 rollout 尾部。
    3. 判断授权：读审查证据与仍有效的 Verified Answers。
    4. 跨 Thread 延续偏好：检索 Long-term Memories。

    判断练习：“新 Thread 应该精确恢复上一 Thread 最后一条工具调用吗？”不应该；这是 resume 的责任。长期记忆只保存值得跨会话复用的事实与偏好。

    “完整 transcript 已经在磁盘上，为什么还需要长期 Memories？”

    展开判断与答案
    Transcript 服务单 Thread 的精确恢复，体积大且包含过程噪声；长期 Memories 服务跨 Thread 检索，只保存经过提取与整理的少量事实。两者分别优化重放正确性与跨会话可用性。
    边界

    记忆不是一个万能数据库。先确定寿命、写入者、读取者和清理动作，再决定放进 active history、rollout、审查证据、Verified Answers 还是长期 Memories。

    两条容易记反的规则

    配置是覆盖，项目指令是拼接。配置层有明确优先级：打包默认、设备管理、系统、企业、用户、项目、会话参数逐层合并，遗留托管层仍可能拥有更高优先级；企业 requirements 还能直接拒绝越界值。项目指令则从项目根到当前目录逐层收集，局部 override 只替换同目录主文件，总量还受字节预算限制。

    Subagent 不是“多开一次模型调用”，而是独立会话：可选择继承全部、最近若干轮或不继承父历史；历史会洗掉推理过程和工具噪声，只保留适合交接的内容。消息可只排队，也可唤醒目标；最终答案会沿父子关系回传。资源还分别受并发、驻留与整棵树预算约束，权限只能收紧不能扩大。

      MODULE 12 · RELIABILITY ENGINEERING

      工具失败、模型流断开或进程重启时，系统怎样确定性收口？

      本模块整合错误分类、工具自救、流式重试、传输降级、取消回执、幂等记录、日志恢复、可观测性和 wire-level 测试。

      失败先分类，再选择去处

      工具层首先判断失败是否可以回给模型：非零退出、沙箱拒绝、用户拒绝和多数超时都变成可行动的 tool output；程序性崩溃才作为 Fatal 结束 Turn。模型看到的是文本，不是内部 success 布尔值。

      采样流失败时，只对明确可重试类别执行带 jitter 的退避，并优先采用服务端等待时间。每次重试从权威 history 重新构建请求；若工具已经执行，调用记录会按 call id 重新附回，减少模型盲目重复副作用。它不是事务或 exactly-once 保证。

      WebSocket 预算耗尽后可以单向切到 HTTPS；中断、崩溃和压缩造成的孤儿调用会在请求前补齐或移除。可靠性目标不是“永不失败”，而是失败必有去处、历史仍可重放。

      1. 分类：可重试、回给模型、终止 Turn 或等待用户。
      2. 收口：每个调用必须有真实或合成回执。
      3. 防重：记录已执行副作用，不假装具备事务。
      4. 验证：断言模型在 wire 上实际收到了什么。
      FIVE-STEP DEBUG LOOP

      定位容器 → 找最后事实 → 检查安全/环境边界 → 核对 active context 与回注 → 设计一个能推翻当前假设的最小实验。

      PROBLEM SET 01 · 架构设计题

      “流在工具执行后断开，重试为什么可能制造重复副作用？”

      展开答题骨架与解耦推演

      【先定位】 工具 Item 已执行，但模型流没有自然完成。重试粒度通常是重新发送从历史派生的请求，不是从断开的字节位置继续。

      【关键风险】 如果模型不知道调用已经执行，就可能再次触发同一命令。系统会记录已尝试调用并在重建请求时附回；这是“告诉模型事实”，不是事务回滚。

      【最小验证】 检查第一次调用是否有稳定 call id、执行记录是否完整、重试请求是否带回已执行事实，以及外部动作本身能否设计为幂等。

      【答题结论】 Agent 重试的底线不是“绝不重复”，而是“重复前拥有足够事实，并让副作用尽量幂等”。

      PROBLEM SET 02 · 故障排查题

      “用户提交了 MCP 表单，为什么工具仍然超时？”

      展开答题骨架与排查路径

      【先定位】 这是反向请求的应答关联问题，不是模型生成问题。先确认请求已发出、客户端已展示、响应已返回、等待项已命中四个事实。

      【关键证据】 请求键是否一致？等待项在响应前是否被取消或清理？连接断开后有没有明确的中止结果？

      【避免误判】 不要在没有证据时断言“多线程竞争”或随意延长超时。先找最后一个已确认事件，再修拥有断点的那一层。

      PROBLEM SET 03 · 安全攻防题

      “WorkspaceWrite 与 OnRequest 同时存在，跨工作区写入该怎么判？”

      展开答题骨架与权限决策

      【先分轴】 WorkspaceWrite 描述当前可写边界，OnRequest 描述何时允许询问。命令规则与企业约束还可能进一步收紧。

      【判断顺序】 先看规则是否禁止或要求询问，再看策略是否允许展示询问，最后由权限画像与系统沙箱执行。某些模式可在明确批准后尝试升级执行，但绝不能把“用户点了同意”直接等同于“沙箱已被关闭”。

      【答题结论】 三轴是组合关系，不是二选一。要回答谁能放行，必须先指出当前拒绝来自哪一轴。

      边界

      课程事实边界为快照 498d40b29f60。实验性能力、事件名和默认配置会继续变化；生产集成应以运行版本的能力协商与生成 schema 为准。能说出结论的失效条件，才算真正掌握。

      模块验收：任选一个失败，能在 60 秒内说清最后事实、负责模块、重试或收口策略、一个可证伪假设和最小验证动作。
