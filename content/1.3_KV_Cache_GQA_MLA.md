# 1.3 KV Cache、GQA 与 MLA：把带宽问题换成算力问题

> **一句话核心直觉**：decode 时每个请求都要把自己那整份 KV 从显存搬一遍，而且这次搬运无法在请求之间摊薄。MQA、GQA、MLA 做的是同一件事：**让更多 query 头共享同一份被搬运的数据**。MLA 走得最远：推理时它就是一个所有头共享、K 和 V 也共享的 MQA。
> **唤醒标签**：KV cache 三轴 · arithmetic intensity · MQA / GQA · MLA 低秩 latent 与矩阵吸收 · decoupled RoPE

前置：5.1 §2（屋脊线、三个不对称性）、§3 Step 5（KV 公式）。

---

## 1. 痛点与钩子：如果没有它，世界会怎样？

接着 5.1 的场景 B：8×H100、70B GQA8 模型、128K 上下文。

权重占 140 GB 后，剩约 500 GB 给 KV。单条序列用量为 `2 × 80 层 × 8 头 × 128 维 × 2 B × 131072 ≈ 43 GB`。按上一课的估算，最多约 11 条并发，每步 23 ms，其中 77% 花在搬 KV 上，算力利用率低于 1%。

```academy-lab
1.3
```

同一个模型，把注意力换成 DeepSeek-V3 式的 MLA（每层每 token 576 个数），单序列 KV 降到约 12 GB，**同样 ~23 ms 一步，并发从 11 涨到 41**。权重没变，算力没变，只改了"每个 token 往显存里存什么"。

**反直觉现象**：把 GQA8 里的 KV 头数砍到 1（MQA），KV 显存再降 8 倍，可很多模型掉点明显。MLA 的 KV 比 MQA 还大一点（576 vs 256），效果却能和 MHA 打平甚至更好。差别不在"存多少个数"，而在"存的是什么"。

## 2. 第一性原理：看透它的几何 / 物理直觉

### 2.1 KV cache 是一个三轴立方体

单条请求的 KV 总量等于三个因子的乘积。

| 因子 | 改变它的设计 |
|---|---|
| 每个 token 每层的 KV 字节数 | MQA、GQA、MLA、FP8 KV |
| 缓存的 token 条目数 | 滑窗、序列压缩（V4 的 CSA/HCA，→ 1.6） |
| 需要 KV 缓存的层数 | 混合线性层（K3 的 KDA，→ 1.6） |

2026 年的前沿模型三条轴一起压（§5）。本篇只打穿纵深轴，因为它是另外两条轴的地基：V4 压缩序列轴时，每个压缩后的条目仍是 MLA 式的共享 KV。

### 2.2 为什么攒 batch 救不了 KV

| 数据 | 批内怎么读 | 增大 batch 后的算术强度 |
|---|---|---|
| 权重 | 所有请求共用一份权重 | 每次读权重服务更多 token，算术强度上升 |
| KV | 请求 $i$ 读自己历史上的 $\mathrm{KV}_i$ | 更多请求也带来更多 KV 读取，算术强度保持不变 |

对同一请求里的注意力，让**一份 KV 被更多头读**，就能用同一份字节完成更多点积。

### 2.3 从 MHA 到 MLA：共享度一路升级

| 方案 | 一个缓存条目服务哪些头？ |
|---|---|
| MHA（8 个 query 头举例） | 每个 query 头有专用 K/V，共 8 份 |
| GQA（每组 4 头） | 第 1–4 头读一份 K/V，第 5–8 头读另一份 |
| MQA | 8 个头共用一份 K/V，共享一个 K 子空间 |
| V3 式 MLA（128 个 query 头） | 128 个头共用 512 维内容和 64 维位置，内容条目同时承担 K 和 V 的角色 |

**MLA 的画面**：每个 token 的内容缓存是一个 512 维向量 c。每个头用自己的矩阵 $W_{UK}^{(i)}, W_{UV}^{(i)}$ 读出独立的 K/V。推理时把解压矩阵**提前并进 query 和输出投影**，128 个头就可以直接用同一份 c 做注意力。[DeepSeek-V3 技术报告](https://arxiv.org/abs/2412.19437)

MQA 失败在"所有头只能看同一个 K 子空间"；MLA 成功在"所有头读同一份数据，却能各自从中投影出不同的子空间"。

### 2.4 RoPE 为什么和 MLA 打架

吸收的前提是：$q^\top W_{UK}\,c$ 中间没有别的东西，$W_{UK}$ 才能往左并进 q。RoPE 恰好在中间插了一个**随相对位置变化的旋转矩阵**，吸收就失效了。解法是**分工**：512 维 c 只管内容、不带位置；另开 64 维 $k_{\text{rope}}$ 专门携带位置，且所有头共享（MQA 式）。一个管"是什么"，一个管"在哪"。

> **和 1.2 的接口**：MLA 里位置信息只活在 64 维、也就是 32 个频率对上。这 32 只"钟"怎么分配，直接决定长上下文行为。V4 更进一步：K、V 共用同一个条目，RoPE 只加在最后 64 维，于是输出里也混进了旋转分量，V4 的做法是对注意力输出再施加位置 −i 的逆旋转，把它转回去。

### 交换乘法顺序，究竟保留了哪个量？

暂时拿掉位置支路。两条历史 latent 是 $c_1=(1,0)$、$c_2=(0,1)$，解压矩阵的两行为 $(2,0)$ 和 $(1,2)$。当前 query 是 $(1,y)$。把 latent 按行放进矩阵 $C$，解压矩阵记作 $W$，query 写作列向量 $q$。先展开 key 的算法计算 $(CW)q$；先投影 query 的算法计算 $C(Wq)$。结合律保证两者都得到 $[2,1+2y]$，下方代码正好逐项核对这两个分数。

两种实现对**每个位置的原始分数**都相同，除以相同的 $\sqrt{2}$、做 softmax、按权重求和当然也相同。直接用 query 点乘 latent 会得到 $[1,y]$；即使维度恰好相等，读到的也可能是另一段历史。实际 MLA 还会单独加上位置支路的分数。能移出历史扫描的是与位置无关的线性解压，不能把 softmax 一起移走。

拖动 query 的第二个分量，比较三个概率。先展开 key 和先投影 query 的两条曲线应始终重合；直接拿 latent 当 key 的曲线只在某些位置与它们相遇。

## 3. 承重墙推导：重新捡起核心数学

### Step 1　每 token 每层存多少（纵深轴）

以 DeepSeek-V3 的规模为例（H=128，d_h=128，MLA：d_c=512，d_r=64）：

| 方案 | 每层每 token 元素数 | 相对 MHA |
|---|---|---|
| MHA | 2 × 128 × 128 = 32768 | 1× |
| GQA-8 | 2 × 8 × 128 = 2048 | 1/16 |
| MQA | 2 × 128 = 256 | 1/128 |
| MLA | 512 + 64 = 576 | 1/57 |

**直觉**：MLA 的存储约等于只有 2–3 个 KV 头的 GQA，但表达力不受分组限制（Step 5）。

### Step 2　decode 注意力的算术强度：本篇的核心公式

对缓存中的每个 token（每层），decode 要做：打分 $2\,d_{qk}$、加权求和 $2\,d_v$ FLOPs/头；要读：这个 token 的 KV 字节。

$$
\text{AI}_{\text{attn}} = \frac{H \cdot 2(d_{qk} + d_v)}{\text{kv\_elems} \cdot s}
\;\xrightarrow{\text{GQA}, d_{qk}=d_v=d_h,\ s=2}\;
\frac{H}{H_{kv}}
$$

| 方案（BF16） | AI | 对照 H100 BF16 ridge ≈ 295 |
|---|---|---|
| MHA | 1 | 严重带宽受限 |
| GQA（128 头 / 8 组） | 16 | 仍带宽受限 |
| MLA 吸收后 | 128 × 2 × (576 + 512) / (576 × 2) ≈ **242** | 贴近屋脊 |
| MLA + FP8 KV | ≈ 484 | 越过屋脊，进入算力受限 |

**物理含义**：GQA 的 AI 就是"共享度"本身。MLA 的 AI 等于 128 个头 × 每份数据用两次（当 K 又当 V）。这就是 MLA 被设计出来的真正理由：**把 decode 注意力从带宽受限推到算力受限**，存储省 57 倍反而是附带效果。

### Step 3　低秩压缩 + 矩阵吸收

$$
c_s = W_{DKV}\,h_s \in \mathbb{R}^{d_c},\qquad
k^{(i)}_s = W^{(i)}_{UK}\,c_s,\qquad
v^{(i)}_s = W^{(i)}_{UV}\,c_s
$$

打分时用结合律把 $W_{UK}$ 挪到 query 一侧：

$$
q_t^{(i)\top} k_s^{(i)} = q_t^{(i)\top} W^{(i)}_{UK}\, c_s
= \underbrace{\big(W^{(i)\top}_{UK} q_t^{(i)}\big)^{\!\top}}_{\tilde q_t^{(i)} \in \mathbb{R}^{d_c}} c_s
$$

输出同理，把 $W_{UV}$ 挪到求和外面，进一步并入 $W_O$：

$$
o_t^{(i)} = \sum_s p^{(i)}_{ts}\, W^{(i)}_{UV} c_s = W^{(i)}_{UV} \Big(\sum_s p^{(i)}_{ts}\, c_s\Big)
$$

- **核心 Trick**：矩阵乘法的结合律让"解压 L 个 token"变成"变换 1 个 query"，成本从 O(L) 变 O(1)。
- **去掉它会怎样**：不吸收就得在每步 decode 时把整段 c 解压成 128 头的 K/V，存储省了，带宽和算力却全回来了。
- **训练 / prefill 时反过来**：那时是算力受限，直接解压成 MHA 计算更高效。**同一组权重，两种计算顺序**，按瓶颈选。

### Step 4　RoPE 冲突与 decoupled RoPE

带上 RoPE（$R_t$ 为位置 t 的旋转矩阵）：

$$
(R_t q_t)^\top (R_s W_{UK} c_s) = q_t^\top\, R_{s-t}\, W_{UK}\, c_s
$$

$R_{s-t}$ 夹在 q 与 $W_{UK}$ 之间且随 (t, s) 变化。想把 $W_{UK}$ 并进 query，就得为每个相对距离预存一个矩阵，等于没吸收。

**解法**：内容与位置分家，打分拆成两项相加：

$$
\text{score}_{ts}^{(i)} = \tilde q_t^{(i)\top} c_s \;+\; \big(R_t\, q^{R,(i)}_t\big)^{\!\top} \big(R_s\, k^{R}_s\big),
\qquad k^R_s \in \mathbb{R}^{64}\ \text{所有头共享}
$$

每 token 缓存 = $c_s$（512）+ $R_s k^R_s$（64）= 576。代价是多存 64 维，以及位置信息只占 64 维。

### Step 5　表达力：同等 KV 预算下 MLA ≥ GQA

GQA 可以看成 MLA 的特例（暂不考虑 RoPE）：让 c 直接等于"各组 K/V 拼起来"，$W_{UK}, W_{UV}$ 取对应组的选择矩阵即可。反过来不成立，GQA 的每组只能看一个固定子空间。TransMLA 一类工作据此把现成的 GQA 模型转换成 MLA，只需少量继续训练。

**一句话**：GQA 是"分组共享原件"，MLA 是"全员共享压缩件 + 各自解码"。后者在同样的缓存预算下自由度更高。

## 4. 极简代码锚点（PyTorch）

吸收式 MLA 的单步 decode。本节末尾用同一组 float64 输入对照先解压的实现，逐元素核对含位置支路的双头输出，绝对容差为 1e-12。为突出主线，省略了 query 低秩压缩和 latent 上的 RMSNorm。

```python
import torch, torch.nn.functional as F

def mla_decode_absorbed(h, cache_c, cache_kr, W, pos, rope):
    """h: (B, D) 当前 token；cache_c: (B, L, d_c) 历史 latent（不含位置）；
       cache_kr: (B, L, d_r) 历史 RoPE key（所有头共享）。"""
    B, H, d_n, d_r = h.shape[0], W["H"], W["d_n"], W["d_r"]
    # 1) 写 cache：每 token 只存 d_c + d_r = 576 个数
    c_new  = h @ W["W_dkv"]                                   # (B, d_c)
    kr_new = rope(h @ W["W_kr"], pos)                         # (B, d_r) 位置只在这 64 维
    cache_c  = torch.cat([cache_c,  c_new[:, None]], 1)       # (B, L+1, d_c)
    cache_kr = torch.cat([cache_kr, kr_new[:, None]], 1)      # (B, L+1, d_r)
    # 2) query 分两路：内容 q_c 与位置 q_r
    q_c = (h @ W["W_qc"]).view(B, H, d_n)                     # (B, H, d_n)
    q_r = rope((h @ W["W_qr"]).view(B, H, d_r), pos)          # (B, H, d_r)
    # 3) 吸收 W_UK：把 query 投进 latent 空间，而不是把 cache 解压成 K
    q_lat = torch.einsum("bhn,hnc->bhc", q_c, W["W_uk"])      # W_uk: (H, d_n, d_c) → (B, H, d_c)
    # 4) 打分：所有头共享同一份 cache（= 头维 576 的 MQA）
    s = (torch.einsum("bhc,blc->bhl", q_lat, cache_c)
         + torch.einsum("bhr,blr->bhl", q_r, cache_kr)) / (d_n + d_r) ** 0.5
    p = F.softmax(s, dim=-1)                                  # (B, H, L+1)
    # 5) 在 latent 空间加权求和（cache_c 第二次被用：当 V），再用 W_UV 解压
    o_lat = torch.einsum("bhl,blc->bhc", p, cache_c)          # (B, H, d_c)
    o = torch.einsum("bhc,hcv->bhv", o_lat, W["W_uv"])        # W_uv: (H, d_c, d_v)
    return o.reshape(B, -1) @ W["W_o"], cache_c, cache_kr     # (B, D)
```

**对照看维度**：第 4 步的两个 einsum 里，`cache_c` 和 `cache_kr` 都没有 `h`（头）维度，这就是"所有头共享"在张量上的样子。第 5 步 `cache_c` 又出现一次，这就是"一份数据用两次"。

### 数值复算 · 交换乘法顺序，究竟保留了哪个量？

在同一个 Python 会话中先运行本节上方的实现，再运行以下算例。

```python
import torch
C = torch.eye(2, dtype=torch.float64)
W = torch.tensor([[2., 0.], [1., 2.]], dtype=C.dtype)
for y in [-1., 0.5, 1.]:
    q = torch.tensor([1., y], dtype=C.dtype)
    explicit = (C @ W) @ q
    absorbed = C @ (W @ q)
    assert torch.allclose(explicit, absorbed)
    prob = lambda scores: (scores / 2**0.5).softmax(0)[1].item()
    print(f"{y:+.1f}  {prob(explicit):.3f}  {prob(C @ q):.3f}")

# 在整次 decode 上对拍，包括新缓存写入、位置项和输出投影。
torch.manual_seed(12)
def rand(*shape):
    return torch.randn(shape, dtype=torch.float64)
H, D, dc, dn, dr, dv = 2, 4, 3, 2, 2, 2
W = dict(H=H, d_n=dn, d_r=dr, W_dkv=rand(D,dc), W_kr=rand(D,dr),
         W_qc=rand(D,H*dn), W_qr=rand(D,H*dr), W_uk=rand(H,dn,dc),
         W_uv=rand(H,dc,dv), W_o=rand(H*dv,D))
def rotate(pair, pos):
    angle = pair.new_tensor(pos * 0.25)
    a, b = pair.unbind(-1)
    return torch.stack([a*angle.cos()-b*angle.sin(), a*angle.sin()+b*angle.cos()], -1)

h, cache, positions = rand(1,D), rand(1,3,dc), rand(1,3,dr)
out, latents, kr = mla_decode_absorbed(h, cache, positions, W, 3, rotate)
keys = torch.einsum("blc,hnc->bhln", latents, W["W_uk"])
values = torch.einsum("blc,hcv->bhlv", latents, W["W_uv"])
qc = (h @ W["W_qc"]).reshape(1,H,dn)
qr = rotate((h @ W["W_qr"]).reshape(1,H,dr), 3)
raw = (keys * qc[:,:,None,:]).sum(-1) + torch.einsum("bhr,blr->bhl", qr, kr)
dense = ((raw/(dn+dr)**0.5).softmax(-1)[...,None]*values).sum(2)
assert torch.allclose(out, dense.reshape(1,-1) @ W["W_o"], rtol=0, atol=1e-12)
print("含位置支路的双头输出吻合（绝对容差 1e-12）")
```

## 5. 实战直觉、避坑与面试深挖

**2026 前沿现状**
- **纵深轴：MLA 已扩散成主流选项**。DeepSeek-V4 的注意力在论文里被描述为"共享 KV 的 MQA"：每个条目同时当 K 和 V，头维 512，RoPE 只加在最后 64 维，非 RoPE 部分以 FP8 存储，KV 体积因此再降近一半。这正是 §2.3 那个"推理时 MLA = MQA"的画面成了官方表述。GLM-5 用 MLA + Muon 训练时发现 MLA 相对 GQA 有性能差距，用"按头拆分上投影矩阵、各自正交化"（Muon Split）补上：架构与优化器会互相牵制。
- **序列轴：V4 的 CSA / HCA**。CSA 每 4 个 token 池化成 1 个条目，再由 lightning indexer 选 top-k（Flash 512、Pro 1024）；HCA 每 128 个 token 压成 1 个条目，做稠密注意力；两者都另配 128 token 的未压缩滑窗。1M 上下文下，V4-Pro 的 KV 只有 V3.2 的 10%，约为 BF16 GQA8 基线的 2%。
- **层轴：Kimi K3 的 KDA + Gated MLA 混合**。线性注意力层（KDA）只维护固定大小状态，只有 MLA 层的 KV 随长度增长；SemiAnalysis 称 K3 沿用 Kimi Linear 的 3:1（KDA:MLA）比例。
- **结论**：GQA8 已从"主流方案"变成论文里的**比较基线**，V4 就拿 BF16 GQA8 当参照来报 KV 压缩比。

**与工程 / 应用的连接**
- **KV 架构决定 prefix cache 的单位成本**。同样 142k 前缀（Claude Code trace 的中位输入），70B 级 GQA8 要常驻约 47 GB，V3 式 MLA 约 10 GB。也就是说，同一张卡能"挂着"的 Agent 会话数，在模型训练时就被注意力结构定死了。
- **"1M 上下文"的真实含义要按三轴拆**：只压纵深轴（纯 MLA）时 1M 单序列仍要 ~70 GB；只有序列轴和层轴也压了，1M 才是能商用的规格。看到一个新模型宣称长上下文，先问它压的是哪条轴。
- **MLA 的 decode 是算力型负载**。它在 FP8 KV 下越过屋脊（按 BF16 计算口径），所以 MLA 模型的推理优化重点会从"省带宽"转向"榨算力"（FP8/FP4 注意力 kernel、更高效的 MQA 式 kernel），和 GQA 模型的调优思路不同。

**常见误区 / 反直觉点**
1. **"MLA 是为了省计算"** ✗：训练和 prefill 时 MLA 解压回 MHA，计算量不降反增（多了投影）。它省的是 decode 时的存储与带宽，并把 decode 注意力推向算力受限。
2. **"GQA 掉点是因为参数少了"** ✗：K/V 投影的参数量不是关键，关键是每组只能看一个子空间（秩被分组钉死）。MLA 用同样甚至更少的缓存，换回了每头独立的投影。
3. **"稀疏注意力（top-k 选择）也省 KV 显存"** ✗：纯 top-k 选择（如 V3.2 的 DSA）只减少每步**读和算**的量，全量 KV 仍要存，还多了 indexer 的 key。省存储必须压序列轴（V4 的池化）或换成固定状态的线性层。

**高频深挖题**
- **Q1：MLA 推理时为什么不能直接用标准 RoPE？decoupled RoPE 的代价是什么？**
  思路：先写 $q^\top R_{s-t} W_{UK} c$，指出旋转夹在中间、吸收失效 → 内容/位置分家，位置走 64 维共享 key → 代价：每 token 多存 64 维；位置信息只占 32 个频率对，长上下文外推行为由这 32 只钟决定（→ 1.2）。加分项：V4 让 K=V 共用条目，所以要对输出做逆旋转。
- **Q2：给你一个 GQA 的开源模型，想降推理成本，"转 MLA" 和 "KV 量化到 FP8" 怎么选？**
  思路：先用 Step 2 的 AI 公式定位瓶颈。FP8 KV 不改架构、零训练，存储和 AI 都 ×2，但共享度不变；转 MLA 要少量继续训练（GQA 是 MLA 的特例，可以近似无损地初始化，RoPE 部分需要单独处理），把共享度从 H/H_kv 提到全体头，适合长上下文、高并发场景。两者可叠加。再追问一层：如果瓶颈其实在权重（短上下文、小 batch），两者都帮不上，应该去攒 batch 或做投机解码（→ 5.1 §3 Step 4）。
