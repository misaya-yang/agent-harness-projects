# 1.4 MoE：路由与负载均衡

> **一句话核心直觉**：MoE 把"参数量"和"每个 token 的计算量"拆开：存 2.8T，算 104B。代价是三个新麻烦：**路由会自我强化，导致少数专家被挤爆；专家越稀疏，负载越难平衡；token 要在机器之间来回搬运（all-to-all）**。2026 年的前沿是把稀疏度推到极致（896 选 16），并且让它稳定。
> **唤醒标签**：top-k 路由 · 辅助损失 vs 无辅助损失 · 细粒度 + 共享专家 · 专家并行与 all-to-all · LatentMoE · 哈希路由

前置：5.1 §3 Step 4（MoE 的 decode 账）。

---

## 1. 痛点与钩子：如果没有它，世界会怎样？

稠密模型想变聪明就得变大，而每多一个参数，每个 token 就多付 6 FLOPs 的训练成本（→ 5.1）。MoE 的承诺是：参数可以多到存下更多知识，计算只花在少数被选中的专家上。Kimi K3 是这个思路的极端：**2.8T 总参数、每个 token 只激活约 104B；每层 896 个路由专家里选 16 个，外加 2 个共享专家**。

但路由器天生不公平。本篇代码的模拟：16 个专家、每个 token 选 2 个，其中 3 个专家的路由权重天生偏大一点：

```
                     负载变异系数    最忙专家 / 平均负载
不做均衡                 2.17            7.11 倍
无辅助损失的 bias 调节     0.30            1.79 倍
```

不做均衡时，最忙的专家要处理平均负载的 7 倍。训练时它拖慢整个专家并行组（大家都在等它），推理时它决定了延迟的上限。而且情况会越来越糟：被选得多的专家学得多，学得多就更容易被选中。

---

## 2. 第一性原理：看透它的几何 / 物理直觉

### 2.1 一个 MoE 层长什么样

```
token x ──┬──► 共享专家（每个 token 都过）─────────────────────┐
          │                                                   (+)──► 输出
          └──► 路由器：打分 → 选 top-k → 归一化门控权重          │
                    └──► 专家 i₁, …, i_k（只算被选中的）── 加权求和 ┘
```

- **细粒度专家**：把一个大 FFN 拆成很多小专家，每个 token 选更多个。组合数暴增，专业化更细。DeepSeek-V4-Pro 是 384 个路由专家里选 6 个加 1 个共享专家；K3 是 896 选 16 加 2 个共享。
- **共享专家**：每个 token 都要用到的通用知识放在这里，路由专家就不必各自重复学一遍。

### 2.2 为什么路由会坍塌

```
专家 A 初始稍好 → 被选得更多 → 收到更多梯度 → 变得更好 → 被选得更多 ……
```

这是一个正反馈。不加干预，最终只有少数专家在工作，其余专家几乎学不到东西。负载均衡的三代做法：

| 方法 | 做法 | 问题 |
|---|---|---|
| **辅助损失**（Switch 等） | 在主损失外加一项"负载越不均越罚" | 这项梯度和语言建模目标互相干扰，系数大了伤效果，小了压不住 |
| **无辅助损失的 bias**（DeepSeek-V3） | 每个专家一个偏置，**只参与选专家、不参与加权**；过载就调低、欠载就调高 | 每步按固定步长调，稀疏度极高时调得慢、估计噪声大 |
| **分位数均衡**（Kimi K3） | 直接从路由打分的分布里算出让每个专家恰好分到目标份额的偏置 | 需要在所有设备上估计全局分位数 |

### 2.3 LatentMoE：在更窄的空间里路由和计算

LatentMoE 先把 token 从隐藏维度 d 投影到更小的潜在维度 ℓ，在潜空间里路由和计算专家，再投影回来。路由的参数量和 all-to-all 的通信量都缩小 d/ℓ 倍。**在同等 FLOPs 和参数量下，省出来的预算可以换成更多专家和更大的 top-k。** Nemotron 3 用 4 倍压缩，Kimi K3 用 2 倍；K3 的 Stable LatentMoE 再加了三处稳定化：聚合后先过 RMSNorm 再上投影、有界的 SiTU-GLU 激活、分位数均衡。

### 2.4 通信：MoE 的另一半成本

专家分散在不同 GPU 上（专家并行，→ 5.2），每个 MoE 层都要做两次 all-to-all：把 token 发给它选中的专家（dispatch），再把结果收回来（combine）。这部分是带宽受限的，必须和计算重叠起来。

## 3. 承重墙推导：重新捡起核心数学

### Step 1　门控与输出

DeepSeek-V3 式的门控（sigmoid 亲和度 + 归一化）：

$$
s_{i} = \sigma(x^\top e_i),\qquad
\mathcal{T} = \mathrm{TopK}_i\big(s_i + b_i\big),\qquad
g_i = \frac{s_i}{\sum_{j\in\mathcal{T}} s_j}\ (i\in\mathcal{T})
$$

$$
y = \sum_{j=1}^{N_s}\mathrm{FFN}^{\text{shared}}_j(x) + \sum_{i\in\mathcal{T}} g_i\,\mathrm{FFN}_i(x)
$$

**关键细节**：偏置 $b_i$ 只出现在 TopK 里，不出现在 $g_i$ 里。它只决定"选谁"，不改变"选中后的权重"，所以不会扭曲模型的输出。

### Step 2　辅助损失

$$
\mathcal{L}_{\text{aux}} = \alpha\, E\sum_{i=1}^{E} f_i\, P_i,\qquad
f_i = \text{专家 } i \text{ 实际分到的 token 比例},\quad P_i = \text{路由给专家 } i \text{ 的平均概率}
$$

完全均衡时 $f_i = P_i = 1/E$，损失取最小值 α。$f_i$ 来自离散的 top-k，不可导，梯度只通过 $P_i$ 回传：把概率从热门专家往冷门专家推。§1 那组不均衡路由的模拟里，这一项是 5.49（均衡时为 1）。

### Step 3　无辅助损失的 bias 调节

$$
b_i \leftarrow b_i + \gamma\cdot\mathrm{sign}\big(\overline{\text{load}} - \text{load}_i\big)
$$

- 不往语言建模损失里加任何项，所以不干扰主目标的梯度。
- §1 的模拟里，300 步调节把最忙专家的负载从平均的 7.11 倍压到 1.79 倍。

### Step 4　分位数均衡的思路

对每个 token，记 $\tau_t$ 为 $z_t + b$ 里第 K+1 大的值（刚好没被选中的那个）。要让专家 e 恰好分到目标份额，可以直接从全 batch 的"路由余量"分布里取相应的分位数作为 $b_e$，一步到位，而不是一点点调。难点在于分布式：每个设备只看到局部 batch，Kimi 的做法是在各设备之间汇总路由余量的直方图计数，得到与切分方式无关的全局分位数估计。稀疏度越高，每个专家每步看到的 token 越少，固定步长调节的估计越嘈杂，这正是 K3 要换方法的原因。

### Step 5　稀疏度与 decode 批量（接 5.1）

每个专家每步分到的 token 数是 $b\cdot k/E$。要让专家的矩阵乘进入算力受限区，全局 batch 要放大 $E/k$ 倍。K3 的 $E/k = 56$。**稀疏度越高，训练越省、部署越要求大规模专家并行和大 batch。**

## 4. 极简代码锚点（PyTorch）

一个带共享专家、sigmoid 门控、无辅助损失 bias 调节的 MoE 层（按专家循环分发，便于读懂；生产实现用分组 GEMM 和 all-to-all）。已跑通。

```python
import torch, torch.nn as nn, torch.nn.functional as F

class MoE(nn.Module):
    def __init__(self, D, E=16, k=2, n_shared=1, d_ff=64, gamma=1e-3):
        super().__init__(); self.E, self.k, self.gamma = E, k, gamma
        self.router = nn.Linear(D, E, bias=False)
        ffn = lambda: nn.Sequential(nn.Linear(D, d_ff), nn.SiLU(), nn.Linear(d_ff, D))
        self.experts = nn.ModuleList([ffn() for _ in range(E)])
        self.shared = nn.ModuleList([ffn() for _ in range(n_shared)])
        self.register_buffer("bias", torch.zeros(E))            # 只用于选专家，不参与加权、不求导

    def forward(self, x):                                       # x: (N, D)，N = B·L 个 token
        s = torch.sigmoid(self.router(x))                       # (N, E) 亲和度
        idx = (s + self.bias).topk(self.k, -1).indices          # (N, k) bias 只影响"选谁"
        g = s.gather(-1, idx); g = g / g.sum(-1, keepdim=True)  # (N, k) 门控权重不含 bias
        y = sum(f(x) for f in self.shared)                      # 共享专家：每个 token 都过
        for e in range(self.E):                                 # 分发：每个专家只算选中它的 token
            tok, slot = (idx == e).nonzero(as_tuple=True)
            if len(tok): y = y.index_add(0, tok, g[tok, slot, None] * self.experts[e](x[tok]))
        if self.training:                                       # 无辅助损失的负载均衡
            load = torch.bincount(idx.flatten(), minlength=self.E).float()
            self.bias += self.gamma * torch.sign(load.mean() - load)
        return y
```

## 5. 实战直觉、避坑与面试深挖

**2026 前沿现状**
- **极致稀疏 + 稳定化**：K3 的 Stable LatentMoE 在 896 选 16（稀疏度 56）下做到全程稳定、无辅助损失的负载均衡，靠的是潜空间路由、RMSNorm、有界激活和分位数均衡这一组改动。社区的解读是：稀疏度极高时每个专家每批看到的 token 很少，负载均衡的估计会变得非常嘈杂，Stable LatentMoE 正是在修这个问题。
- **前几层用哈希路由**：DeepSeek-V4 的前 3 个 MoE 层不用学习式路由，而是一个确定性的"词表 → 专家"映射，作为负载均衡的兜底。
- **通信和计算融合**：V4 提出细粒度的专家并行方案，把每个 MoE 层拆成 dispatch、Linear-1、Linear-2、combine 四个阶段，按"波次"划分专家，一波的通信完成就开始计算；相比不融合的基线，通用推理加速 1.50–1.73 倍，RL rollout 这类延迟敏感场景最高 1.96 倍。论文给出的经验关系是：对 V4-Pro，每 1 GB/s 的互联带宽足以掩盖 6.1 TFLOP/s 计算的通信。

**与工程 / 应用的连接**
- **显存按总参数、算力按激活参数、带宽看 batch**（→ 5.1）：MoE 的"推理便宜"指的是每 token 的计算便宜，部署门槛（装下全部专家的显存）一点没降。
- **延迟抖动**：小 batch 时，某个专家恰好被很多请求同时选中，就会成为这一步的瓶颈。高并发服务里，专家负载不均会直接表现为尾延迟。
- **RL 里的 MoE 更难**：路由的离散跳变是训推失配的放大器（→ 2.7 的路由回放）。

**常见误区 / 反直觉点**
1. **"MoE 推理便宜，所以部署也便宜"** ✗：显存要装下全部专家，带宽在大 batch 下也趋近总参数。便宜的只是 FLOPs。
2. **"专家会自然分工成数学专家、代码专家"** ✗：对开源 MoE 的分析一般发现，专家更多是按 token、语法这类表层模式分工，而不是按人类理解的领域分工。
3. **"负载越均衡越好，辅助损失系数越大越好"** ✗：辅助损失的梯度会和主目标打架，系数过大会伤效果。这正是无辅助损失方法出现的原因。

**高频深挖题**
- **Q1：辅助损失和无辅助损失的负载均衡各是怎么工作的？后者为什么更好？**
  思路：写出 $E\sum f_iP_i$，指出 $f_i$ 不可导、梯度只经 $P_i$ 回传，并且会干扰语言建模目标 → bias 只参与 top-k 选择、不参与门控加权，按负载符号调节，不进损失 → 再往前一步：稀疏度极高时固定步长调节噪声大，K3 改用分位数直接算 bias，并在设备间汇总直方图得到全局分位数。
- **Q2：为什么要用细粒度专家 + 共享专家？LatentMoE 又在此基础上省了什么？**
  思路：细粒度 → 组合数多、专业化细；共享专家 → 通用知识不必在每个路由专家里重复 → LatentMoE 在潜空间里路由和计算，路由参数和 all-to-all 通信都按 d/ℓ 缩小，同等预算可以换更多专家和更大 top-k → 收尾：稀疏度越高，部署越依赖大规模专家并行和大 batch（$E/k$ 倍）。
