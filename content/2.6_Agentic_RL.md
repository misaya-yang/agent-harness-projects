# 2.6 Agentic RL：从答题到办事

> **一句话核心直觉**：Agentic RL 把单轮 bandit（一个 prompt → 一段回答 → 一个分）变成了多轮 POMDP（模型的输出会改变世界，世界的回应又成为下一步的输入）。算法骨架还是 2.3 / 2.5 那一套，真正变难的是三件事：**哪些 token 算模型的动作；300 步之后的一个结果怎么分给每一步；rollout 里的每个工程细节都在悄悄改变训练分布**。
> **唤醒标签**：POMDP 与观测 mask · 回合级信用分配 · 环境合成与沙箱 · 上下文管理进入训练 · Token-In-Token-Out（TITO）

前置：2.3（策略梯度、KL 正则目标）、2.5（GRPO 家族、rollout 一致性）。

---

## 1. 痛点与钩子：如果没有它，世界会怎样？

把 2.5 的 GRPO 流水线原样接上工具调用，通常会经历这样一个过程：

```
单轮：曲线干净，reward 稳步上涨
接上工具、变成多轮：reward 抖动、KL 莫名漂移、训着训着工具调用格式坏掉
```

HF 一篇 2026 年 5 月的文章给出了最常见的元凶：rollout 循环悄悄违反了 TITO 不变式。你解析模型输出、检测工具调用、再把更新后的对话**重新分词**交给下一轮，结果训练端看到的 token 已经不是模型当初采样的那些了（§2.5）。

即使管道全对，还有三个单轮时不存在的问题：
1. **信用分配**：一条 300 步的轨迹最后失败了，第 40 步那条错误命令和其余 260 步正确操作，在 GRPO 里共享同一个负优势。
2. **rollout 成本由环境决定**：起容器、跑测试、等网页，比生成 token 慢得多。DeepSeek-V4 的 preview 版技术报告里，沙箱集群要同时管理数十万个沙箱实例。
3. **上下文装不下**：真实 Agent 轨迹远超上下文窗口，部署时的 harness 会做压缩。训练时不做，分布就对不上；训练时做了，策略梯度怎么算又成了问题（§2.4）。

## 2. 第一性原理：看透它的几何 / 物理直觉

### 2.1 从 bandit 到 POMDP：轨迹里有三种 token

```
单轮（2.5）：  prompt ──► [模型生成 o] ──► verifier ──► r

多轮（2.6）：  task ──► a₁ ──► 环境 ──► o₁ ──► a₂ ──► 环境 ──► o₂ ──► … ──► a_T ──► r
               真实状态（文件系统、网页、数据库）在环境里，模型只看得到被 harness 渲染 / 压缩后的历史 h_t

轨迹里的 token：
  动作 token   a_t   模型自己采样的      → 计 loss，记录 rollout 端 logp
  观测 token   o_t   工具 / 环境返回的   → 只当条件，mask 掉
  harness token      系统提示、模板、harness 插入的摘要 → 只当条件，mask 掉
```

只对模型自己采样的 token 求梯度，不是工程习惯，而是数学推出来的（§3 Step 1）。

### 2.2 信用分配：一条光谱

```
轨迹级   所有动作 token 共享一个优势（GRPO 原样）       简单、无偏、方差大
回合级   每个回合一个优势（回合奖励 / 中间状态 baseline） 折中
token 级  critic 或过程奖励模型给每步估值                精细、有偏、贵
```

三种主流做法：
- **设计回合奖励**：可验证的（工具是否执行成功、搜索是否命中）或 LLM 判定的，再与结果奖励合并。
- **与参考轨迹匹配**：MatchTIR（ACL 2026）把信用分配建模成预测轨迹与标准轨迹之间的二分图匹配，得到稠密的回合奖励，再用"回合级 + 轨迹级"的双层优势平衡局部精度与全局成败。
- **树状 rollout**：在中间回合分叉。AT2PO 用熵引导决定在哪里展开，再做逐回合的信用回传。

**树状 rollout 的画面最值得记住**：GRPO 比较的是"同一个 prompt 出发的不同回答"；树状方法比较的是"**同一个中间状态**出发的不同后续"。兄弟分支天然构成了这一步的 baseline，不需要 critic 就得到了回合级优势（§3 Step 2）。

### 2.3 环境就是新的数据集

预训练时，数据的覆盖面决定泛化；Agentic RL 里，这个角色由环境承担，而且环境的 bug 会直接变成 reward hacking 的入口。

| | 规模与设计 |
|---|---|
| DeepSeek-V3.2 | 大规模合成 Agent 任务：超过 1,800 个环境、85,000 条复杂 prompt |
| DeepSeek-V4（preview 报告） | DSec 沙箱：Function Call / Container / microVM / fullVM 四种执行底座，统一 Python SDK，单集群管理数十万并发沙箱；轨迹日志让被抢占的任务恢复时回放缓存结果，避免重复执行**非幂等操作**；Agent 评测允许最多 500 步、512K 上下文 |
| Kimi K3 | 百万 token 级的 Agentic RL，rollout 与沙箱状态可持久化 |

"非幂等操作"这一条很有代表性：rollout 被打断后重放，如果重新执行了"发邮件""删文件""扣款"，环境状态就和原轨迹对不上了。**分布式系统的容错语义直接决定了训练数据的正确性。**

### 2.4 上下文管理进入训练

```
部署时：  harness 在 300K 处压缩历史 → 模型看到的是"摘要 + 最近几轮"
训练时不压缩：模型只在完整历史上学过 → 部署时的条件分布没见过
训练时压缩：  同一条轨迹被切成几段，每段的"可见历史"不同 → 策略梯度要按段算
```

2026 年的几条路线：
- **SUPO**（字节 Seed，ACL 2026）：周期性地用 LLM 生成的摘要压缩工具调用历史，端到端地同时优化工具使用行为和摘要策略；测试时把摘要轮数开得比训练时更多，复杂搜索任务的表现还能继续提升。
- **CompactionRL**：把压缩作为 rollout 采样的一部分。历史接近上限时，Agent 自己写摘要，然后从重建的上下文继续；训练时用后续段被优化的 token 数修正本段的 GAE 优势，把奖励跨段传回去。
- **CM-GSPO**（Glasseek）：每次压缩事件把 rollout 切成子轨迹，并**记录每段的条件上下文**，在此基础上做序列级优化。

两个关键点：摘要如果由模型生成，它就是一个**动作**，好坏要由后续段的成败来评价；每一段的 logp 必须在**当时真实可见的上下文**上计算。后者就是 TITO 在上下文管理场景下的推广。

### 2.5 rollout 一致性：多轮场景特有的四个坑

权重完全相同，rollout 端和训练端算出的 logp 仍可能不同：

| 坑 | 机制 |
|---|---|
| **重新分词** | 解码是多对一的：模型可能采样出合法但"不规范"的 token 序列，转成文本再分词就变成另一串 id（§4 有最小例子）；聊天模板在渲染工具调用时也可能有损 |
| **思考内容是否回传** | Kimi K3 要求多轮对话和工具调用时，客户端必须回传完整的 assistant 消息，包括 reasoning_content 和 tool_calls。训练时保留、部署时丢掉（或反过来），条件分布就变了 |
| **序列化方式** | 把多轮历史按原生 role 消息格式化，比把整段历史塞进一个 user 回合，工具调用准确率稳定高约 6–8% |
| **中断与恢复** | 被抢占的 rollout 从头重来会引入长度偏置（→ 2.5）；工具调用重放会破坏环境状态（§2.3） |

## 3. 承重墙推导：重新捡起核心数学

### Step 1　为什么观测 token 必须 mask：环境项在梯度里消失

轨迹 $\tau = (a_1, o_1, \dots, a_T)$ 的概率分解为策略项和环境项：

$$
p_\theta(\tau) = \prod_{t} \underbrace{\pi_\theta(a_t \mid h_t)}_{\text{策略}}\ \cdot\ \underbrace{P_{\text{env}}(o_t \mid h_t, a_t)}_{\text{环境，不含 }\theta}
\quad\Rightarrow\quad
\nabla_\theta \log p_\theta(\tau) = \sum_t \nabla_\theta \log \pi_\theta(a_t \mid h_t)
$$

- **物理含义**：环境转移不依赖 θ，取对数后求导直接为零。所以策略梯度**本来就不包含**观测 token，mask 只是把数学结果如实实现出来。环境也因此可以是不可微的、未知的黑盒。
- **不 mask 会怎样**：对工具返回的 token 做"梯度上升"，等于训练模型去预测和模仿工具输出。推理时模型会更倾向于自己"编"工具结果，而不是真的去调用。

### Step 2　回合级优势：把 GRPO 的组内比较推广到中间状态

从第 k 回合之前的同一状态 $h_k$ 分叉出 m 个后续，回报分别为 $R_1,\dots,R_m$：

$$
\hat A_k^{(j)} = R_j - \frac1m\sum_{i=1}^m R_i \;\approx\; Q(h_k, a_k^{(j)}) - V(h_k)
$$

- k=0 时就是 GRPO。树越深，baseline 越"局部"，越能区分"这一步好"还是"后面运气好"。
- 实践中常与轨迹级优势加权组合：$A_t = A_{\text{traj}} + \lambda\, A_{\text{turn}(t)}$。
- **代价**：分叉需要从中间状态恢复环境，这要求沙箱支持快照或确定性重放，又回到了 §2.3 的环境工程。

### Step 3　长度加权：长轨迹该占多大话语权

多轮轨迹的长度差异远大于单轮回答：3 回合和 300 回合的轨迹可能差两个数量级。
- **token 级平均**：长轨迹在梯度里占绝对主导。
- **按轨迹先平均**（GRPO 原样）：长轨迹里每个 token 的权重被稀释到极小（→ 2.5 §3 Step 3 的长度偏置，在这里被放大）。

两者都不是"正确答案"，而是一个加权决策：你希望模型优先从长任务里学，还是让每个任务平等发声？面试时能说出这是一个**选择**，比背出某个默认值更重要。

### Step 4　带压缩的轨迹：按段计算似然

压缩把轨迹切成 S 段，第 s 段的可见上下文是 $c_s$（之前的摘要 + 本段历史）：

$$
\log p_\theta(\tau) = \sum_{s=1}^{S} \sum_{t \in \text{seg}_s} \log \pi_\theta\big(a_t \mid c_s,\ \text{本段内 } t \text{ 之前的动作与观测}\big)
$$

- $c_s$ 必须**原样记录**下来，训练时在它上面重算 logp，不能用"完整历史"代替。
- 第 s 段末尾的摘要动作，其优势应来自最终奖励（加上后续段的贡献），这就是 CompactionRL 做跨段优势修正的原因。

### Step 5　一致性问题的统一视角

训练端用的重要性比率实际上是：

$$
\rho_t = \frac{\pi_\theta\big(a_t \mid h_t^{\text{train}}\big)}{\pi_{\text{rollout}}\big(a_t \mid h_t^{\text{rollout}}\big)}
$$

只要 $h_t^{\text{train}} \neq h_t^{\text{rollout}}$（重新分词、丢了思考内容、模板不同、压缩后上下文没记录），即使权重一模一样，ρ 也会偏离 1。LMSYS 的 Miles 文档把这种现象描述为：服务端和训练端给名义上同一条轨迹分配了不同的概率，重要性比率因此漂离 1，不加修正就会损害本该被改进的策略。**TITO、记录条件上下文、回传思考内容，本质上都是在保证 $h^{\text{train}} = h^{\text{rollout}}$。**

## 4. 极简代码锚点（PyTorch）

一个保持 TITO 的多轮轨迹缓冲区，加上"轨迹级 + 树状回合级"优势。最后几行是重新分词改变 token id 的最小例子。已跑通。

```python
import torch

class Trajectory:
    """TITO：全程保存 token id，绝不经过"文本 → 重新分词"的往返。"""
    def __init__(self, prompt_ids):
        n = len(prompt_ids)
        self.ids, self.mask, self.logp = list(prompt_ids), [0] * n, [0.0] * n
        self.turn_of, self.n_turns = [-1] * n, 0          # 每个 token 属于第几回合（-1 = 非动作）

    def add_action(self, ids, logps):                     # 模型采样的 token：计 loss，记下 rollout 端 logp
        self.ids += ids; self.mask += [1] * len(ids); self.logp += logps
        self.turn_of += [self.n_turns] * len(ids); self.n_turns += 1

    def add_observation(self, ids):                       # 工具返回 / harness 插入：只当条件，不计 loss
        self.ids += ids; self.mask += [0] * len(ids); self.logp += [0.0] * len(ids)
        self.turn_of += [-1] * len(ids)

def token_advantages(traj, traj_adv, branch_returns=None, lam=0.5):
    """traj_adv：轨迹级优势（同任务多条轨迹做组内比较得到）。
       branch_returns[k]：从第 k 回合之前的同一状态分叉出的兄弟回报，第 0 个是本轨迹自己的。"""
    turn_adv = torch.zeros(traj.n_turns)
    for k, rets in (branch_returns or {}).items():
        rets = torch.tensor(rets, dtype=torch.float)
        turn_adv[k] = rets[0] - rets.mean()               # 同一中间状态下的组内比较 ≈ Q − V
    adv = torch.tensor([traj_adv + lam * turn_adv[k] if k >= 0 else 0.0 for k in traj.turn_of])
    return adv * torch.tensor(traj.mask, dtype=torch.float)   # (L_total,) 观测与 prompt 位置为 0

# TITO 为什么必要：解码是多对一的
vocab = {"a": 0, "b": 1, "ab": 2}; inv = {v: k for k, v in vocab.items()}
def encode(s):                                            # 贪心最长匹配 = "规范"分词
    out, i = [], 0
    while i < len(s):
        tok = "ab" if s[i:i+2] == "ab" else s[i]
        out.append(vocab[tok]); i += len(tok)
    return out
sampled = [0, 1]                                          # 模型采样出 "a" + "b"：合法但非规范
encode("".join(inv[i] for i in sampled))                  # → [2]：训练端将在另一串 token 上算 logp
```

## 5. 实战直觉、避坑与面试深挖

**2026 前沿现状**
- **环境规模成为核心竞争力**：从 V3.2 的 1,800+ 环境、85,000 条 prompt，到 V4 preview 报告里数十万并发沙箱、四种执行底座、为非幂等操作设计的轨迹回放；K3 做到了百万 token 级、rollout 与沙箱状态可持久化的 Agentic RL。前沿实验室在 Agent 上的差距，越来越多地体现在**环境工程**上，而不是目标函数上。
- **上下文管理从推理技巧变成被训练的行为**：SUPO、CompactionRL、CM-GSPO 都把压缩放进 rollout，再在训练中正确地处理分段。K3 在 BrowseComp 上同时报告了两种模式：300K 处触发压缩的主结果，以及不做任何上下文管理、直接用满 1M 窗口时的 90.4 分。
- **TITO 成为基础设施的标配**：HF、LMSYS（Miles）、Agent Lightning、NVIDIA NeMo Gym 在 2026 年都发布了专门的 TITO 设计或修正方案。Laguna 的技术报告更进一步：加了一个 `render_assistant_messages_raw` 开关，让生产环境的聊天模板把 rollout 的原始 token 原样插入 assistant 消息块，保证生产模板与 RL 时的行为完全一致。
- **harness 是训练分布的一部分**：K3 的多项编码基准（如 DeepSWE、ProgramBench）都在自家的 Kimi Code harness 下评测，多轮调用时还要求回传完整的思考内容。用 A harness 训出来的模型换到 B harness 上表现下降，并不奇怪。

**与工程 / 应用的连接**

你在 harness 上做的每个决定，在 Agentic RL 里都有对应的概念：

| harness 里的决定 | 在 Agentic RL 里它是 |
|---|---|
| 工具定义、参数 schema、返回格式 | 动作空间与观测空间 |
| compaction / 摘要策略 | 状态表示；如果摘要由模型写，它还是一个动作 |
| 是否回传 thinking、怎么序列化历史 | 条件分布的一部分，决定训推是否一致 |
| 权限、沙箱、可回滚 | 环境设计，同时也是 reward hacking 的边界 |
| 验收标准、单元测试 | 奖励函数 |
| trace 排查 | rollout 诊断：逐 token 对齐 logp、监控 ρ 的分布 |

**常见误区 / 反直觉点**
1. **"工具返回不计 loss 只是工程习惯"** ✗：环境转移不含 θ，梯度里本来就没有这一项（§3 Step 1）。错误地计入 loss，会教模型自己编造工具输出。
2. **"多轮就是把整段对话当成一个长回答做 GRPO"** ✗：作为基线可以跑，但丢掉了回合级信用分配，而且很容易在重新分词、模板序列化、上下文压缩上引入训推不一致。光是序列化方式就能造成约 6–8% 的工具调用准确率差异。
3. **"Agent 的 reward hacking 和 RLHF 的一样"** ✗：Agent 能**作用于环境**。修改测试、从版本历史或日志里翻出答案、利用沙箱漏洞，都是单轮 RLHF 里不存在的攻击面。环境设计本身就是安全边界。

**高频深挖题**
- **Q1：多轮工具调用的 RL 里，工具返回的 token 为什么不计 loss？如果计了会怎样？**
  思路：写出轨迹概率分解 → 环境项不含 θ、对数求导为零 → 所以 mask 是正确梯度的实现 → 计入会把"预测工具输出"当成策略目标，推理时模型倾向于编造工具结果；同时这些 token 不是从 π 采样的，它们的"重要性比率"没有意义。
- **Q2：你的 Agent 部署时会做上下文压缩，RL 训练时要不要也做？怎么做才不破坏策略梯度的正确性？**
  思路：要做，原因有二：对齐部署时的条件分布、控制 rollout 成本 → 做法：压缩事件把轨迹切段，原样记录每段的可见上下文，在它上面重算 logp（TITO 的推广）→ 摘要若由模型生成就是动作，需要跨段把最终奖励传回去 → 评估时可以开比训练时更多的压缩轮数，检验泛化。收尾：这类问题的本质都是保证 $h^{\text{train}} = h^{\text{rollout}}$。
