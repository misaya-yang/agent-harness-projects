# 2.7 RL 系统与训练稳定性：看不见的 off-policy

> **一句话核心直觉**：现代 RL 系统为了快，用两套引擎：推理引擎（vLLM / SGLang）负责 rollout，训练框架（Megatron / FSDP）负责算梯度。**权重完全相同，算出的概率却不同**，on-policy 就悄悄变成了 off-policy。本篇讲这层看不见的 off-policy 从哪来（数值精度、MoE 路由、异步滞后、多轮渲染），怎么量化（逐 token 对齐 logp），怎么修（换精度、路由回放、重要性修正、按陈旧度收紧信任域）。
> **唤醒标签**：训推不一致 · TIS / MIS · BF16 vs FP16 · 路由回放（R2 / R3）· 异步与陈旧度 · 熵坍塌

前置：2.3（重要性采样与 clip）、2.5（rollout 一致性）、2.6（TITO）、1.5（浮点累加顺序）。

## 1. 痛点与钩子：如果没有它，世界会怎样？

一个典型的事故现场：算法没改、超参没动，换了一版推理引擎或者开了 FP8 rollout，RL 训练几百步后突然崩掉，reward 断崖下跌。

[NeurIPS 2025 OPT workshop 上的 TIS 研究](https://neurips.cc/virtual/2025/124259)分析了混合引擎引入的训推失配。**即使权重和结构相同，两个后端也可能算出显著不同的 token 概率**，原本按 on-policy 设定更新的过程就变成了 off-policy。

**失配为什么在长序列上特别致命**。本篇代码做了一个模拟：同一组 logits，一路用 FP32 算 log 概率，另一路先把 logits 过一遍低精度再算（模拟另一套引擎的数值误差），按 FP32 分布采样，统计整条序列的 |对数概率比|：

| 舍入精度 | 64 token | 512 token | 4,096 token |
|---|---:|---:|---:|
| BF16 | 0.042 | 0.23 | 0.67 |
| FP16 | 0.008 | 0.033 | 0.089 |

表中单位为 nat。对于绝对对数比为 0.67 的序列，两端赋给它的概率相差约 $e^{0.67}\approx 2$ 倍。单个 token 的差别很小，长思维链和多轮 Agent 轨迹仍可能累积出明显的序列级偏差（见 §3 Step 2）。

## 2. 第一性原理：看透它的几何 / 物理直觉

### 2.1 系统长什么样

| 组件 | 做什么 | 向另一侧发送什么 |
|---|---|---|
| 推理引擎（vLLM / SGLang） | 用连续批处理、自定义 kernel 和可选的 FP8/FP4 权重生成轨迹 | token ID 与采样时的 log 概率 |
| 训练框架（Megatron / FSDP） | 重算轨迹 log 概率，用两端的概率计算比率并更新策略 | 每隔若干步同步策略权重 |

### 2.2 两种 off-policy，一个比率

| | 来源 | PPO 的 clip 能看见吗 |
|---|---|---|
| **失配**（mismatch） | 同一份权重，两套引擎的数值、路由、采样截断、模板渲染不同 | **看不见** |
| **陈旧度**（staleness） | rollout 用的是 k 步之前的权重：一批数据切多个 mini-batch 更新，或者异步流水线 | 部分看见（只看到训练端自己重算的旧策略） |

2.3 的代理目标在两者都很小时才成立。一项用 30B MoE 模型、投入数十万 GPU 小时的系统研究从一阶近似的角度证明：只有训推差异和策略陈旧度都被压到很小时，代理目标才有效。这为重要性修正、clip、路由回放这些常用技巧提供了统一的解释。

### 2.3 失配从哪来

| 来源 | 造成失配的机制 |
|---|---|
| 数值精度 | BF16 有 8 位有效二进制位，舍入误差较大。两个 kernel 也可能使用不同的累加顺序。 |
| 批不变性 | 同一个请求随 batch 大小改变 kernel 分块，浮点结果可能随之改变（→ 1.5）。 |
| 量化 rollout | 推理用 FP8 或 FP4，训练用 BF16。 |
| MoE 路由 | top-k 是离散选择，微小的 logit 差异也能改变专家集合。 |
| 采样截断 | 推理用 top-p 或 top-k 截断词表，训练端仍在全词表上计算概率。 |
| 多轮渲染 | 重新分词、聊天模板差异和思考内容的保留方式都会改变条件历史（→ 2.6）。 |

### 2.4 修法的三层

1. 先对齐前向计算和输入。[FP16 训推失配研究](https://arxiv.org/abs/2510.26788)比较了计算精度对 rollout 和训练端概率差异的影响。对于其他来源，可分别检查批不变 kernel、路由回放、采样掩码、TITO 或 rollout 的部署精度。
2. 再用实际的 $\pi_{\text{rollout}}$ 修正失配。TIS 截断 token 级权重，MIS 或 KL 阈值可以筛掉不匹配的序列。
3. 用 clip、按陈旧度调整信任域，或在梯度噪声增大时降低学习率，限制策略继续偏离。

### 2.5 熵：最早报警的指标

策略熵是 RL 训练里最早出现异常的曲线之一：熵骤降意味着分布在迅速变尖（探索消失、回答同质化，→ 2.5 的 clip-higher），熵暴涨往往意味着策略被失配或过大的步长推出了稳定区域。有研究从 softmax 策略梯度出发分析熵的变化，指出它大致由"动作 log 概率与优势的协方差"驱动：高概率且高优势的 token 被不断强化，熵就持续下降，据此提出了只对高协方差 token 做 clip 或加 KL 的控制方法。实践上，把熵和 §4 的失配指标放在同一张图上看：熵异常如果和序列级失配同时出现，先查系统，再调算法。

### 同样八个 token，实际由几个样本说了算？

给每项权重 $w_i$，归一化后的份额是 $u_i=w_i/\sum_j w_j$。两次独立按份额抽取，落在同一项的概率为 $\sum_i u_i^2$；把它取倒数就是常用的有效样本量诊断。八项等重时得到 8，一项独占时趋近 1。它反映权重集中度，不能单独判定梯度有多准确。

令七项权重都为 1，最后一项为 8。仅这一项就占据全部权重的 8/15，ESS 比例降至 $225/(8\times71)$。截断到 2 后，重算得到 $81/(8\times11)$。第二个结果显著上升，同时原本应当贡献 8 的动作只贡献了 2。比较截断策略时，要一起看任务得分与被截掉的权重质量。

```academy-lab

```

**互动观察指南**：在上方实验中，读者可调节第 8 个 token 的离群权重（如从 1、2 到 8、16），并切换是否启用截断（如截断阈值 $C=2.0$）：
- 观察**未截断时的 ESS（有效样本量）比例**：当离群权重达到 8 时，仅该单个 token 就霸占了全部权重的 8/15，导致 ESS 比例从 1.0 骤降到 0.396（权重剧烈集中在少数离群点上，造成梯度的极大方差）；
- 观察**开启 TIS 截断后**：离群权重被强制限制在 2.0，ESS 比例立刻回升至 0.920，有效平抑了梯度方差。
体会 TIS 如何通过截断过大权重来换取训练梯度的稳定性，以及截掉过大权重所带来的一定偏差。

**迁移练习。** 所有权重都等于 10 时 ESS 仍为 8。因此一次小批量的 ESS 比例接近 1，并不能证明两套引擎输出同一概率分布。

## 3. 承重墙推导：重新捡起核心数学

### Step 1　真正的比率有两个因子

在理想的 on-policy 强化学习中，策略梯度要求使用当前更新策略与实际收集样本策略的概率比率：$\frac{\pi_\theta(y_t)}{\pi_{\text{rollout}}(y_t)}$。
然而在现代工业级分布式 RL 系统中，由于推理引擎（vLLM 等）负责采样生成，而训练框架（Megatron / FSDP 等）负责反向传播，训练框架实际使用的是自己在训练端用当前保存的旧权重重算出的旧概率 $\pi_{\text{old}}^{\text{train}}(y_t)$。
于是，真实的重要性比率被自然分解为两项乘积：

$$
\frac{\pi_\theta(y_t)}{\pi_{\text{rollout}}(y_t)}
= \underbrace{\frac{\pi_\theta(y_t)}{\pi_{\text{old}}^{\text{train}}(y_t)}}_{\text{策略更新：PPO 会 clip}}
\times
\underbrace{\frac{\pi_{\text{old}}^{\text{train}}(y_t)}{\pi_{\text{rollout}}(y_t)}}_{\text{训推失配：PPO 完全看不见}}
$$

- 标准 PPO 损失中只包含了第一个因子，相当于默认第二项工程失配因子恒等于 1。
- 一旦两端存在数值精度、MoE 路由选择或 kernel 累加顺序差异，第二个因子就会系统性偏离 1，使得策略更新的方向发生静默失真。
- **修正做法**：TIS 在计算每个 token 的策略损失时，显式乘上截断梯度的第二项因子作为常数修正权重，并将其截断在常数 $C$ 以内，用可控的轻微偏差换取有界的方差。

### Step 2　为什么失配会随长度系统性漂移

采样来自 $\pi_{\text{rollout}}$ 时，逐 token 对数比率的期望是：

$$
\mathbb{E}_{y_t\sim\pi_{\text{rollout}}}\Big[\log\frac{\pi_{\text{rollout}}(y_t)}{\pi_{\text{train}}(y_t)}\Big] = \mathrm{KL}\big(\pi_{\text{rollout}}\,\|\,\pi_{\text{train}}\big) \;\ge\; 0
$$

单次采样的对数比率有正有负，给定前缀的期望为非负的 KL。每步失配相近时，期望漂移随长度 $L$ 累积。若各步独立且方差相同，总和的标准差按 $\sqrt L$ 增长。下面用二词表固定分布单独检验这两项。

```academy-lab
2.7
```

**互动观察指南**：在上方实验中，读者可调节序列长度 $L$（如 64、512 到 4096）与数值精度（BF16 对比 FP16）：
- 观察由二词表与正态权重模拟出的累积绝对对数比率：尽管单步 token 的平均失配微小，但由于其期望严格非负（等于两端概率分布的 KL 散度 $\ge 0$），该失配随着序列长度 $L$ 呈现不可避免的系统性累积放大；
- 在长序列（4096 token）下，BF16 的累积绝对对数比率高达 0.67 nat（对应两端概率比相差约 2 倍），而换用 FP16 则能将漂移压制在 0.089 nat。这清楚说明了为什么长思维链推理模型与多轮 Agent 场景对训推失配格外敏感。

§1 的 BF16 模拟中，序列长度增加 64 倍时，绝对对数比率增加约 16 倍。另一组合成数据里，token 级 KL 为 0.0002，有效样本比例为 0.9996。256 token 的典型序列中，平均每 token 差约 0.003 nat，合计绝对对数比约 0.74 nat，序列级掩码筛掉约一半的序列。排查时可以按长度分桶看序列统计量。

### Step 3　TIS 与 MIS

$$
\text{TIS:}\quad w_t = \min\!\Big(\frac{\pi_{\text{old}}^{\text{train}}(y_t)}{\pi_{\text{rollout}}(y_t)},\ C\Big)
\qquad\qquad
\text{MIS:}\quad w_i = \mathbb{1}\Big[\ \ell < \prod_t \frac{\pi_{\text{old}}^{\text{train}}(y_{i,t})}{\pi_{\text{rollout}}(y_{i,t})} < h\ \Big]
$$

- TIS 在 token 级修正，计算便宜，但奖励是序列级的，token 级加权并不完全对应。
- MIS 在序列级判断，与序列级奖励一致，代价是丢样本。DeepSeek-V3.2 的 off-policy 序列掩码是同一思路的变体：只丢弃负优势且 KL 超阈值的序列（→ 2.5）。

### Step 4　MoE 路由回放

离散的 top-k 路由是 MoE 特有的失配放大器：同一个 token 在推理引擎和训练框架里可能被送到不同的专家，概率差异会远大于数值误差。R3 的做法是**专家集合沿用 rollout 时的选择，门控权重仍用训练端的 router logits 计算**：

$$
g_e = \frac{\mathbb{1}_{\text{infer},e}\ \exp(z_{\text{train},e})}{\sum_{e'} \mathbb{1}_{\text{infer},e'}\ \exp(z_{\text{train},e'})}
$$

- 这样离散的专家集合与 rollout 对齐，梯度仍能流过当前的 router。它不能复现整个前向（隐状态、专家权重本身仍可能有差异），但消除了最大的一个失配源。
- **两种回放要分清**：R2（vanilla routing replay）在梯度更新时回放旧策略的路由，针对的是**陈旧度**；R3 回放推理引擎的路由，针对的是**失配**。
- **代价**：router 只能在回放的专家集合里调整权重。而且路由一旦被冻结在旧轨迹上，router 本身在 off-policy 更新中的演化就被忽略了。2026 年的 PR2 给每个 router 加了一个轻量的演化预测器，让 rollout 时的路由提前预测短期内 router 会怎么变。

### Step 5　陈旧度与信任域

异步流水线里，rollout 和训练是错开的，数据天然滞后若干步。直觉上，越陈旧的数据越不可信，信任域应该越窄。2026 年的"Stale but Stable"按陈旧度自适应地收紧信任域；上面那项 30B MoE 研究的实证结论更具体：**纯 on-policy 训练时，带重要性修正的基础策略梯度最稳定；一旦引入 off-policy 更新来加速收敛，clip 加路由回放就成了必需品**。

## 4. 极简代码锚点（PyTorch）

三件工具：失配诊断报告、两种重要性权重、R3 式路由回放。已跑通，Step 2 里"token 级看着没问题、序列级已经漂了"的数字就来自 `mismatch_report`。

```python
import torch

def mismatch_report(logp_train, logp_roll, mask):
    """logp_*: (B, T) 同一批 rollout token 在两套引擎下的 log 概率"""
    d = (logp_train - logp_roll) * mask                      # 逐 token log(π_train / π_roll)
    kl = ((torch.exp(d) - 1 - d) * mask).sum() / mask.sum()  # k3 估计 KL(π_roll ‖ π_train)
    seq = d.sum(1)                                           # 序列级对数比率：会随长度漂移
    w = torch.exp(d)[mask.bool()]
    ess = (w.sum() ** 2 / (w ** 2).sum() / len(w)).item()    # token 级有效样本比例
    return dict(kl=kl.item(), max_tok=d.abs().max().item(), seq_abs=seq.abs().mean().item(), ess=ess)

def is_weights(logp_train_old, logp_roll, mask, mode="tis", C=2.0, lo=0.5, hi=2.0):
    log_r = (logp_train_old - logp_roll).detach() * mask     # 失配因子，不求导
    if mode == "tis":                                        # token 级截断
        return torch.exp(log_r).clamp(max=C) * mask
    seq = torch.exp(log_r.sum(1))                            # 序列级：越界整条丢弃
    return ((seq > lo) & (seq < hi)).float()[:, None] * mask

def replay_routing(router_logits_train, rollout_topk):
    """R3：专家集合用 rollout 的选择，权重用训练端 logits。(N, E), (N, k) → (N, E)"""
    keep = torch.zeros_like(router_logits_train).scatter_(-1, rollout_topk, 1.0)
    return torch.softmax(router_logits_train.masked_fill(keep == 0, float("-inf")), -1)

# 用法：policy_loss(...) 里把每个 token 的损失乘上 is_weights(...)；
# 监控时把 mismatch_report 的 seq_abs 按回答长度分桶画出来，比看平均值有用得多。
```

### 数值复算 · 同样八个 token，实际由几个样本说了算？

在同一个 Python 会话中先运行本节上方的实现，再运行以下算例。

```python
import torch
for heavy in [1., 2., 8., 16.]:
    w = torch.tensor([[1.] * 7 + [heavy]], dtype=torch.float64)
    # 已采到的八个动作各自在独立前缀下；取足够小的行为概率，保证目标概率不超过 1。
    old = torch.full_like(w, 0.02).log()
    target = old + w.log()
    mask = torch.ones_like(w)
    raw = mismatch_report(target, old, mask)["ess"]
    clipped = is_weights(target, old, mask, C=2.)
    ess_clip = clipped.sum()**2 / (8 * clipped.square().sum())
    print(f"w={heavy:2.0f}  原始={raw:.3f}  截断={ess_clip:.3f}")
```

**运行结果**

```text
w= 2  原始=0.920  截断=0.920
w= 8  原始=0.396  截断=0.920
w=16  原始=0.251  截断=0.920
```

## 5. 实战直觉、避坑与面试深挖

**2026 前沿现状**
- **一致性被当作一等公民来设计**：DeepSeek-V4 技术报告（preview 版）在 rollout 时直接使用原生 FP4 量化权重而非模拟量化，让采样行为与线上部署完全一致；被抢占的 rollout 从 token 级预写日志续写（→ 2.5）。DeepSeek-V3.2 的 Keep Routing 与 Keep Sampling Mask、Fireworks 在 Kimi K3 上跑 RL 时做的数值对齐与路由回放，都是同一思路。ScaleRL 里单项提升最大的一处，是把 LM head 换成 FP32 计算（→ 2.5）。
- **精度之争**：Sea AI Lab 指出，广泛采用的 BF16 虽然动态范围大，舍入误差却会破坏训练与推理的一致性，简单地换回 FP16 就能有效消除这种失配，他们因此主张把 FP16 重新当作 RL 微调的基础选项。2026 年还有工作在标题里就直说：BF16 舍入会悄悄丢掉大部分 RL 策略更新，并给出了一个无偏的一行修正。
- **MoE 的路由失配是独立的一类问题**：R3 发现，即使条件完全相同，路由框架在多次前向中也可能选出不同的专家；它在防止训练崩溃上的表现优于 GSPO 和 TIS。2026 年的 PR2 进一步处理回放带来的 router 陈旧问题。

**与工程 / 应用的连接**
- **推理侧的同一个问题**：批不变性缺失导致 temperature=0 也不可复现（→ 1.5）。这在应用侧是"偶发不一致"，在 RL 训练里就是失配源。Thinking Machines 关于消除 LLM 推理非确定性的工作，被 FP16 那篇论文直接列为相关背景。
- **量化部署的隐性代价**：RL 时用 BF16 rollout，部署时用 FP8 / FP4，部署模型的行为就和训练时被优化的那个策略不完全是一个东西。V4 选择让 rollout 直接使用部署精度，正是为了关上这个缺口。
- **自己跑 Agent RL 时第一件该监控的事**：逐 token 的 |logp_train − logp_rollout| 直方图、按长度分桶的序列级对数比率、有效样本比例。这些指标在 reward 曲线出问题之前就会先报警。

**常见误区 / 反直觉点**
1. **"同一份权重，推理和训练算出的概率一定相同"** ✗：精度、kernel、批大小、路由、采样截断、模板渲染，任何一项不同都会造成差异，而且 MoE 和长序列会把差异放大。
2. **"PPO 的 clip 已经处理了 off-policy"** ✗：clip 用的是训练端自己重算的旧策略，看不见 rollout 引擎与训练框架之间的失配因子。
3. **"失配是随机噪声，平均一下就没了"** ✗：逐 token 对数比率的期望恰好是一个 KL，非负，所以序列级偏差随长度系统性漂移。长思维链和多轮 Agent 受影响最大。

**高频深挖题**
- **Q1：RL 训练用 vLLM 采样、Megatron 训练，权重也同步了，为什么还会训崩？怎么定位、怎么修？**
  思路：先说清"同权重 ≠ 同概率"，列出失配源 → 定位：同一批 rollout 在两边算 logp，看 token 级直方图、按长度分桶的序列级比率、是否集中在 MoE 层或特定 token 上 → 修：先从源头消除（精度、确定性 kernel、路由回放、采样掩码、TITO），再用 TIS / MIS 做事后修正，最后用 clip 和陈旧度自适应信任域兜底 → 收尾：比率要拆成"策略更新"和"失配"两个因子，PPO 只管前一个。
- **Q2：MoE 模型上做 RL，路由回放解决了什么？会引入什么问题？**
  思路：离散 top-k 让微小的 logit 差异变成整组专家的切换，是 MoE 特有的失配放大器 → R3 回放 rollout 的专家集合、用训练端 logits 算门控，对齐离散选择、保留 router 梯度；R2 回放旧策略路由，针对陈旧度 → 代价：router 只能在回放集合内调整；路由被冻结在旧轨迹上，忽略了 router 自身的演化（PR2 想解决的问题）。
