# 5.1 显存与算力手算：训练两笔账，推理一笔账

> **一句话核心直觉**：训练看"每参数几个字节 × 每 token 几个 FLOPs"，推理看"每吐一个 token 要从显存搬多少字节"。GQA/MLA、MoE、FlashAttention、ZeRO、FP4、PD 分离……几乎所有架构与系统设计，都是在这几笔账之间做交易。
> **唤醒标签**：16 bytes/param · 6ND · 激活重算 · arithmetic intensity / roofline · MFU

---

## 1. 痛点与钩子：不会算账，世界会怎样？

**场景 A：一个公开数字能榨出多少信息？**
DeepSeek-V3 技术报告给了三个数：预训练 2.664M H800 GPU 小时、14.8T tokens、37B 激活参数。30 秒手算：

| 要算什么 | 手算过程 | 结果 |
| --- | --- | --- |
| 预训练计算量 | 6 × 37B 激活参数 × 14.8T token | 约 3.3 × 10²⁴ FLOP |
| 每卡有效吞吐 | 总计算量 ÷（2.664M GPU 小时 × 3600 秒/小时） | 约 343 TFLOP/s |
| 名义 MFU | 343 ÷ 1979（FP8 稠密）或 343 ÷ 989（BF16 稠密） | 约 17% 或 35% |

会这一步，就能判断任何"我们用 X 卡训了 Y 天"的说法是否可信，还能追问下一句：为什么只有 17%？（6ND 没算注意力、MTP 和重算；MoE 有 all-to-all；FP8 只覆盖了部分 GEMM。）面试官最爱的就是这种追问。

**场景 B：GPU 为什么一直在"闲着"？**
8×H100 部署一个 GQA8 的 70B 模型（BF16），128K 上下文，11 个并发：

| 每个解码步 | 估算 |
| --- | --- |
| 权重和 KV 读取量 | 140 GB + 11 × 43 GB ≈ 612 GB，其中约 77% 为 KV |
| 数据搬运时间 | 612 GB ÷（8 × 3.35 TB/s）≈ 23 ms |
| 算术计算时间 | 11 × 2 × 70B FLOP ÷（8 × 989 TFLOP/s）≈ 0.2 ms |

若两项理想重叠，每个请求约能生成 44 token/s，算力利用率低于 1%。把这一批解码的计算量除以读取量，算术强度约为 **2.51 FLOP/B**，下面屋脊图的默认点就来自这笔账。

你在应用侧感受到的"长上下文贵、并发上不去、输出 token 比输入贵"，根因都在这张账上。

## 2. 第一性原理：两种瓶颈，一条屋脊线

在理想重叠、算力和带宽都能跑到峰值的假设下，kernel 的耗时下限为：

$$
t_{\min} = \max\left(\frac{\text{FLOPs}}{\text{峰值算力}},\ \frac{\text{Bytes}}{\text{带宽}}\right)
$$

定义**算术强度** $\mathrm{AI}=\mathrm{FLOP}/\mathrm{B}$，也就是每搬 1 字节做几次浮点运算。性能上限是 $\min(\text{峰值算力},\ \text{带宽}\times\mathrm{AI})$。两项相等的地方是**屋脊点**，用峰值除以带宽得到。带宽以 TB/s 计时，乘以 FLOP/B 后正好是 TFLOP/s，因为两种单位都按 $10^{12}$ 换算。

```academy-lab
5.1
```

以 H100 BF16 为例，屋脊点约为 $989/3.35=295$ FLOP/B。左侧只增加峰值算力，斜坡的高度保持原样。右侧已经触到算力平顶，增加屋脊模型中的带宽也不会抬高这个工作点的上限。实际 profiling 时，用对应显存层级测到的字节数计算 AI，避免把缓存内复用当作 HBM 流量。

为什么同一层的 GEMM 在训练和 prefill 时往往更靠右？一个矩阵乘同时处理 M 个 token，做 $2MN$ 次浮点运算，权重只需读约 $Ns$ 字节（s 是每参数字节数）。只计权重读取时，**AI 约为 $2M/s$**。训练和 prefill 用序列中的许多 token 复用权重，decode 的 M 是这一步同时生成的 token 数。长上下文还会增加 KV 读取量，把 decode 的工作点进一步推向左侧。

**三个不对称性**决定了后面所有篇目的设计动机：

| 被搬运的数据 | 被谁共享 | 攒 batch 能提高它的 AI 吗 | 唯一的出路 |
|---|---|---|---|
| 稠密权重 | batch 里所有请求 | 能，AI ∝ batch | 攒大 batch、投机解码（一次读权重验证多个 token） |
| KV cache | 只有自己这个请求 | **不能** | 让更多 query 头共享同一份 KV → **1.3 GQA/MLA** |
| MoE 专家权重 | 只有被路由到它的 token | 能，但被稀释 E/k 倍 | 更大的全局 batch + 专家并行 → **1.4 / 5.2** |

**屋脊线在抬高**：

| 硬件 | 显存 | 带宽 | 代表峰值（稠密） | ridge（FLOPs/Byte） |
|---|---|---|---|---|
| H100 SXM | 80 GB | 3.35 TB/s | BF16 989 TF / FP8 1979 TF | 295 / 591 |
| B300 | 288 GB HBM3e | 8 TB/s | FP4 15 PF | ≈ 1875 |
| Rubin | 288 GB HBM4 | 22 TB/s（官方初步规格），19.2 TB/s（出货报道） | NVFP4 训练 35 PF / 推理 50 PF（官方标称） | ≈ 1591 / 1823（两档带宽，均用训练峰值） |

H100 的稠密峰值按规格页标注的结构化稀疏峰值折半。B300 用 GB300 NVL72 的全柜稠密 FP4 总值 1080 PFLOP/s 除以 72。Rubin 沿用 NVIDIA 标注的稠密训练峰值做两种带宽的对照。规格见 [NVIDIA H100](https://www.nvidia.com/en-us/data-center/h100/)、[NVIDIA GB300 NVL72](https://www.nvidia.com/en-us/data-center/gb300-nvl72/) 和 [NVIDIA Vera Rubin NVL72](https://www.nvidia.com/en-us/data-center/vera-rubin-nvl72/)。修订带宽见 [ServeTheHome 出货规格报道](https://www.servethehome.com/nvidia-updates-rubin-gpu-specs-as-first-production-hardware-arrives/)。

从 H100 BF16 的约 300 到 FP4 时代的 1600–1900，ridge 抬高了 5–6 倍。主因是**低精度让算力涨得比 HBM 带宽快**。Rubin 把带宽拉到 ~20 TB/s，算是往回拉了一点，但量级没变。后果有两个：decode 要攒更大的 batch 才能吃满算力；prefill 与 decode 的硬件需求分化到 NVIDIA 专门做了 Rubin CPX，一颗算力厚（FP4 稠密 20 PF）、带宽薄（2 TB/s GDDR7）的 prefill 专用芯片。PD 分离已经从软件架构走进了芯片设计。

### 批处理能摊薄权重，不能摊薄每个请求自己的历史

一轮 decode 同时服务 $B$ 条请求，各生成一个 token。假设稠密模型的权重读一次共 140 GB，每条请求扫描自己的 KV 共 40 GB，那么这轮流量为 $140+40B$ GB，平均到每个输出 token 是 $140/B+40$ GB。批量趋于很大时，第二项仍在。仅用“权重大小除以批量”来估计吞吐，会漏掉这个下限。

若允许请求共享同一段前缀的物理缓存，分配容量和实际读取流量又是两件事。前缀只存一份，并不能保证不同 query 在一次内核调用中只读它一次。因此要用内核的实际读字节数验证复用，而不能仅从显存占用推断。

```academy-lab
5.1-batch-bytes
```

**迁移练习。** 固定批量 16，将 KV 字节量减半时，每个输出 token 从 48.75 GB 变成 28.75 GB。检查瓶颈后才能把节省的读取量换成端到端加速。

## 3. 承重墙推导：重新捡起核心数学

### Step 1　训练静态显存：每参数 16 字节从哪来

| 项 | 精度 | 字节 | 为什么需要 |
|---|---|---|---|
| 权重（前向用） | BF16 | 2 | GEMM 输入 |
| 梯度 | BF16 | 2 | 反向输出 |
| 主权重 master | FP32 | 4 | **核心 Trick**：BF16 只有 8 位有效位，lr × grad 常比权重小 2⁻⁸ 以上，直接加到 BF16 权重上会被舍入成 0，更新就"消失"了 |
| Adam 一阶矩 m | FP32 | 4 | 动量 |
| Adam 二阶矩 v | FP32 | 4 | 逐元素自适应步长 |
| **合计** | | **16** | 主权重和优化器矩占 12 字节，前向权重和梯度共占 4 字节 |

- **Muon**：在这一精度口径下，Muon 只维护一个动量缓冲，被它覆盖的 2D 矩阵约 12 B/参数。常见混合方案里的 embedding、输出头和 norm 仍用 AdamW。
- **FP8 / FP4 训练不会让这张表缩水多少**：低精度主要用在 GEMM 的输入和激活上，master 权重和优化器状态仍是高精度。
- ZeRO-3 / FSDP 把这 16 字节均摊到 N 张卡上 → 5.2。

### Step 2　激活显存：随 B·L 线性（或平方）增长的那一块

Megatron 对 GPT 类模型的经典估算（BF16、不重算），每层：

$$
\text{Act}_{\text{layer}} \approx s\,b\,h\left(34 + \frac{5\,a\,s}{h}\right)\ \text{bytes}
$$

- $34\,sbh$：线性项（QKV 输入、FFN 中间态、LN 输入、dropout mask……）
- $5\,a\,s^2 b$：注意力分数和 softmax 矩阵，**平方项**
- **FlashAttention 不落地 L×L 矩阵，直接消掉平方项**（→ 1.5）；全量重算则每层只存输入 $2\,sbh$。

7B（h=4096、a=32、32 层）、s=8192、b=1：线性项合计 **36.5 GB**，平方项合计 **344 GB**。没有 FlashAttention，长序列训练根本跑不起来。

### Step 3　训练 FLOPs：6ND，以及它漏掉的注意力

**为什么是 6**：前向 $y = Wx$，每个参数每 token 一乘一加 = 2；反向要算两个梯度，$\partial L/\partial x = W^\top g$（2）和 $\partial L/\partial W = g\,x^\top$（2），合计 4。前向 2 + 反向 4 = **6**。MoE 用 $N_{\text{active}}$。

**漏掉的注意力项**：每 token 每层前向 $QK^\top$ 与 $PV$ 共 $4 L d_{\text{attn}}$，因果掩码平均减半 → $2 L d_{\text{attn}}$，乘 3 得训练量：

$$
\text{FLOPs/token} \approx 6N + 6\,n_{\text{layer}}\,L\,d_{\text{attn}}
$$

7B 模型的注意力占比：**4K 时 7%，32K 时 38%，128K 时 71%**。

- 这就是为什么长上下文训练总放在最后的短阶段；也是 DeepSeek-V4 在 1M 上下文下把单 token 推理 FLOPs 压到 V3.2 的 27%（Pro）的意义：长上下文下注意力就是算力主体。
- FlashAttention 省的是显存和访存，**不省 FLOPs**。省 FLOPs 要靠稀疏或压缩注意力（→ 1.6）。

### Step 4　Decode：一次读，换几个 FLOPs

**稠密权重**：batch 为 b 时，AI = 2b / s_w。要进入算力受限区，需要

$$
b > b^* = \frac{\text{ridge}\cdot s_w}{2}
$$

| 硬件 / 权重精度 | b* |
|---|---|
| H100 / FP8（s_w = 1） | ≈ 295 |
| B300 / NVFP4（s_w ≈ 0.5625：4 bit + 每 16 个元素一个 FP8 scale） | ≈ 530 |
| Rubin / NVFP4（训练口径 ridge） | ≈ 450 |

**MoE**：每个专家每步只分到 b·k/E 个 token，所以全局 batch 要放大 E/k 倍：

$$
b_{\text{global}} > b^* \cdot \frac{E}{k}
$$

Kimi K3（E=896，k=16，E/k=56）按 H100-FP8 口径要 **~1.65 万 token/步**；DeepSeek-V4-Pro（384/6=64）要 **~1.9 万**。大规模专家并行 + PD 分离的部署形态，是算术逼出来的，不是品味选择。

**MoE 在小 batch 和大 batch 下是两种生物**：一步内被触达的专家比例 $1-(1-k/E)^b$。K3 在 b=64 时为 68%，b=256 时为 99%。小 batch 时 MoE 真的省带宽（只读激活专家）；大 batch 时几乎每步读全部专家，省的是算力。

### Step 5　KV cache：一个公式管所有注意力变体

$$
\text{KV bytes/token} = n_{\text{layer}} \times \text{kv\_elems} \times s_{kv},\quad
\text{kv\_elems} = \begin{cases} 2\,H_{kv}\,d_h & \text{GQA/MHA} \\ d_c + d_r & \text{MLA} \end{cases}
$$

| 配置 | 每 token（KiB） | 128K 单序列 | 1M 单序列 |
|---|---|---|---|
| 70B 级 GQA8（80 层、d_h=128、BF16） | 320 | 43 GB | 328 GB |
| 同一模型换成 V3 式 MLA（576 元素/层） | 90 | 12 GB | 92 GB |
| DeepSeek-V3（61 层 MLA） | 69 | 9.2 GB | 70 GB |

表内 1 KiB 为 1024 字节，1 GB 为 10⁹ 字节。128K 指 131,072 个 token，1M 指 1,000,000 个 token。

DeepSeek-V4 在同口径下，KV cache 约为 BF16 GQA8 基线的 2%：它同时压了"每 token 多大"和"存多少个 token"两条轴（→ 1.3 §2）。

## 4. 极简代码锚点（Python 算账器）

本篇的"张量"是数字。下面这段把 Step 1–5 写成可复用的函数，注释里的结果都实际跑过。

```python
from dataclasses import dataclass

@dataclass
class Model:
    n_total: float; n_active: float; n_layer: int
    kv_elems: int           # 每层每 token 缓存元素数：GQA = 2*H_kv*d_h；MLA = d_c + d_r
    d_attn: int             # H * d_h
    E: int = 1; k: int = 1  # 路由专家总数 / 每 token 激活数（dense 为 1）

def attn_share(m, ctx):                              # 训练 FLOPs 中注意力的占比
    a = 6 * m.n_layer * ctx * m.d_attn
    return a / (6 * m.n_active + a)

def implied_mfu(n_active, tokens, gpu_hours, peak):  # 用公开 GPU 时数反推有效利用率
    return 6 * n_active * tokens / (gpu_hours * 3600) / peak

def decode_step(m, ctx, batch, bw, peak, w_bytes, kv_bytes=2.0):
    p = m.k / m.E                                    # MoE：b 越大，被触达的专家越多
    extra = 0.0 if m.E == 1 else ((1 - (1 - p) ** batch) - p) / (1 - p)
    w_read  = (m.n_active + (m.n_total - m.n_active) * extra) * w_bytes
    kv_read = batch * ctx * m.n_layer * m.kv_elems * kv_bytes   # 每个请求只读自己的 KV
    t_mem, t_cmp = (w_read + kv_read) / bw, batch * 2 * m.n_active / peak
    return dict(ms=1e3 * max(t_mem, t_cmp), kv_share=kv_read / (w_read + kv_read),
                util=t_cmp / max(t_mem, t_cmp))

implied_mfu(37e9, 14.8e12, 2.664e6, 1979e12)         # → 0.173（DeepSeek-V3 vs FP8 峰值）
attn_share(Model(7e9, 7e9, 32, 8192, 4096), 131072)  # → 0.71
gqa70 = Model(70e9, 70e9, 80, 2 * 8 * 128, 8192)
decode_step(gqa70, 131072, 11, bw=8*3.35e12, peak=8*989e12, w_bytes=2)
# → {'ms': 22.9, 'kv_share': 0.77, 'util': 0.0085}
mla70 = Model(70e9, 70e9, 80, 576, 8192)             # 同模型换 MLA：同样 ~23ms/步，并发 11 → 41
decode_step(mla70, 131072, 41, bw=8*3.35e12, peak=8*989e12, w_bytes=2)
```

> 验证习惯：真实训练时用 `torch.cuda.max_memory_allocated()` 对照 Step 1+2 的预测。偏差超过 20%，通常是碎片、通信 buffer，或者某处意外落地了 L×L 矩阵。

## 5. 实战直觉、避坑与面试深挖

**2026 前沿现状**
- **4-bit 进入训练与原生发布**：NVIDIA 用 NVFP4 预训练 12B 模型跑了 10T tokens，损失和下游指标与 FP8 基线相当。DeepSeek-V4 技术报告（preview 版）里，路由专家权重用 FP4，后训练阶段对专家权重和 indexer 做了 FP4 QAT；Kimi K3 以 MXFP4 权重 / MXFP8 激活的 QAT 形式发布。算推理显存时，每参数按约 0.5–0.56 字节记：K3 的 2.8T 参数，4-bit 下仅权重就约 1.4 TB，一台 8×B300（8 × 288 GB ≈ 2.3 TB）装得下，剩下的才是 KV 预算。
- **Muon 成为前沿开源模型的主流优化器**：Kimi-K2、GLM-5、DeepSeek-V4 都用 Muon 训练。静态显存每参数少一个状态；NVIDIA 在 GB300 上实测 Kimi K2 训练，Muon 自身开销约占总算力的 5%（1,080 TFLOPs/s 中 51 用在优化器）。
- **硬件把 PD 分离写进了芯片**：Rubin 为 decode 拉满 HBM4 带宽，Rubin CPX 为 prefill 堆算力、砍带宽。读懂 §2 的屋脊表，就读懂了这条产品线。

**与工程 / 应用的连接**
- **Agent 负载 = prefill + 缓存驻留主导**：SemiAnalysis 用回放的 Claude Code trace 做推理基准，中位数是每轮 142k 输入、444 输出、每会话 65 轮，输入输出比约 320:1。这种负载下，成本大头是"142k 前缀的 KV 能不能常驻并被命中"，而不是生成。同样 142k 前缀，70B 级 GQA8 要常驻约 47 GB，V3 式 MLA 约 10 GB：KV 架构直接决定了 prefix cache 的单位成本。
- **API 定价的成本来由**。以 Moonshot AI 在 OpenRouter 上列出的标价为例，每百万输入 token 3 美元，同样数量的输出 token 15 美元。Decode 受 HBM 带宽约束，前缀缓存命中可以跳过已有部分的 prefill。这些成本差异有助于解释价格分档，报价也会随服务商和时间变化。[OpenRouter 的 Kimi K3 服务商报价](https://openrouter.ai/moonshotai/kimi-k3)

**常见误区 / 反直觉点**
1. **"FP8/FP4 训练能把显存砍半甚至砍到四分之一"** ✗：静态显存的大头是 FP32 的 master 和优化器状态，低精度主要加速 GEMM、减少激活与通信。真正砍静态显存的是 ZeRO 切分和更省状态的优化器。
2. **"6ND 就是总训练算力"** ✗：128K 上下文下注意力能占七成；MoE 必须用激活参数；MTP、重算、通信都不在里面。
3. **"MoE 推理成本按激活参数算"** ✗：显存永远按总参数算；带宽只在小 batch 时按激活参数算，batch 一大就趋近总参数。激活参数只决定 FLOPs。

**高频深挖题**
- **Q1：8×H100 能全参微调一个 70B 模型吗？差多少，怎么补？**
  思路：静态 16 B × 70B = 1.12 TB > 640 GB，ZeRO-3 也装不下 → 先给出差额，再按"砍哪一项"给方案：LoRA（梯度和优化器只覆盖 <1% 参数）、优化器状态 offload 到 CPU、8-bit / 单状态优化器、QLoRA（权重也压到 4-bit）。最后补一句激活：s=8K 时还要几十 GB，靠 FlashAttention + 重算。
- **Q2：为什么增大 decode batch 几乎不增加单步延迟，上下文变长却会让每步线性变慢？**
  思路：权重被 batch 共享，AI ∝ b，b < b* 时多加请求几乎是免费的算力；KV 是每个请求私有的，长度翻倍搬运量就翻倍，攒 batch 帮不上忙。顺势引到 GQA/MLA 是在提高 KV 的"共享度"（→ 1.3），再引到 MoE 把 b* 放大 E/k 倍（→ 1.4）。
