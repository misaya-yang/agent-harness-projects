# 5.2 分布式训练：切什么，付什么通信

> **一句话核心直觉**：每种并行都是在"切什么"和"为此付出什么通信"之间做交易。DP 切数据、复制模型；ZeRO 把优化器状态、梯度、参数也切开，用更多通信换显存；TP 切矩阵，通信最密，只能留在高速互联域内；PP 切层，付出流水线气泡；EP 切专家，付出 all-to-all；CP 切序列，付出 KV 交换。**选择顺序由"装不装得下"和"带宽的层级"共同决定。**
> **唤醒标签**：DP / ZeRO-1/2/3 / FSDP · TP（列切 / 行切）· PP 与气泡 · EP 与 all-to-all · CP · 多维并行

前置：5.1（每参数 16 字节、激活显存）、1.4（MoE）。

真实的前沿训练配置是多种并行的组合。NVIDIA 在 256 张 GB300 上测量 Kimi K2 训练吞吐时，用的配置是 PP4 / DP64 / EP64（专家并行嵌在数据并行维度里）。读懂这样一个配置串，就是本篇的目标。

## 2. 第一性原理：看透它的几何 / 物理直觉

### 2.1 六种并行一张表

| 并行 | 切什么 | 通信什么 | 通信模式 | 放在哪层互联 | 什么时候必须用 |
|---|---|---|---|---|---|
| **DP** | 数据（batch） | 梯度 | all-reduce，每步一次 | 任意 | 永远是最外层 |
| **ZeRO-1/2/3 / FSDP** | 优化器状态 / 梯度 / 参数 | 参数 all-gather + 梯度 reduce-scatter | 每层前向、反向各一次 | 任意，可与计算重叠 | 模型状态单卡装不下 |
| **TP** | 每层的权重矩阵 | 激活 | 每层多次 all-reduce | **高速互联域内** | 单层太大、激活太大，或想降低 DP 的通信压力 |
| **PP** | 层 | 层间激活 | 点对点 | 可跨机 | 层数多，或 TP 已到互联域上限 |
| **EP** | MoE 的专家 | token 与专家输出 | all-to-all，每个 MoE 层两次 | 越快越好 | MoE 模型 |
| **CP** | 序列 | KV（或压缩后的 KV） | 环形传递或 all-gather | 视序列长度 | 超长上下文，激活单卡放不下 |

### 2.2 带宽的层级决定摆放

| 位置 | 互联 | 大致速率 |
| --- | --- | --- |
| GPU 内部 | HBM | 数 TB/s 至约 20 TB/s |
| 高速互联域 | NVLink | 新一代系统标称每卡双向约 1.8–3.6 TB/s，Rubin NVL72 初步规格为整柜 260 TB/s |
| 跨机网络 | InfiniBand / 以太网 | 本课示例按每卡单向 50–100 GB/s 估算 |

比较通信时间时统一使用同一方向的有效带宽，并区分每卡和整柜口径。

- **通信越频繁、量越大的并行，放在越快的互联上**：TP 每层都要 all-reduce，只能放在 NVLink 域内；DP 和 PP 通信稀疏，可以跨机。
- **NVL72 改变了"机内"的定义**：一个高速互联域从 8 张卡扩大到 72 张，TP 和 EP 可以在整个机柜内展开，以前只能跨机做的切分，现在能放进高速域。

### 2.3 TP：一列一行，一次 all-reduce

以 MLP 为例（Megatron-LM 经典切法）：
第一层权重矩阵 $A$ 按**列切分（Column Parallel）**，每张卡持有分块 $A_i$。输入激活 $X$ 完整复制到各卡，各卡本地独立计算 $Z_i = \operatorname{GeLU}(XA_i)$。由于 GeLU 是逐元素激活函数，各卡可以完全在本地完成非线性变换，**期间无需任何跨卡通信**。
接着第二层权重矩阵 $B$ 按**行切分（Row Parallel）**，每张卡持有分块 $B_i$，本地计算部分和输出 $Y_i = Z_i B_i$。此时，为了得到完整的输出张量 $Y = \sum_i Y_i$ 并输入给后续的残差连接与 LayerNorm，必须在所有 TP rank 之间进行一次 **All-Reduce 求和通信**。

自注意力机制同理：QKV 投影按注意力头做列切分，输出投影做行切分，在注意力输出处做一次 All-Reduce。因此每个 Transformer 层在前向传播中恰好发生 **2 次 All-Reduce**（注意力 1 次 + MLP 1 次），在反向传播中同样需要 **2 次 All-Reduce**。序列并行（SP）在 LayerNorm、dropout 这些逐 token 的独立操作上沿序列维切分，把 all-reduce 拆解为 reduce-scatter（反向）+ all-gather（前向），总通信量保持不变，但将这些原本在每张卡重复常驻的激活显存砍到了 $1/\text{TP}$。

### 2.4 PP：气泡与调度

以 3 个阶段、4 个微批次为例。先完成所有前向 F，再开始反向 B。每个阶段的操作耗时相同时，调度占 12 个时间槽。

| 设备 | 执行 F1 到 F4 的时间槽 | 执行 B4 到 B1 的时间槽 |
| --- | --- | --- |
| GPU 1 | 1–4 | 9–12 |
| GPU 2 | 2–5 | 8–11 |
| GPU 3 | 3–6 | 7–10 |

每台设备只有 8 个活跃时间槽，另 4 个在等相邻阶段。用 §3 的公式，气泡比例也正好为 $(3-1)/(4+3-1)=1/3$。

微批次越多，气泡占比越小；1F1B 调度让每张卡尽早开始反向、尽早释放激活；交错调度和 DualPipe 进一步把前向、反向和通信重叠起来。

### 一条时间线解释流水线气泡

把同一阶段处理一个微批所需时间记作一格。理想均衡的前向流水线需要 $p-1$ 格把首个微批送到末段，随后每格产出一个微批。处理 $m$ 个总用时为 $m+p-1$ 格，单阶段有效时间为 $m$ 格，空闲比例因此为 $(p-1)/(m+p-1)$。在均匀前反向成本、普通无交错调度的理想估算里，同一个比例也常作为训练气泡基线。

如果把微批数固定为 8，把阶段数从 4 增到 8，气泡从 3/11 增至 7/15。分段可以让原先放不下的模型装下，却可能让设备等得更久。真实时间线中最慢阶段、点对点通信与重计算还会增加额外空隙。

## 3. 承重墙推导：重新捡起核心数学

### Step 1　ZeRO 的每卡静态显存

记 Ψ 为参数量，$N_d$ 为 DP 组大小，混合精度 Adam 为 2 + 2 + 12 字节：

$$
\text{ZeRO-1: } (2+2)\Psi + \frac{12\Psi}{N_d},\qquad
\text{ZeRO-2: } 2\Psi + \frac{(2+12)\Psi}{N_d},\qquad
\text{ZeRO-3: } \frac{16\Psi}{N_d}
$$

70B、$N_d = 64$ 时分别为 293 GB、155 GB、17.5 GB。PyTorch FSDP 的完全切分模式也采用 ZeRO-3 的这三个切分维度。原始状态记账见 [ZeRO 论文](https://arxiv.org/abs/1910.02054)。

### Step 2　通信量：为什么 ZeRO-3 是纯 DP 的 1.5 倍

- **传统 DP 的梯度 All-Reduce**（环形通信）：
  反向传播结束后，每卡需要对全量梯度做一次同步。一个完整的环形 All-Reduce 分为两阶段：Reduce-Scatter 聚合分片（每卡传输 $\frac{N_d-1}{N_d}\cdot 2\Psi$ 字节）+ All-Gather 广播全局累加结果（每卡传输 $\frac{N_d-1}{N_d}\cdot 2\Psi$ 字节）。
  因此每卡收发总量为 $2\frac{N_d-1}{N_d}\cdot 2\Psi$ 字节（对应 2 份参数量），70B 时约 276 GB。
- **ZeRO-3 通信量拆解与 1.5 倍原理**：
  ZeRO-3 将权重、梯度和优化器状态全部切分到各卡，因此在计算过程中需要动态按需拉取：
  1. **前向传播**：每计算一层，各卡通过 All-Gather 从同组卡拉取该层的完整权重（传输 $\frac{N_d-1}{N_d}\cdot 2\Psi$ 字节，算完前向立即释放）；
  2. **反向传播**：为了计算输入的激活梯度，每层再次通过 All-Gather 重新拉取一次完整权重（传输 $\frac{N_d-1}{N_d}\cdot 2\Psi$ 字节）；
  3. **梯度同步**：反向算完该层局部梯度后，立即通过 Reduce-Scatter 将各卡的分片梯度累加到其属主卡上（传输 $\frac{N_d-1}{N_d}\cdot 2\Psi$ 字节）。注意：此处无需像传统 DP 那样再执行一次 All-Gather 广播梯度，因为每张卡只需使用本地聚合后的梯度分片来更新自己持有的那份参数分片！
  将上述三步相加，ZeRO-3 每步的总通信量为 $3 \times \frac{N_d-1}{N_d}\cdot 2\Psi$ 字节（对应 3 份参数量）。
  两相对比，**$3 / 2 = 1.5$ 倍**！ZeRO-3 正是以这额外的 50% 通信量换来了模型全部状态在 $N_d$ 张卡上的完全均摊；并且由于前后向的 All-Gather 是一层层流水触发的，大部分通信可以与前序层的计算相互掩盖（Prefetch Overlap）。

### Step 3　TP 的通信：为什么落在关键路径上

每次 all-reduce 的数据量是一层的激活 $b\cdot s\cdot h$，环形实现下每卡收发约 $2\frac{t-1}{t}bsh$ 个元素。b=1、s=8192、h=8192、t=8 时，**每层前向约 0.47 GB**。

**为什么张量并行通信发生在计算的关键路径（Critical Path）上？**
在计算图依赖中，后续的 LayerNorm、残差加法以及下一层的输入，都严格依赖当前层 All-Reduce 汇总后的完整输出 $Y$。在集合通信完成前，后续计算核心必须完全挂起阻塞，无法异步掩盖！由于每层前向加反向要经历 4 次强制同步阻塞，TP 必须严格部署在具备数百 GB/s 至 TB/s 带宽的高速机内互联域（如 NVLink/NVSwitch）；一旦跨越机间网络，GPU 将长期陷入通信等待。

### Step 4　PP 的气泡

p 个流水线阶段、m 个微批次时：

$$
\text{气泡占比} = \frac{p-1}{m+p-1}
$$

p=8 时：m=8 → 46.7%，m=32 → 17.9%，m=128 → 5.2%。**微批次数要远大于阶段数**，这又反过来要求全局 batch 足够大。

### Step 5　EP 的 all-to-all 与计算重叠

每个 MoE 层的 dispatch + combine 共搬运约 $2\cdot T\cdot k\cdot h$ 个元素（T 为本组 token 数）。16K token、h=7168、k=8 时，BF16 下每层约 3.76 GB。DeepSeek-V4-Pro 的理论重叠条件是计算吞吐除以互联带宽不超过 6144 FLOP/B，即 1 GB/s 约可支撑 6.1 TFLOP/s 的计算吞吐。计算越快，留下来搬数据的时间越短。具体推导见 [DeepSeek-V4 预览报告 §3.1](https://arxiv.org/html/2606.19348v1#S3.SS1)。

## 4. 极简代码锚点（Python 算账器）

本篇的"张量"仍是数字。下面的函数覆盖 Step 1–5，§1 和 §3 的数字都来自它们。

```python
def zero_static_gb(N, n_dp, stage, bw=2, bg=2, bo=12):
    """混合精度 Adam：权重 bw、梯度 bg、优化器 bo 字节/参数；stage 0–3"""
    w = N * bw / (n_dp if stage >= 3 else 1)
    g = N * bg / (n_dp if stage >= 2 else 1)
    o = N * bo / (n_dp if stage >= 1 else 1)
    return (w + g + o) / 1e9

def dp_allreduce_gb(N, n_dp, bytes_=2):                    # 环形 all-reduce：每卡收发量
    return 2 * (n_dp - 1) / n_dp * N * bytes_ / 1e9

def tp_comm_gb_per_layer_fwd(b, s, h, tp, bytes_=2):        # 每层前向 2 次 all-reduce（attn + mlp）
    return 2 * 2 * (tp - 1) / tp * b * s * h * bytes_ / 1e9

def pp_bubble(p, m):                                        # p 个阶段、m 个微批次
    return (p - 1) / (m + p - 1)

def ep_a2a_gb_per_layer(tokens, h, k, bytes_=2):            # dispatch + combine
    return 2 * tokens * k * h * bytes_ / 1e9

for st in range(4):
    print(f"70B, DP=64, ZeRO-{st}: {zero_static_gb(70e9, 64, st):.1f} GB/卡")   # 1120 / 293 / 155 / 17.5
print(dp_allreduce_gb(70e9, 64))                           # ≈ 276 GB/步
print(tp_comm_gb_per_layer_fwd(1, 8192, 8192, 8))          # ≈ 0.47 GB/层
print([round(pp_bubble(8, m), 3) for m in (8, 32, 128)])   # [0.467, 0.179, 0.052]
print(ep_a2a_gb_per_layer(16384, 7168, 8))                 # ≈ 3.76 GB/层
```

**怎么用它选配置**：先用 ZeRO 公式看"装不装得下"；装不下或通信太重，再按"TP 放互联域内 → PP 跨机 → DP 最外层"的顺序加维度；MoE 加 EP，超长序列加 CP；最后用气泡和通信公式检查每一维的代价。

## 5. 实战直觉、避坑与面试深挖

**2026 前沿现状**
- **优化器换代倒逼并行策略**：Muon 需要完整的梯度矩阵来做正交化，和 ZeRO 按元素切分的方式冲突。DeepSeek-V4 用了一种混合策略：稠密参数用背包算法把整个矩阵分配到各 rank，限制 ZeRO 的并行度，padding 带来的显存开销通常低于 10%，超出上限的部分在额外的 DP 组里冗余计算 Muon 更新；MoE 参数则把专家展平后平均分配。MoE 梯度用 BF16 加随机舍入同步，通信量减半。
- **长上下文的 CP 要适配新注意力**：V4 的压缩注意力会跨越 rank 的边界，而且各 rank 压缩后的长度不同。它的做法分两步：每个 rank 先把最后 m 个未压缩的 KV 发给下一个 rank 一起压缩，再 all-gather 所有 rank 的压缩结果，并做一次融合的选择与填充。
- **残差结构的改动影响流水线**：V4 为 mHC 带来的额外流水线通信调整了 DualPipe 的 1F1B 重叠方案；Kimi 的 Block AttnRes 把跨层通信从 O(Ld) 降到 O(Nd)，据报道流水线开销只有 4%。K3 的技术报告还专门强调了完全均衡的专家并行训练和高效的显存管理。

**与工程 / 应用的连接**
- **推理部署是同一套语言**：TP 降低单请求延迟（每层都要通信，所以只在机内）；EP 让 MoE 的专家分散在多卡上（→ 1.4）；DP 复制副本提高吞吐；PD 分离把 prefill 和 decode 放在不同的卡组上。看懂训练的并行串，部署的 `--tp-size 8 --ep-size 8` 也就看懂了。
- **为什么 TP 不跨机**：每层多次 all-reduce、处在关键路径上，跨机带宽低一两个数量级，跨机做 TP 会让 GPU 大部分时间在等通信。

**常见误区 / 反直觉点**
1. **"FSDP 就是数据并行"** ✗：FSDP 是 ZeRO-3，参数、梯度、优化器状态全切开，前后向时临时 all-gather。它的通信量约为普通 DP 的 1.5 倍，换来的是显存按卡数线性下降。
2. **"TP 越大越好"** ✗：TP 每层都要通信，超出高速互联域后效率断崖式下降；TP 过大时每张卡上的矩阵太小，GEMM 效率也会下降。
3. **"流水线气泡可以忽略"** ✗：微批次数和阶段数相当时，气泡能占到近一半时间。要么增大微批次数，要么用交错调度或 DualPipe 这类重叠方案。

**高频深挖题**
- **Q1：给你 1024 张 H100（每机 8 卡），训练一个 400B 稠密模型，并行怎么配？**
  思路：先算静态显存：400B × 16 B ≈ 6.4 TB，必须 ZeRO 或模型并行 → TP=8 放满机内 NVLink → 层数多，PP 跨机（如 8 段），用足够多的微批次压低气泡 → 剩下的 1024/(8×8)=16 做 DP + ZeRO-1 切优化器状态 → 用公式核对每卡显存、TP 每层通信、PP 气泡、DP 梯度同步能否被重叠 → 长上下文阶段再加 CP。
- **Q2：MoE 模型训练里 EP 和 TP 怎么取舍？all-to-all 怎么藏起来？**
  思路：专家之间计算独立，EP 天然适合 MoE，通信是 all-to-all 而不是每层的 all-reduce → 专家很多时 EP 维度大，最好放进高速互联域（NVL72 让这件事容易很多）→ 隐藏通信：把专家分波、通信与计算流水线化；判断能否藏住，用"计算 / 带宽"的比值对照 V4 给出的"每 GB/s 掩盖 6.1 TFLOP/s"→ 补一句：LatentMoE 把 all-to-all 的数据量按 d/ℓ 缩小，是从结构上减通信。
