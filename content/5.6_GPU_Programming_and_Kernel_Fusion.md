# 5.6 GPU 编程与算子融合：把中间结果留在芯片上

> **一句话核心直觉**：GPU 快不只靠更多 FLOP/s，还靠让足够多的线程一起工作、合并访存，并避免每个小算子都把中间结果写回全局内存。融合减少往返和启动，但也可能增加寄存器压力、破坏并行度，最后要用正确的计时方法验证。
>
> **唤醒标签**：SM 与 warp · 寄存器 / 共享内存 / HBM · roofline · kernel launch · Triton 分块与 mask · 编译器图断裂

本篇接在 [5.1 显存与算力手算](/lessons/5-1.html)之后，把“搬多少字节”落实到一段 kernel。**文中的微秒数全部是明确给定参数下的算术估算，不是任何 GPU 的实测成绩。** 第 4 节附可在有 CUDA 的机器上运行的 Triton 基准；当前编写环境没有可用 CUDA 或 Triton，GPU 部分尚未在此环境实测。

## 1. 痛点与钩子：GPU 很强，为什么一个简单网络还是慢？

一个推理图里有许多这样的逐元素运算，输入是 FP32 向量 $x$，$a,b$ 是标量：

$$
t_1=a x,\qquad t_2=t_1+b,\qquad y=\operatorname{ReLU}(t_2)=\max(0,t_2).
$$

如果三步各启动一次 kernel，且每个中间向量都在全局内存读写，那么每个元素经过三次“读 4 B、写 4 B”，共 24 B；把三步放入一个 kernel，读取 $x$ 后在寄存器继续计算，最后只写 $y$，共 8 B。两种情形中乘加算 2 FLOP；ReLU 的比较不计入这 2 FLOP。这里假设输入连续、标量成本可忽略、每次读写都流到所考虑的内存层级、没有额外临时量或缓存命中。

现实里的全局内存访问可能被 L2 缓存吸收；输入小到适合缓存时，上面的 24 B 并非实测 HBM 流量。判断应看 profiler 所选内存层级的计数，不能把代码里的每次逻辑 load/store 一律称为 HBM 读写。

给一个**虚构的有效性能模型**：全局内存带宽 1 TB/s，FP32 标量算力 10 TFLOP/s，每次启动 5 μs；向量有 $N=2^{20}=1,048,576$ 个元素。三次 kernel 的流量是 25,165,824 B，融合是 8,388,608 B。假设各步受带宽限制，且每次 kernel 的执行与下一次串行：

| 估算项目 | 三次独立 kernel | 一次融合 kernel |
|---|---:|---:|
| 流量 / 带宽 | 25.166 μs | 8.389 μs |
| 启动 | 15 μs | 5 μs |
| 总耗时估算 | **40.166 μs** | **13.389 μs** |

这是该简化模型恰好得到的 3 倍，不是“融合一定快 3 倍”的经验定律。调小和调大向量，观察启动开销占比从接近 100% 下降：

```academy-lab
5.6
```

【交互实验说明】：在上方性能估算图中，你可以滑动**向量长度 N（对数刻度 $\log_2 N$）**滑块（从 $2^8 = 256$ 到 $2^{25} \approx 3355$ 万元素）：
- 观察**三次独立 kernel 耗时（蓝线）与一次融合 kernel 耗时（红线）**的对比趋势；
- 当向量极短时（例如 $N=256$）：计算和访存时间均不足 0.01 μs，分离方案总耗时为 15.006 μs，其中三次 kernel launch 的固定启动开销（$3 \times 5 = 15$ μs）占了高达 99.96%！此时融合的核心收益在于消除了两次 host 发射与硬件就绪的开销；
- 当向量增长到海量级别（例如 $N=2^{20}$ 及以上）：总耗时完全被数据搬运吞吐（Memory-bound）主导，启动开销占比下降至极低水平（$N=2^{25}$ 时仅占 1.83%）。此时融合的加速收益完全来自于访存总量的削减（每个元素从 24 字节降至 8 字节，数据往返显存流量净减 67%）；
- 这清晰展示了算子融合的双重收益区间：短向量吃 launch 节省，长向量吃显存带宽节省。本模型中 256 个元素时，三次启动就占分离方案约 99.96%；$2^{25}$ 个元素时约占 1.83%。实际是否启动受限，应在目标设备上测量多个大小，且把计时边界说清楚。

## 2. 第一性原理：从线程到显存

### 2.1 一个 kernel 怎样在 GPU 上执行

以 NVIDIA CUDA 的术语说明；不同厂商的名称和执行细节并不完全相同。

| 层次 | 做什么 | 对编程的约束 |
|---|---|---|
| grid（网格） | 一次 kernel 启动的全部线程块 | 线程块之间不能假定执行顺序；普通 kernel 没有通用的跨块同步屏障 |
| block / CTA（线程块） | 一组线程驻留在一个 SM 执行 | 同一块内可用共享内存和块级屏障；屏障必须被所有需要参与的线程一致到达 |
| SM（流式多处理器） | 调度多个驻留块及其 warp | 每个块的寄存器、共享内存和线程数会限制同时驻留数量 |
| warp（执行束） | NVIDIA 通常把 32 个线程作为调度与执行的基本组 | 邻近线程访问邻近地址便于合并访存；控制流分叉时不同路径需要分别执行 |

warp 内有一个线程因越界被 mask，不代表整个块停下；它只是不执行对应的有效 load/store。维持大量可运行 warp 有助于用其他工作掩盖访存延迟，但更高 occupancy 不是速度的充分条件：依赖链、带宽、指令数量也可能是瓶颈。硬件的具体限制见 [CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)。

### 2.2 数据住在哪里

- **寄存器**：线程私有，适合复用本线程的中间标量。一个融合 kernel 活跃变量增多会消耗更多寄存器，可能减少驻留 warp，甚至触发寄存器溢出。
- **共享内存**：线程块内显式管理、线程间可共享的片上存储。适合重复使用的 tile 或块内归约；要安排同步并留意 bank conflict。它不是所有块共享的缓存。
- **全局内存与缓存**：线程都可访问的全局地址空间通常由设备内存提供，读写可经过 L1/L2；寄存器溢出的 local memory 也是线程私有地址空间，但其数据可能落在缓存或设备内存中，不是额外免费的片上寄存器。

一个块搬一块数据进共享内存、多次复用、最后写回，是矩阵乘与分块注意力的基本套路。带宽分析应说清是哪一级：一个在 L2 复用命中的中间向量与一次真 HBM 往返，代价不同。

### 2.3 先分清两种等待，再选择优化

对单个 kernel，用给定层级的有效带宽 $B$、对应指令的有效算力 $F$、流量 $Q$ 与算术量 $W$ 粗略估计：

$$
t_{\rm kernel}\approx t_{\rm launch}+\max(Q/B,\ W/F).
$$

这是**假设访存与计算充分重叠**的工作模型，不是精确计时器。串行的三个 kernel 分别取最大值再求和，不能先把三个算术量与字节量相加再一概取最大值。若启动与其他工作部分重叠、访问未达稳态、依赖未隐藏或缓存命中，这个模型会偏离。$B$、$F$ 应是针对操作类型与内存层级的可用吞吐；不能直接拿 Tensor Core 的 BF16 峰值代入本例的逐元素 FP32。

算术强度 $I=W/Q$：本例分离约 $2/24=0.083$ FLOP/B，融合约 $2/8=0.25$ FLOP/B。假定 $F/B=10$ FLOP/B，两者都在带宽侧；如果向量很短，5 μs 启动本身反而主导。融合把点向右移并减少启动，但**如何兑现速度取决于缓存、实现、并行度及真实利用率**。

## 3. 承重墙推导：融合在哪些边界会失效

### Step 1　逐元素数据依赖决定可以省下哪些访问

一个输出元素只依赖同一索引的 $x_i$、标量 $a,b$，所以同一个线程可依次算出 $t_{1,i}$、$t_{2,i}$ 和 $y_i$。中间结果不必公开给其他 kernel 或线程。三次独立 kernel 的每阶段流量为 $8N$，因此

$$
t_{\rm sep}=3\tau+2\max(8N/B,\ N/F)+8N/B
\approx3\tau+24N/B,
\qquad
t_{\rm fused}=\tau+\max(8N/B,\ 2N/F)
\approx\tau+8N/B.
$$

第一式中乘、加各算 1 FLOP，ReLU 的比较不计入 FLOP；三阶段均为带宽受限。融合可利用硬件 fused multiply-add（FMA），但 FMA 一次舍入，而分离乘加各舍入一次，结果不保证逐位相同。第 4 节关闭 Triton 的 FP 融合并用容差验证输出；真实训练仍需检查前向与反向误差、NaN、Inf、边界与 dtype。

### Step 2　中间结果被两个输出使用，并不等于必须读写两次

换一个计算图：$u_i=f(x_i)$，$y_i=\operatorname{ReLU}(u_i)$，$z_i=u_i+c$。假设 $f$ 需要 80 FLOP/元素，$z$ 的加法需要 1 FLOP。分离方案先算出 $u$，再各自算 $y,z$，三步总流量仍是 $24N$ B；融合方案一个线程先算一次 $u_i$，直接产生两个输出，只读一次 $x$、写一次 $y$ 和 $z$，为 $12N$ B，算术总量 81 FLOP/元素。

融合增加存活变量，可能减少有效吞吐。为说明权衡，假设融合后的带宽和算力**同时**变为原先的 $\eta$ 倍；这只是教学参数，不是寄存器数到速度的物理公式。使用相同的 $B=1$ TB/s、$F=10$ TFLOP/s、$\tau=5$ μs：

$$
\begin{aligned}
t_{\rm sep}&=3\tau+\max(8N/B,80N/F)+8N/B+\max(8N/B,N/F),\\
t_{\rm fused}&=\tau+\max(12N/(\eta B),81N/(\eta F)).
\end{aligned}
$$

$N=2^{20}$ 时，分离估算为 40.166 μs；$\eta=1$ 时融合为 17.583 μs，$\eta=0.35$ 时却为 **40.951 μs**。这组参数下解 $t_{\rm fused}=t_{\rm sep}$，得到持平阈值 $\eta\approx0.358$；低于阈值则融合反而慢。实际 $\eta$ 是否下降、带宽和算力是否下降相同，均需通过具体硬件测量。


【交互实验说明】：在上方融合盈亏预算图中，你可以调节**融合后相对吞吐 $\eta$**（从 0.20 到 1.0）与**向量长度 N**（从 $2^8$ 到 $2^{25}$）：
- 观察**融合后耗时曲线（绿线）与三个独立 kernel 耗时参考线（蓝实线）的交叉临界点（持平阈值 $\eta^*$）**；
- 在默认 $N=2^{20}$（约 100 万元素）下，三个独立 kernel 估算为 40.166 μs。由于融合算子需要在一个线程内同时驻留中间变量 $u_i$，如果增加的寄存器压力导致 SM 上可并发调度的 warp 数骤减，使得融合后的有效吞吐折损至 $\eta = 0.35$（低于临界持平阈值 $\eta^* \approx 0.358$），融合耗时反而反弹至 40.951 μs，此时“融合反而变慢”；
- 切换到【小向量也为 35%】预设（将向量长度缩小至 $N=1024$）：即便吞吐折损同样严重（$\eta = 0.35$），融合估算耗时依然从 15.025 μs 显著降低到 5.035 μs！因为对于小向量，省下的两次 5 μs launch 启动开销足以完全吸收吞吐折损的代价；
- 这直观说明了：算子融合并非稳赚不赔。对于大张量，若强行融合过多算子导致寄存器溢出（spill to local memory）或占用率严重暴跌，省下的显存带宽可能不足以对冲执行效率的倒退。把长度降到 1024，即使 $\eta=0.35$，估算仍从 15.025 μs 降到 5.035 μs：节约的两次启动足以补偿较低的吞吐。这个阈值只属于模型与当前大小，不可推广为某款卡的规则。[用 Python 复算吞吐损失与阈值](#section-4-2)

### Step 3　哪些融合变难，为什么

1. **跨元素依赖和归约**：softmax 的分母需要一行所有元素，不能仅像 ReLU 一样每个线程独立算完。分块归约、块内同步或在线归一化可支持融合，但行过大可能放不下片上资源；见 [Triton fused softmax 教程](https://triton-lang.org/main/getting-started/tutorials/02-fused-softmax.html)。
2. **多消费者与重复计算**：上例的两个消费者具有相同逐元素索引，可在同一线程共享 $u_i$；若消费者访问模式或调度不同，强行融合可能重复计算 $f$、需要额外同步，或难以让其他消费者继续复用 $u$。
3. **资源和并行度**：融合加重寄存器压力、产生 spill 或让一个巨大的块降低并发；还可能把原本优化良好的矩阵乘换成慢实现。是否发生由编译和 profile 决定。
4. **数值及随机性**：不同归约顺序、FMA、混合精度或随机数使用顺序会改变结果。需要按应用允许的容差测试，不能只核对输出形状。

这也是 [FlashAttention](/lessons/1-5.html) 的 IO 思路：按块扫描并在线维护 softmax 所需统计量，避免显式写出完整的注意力矩阵。它涉及跨元素归约与重新组织算法，不能简单套用“所有算子拼成一行”。原始算法和 IO 分析见 [FlashAttention 论文](https://arxiv.org/abs/2205.14135)。

### 4.2 双输出与吞吐损失

本段同样独立运行。下面的 `eta` 是人为假设，持平阈值使用当前例子中 12 B/元素的访存项，因为它比 81 FLOP/元素的计算项更慢。

```python
for n, eta in [(1048576, 1.0), (1048576, 0.35), (1024, 0.35)]:
    bw, peak = 1e6, 1e7  # B/us, FLOP/us
    stage_f = max(8 * n / bw, 80 * n / peak)
    relu = 8 * n / bw
    add = max(8 * n / bw, n / peak)
    separate = 15 + stage_f + relu + add
    fused = 5 + max(12 * n / (eta * bw), 81 * n / (eta * peak))
    threshold = (12 * n / bw) / (separate - 5)
    print(f"N={n:7d}, eta={eta:.2f}: 分离={separate:.3f} us, 融合={fused:.3f} us, "
          f"加速={separate/fused:.3f}x, 持平阈值={threshold:.3f}")
```

### 可运行例子 · Triton 的分块、边界和测量

Triton 中一个 program 负责一块数据，用 `program_id` 算块起点，`arange` 生成块内连续索引，`mask` 避免最后一块越界，`tl.load` / `tl.store` 只访问有效位置。一个 Triton program 通常映射到一个线程块，具体线程分配由编译器决定；`BLOCK=256` 是逻辑元素块大小，不等于保证有 256 个 CUDA 线程。参照 [Triton 向量加法教程](https://triton-lang.org/main/getting-started/tutorials/01-vector-add.html)。

先把下面保存成 `fusion_bench.py`。默认只打印 CPU 标量参考结果，任何标准 Python 都可运行；若机器配有兼容的 CUDA GPU、PyTorch 和 Triton，再用 `ACADEMY_RUN_CUDA=1 python3 fusion_bench.py` 运行真实 benchmark。GPU 分支会自行打印设备、软件版本及测到的时间；数字随硬件和软件改变，**不是下方固定输出，也不是上面的估算参数**。

```python
import os

def reference(values):
    return [max(0.0, 2.0 * x - 0.25) for x in values]

print("CPU 参考输出:", reference([-1.0, 0.0, 0.5, 1.0]))
if os.environ.get("ACADEMY_RUN_CUDA") != "1":
    print("GPU 未测量；设置 ACADEMY_RUN_CUDA=1 启动基准")
else:
    import torch
    import triton
    import triton.language as tl

    if not torch.cuda.is_available():
        raise RuntimeError("需要可用的 CUDA GPU 和对应的 PyTorch/Triton 环境")

    @triton.jit
    def fused_kernel(x_ptr, y_ptr, n, BLOCK: tl.constexpr):
        idx = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
        x = tl.load(x_ptr + idx, mask=idx < n, other=0.0)
        t1 = x * 2.0
        t2 = t1 - 0.25
        y = tl.maximum(t2, 0.0)
        tl.store(y_ptr + idx, y, mask=idx < n)

    n = 2**20 + 13  # 故意不整除 256，覆盖最后一个 block 的 mask
    x = torch.linspace(-1, 1, n, device="cuda", dtype=torch.float32)
    t1, t2 = torch.empty_like(x), torch.empty_like(x)
    eager_out, fused_out = torch.empty_like(x), torch.empty_like(x)

    def eager():
        torch.mul(x, 2.0, out=t1)
        torch.add(t1, -0.25, out=t2)
        torch.clamp(t2, min=0.0, out=eager_out)

    def fused():
        fused_kernel[(triton.cdiv(n, 256),)](
            x, fused_out, n, BLOCK=256, enable_fp_fusion=False
        )

    eager()
    fused()  # 首次调用编译；不放入计时
    torch.testing.assert_close(fused_out, eager_out, rtol=1e-6, atol=1e-6)

    def time_us(fn, repeats=200):
        for _ in range(30):
            fn()  # 预热
        torch.cuda.synchronize()
        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        for _ in range(repeats):
            fn()
        end.record()
        end.synchronize()
        return start.elapsed_time(end) * 1000 / repeats

    print(f"GPU: {torch.cuda.get_device_name(0)}; torch={torch.__version__}; "
          f"triton={triton.__version__}; N={n}")
    print(f"CUDA event 平均: eager={time_us(eager):.3f} us; "
          f"Triton={time_us(fused):.3f} us")
    print("输出校验通过（rtol=atol=1e-6）")
```

**运行结果**

```text
CPU 参考输出: [0.0, 0.0, 0.75, 1.75]
GPU 未测量；设置 ACADEMY_RUN_CUDA=1 启动基准
```

上面是本机执行**默认 CPU 分支**的实测输出。GPU 路径需要另有 CUDA 和 Triton，基准中的输出缓冲提前分配、编译和预热不计时；CUDA event 测的是同一 stream 上两事件之间经过的设备时间，可能包含设备等待 host 排队的空隙，不等于整个应用的端到端时间。它平均了 200 次连续调用，并复用输入和缓冲，缓存状态可能与生产不同。请重复多组、改变 $N$，用 profiler 看 kernel 数、实际内存层级的流量、寄存器和 spill，记录设备、版本与时钟；既比较正确性，也报告完整应用中的收益。[PyTorch CUDA 异步执行说明](https://docs.pytorch.org/docs/stable/notes/cuda.html#asynchronous-execution)解释了为什么普通的未同步 CPU 时钟不能直接当作 GPU 完成时间。

## 5. 实战直觉：何时让编译器做，何时自己写

### 5.1 `torch.compile` 能做什么

`torch.compile` 捕获可追踪的 PyTorch 计算图，后端可对捕获的部分做优化，包括一些逐元素运算的融合；是否融合、采用何种内核依赖后端、版本、形状和 dtype，不能从 Python 表达式直接保证。矩阵乘可能交给高性能库，某些后端也能融合特定 epilogue；归约也可能得到融合，不应把它们一概当成禁止融合的边界。

数据依赖的 Python 控制流、取出张量标量等可能导致 [graph break](https://docs.pytorch.org/docs/stable/compile/programming_model.common_graph_breaks.html)，版本和配置会影响具体行为。图断裂让编译器在断点处分段，跨段优化受到限制；即便没有图断裂，寄存器和算法代价也可能使编译器选择不融合。动态形状和 guard 失效可能产生重编译；首次编译时间、预热及稳态运行要分开报告。参考 [PyTorch 官方教程](https://docs.pytorch.org/tutorials/intermediate/torch_compile_tutorial.html)。

实际顺序是：固定任务和输入分布 → profile 找到频繁、耗时或同步密集的内核 → 先量 eager 与 compile 的正确性和稳态性能 → 检查图断裂、内核数和访存 → 确实存在有价值的瓶颈，再考虑 Triton 或 CUDA。优化一个仅占总延迟 5% 的片段，即使把它加速到无限快，端到端也最多加速 $1/(1-0.05)\approx1.053$ 倍。若多种改法一起比较，还应计入编译成本、部署复杂度和不同形状的退化。

### 5.2 2026 实践视角

手写融合仍常用于编译器难以覆盖的结构，如特殊 attention、量化数据格式或自定义布局；同一项工作也可能被后续编译器版本吸收。版本固定并保留基准是必要的。FlashAttention 系列体现的是算法、数值稳定与硬件调度共同设计，逐元素融合只是最小入口。不要将某个硬件上的 kernel 提升直接写成整个模型或所有 batch 的提升；例如 [1.5 注意力](/lessons/1-5.html) 的训练与 decode 就有不同的流量形态。

### 5.3 两道迁移练习（含答案）

**练习一：** 假定 FP32 向量 $y=\operatorname{ReLU}(ax+b)$ 的中间结果都真实往返某内存层级，$N=2^{20}$，带宽 1 TB/s，忽略启动和计算。三次与一次 kernel 的流量和时间各是多少？

**答案：** 三次共 $24N=25,165,824$ B，约 25.166 μs；融合 $8N=8,388,608$ B，约 8.389 μs。两次中间写读共节省 $16N$ B。缓存命中或实际融合后吞吐改变，会使实测偏离。

**练习二：** 一个算子组只占端到端延迟 20%，单独加速 4 倍，其余部分不变。最终最多加速多少？如果 kernel 的 GPU event 时间降了但服务 p99 没变，下一步看什么？

**答案：** Amdahl 定律给 $1/(0.8+0.2/4)=1/0.85\approx1.176$ 倍。检查优化是否覆盖真实形状与流量，再拆分调度、排队、通信、数据传输和其他算子；kernel event 不直接包含整个服务路径。

## 6. 3 分钟记忆唤醒自测

1. 一个 NVIDIA warp、一个 block 和一个 SM 的关系是什么？更高 occupancy 为什么不一定更快？
2. 对 $\operatorname{ReLU}(ax+b)$，24 B 与 8 B 的计算假设了什么？什么时候这个数字不是 HBM 流量？
3. `torch.compile` 没报错是否保证融合？如何分离编译、预热、设备时间与端到端时间？

答案：warp 是常见的 32 线程执行组，block 由多个 warp 组成并调度到 SM；占用率只是隐藏延迟的条件之一。24 B 与 8 B 假设 FP32 全局读写且中间结果分别落地，缓存和其他消费者会改变 HBM 流量。编译不保证融合；查看图断裂和 profiler，预热后用同步的设备事件测 kernel，再另量应用端到端。
