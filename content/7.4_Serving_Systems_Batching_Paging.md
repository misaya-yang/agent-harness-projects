# 7.4 推理服务系统

> **一句话核心直觉**：decode 受带宽限制，一次前向服务 1 个请求和 256 个请求，读的权重一样多，所以推理服务的全部功夫在于**把 batch 做大，同时让首 token 延迟（TTFT）和每 token 延迟（TPOT）留在可接受的范围内**。静态批处理在两处浪费：一批要等最长的那条结束（输出长度服从指数分布时利用率只有 $1/H_B$，$B = 32$ 时约 25%），KV 按最大长度预留（真正存了 token 的不到四成）。连续批处理按 token 步调度，结束一条就补进一条；PagedAttention 把 KV 切成 16 个 token 的页，用页表映射，浪费只剩最后一页，还能在请求之间共享前缀。前缀缓存用链式哈希识别相同的前缀，多轮对话和 Agent 的 prefill 量可以少一个数量级。长 prompt 的 prefill 一步就要上百毫秒，会卡住所有正在 decode 的请求；分块 prefill 给每步设一个 token 预算，用略高的 TTFT 换平稳的 TPOT。prefill 受算力限制、decode 受带宽限制，把两者分到不同的 GPU 上，可以各自选择最合适的并行方式。
> **唤醒标签**：TTFT / TPOT / goodput · batch 几乎免费 · 静态批处理利用率 $1/H_B$ · 预留 KV 只用了 20%–38% · Orca：按迭代调度 36.9× · 页 = 16 token · 页表 + 写时复制 · vLLM 2–4× · 链式块哈希 · RadixAttention · DeepSeek 56.3% 命中磁盘 KV 缓存 · 长 prefill 卡住 decode · 分块 prefill：token 预算 · PD 分离 · 注意力算术强度 MHA 1、GQA 4、MLA 242

## 1. 问题：一张 GPU 同时服务几百个用户

先看一个真实系统的规模。DeepSeek 在 2025 年 2 月公开了一天（24 小时）的线上统计：

- 输入 6080 亿 token，其中 3420 亿（56.3%）命中了磁盘上的 KV 缓存；输出 1680 亿 token。
- 每个用户看到的输出速度平均 20–22 token/s，平均每个输出 token 对应的 KV 长度是 4,989。
- 每个 H800 节点（8 卡）在 prefill 时平均每秒处理约 7.37 万个输入 token，在 decode 时每秒输出约 1.48 万个 token。
- prefill 和 decode 分开部署：prefill 每个单元 4 个节点，decode 每个单元 18 个节点。

这些数字背后是本课的几个主题：KV 缓存（56.3% 的输入不用重算）、批处理（一个节点每秒输出 1.48 万 token，而每个用户只有 20 token/s，说明同时服务着几百条请求）、PD 分离（两个阶段用不同规模的部署）。

衡量一个推理服务，常用这几个指标：

- **TTFT**（time to first token）：从请求到达到第一个 token 返回。包括排队和 prefill。
- **TPOT**（time per output token）：第一个 token 之后，平均每个 token 的间隔。决定用户看到的"打字速度"。
- **吞吐**：每秒总共输出多少 token，决定成本。
- **goodput**：在满足 TTFT 和 TPOT 要求（SLO）的前提下能承受的请求速率。DistServe 认为这才是该优化的目标：吞吐再高，如果一半请求超时也没有意义。

为什么 batch 是核心？§10.6 用屋脊线算了 Llama-3-8B 在 H100 上的 decode（上下文 512）：

| batch | 每 token 延迟 | 总吞吐 |
|---|---|---|
| 1 | 4.8 ms | 208 token/s |
| 16 | 5.1 ms | 3,128 token/s |
| 64 | 6.1 ms | 10,533 token/s |
| 256 | 9.9 ms | 25,800 token/s |

batch 从 1 增加到 256，每个用户的 token 只慢了一倍，总吞吐却涨了 124 倍：读一遍权重的成本被 256 个请求分摊了。推理服务的设计，就是在显存和延迟的约束下让 batch 尽量大。

## 2. 静态批处理的两种浪费

最朴素的做法是攒一批请求，一起 prefill，一起 decode，全部结束再处理下一批。

### 2.1 一批要等最长的那条

每条请求的输出长度不同。一批 $B$ 条里，先结束的请求只能空等，直到最长的那条结束。decode 的利用率是

$$
\text{利用率} = \frac{\mathbb{E}\big[\sum_i o_i\big]}{B\cdot\mathbb{E}[\max_i o_i]} = \frac{\mathbb{E}[o]}{\mathbb{E}[\max_i o_i]}
$$

若输出长度服从均值为 $\mu$ 的指数分布，$B$ 个独立样本的最大值的期望是 $\mu H_B$，$H_B = 1 + \frac{1}{2} + \cdots + \frac{1}{B}$ 是调和数（最大值可以拆成依次出现的 $B$ 个间隔，第 $k$ 个间隔是 $B - k + 1$ 个指数变量的最小值，均值 $\mu/(B-k+1)$）。所以利用率约为 $1/H_B$：$B = 32$ 时 $H_{32} = 4.06$，**利用率只有 24.6%**。§10.2 用截断到 1024 的几何分布模拟，得到 27.9%。batch 越大，最长的那条越长，浪费越严重。新到的请求还要等当前这一批全部结束，所以 TTFT 也很差。

### 2.2 KV 按最大长度预留

请求开始时不知道会生成多长，早期系统按最大长度给每条请求预留一块连续的 KV 显存。§10.3 用典型的长度分布（prompt 中位数 800、输出均值 250、最大长度 8192）估算，**预留的显存只有 17.4% 真正存了 token**。vLLM 的作者实测了当时的系统，只有 20.4%–38.2% 的 KV 显存存的是真实的 token 状态。

显存浪费直接限制了 batch：H100 上扣掉 8B 模型的权重，能放约 42.7 万个 token 的 KV；按 8192 预留只能同时服务 52 条请求，按实际长度可以服务约 300 条（§10.3）。

## 3. 连续批处理：按 token 步调度

Orca 提出**迭代级调度**：调度的单位不是一个请求，而是模型的一次前向（一个 token 步）。每一步：

1. 已经结束的请求立刻离开，返回结果；
2. 等待中的请求只要显存够就加入，在这一步做 prefill；
3. 所有在跑的请求各 decode 一个 token。

这需要解决一个技术问题：同一个 batch 里的请求长度各不相同，有的在 prefill 几百个 token，有的在 decode 1 个 token，没法拼成规整的张量。Orca 的**选择性批处理**观察到：线性层（QKV 投影、FFN）对每个 token 独立计算，可以把所有请求的 token 拼成一个长序列一起算；只有注意力需要按请求分开，每个请求只看自己的 KV。在 GPT-3 175B 上，Orca 在相同延迟下比 FasterTransformer 吞吐高 36.9 倍。今天所有主流推理框架（vLLM、SGLang、TensorRT-LLM）都是连续批处理。

## 4. PagedAttention：给 KV 分页

### 4.1 机制

连续批处理解决了"等最长的那条"，但 KV 显存还是要按最大长度预留，否则请求生成到一半可能没有地方放新的 KV。vLLM 借用操作系统的虚拟内存：

- 把 KV 缓存切成固定大小的**块**（页），默认每块 16 个 token；
- 每个请求有一张**块表**，把逻辑上连续的 token 位置映射到物理上不连续的块；
- 请求每生成满 16 个 token，再分配一个新块。

浪费只剩每个请求最后一个没填满的块，平均 7.5 个 token。§10.3 的同一组请求，分页之后利用率是 **99.47%**。代价在内核里：注意力要通过块表间接寻址，从不连续的块里读 K 和 V；块太小寻址开销大，太大浪费多，16 是折中。

### 4.2 共享与写时复制

块表让多个请求可以**指向同一个物理块**：

- **并行采样**：同一个 prompt 采 $n$ 个回答，prompt 的 KV 只存一份，$n$ 个序列的块表都指向它。
- **beam search**：候选之间共享公共前缀的块。
- **写时复制**：每个块有引用计数，某个序列要往一个共享块里写新 token 时，才复制一份。

这些共享让 vLLM 在并行采样和 beam search 时省下更多显存。论文报告在相同延迟下吞吐是 FasterTransformer 和 Orca 的 2–4 倍，序列越长、模型越大、解码算法越复杂，优势越明显。

### 4.3 显存不够时

请求的 KV 一直在增长，显存可能被占满。这时要**抢占**一些请求：把它们的 KV 换出到 CPU 内存，或者直接丢掉、之后重新 prefill。重算听起来浪费，但 prefill 是算力受限的高效计算，对短一些的上下文往往比在 PCIe 上来回搬运更快。

## 5. 前缀缓存：相同的前缀只算一次

### 5.1 链式块哈希

很多请求共享相同的开头：系统提示、工具定义、few-shot 示例、多轮对话的历史、Agent 的已有轨迹。它们的 KV 完全一样，没有必要重算。

识别相同前缀的方法是给每个**满块**算一个哈希，哈希的输入包括**前一个块的哈希**和本块的 token：

$$
h_b = \mathrm{hash}(h_{b-1},\ \text{token}_{16b}, \dots, \text{token}_{16b+15})
$$

于是 $h_b$ 相同等价于从开头到第 $b$ 块的整个前缀都相同，一张"哈希 → 物理块"的表就能找到可复用的 KV。vLLM 的自动前缀缓存就是这样做的；SGLang 的 RadixAttention 用基数树组织所有缓存的前缀，按 LRU 淘汰，在 Agent、few-shot、多轮对话等任务上吞吐最高提升 6.4 倍。

### 5.2 前缀缓存值多少钱

§10.5 模拟了两种场景：

- **多轮对话**：1200 token 的系统提示，50 个用户各聊 4 轮。输入一共 40.5 万 token，**82.7% 命中缓存**，真正需要 prefill 的只有 7.0 万。
- **Agent 循环**：起始上下文 3000 token，30 轮，每轮追加 1500 token 的工具输出和 200 token 的模型输出。不缓存时每轮都要把整个上下文重新 prefill，总量是轮数的平方级：0.83M token；缓存后只算每轮新增的部分：0.052M token，**少 15.9 倍**。按 8B 模型的理想算力，prefill 时间从 13.5 秒降到 0.85 秒。

API 的定价反映了这一点。DeepSeek-R1 的价格是每百万输入 token 缓存未命中 0.55 美元、命中 0.14 美元（约四分之一），上面的 Agent 循环不缓存要 0.456 美元，缓存后 0.138 美元。DeepSeek 甚至把 KV 缓存放在磁盘上，一天的输入有 56.3% 命中。

前缀缓存要求**逐 token 完全相同**，这对 prompt 的写法有直接影响：

- 稳定的内容放前面（系统提示、工具定义、文档），变化的内容放后面（用户问题）；
- 不要在系统提示开头放时间戳、请求 ID 这类每次都变的东西，否则后面所有块的哈希都变了；
- 多轮对话要原样保留历史，改写或截断中间的轮次会让后面的缓存全部失效。

Kimi 的 Mooncake 把这个思路推到集群级别：以 KV 缓存为中心设计整个架构，用集群里的 CPU 内存和 SSD 组成一个大的 KV 缓存池，调度时优先把请求发给已经缓存了它前缀的节点。真实负载下，这让 Kimi 能多处理 75% 的请求。

## 6. 调度：TTFT 与 TPOT 的拉锯

### 6.1 长 prefill 会卡住所有人

连续批处理里，新请求在加入的那一步做完整个 prefill。一个 8000 token 的 prompt，prefill 需要 $2\times 8.03\times 10^9\times 8000 \approx 1.3\times 10^{14}$ FLOPs，理想情况下约 130 ms。这一步里，所有正在 decode 的请求都在等：平时 6–10 ms 一个 token，现在突然卡了一百多毫秒。用户看到的就是输出过程中莫名其妙的停顿。

§10.4 写了一个调度模拟器（Llama-3-8B，H100，理想屋脊线；请求按泊松过程到达，prompt 长度中位数 800、最长 8000，输出长度均值 250）：

| 到达率 | 策略 | TTFT p50 | TTFT p99 | TPOT p50 | TPOT p99 | 吞吐 | 最长的一步 |
|---|---|---|---|---|---|---|---|
| 4/s | 静态批处理 | 3,091 ms | 7,197 ms | 5.9 ms | 6.8 ms | 977 | 822 ms |
| 4/s | 连续批处理 | 18 ms | 122 ms | 5.4 ms | 7.6 ms | 987 | 147 ms |
| 4/s | 连续 + 分块 prefill | 18 ms | 121 ms | 5.2 ms | 6.2 ms | 987 | 10 ms |
| 16/s | 静态批处理 | 47 s | 94 s | 7.3 ms | 8.2 ms | 1,473 | 1,299 ms |
| 16/s | 连续批处理 | 23 ms | 160 ms | 8.7 ms | 16.0 ms | 3,830 | 148 ms |
| 16/s | 连续 + 分块 prefill | 26 ms | 164 ms | 6.9 ms | 8.4 ms | 3,862 | 10 ms |
| 32/s | 连续批处理 | 52 ms | 362 ms | 25.2 ms | 44.2 ms | 6,103 | 292 ms |
| 32/s | 连续 + 分块 prefill | 77 ms | 430 ms | 9.1 ms | 10.3 ms | 7,347 | 10 ms |

（吞吐单位是 token/s。）几个现象：

- **静态批处理在低负载下 TTFT 就要 3 秒**（新请求要等当前一批结束），负载一高吞吐卡在约 1,500 token/s，排队时间涨到几十秒：服务能力不够时，等待时间会随负载急剧上升。
- **连续批处理的 TTFT 降了两个数量级**，但到了 32/s，大量 prefill 挤在一起，最长的一步 292 ms，TPOT 的 p99 涨到 44 ms。

### 6.2 分块 prefill

Sarathi-Serve 的做法是给每一步设一个 **token 预算**（比如 512）：先给所有正在 decode 的请求各 1 个 token，剩下的预算分给等待 prefill 的请求，长 prompt 切成多块，分几步做完。这样每一步的计算量都差不多，decode 永远不会被长 prefill 卡住。

上表里分块之后，最长的一步从一两百毫秒降到 10 ms，32/s 时 TPOT 的 p99 从 44 ms 降到 10 ms，吞吐反而从 6,103 升到 7,347：每一步都处在接近屋脊点的位置，既不浪费带宽也不浪费算力。代价是 TTFT 略有上升（p50 从 52 ms 到 77 ms），因为长 prompt 要分几步才做完。Sarathi-Serve 在尾延迟约束下，让 Mistral-7B（单张 A100）的服务能力达到 vLLM 的 2.6 倍，Yi-34B（两张 A100）达到 3.7 倍。

token 预算怎么选？每一步要读一遍权重（约 4.8 ms），预算太小，计算量填不满这段时间，算力闲置；预算太大，又回到长步卡住 decode 的问题。H100 的屋脊点约 295 FLOP/字节，对应每步大约几百个 token，所以 512 是常见的起点，再按 TPOT 的 SLO 调整。


## 7. Prefill 与 decode 分离

分块 prefill 让两种阶段和平共处，但它们的性质终究不同：prefill 受算力限制，适合较小的张量并行、追求每张卡的算力利用率；decode 受带宽限制，需要大 batch，对 MoE 来说还需要很大的专家并行把每个专家的 batch 凑大。放在同一组 GPU 上，两者互相干扰，也只能用同一种并行方式。

**PD 分离**把 prefill 和 decode 放到不同的 GPU 上：prefill 节点算完 prompt 的 KV，通过高速网络传给 decode 节点。DistServe 按 TTFT 和 TPOT 的要求分别为两个阶段选择资源和并行方式，在保证 90% 以上请求满足延迟要求的前提下，能多服务 7.4 倍的请求，或满足 12.6 倍严格的 SLO。Splitwise 用同样的思路设计集群，在成本降低 20% 的同时吞吐提升 1.4 倍。DeepSeek 的线上服务也是这样：prefill 用 4 个节点、32 路专家并行，decode 用 18 个节点、144 路专家并行，每张卡只放 2 个路由专家。

代价是传输 KV。Llama-3-8B 一个 4K token 的 prompt，KV 是 512 MiB，按 50 GB/s（400 Gb/s 网卡）约 10.7 ms，而 prefill 本身理想情况下要 67 ms，传输只占一小部分，而且可以按层流水起来，边算边传。MLA 把每 token 的 KV 压到 68.6 KiB（DeepSeek-V3，§10.1），对 PD 分离更友好。

## 8. 注意力的算术强度：为什么 decode 一直在读 KV

§1 的表里，batch 增大时吞吐一路上涨，因为权重的读取被分摊了。但 KV 不一样：**每条序列有自己的 KV，batch 再大也无法分摊**。看一层注意力在 decode 时每读 1 字节 KV 能做多少计算（§10.6）：

| 注意力 | 每个 token 的 KV（每层） | FLOP / 字节 |
|---|---|---|
| MHA（32 个 KV 头） | 16 KiB | 1.0 |
| GQA（8 个 KV 头，Llama 3） | 4 KiB | 4.0 |
| MLA（DeepSeek-V3，128 个头共享 576 维潜向量） | 1.1 KiB | 241.8 |

H100 的屋脊点约 295 FLOP/字节。MHA 和 GQA 的 decode 注意力离它差了两个数量级，**无论 batch 多大都受带宽限制**，长上下文时读 KV 的时间甚至超过读权重：上下文 8192 时，batch 16 的每 token 延迟从 5.1 ms 涨到 9.9 ms，batch 64 已经放不下了（§10.6）。这就是 GQA、MLA 对推理服务如此重要的原因（→ 1.3）：GQA 让一份 KV 被 4 个查询头复用；MLA 让 128 个头共享同一个 576 维的潜向量，算术强度接近屋脊点。DeepSeek 的 FlashMLA 内核在 H800 上做到了 660 TFLOPS，decode 注意力从带宽受限变成了算力受限。


## 9. 与 1.3、5.1、7.2、7.3 的联系

- **1.3 KV 缓存、GQA 与 MLA**：KV 的大小决定能同时服务多少请求、每步要读多少字节；MLA 把注意力的算术强度推到屋脊点附近（§8）。
- **5.1 屋脊线**：本课所有的时间估算都是 $\max(\text{字节}/\text{带宽}, \text{FLOPs}/\text{算力})$；分块 prefill 的预算就是让每一步落在屋脊点附近。
- **7.2 投机解码**：batch 越大，投机解码的收益越小，甚至亏损；长上下文时 decode 一直受带宽限制，投机解码又重新有效。调度器要根据负载决定开不开。
- **7.3 量化**：FP8 / FP4 的 KV 缓存让同样的显存放下更多请求；权重量化减少每步读取的字节。

## 10. 从零实现

### 10.1 KV 的账

```python
import numpy as np, hashlib
def kv_bytes(layers, kv_heads, head_dim, nbytes=2):     # K 和 V，每层每个 KV 头
    return 2 * layers * kv_heads * head_dim * nbytes
for name, b in [("Llama-3-8B（GQA 8 头）", kv_bytes(32, 8, 128)), ("Llama-3-70B（GQA 8 头）", kv_bytes(80, 8, 128)),
                ("假想的 8B MHA（32 头）", kv_bytes(32, 32, 128)), ("DeepSeek-V3（MLA 576 维）", 61 * 576 * 2)]:
    print(f"{name:24s} 每 token {b / 1024:6.1f} KiB   8K 上下文一条 {b * 8192 / 2**30:5.2f} GiB")
b4k = kv_bytes(32, 8, 128) * 4096
```

### 10.4 调度模拟器：静态、连续、分块 prefill

```python
N, WB, KV, L, D = 8.03e9, 16.06e9, 131072, 32, 4096      # Llama-3-8B
BW, PEAK = 3.35e12, 989e12                               # H100，理想屋脊线
CAP = int((80e9 * 0.9 - WB) / KV)
def step_time(kv_tokens, new_tokens, attn_flops):        # 一步 = max(读权重和 KV, 计算)
    return max((WB + kv_tokens * KV) / BW, (2 * N * new_tokens + attn_flops) / PEAK)

def make_requests(n, rate, seed=0):
    rng = np.random.default_rng(seed)
    t = np.cumsum(rng.exponential(1 / rate, n))          # 泊松到达
    prompt = np.clip(rng.lognormal(np.log(800), 0.9, n), 32, 8000).astype(int)
    out = np.clip(rng.geometric(1 / 250, n), 2, 1024)
    return [dict(arr=a, p=int(p), o=int(o)) for a, p, o in zip(t, prompt, out)]

def simulate(reqs, policy, max_batch=256, budget=512, max_len=8192):
    reqs = [dict(r, done_p=0, gen=0, first=None, end=None) for r in reqs]
    now, i, waiting, running, steps = 0.0, 0, [], [], []
    t_last, emitted = reqs[-1]["arr"], 0
    while i < len(reqs) or waiting or running:
        while i < len(reqs) and reqs[i]["arr"] <= now: waiting.append(reqs[i]); i += 1
        if not waiting and not running: now = reqs[i]["arr"]; continue
        new_tok, attn, emit = 0, 0.0, []
        if policy == "static":
            if not running:                              # 上一批全部结束才组新的一批；KV 按最大长度预留
                k = min(len(waiting), max_batch, CAP // max_len)
                running, waiting = waiting[:k], waiting[k:]
            for r in running:
                if r["done_p"] < r["p"]:
                    c = r["p"]; new_tok += c; attn += 4 * L * D * c * c / 2; r["done_p"] = c; emit.append(r)
                elif r["gen"] < r["o"]:
                    new_tok += 1; attn += 4 * L * D * (r["p"] + r["gen"]); emit.append(r)
            kv_now = sum(r["p"] + r["gen"] for r in running)
        else:
            used = sum(r["done_p"] + r["gen"] for r in running)
            left = budget if policy == "chunked" else 10**9
            for r in running:                            # 先给 decode 中的请求各 1 个 token
                if r["done_p"] == r["p"]:
                    new_tok += 1; attn += 4 * L * D * (r["p"] + r["gen"]); emit.append(r); left -= 1
            while waiting and len(running) < max_batch and used + waiting[0]["p"] + waiting[0]["o"] <= CAP:
                r = waiting.pop(0); running.append(r); used += r["p"] + r["o"]     # 分页：按实际长度
            for r in running:                            # 剩下的预算给 prefill，可以分块
                if r["done_p"] < r["p"] and left > 0:
                    c = min(r["p"] - r["done_p"], left)
                    attn += 4 * L * D * c * (r["done_p"] + c / 2); new_tok += c; left -= c; r["done_p"] += c
                    if r["done_p"] == r["p"]: emit.append(r)
            kv_now = sum(r["done_p"] + r["gen"] for r in running)
        dt = step_time(kv_now, new_tok, attn); now += dt; steps.append(dt)
        if now <= t_last: emitted += len(emit)
        for r in emit:
            r["gen"] += 1
            if r["first"] is None: r["first"] = now
            if r["gen"] >= r["o"]: r["end"] = now
        if policy == "static":
            if all(r["end"] is not None for r in running): running = []
        else:
            running = [r for r in running if r["end"] is None]
    ttft = np.array([r["first"] - r["arr"] for r in reqs]) * 1e3
    tpot = np.array([(r["end"] - r["first"]) / (r["o"] - 1) for r in reqs]) * 1e3
    return (np.median(ttft), np.percentile(ttft, 99), np.median(tpot), np.percentile(tpot, 99),
            emitted / (t_last - reqs[0]["arr"]), max(steps) * 1e3)

for rate in (4, 16, 32):
    reqs = make_requests(1000, rate)
    for pol in ("static", "continuous", "chunked"):
        a, b, c, d, thr, stall = simulate(reqs, pol)
        print(f"λ={rate:2d}/s {pol:10s} TTFT p50 {a:7.0f} p99 {b:7.0f} ms | TPOT p50 {c:5.1f} p99 {d:5.1f} ms | 吞吐 {thr:5.0f} | 最长一步 {stall:5.0f} ms")
```

### 10.5 前缀缓存：链式块哈希

```python
rng = np.random.default_rng(1)
BLOCK = 16
class PrefixCache:
    def __init__(self): self.blocks = {}                 # 块哈希 → 物理块编号
    def lookup_and_insert(self, tokens):
        h, hit = b"", 0
        for b in range(len(tokens) // BLOCK):            # 只有满块才缓存
            chunk = np.asarray(tokens[b * BLOCK:(b + 1) * BLOCK], np.int32).tobytes()
            h = hashlib.sha256(h + chunk).digest()       # 链式：哈希依赖整个前缀
            if h in self.blocks and hit == b * BLOCK: hit += BLOCK
            else: self.blocks.setdefault(h, len(self.blocks))
        return hit
system = list(rng.integers(0, 128000, 1200))             # 系统提示 + 工具定义
cache, total, hits = PrefixCache(), 0, 0
for user in range(50):                                   # 50 个用户，各聊 4 轮
    convo = system + list(rng.integers(0, 128000, 300))
    for turn in range(4):
        hit = cache.lookup_and_insert(convo); total += len(convo); hits += hit
        convo = convo + list(rng.integers(0, 128000, 350))   # 回答 200 + 下一问 150
print(f"多轮对话：输入 {total:,} token，命中 {hits:,}（{hits / total:.1%}），真正 prefill {total - hits:,}")
ctx, no_cache, with_cache = 3000, 0, 0
for turn in range(30):                                   # Agent：每轮追加 1500 工具输出 + 200 模型输出
    no_cache += ctx; with_cache += ctx if turn == 0 else 1700; ctx += 1700
print(f"30 轮 Agent：prefill {no_cache / 1e6:.2f}M → {with_cache / 1e6:.3f}M token（少 {no_cache / with_cache:.1f} 倍），"
      f"理想 prefill 时间 {no_cache * 2 * 8.03e9 / 989e12:.1f} s → {with_cache * 2 * 8.03e9 / 989e12:.2f} s")
cost = lambda miss, hit: (miss * 0.55 + hit * 0.14) / 1e6     # DeepSeek-R1：未命中 / 命中，美元每百万 token
print(f"按 DeepSeek 的价格：${cost(no_cache, 0):.3f} → ${cost(with_cache, no_cache - with_cache):.3f}")
# 多轮对话：输入 405,000 token，命中 334,800（82.7%），真正 prefill 70,200
# 30 轮 Agent：prefill 0.83M → 0.052M token（少 15.9 倍），理想 prefill 时间 13.5 s → 0.85 s
# 按 DeepSeek 的价格：$0.456 → $0.138
```

## 11. 实战直觉、避坑与面试深挖

**与工程 / 应用的连接**
- **先定 SLO 再调参数**：交互式产品关心 TTFT 和 TPOT 的 p99，离线批处理只关心吞吐。最大 batch、分块预算、是否开投机解码都要按 SLO 调，而不是追求峰值吞吐。
- **为前缀缓存设计 prompt**：稳定的内容放前面，变化的放后面，不要在开头放时间戳；Agent 框架要原样追加历史，不要改写中间的轮次。缓存命中率是推理成本最大的单一杠杆之一。
- **长上下文看 KV**：长上下文服务的瓶颈是 KV 的显存和带宽，而不是权重。GQA / MLA、FP8 KV、前缀缓存和分页都在解决这件事。
- **规模上去之后考虑 PD 分离**：两个阶段的并行方式、硬件甚至机器类型都可以不同；代价是 KV 传输和更复杂的调度。

**常见误区 / 反直觉点**
1. **"batch 越大，每个用户越慢，所以要小 batch"** ✗：decode 受带宽限制，batch 从 1 到 256 每 token 只慢一倍，总吞吐涨 124 倍。真正的约束是显存和 TPOT 的 SLO。
2. **"连续批处理就是动态攒 batch"** ✗：关键在调度粒度是一个 token 步，请求随时进出；配合选择性批处理，不同长度、不同阶段的请求才能在一步里一起算。
3. **"分页只是省了一点显存"** ✗：预留时只有约 17%–38% 的 KV 显存存了真实 token；分页之后能同时服务的请求从 52 条变成约 300 条，batch 大了吞吐才上得去。还顺带带来了前缀共享和写时复制。
4. **"前缀缓存只要内容差不多就能命中"** ✗：要求逐 token 完全相同，并且是从开头起的前缀；开头一个时间戳就让整个缓存失效。
5. **"batch 足够大，decode 就会变成算力受限"** ✗：权重的读取能被 batch 分摊，KV 不能。MHA / GQA 的 decode 注意力算术强度只有 1–4，永远受带宽限制；只有 MLA 这类共享潜向量的设计能接近屋脊点。

**高频深挖题**
- **Q1：静态批处理浪费在哪里？连续批处理怎样解决？**
  思路：等最长的那条，指数分布下利用率 $1/H_B$ → 新请求要等整批结束，TTFT 差 → KV 按最大长度预留 → Orca：按 token 步调度 + 选择性批处理（线性层拼 token，注意力按请求分开）→ 加分项：36.9×；分页解决预留。
- **Q2：PagedAttention 的原理是什么？带来了哪些额外好处？**
  思路：KV 切成 16 token 的块，块表映射逻辑位置到物理块 → 浪费只剩最后一块 → 并行采样、beam search 共享块，写时复制 → 前缀缓存的基础 → 加分项：内核要间接寻址；抢占时换出或重算。
- **Q3：前缀缓存怎样识别相同的前缀？为什么它对 Agent 特别值钱？**
  思路：每个满块的哈希依赖前一块的哈希 → 哈希相同 = 整个前缀相同 → Agent 每轮重新 prefill 整个上下文，总量是平方级 → 缓存后只算新增部分（30 轮少 15.9 倍）→ 加分项：RadixAttention、Mooncake；prompt 的写法。
- **Q4：为什么长 prompt 会让其他用户的输出卡顿？怎样解决？**
  思路：连续批处理在一步里做完整个 prefill，8K token 约 130 ms，所有 decode 都在等 → 分块 prefill：每步 token 预算，decode 优先 → TPOT 平稳，吞吐甚至更高，TTFT 略升 → 加分项：预算的选择与屋脊点；PD 分离是更彻底的方案。
- **Q5：GQA 和 MLA 对推理服务的价值是什么？**
  思路：decode 时 KV 无法被 batch 分摊 → 算术强度 MHA 1、GQA 4、MLA 242，屋脊点 295 → KV 越小，同样显存放越多请求、每步读得越少 → MLA 让 decode 注意力接近算力受限（FlashMLA 660 TFLOPS）→ 加分项：PD 分离时传输的 KV 也更小。

## 12. 练习（附解答）

**练习 1**　Llama-3-70B（80 层，8 个 KV 头，头维度 128，bf16）部署在 8 张 H100 上（共 640 GB），权重 141 GB，显存利用率 0.9。平均上下文 4K 时，最多能同时服务多少条请求？

> **解答**：每 token 的 KV 是 $2\times 80\times 8\times 128\times 2 = 327{,}680$ 字节（320 KiB），一条 4K 请求 1.25 GiB（1.34 GB）。可用于 KV 的显存是 $640\times 0.9 - 141 = 435$ GB，可放 $435/1.34 \approx 324$ 条。如果按最大长度 32K 预留，每条要 10.7 GB，只能放 40 条。

**练习 2**　输出长度服从均值 200 的指数分布，静态批处理 $B = 8$。decode 的利用率约是多少？$B = 128$ 呢？

> **解答**：$H_8 = 1 + 1/2 + \cdots + 1/8 = 2.718$，利用率约 $1/2.718 = 36.8\%$。$H_{128} \approx \ln 128 + 0.5772 + 1/256 = 5.43$，利用率约 18.4%。batch 越大越浪费，这与"batch 大才能提高吞吐"直接矛盾，连续批处理消除了这个矛盾。

**练习 3**　一个系统提示有 2000 token，每个请求再加 500 token 的用户内容。每秒 50 个请求，前缀缓存命中时 8B 模型每秒节省多少 prefill FLOPs？相当于 H100 理想算力的多少？

> **解答**：每个请求节省 2000 个 token 的 prefill（2000 正好是 16 的倍数，全部是满块），每秒 $50\times 2000 = 10^5$ 个 token，约 $2\times 8.03\times 10^9\times 10^5 = 1.6\times 10^{15}$ FLOPs/s（忽略注意力），是 H100 峰值 989 TFLOPS 的 1.6 倍：不缓存的话，单是重复算系统提示就要两张 H100 满载。

**练习 4**　分块 prefill 的预算设为 512 token。一个 8000 token 的 prompt 需要几步才能做完？如果同时有 100 条请求在 decode，每步给 prefill 的预算还剩多少？

> **解答**：decode 优先，100 条各占 1 个 token，每步剩 412 个 token 给 prefill，8000 token 需要 $\lceil 8000/412\rceil = 20$ 步。每步约 10 ms 的话，TTFT 比一次做完（约 130 ms 加排队）多出几十毫秒；换来的是这 20 步里那 100 条请求的 TPOT 都保持在约 10 ms，而不是被一个 130 ms 的长步卡住。

**练习 5**　用 PD 分离部署 Llama-3-8B，prefill 节点到 decode 节点的带宽是 25 GB/s。一个 16K token 的 prompt，KV 传输要多久？和 prefill 本身相比如何？

> **解答**：KV 是 $16384\times 128\ \text{KiB} = 2$ GiB，即 2.15 GB，传输约 86 ms。prefill 的线性层 FLOPs 是 $2\times 8.03\times 10^9\times 16384 = 2.6\times 10^{14}$，注意力还要加 $4\times 32\times 4096\times 16384^2/2 \approx 7.0\times 10^{13}$，合计 $3.3\times 10^{14}$，理想时间约 0.34 s。传输约占 prefill 的四分之一，按层流水（算完一层传一层）就能大部分藏起来；带宽再低或模型的 KV 更大，传输就会成为瓶颈，这也是 MLA 这类小 KV 设计适合 PD 分离的原因。
