# 8.2 RAG 全链路：找到证据，放对位置，再回答

> **一句话核心直觉**：RAG 系统的最终答案质量由数据清洗、文本切块、多路召回、候选重排、上下文编排以及语言模型生成六个环节环环相扣决定。排查问答故障时，必须在同一道测试题上全链路保留各阶段的中间输入、候选快照与模型输出，才能从根因上彻底区分究竟是“底层根本没召回”“召回后被重排丢弃”，还是“证据已完整送入上下文却被大模型忽略”。
> **唤醒标签**：切块 · BM25 + 稠密 · RRF · cross-encoder · 证据覆盖 · 重排 · 位置与干扰 · 忠实度 ≠ 正确率 · 反事实诊断

前置：双塔、ANN 与 exact 邻居（→ 8.1）；本课是 Agent 系统管理外部知识的入口（→ 8.4）。

## 1. 痛点与钩子：手册里有答案，机器人为什么答错？

公司退款政策手册中明确写有两句话：“E42 代表银行卡支付失败”以及“支付失败可在 30 天内申请退款”。与此同时，废弃的旧版本例外条款与其他业务线退款规则中也充斥着 `E42`、`refund` 等高频词汇。当用户提问“E42 退款期限是多少”时，线上问答机器人却回答了错误的数字。

表面上这只是一次问答失败，但沿着 RAG 链路逐级解构，故障可能发端于四个完全不同的截面上：

| 阶段 | 必须记录的可观测对象 | 典型系统性故障 |
|---|---|---|
| **数据与切块** | 原文发布版本、分块物理边界、结构元数据、访问控制权限 | 索引了废弃条款；前提条件与结论被硬生生切断在两个切片（Chunk）；PDF 表格未解析导致漏建索引 |
| **多路召回** | 查询意图改写（Query Rewrite）、元数据过滤条件、各路候选切片 ID 与原始打分 | 包含关键证据的切片未进入候选池；稀疏关键词检索遇上同义改写漏召，或密集向量检索被常见词淹没 |
| **重排与上下文** | 各候选经重排后的次序、上下文窗口截断位置及 Token 消耗明细 | 正确切片虽被初检召回，但因重排打分不足、上下文 Token 预算受限或去重策略而被裁剪丢弃 |
| **生成与引用** | 最终拼接组装的 Prompt、模型生成文本、标注引用切片及事实核验结果 | 上下文已提供正确证据，但模型受“中间迷失”或干扰项误导忽略了生效条件，甚至凭幻觉胡乱生成引用 |

针对相同的模型基底与固定问题，先做一个关键技术决策预判：把两个相邻的短段落强行合并为一个大切片（Chunk），会更容易一次性取回全部事实吗？为此我们又必须在检索精度与上下文预算上付出什么代价？

## 2. 第一性原理：检索的是信息单元，而不是整篇真相

### 2.1 切块粒度决定候选与上下文的信噪比

文本分块策略（Chunking）从物理层面定义了检索系统中最基本的信息单元。切块绝非单纯按固定字符长度暴力硬切，而是在“语义聚焦度”与“语境完整性”之间寻找最优平衡点：

- **小切片（如 100～200 Token）**：语义高度聚焦，向量池化（Pooling）后的信息密度极高，很容易在初筛阶段以较高的余弦相似度排入粗选候选池；然而，它极易将完整的逻辑上下文斩断（例如将“如果用户未实名”的前置条件与“支持全额退款”的结论割裂在两个切片），导致单一切片缺乏自洽解释力，严重破坏多跳推理。
- **大切片（如 800～1500 Token）**：能够保留完整的段落邻接关系、复杂表格及上下文逻辑链条，但随之涌入的大量无关背景词会稀释关键实体的高维表征强度，且大幅挤占下游昂贵的 Cross-Encoder 重排算力与大模型生成时的有效上下文窗口。

工程成熟做法通常依据 Markdown 标题层级、段落自然换行、代码块或表格语义边界进行切分，并在切片元数据中强制注入所属文档 ID、父级章节标题、生效版本与访问权限；在检索召回命中某一切片后，再按需向上展开父级段落或拼接相邻切片（Small-to-Big Retrieval）。在相邻切片之间设置一定比例的滑动重叠（Overlap）虽然能缓解跨边界断裂，但会引入大量近重复冗余项，必须在重排阶段进行语义去重。

下表定义了一组包含 6 个段落的教学语料库。为直观呈现原理，此处采用人工设定的二维特征向量，设定的用户查询向量为 $(1, 0)$。回答用户问题必须同时涵盖事实 A 与事实 B；其中 B1 段落声明原例外已被废弃，B2 是另一条无关的短退款规则。在大切片模式下，仅将同一文档的相邻两段文本合并，其教学向量取两段向量之和后计算余弦相似度；此逻辑用于隔离展示分块对几何分布的影响，而非真实 Embedding 模型对长文本重新编码的数值。

|---|---|---|---|
| A1 | `e42 means card payment failed` | (0.8, 0.6) | 事实 A：错误码业务含义 |
| A2 | `failed card payment refund deadline thirty days` | (1.0, 0.1) | 事实 B：30 天退款期限 |

| B2 | `refund deadline seven days` | (0.3, 0.95) | —（无关业务线干扰项） |
| C1 | `e24 card shipment failed` | (0.5, 0.8) | —（物流错误码干扰项） |

在交互实验中，通过调整控制项观察切块与融合权重对多事实覆盖率的影响：
- **调节参数**：切换「每块的段落数」（小块 1 段 vs 大块 2 段）、滑动「稠密排名权重 $\alpha$」（从纯 BM25 词法检索 0.0 到纯向量检索 1.0），并改变「取回的块数 top-k」（1～4）。
- **观察指标**：观察各切片的加权 RRF 融合得分条形图、最终返回的切片清单，以及对金标准事实（事实 A + 事实 B）的覆盖率（0/2、1/2、2/2）。

在小切片模式下，当采用经典混合检索权重 $\alpha=0.5$ 且仅取 Top-2 时，返回结果为 A2 与 B2，事实覆盖率仅为 1/2（缺少错误码与支付失败的关联 A1）；若切为纯向量检索 $\alpha=1.0$，Top-2 变为 A2 与 A1，能够完整覆盖 2/2 条事实；而若切换为大块合并模式（每块合并 2 段），即使采用 $\alpha=0.5$ 且仅拉取 Top-1，合并切片 A 也能一次性囊括 A1 与 A2，达成 2/2 事实完全覆盖。该实验清晰揭示了“切块粒度 × 检索通道 × 预算窗口”三者共同决定了下游多跳证据链的完整性。[用 Python 复算](#worked-example)

### 2.2 稀疏词法、密集向量与混合检索融合

单一检索通道在复杂生产场景中必然存在固有盲区：

- **稀疏倒排索引（BM25）**：基于精确词项命中频率（TF）、逆文档频率（IDF）以及文档长度归一化进行打分。对于人名、工号、特定错误码（如 `E42`）、API 接口名等稀有专有名词，BM25 具备近乎不可替代的精确定位能力；然而，一旦用户采用口语化同义改写、多语言表述或高位抽象概括，词法匹配将遭遇全面漏召。
- **密集向量检索（Dense Embedding）**：将自然语言映射到连续的语义潜在空间中，依靠余弦或内积捕获概念级别的语义联想与上下文相似性；但面对包含精细数字、否定词（“不可退款”与“可以退款”）或字母型号变体的查询时，向量平均表征极易模糊这些决定性细节。

工程上通常将两路召回的候选列表取并集，再通过排名融合算法交由下游重排。本实验中查询词 $t$ 的 BM25 单项打分遵循经典标准实现：

$$
\operatorname{idf}(t)=\log\!\left(1+\frac{N-\operatorname{df}(t)+0.5}{\operatorname{df}(t)+0.5}\right),\quad
\operatorname{BM25}(d,q)=\sum_{t\in q}\operatorname{idf}(t)\frac{f(t,d)(k_1+1)}{f(t,d)+k_1(1-b+b|d|/\overline{|d|})}.
$$

其中常规超参数设为 $k_1=1.2, b=0.75$，$N$ 为当前分块总数。由于 BM25 的无界数值与稠密向量的余弦打分（$[-1, 1]$）处于完全不同的物理量纲，直接将二者线性加权极其脆弱。工业界广泛采用**加权倒数排名融合（Weighted Reciprocal Rank Fusion, RRF）**，仅依赖各通道返回的名次序位（从 1 开始计）进行无量纲融合：

$$
\operatorname{RRF}(d)=\frac{1-\alpha}{60+r_{\mathrm{BM25}}(d)}+\frac{\alpha}{60+r_{\mathrm{dense}}(d)}.
$$

式中 60 为平滑常数（防止靠前名次的分值权重断崖式下跌），$\alpha \in [0, 1]$ 控制密集通道的偏好权重。RRF 的最大优势是稳健鲁棒、无需校准分数分布；但其代价是完全丢弃了分数之间的相对间隔距离信息（例如第 1 名与第 2 名之间的微弱差距被放大为固定名次衰减）。真实系统中各路通道通常仅召回 Top-$N$（如各自取 Top-50）送入融合，未在上榜名单出现的候选切片不贡献对应倒数项。

## 3. 承重墙推导：从候选到答案，每一步丢了什么？

### Step 1　重排器用计算复杂度换取全量语义交互

双塔检索为了满足海量并发粗排，在生成向量阶段完全剥离了 Query 与 Document 之间的词级跨文本交互；而**交叉编码器重排（Cross-Encoder Reranker）**则将用户查询与每一个候选切片直接拼为单一序列（例如 `[CLS] query [SEP] chunk [SEP]`）送入 Transformer 模型深层，在全部自注意力头中对所有 Token 对执行全量成对交互（Cross-Attention）。

交叉编码器能够敏锐辨析否定修饰、主谓宾从属、时间约束以及细微的因果关联，打分精度远超双塔检索。但这种全交互的计算代价与候选切片数量及长度呈线性乘积增长，在线延迟昂贵；因此在工业管线中，通常严格限制送入重排的深度（例如仅对粗排 Top-100 进行重排，最终截断保留 Top-5 注入 Prompt）。

> [!IMPORTANT]
> 重排器只能在其接收到的输入候选集内部重新排序，**绝不可能凭空创造或复活**在粗排阶段已被漏召的底层切片。此外，重排模型通常具有严格的最大 Token 截断长度（如 512 Token）；若长切片的关键结论落在末尾，被截断后的重排器实际上根本没有看到这部分证据。

下方通过 6 道精心设计的合成测试轨迹，展示端到端链路中证据逐级流失的微观过程。每道题目有唯一的黄金标准证据切片 R，以及 A–E 共 5 个干扰切片；R 在粗排阶段的名次从 Q1 到 Q6 依次递减（排名 1 至 6）。实验中的重排分数为预设固定数值，用于模拟重排器的判别结果。重排器仅对进入粗排候选池的切片进行排序。

在交互实验中，系统性测试各个环节的瓶颈：
- **调节参数**：设置「候选数」（粗排召回深度，1～6）、「重排开关」（是否根据分数重排）、「最多放入上下文的块数」（进入 Prompt 的上下文容量上限，1～3）以及「简化阅读器」（只取上下文首块 vs 匹配问题题号）。
- **观察指标**：观察 6 道题目在各个漏斗阶段的推进情况（条形图分为 0：漏召；1：重排漏选；2：上下文有证据但利用错误；3：正确答对），以及全链路综合转化率。

在默认设置下（候选数选 Top-3，重排后保留 Top-2，阅读器只取首块）：
- **粗排漏召**：Q4、Q5、Q6 的真实证据 R 排在粗排第 4～6 位，因候选深度仅为 3，在第一道关卡便被直接漏召；
- **重排与上下文截断**：Q3 的证据 R 虽然进入了候选池，但在重排打分中仅排第 3 位，被上下文容量上限（Top-2）无情截断；
- **阅读与利用失效**：Q1 与 Q2 的上下文均成功包含了证据 R；但对于 Q1，干扰块 A 因重排得分更高（0.9）占据了上下文首位，导致“只读第一块”的机械阅读器抄录了干扰块中的错误数值；最终 6 道题呈现出极具警示意义的漏斗：**3/6 候选含证据 → 2/6 上下文含证据 → 1/6 最终答对**。

当我们将阅读器切换为能够识别匹配题号的高级策略时，在完全相同的上下文证据下，最终答对题数直接由 1 题翻倍至 2 题；若进一步将粗排候选深度放宽至 6（全量召回），且维持保留 2 个上下文切片并开启题号匹配，链路转化率跃升为 6/6 → 5/6 → 5/6（仅 Q3 依然由于重排打分缺陷被阻隔在上下文之外）。[用 Python 复算](#worked-example-2)

需要强调，此处的规则阅读器是为了精准隔离变量而设计的确定性可执行逻辑，并非真实大型语言模型的绝对性能映射。该闭环假设 R 为唯一能够解题的证据且所有干扰项均包含互斥错误数字。只有在这一受控假设下，“模型答对”才必须以“标注证据完整进入上下文”为绝对前置条件。

### Step 2　上下文长度不等于有效信息利用率

商业长上下文模型动辄支持数十万乃至数百万 Token 的输入窗口，这往往给工程师造成一种错觉：既然能全部塞进 Prompt，何必还要大费周章做切块、检索与重排？

现实中的自注意力机制并非无损的理想处理器。**“中间迷失”（Lost in the Middle）**现象表明：自回归语言模型对位于 Prompt 首部（系统提示词附近）与尾部（最新用户提问附近）的文本具有天然的注意力偏好，而置于冗长上下文深处的信息极易被稀释和忽略。更为致命的是，在真实企业知识库中，直接倒入未经清洗与重排的长文本会引入大量同质噪声、过期制度版本与相互矛盾的事实切片，极易诱发严重的模型幻觉。此外，百万 Token 的全量前向推理在首次响应延迟（TTFT）与计费成本上往往无法承受。长窗口拓宽了信息承载上限，但绝不能替代高精度的精准检索与权限过滤。

在设计位置敏感度对照实验时，必须严格固定测试题目集、证据切片内容、提示词模板与随机采样种子（Temperature），仅将关键证据切片轮流放置在上下文的“头部 / 居中 / 尾部”；随后在固定位置下逐步注入不同数量的非相关干扰切片进行压力测试（→ 5.4）。此外，拼入 Prompt 的切片必须完整附带来源文件名、章节路径与版本元数据，否则模型即便提取出“30 天”这一孤立数值，也无法判断其究竟适用于国内业务还是海外业务。

### Step 3　指标切分清晰，量纲严密对齐

评估 RAG 系统时，切忌仅凭一个笼统的“答案准确率”草率下结论。必须沿着数据流向，将算法与工程指标严格切分：

设某题的人工标注金标准相关证据切片集合为 $G_q$，检索模块实际返回的候选切片集合为 $C_q$：

$$
\operatorname{relevance\ recall@}k(q)=\frac{|G_q\cap C_q|}{|G_q|},\quad
\operatorname{precision@}k(q)=\frac{|G_q\cap C_q|}{|C_q|}.
$$

上述公式在多测试题场景下既可计算宏平均（按题目分别算比值后取均值），亦可计算微平均（全集求和后计算总体比值），工程汇报时必须指明分母口径。针对需要多跳综合推理的复杂问答，必须严密统计**完整证据覆盖率（Full Evidence Coverage）**：即推导最终答案所需的全体多块证据是否均完整进入了上下文集合；仅命中其中一块的简单 Hit@k 往往具有极强的误导性。对于多路径可解的开放题，应建立可接受的黄金证据集合，避免把未标注但在事实层面完全等效的真实佐证误判为漏召。MRR 侧重衡量首个相关切片的排位高低，nDCG 则支持多级相关性打分，二者均用于刻画排序质量，但无法取代证据覆盖率。

在生成端，必须将**忠实度（Faithfulness）**与**事实正确率（Correctness / Accuracy）**严格剥离：
- **忠实度（Faithfulness）**：回答中给出的每一个论点与数值，是否能够严格由当前 Prompt 中提供的参考上下文推导得出，有无捏造未经证实的幻觉主张；
- **事实正确率（Correctness）**：回答的内容是否符合客观物理世界的真实情况。

一个盲目遵循过期上下文的回答，其忠实度可能极高（严格按文档回答），但事实正确率彻底归零；反之，模型依靠自身预训练参数中残留的固有知识答对了最新政策，但上下文给出的其实是错误文档，此时回答事实正确，但对系统而言却属于一次完全失去可溯源性的“不忠实生成”。在引入自动评测（如基于 LLM-as-a-Judge 的 Ragas）时，裁判模型的判定规则必须定期经过资深领域专家的人工标定与校准。

> [!NOTE]
> 本节讨论的“业务相关证据召回率（Relevance Recall@k）”与 → 8.1 中的“向量近似搜索保真度（ANN recall@k）”处于两个完全不同的层次：前者以业务真理标签为基准，后者仅以向量空间的暴力全量暴搜为对照。极高的 ANN recall 绝不保证召回的切片在业务上真正有用。

### Step 4　设计三类反事实干预实验定位瓶颈

面对线上长尾劣质样本，最高效的根因排查手段不是盲目调整提示词，而是采用“反事实受控替换（Counterfactual Intervention）”在各个断点上做定点排查：

1. **查召回（Oracle Retrieval）**：固定原始用户问题，跳过向量检索与 BM25，直接将经过人工核验的金标准证据切片强制注入候选池，与线上真实召回的候选混合。若后续重排与生成阶段指标大幅好转，确证系统短板卡在粗排召回通道；进而通过比对 Exact 暴力搜索与 ANN 结果，彻底分清是向量模型表征缺陷还是近似索引剪枝过度，并仔细排查切块截断与元数据过滤权限。
2. **查重排（Oracle Rerank）**：固定线上粗排召回的真实候选集合，人工将其中命中的正确切片强制置顶（即扮演完美的理想重排器），随后送入相同容量的上下文截断逻辑。若最终生成质量显著提升，表明候选池原本已捕获有效信息，纯粹由于重排器打分偏差或截断窗口过窄导致证据流失。
3. **查利用（Oracle Context）**：跳过整个前置检索与重排管线，直接将人工核准的完整纯净证据编排进 Prompt，在不同上下文位置与不同干扰项密度下反复调用生成器。若大模型在此完美上下文下依然回答错误或生成幻觉，瓶颈必然锁定在大模型自身的理解能力、提示词指令约束或任务定义本身；若人工置入证据后模型能够稳定答对，方可回溯去优化上游的检索与组装管线。

反事实分析的核心在于控制变量：通过人为消除某单一阶段的不确定性，确凿判定该阶段是否构成系统的因果瓶颈。

## 4. 极简代码锚点与数值复算

### 数值复算 · 切块和混合排名

两段代码均基于 Python 纯标准库实现，无需联网或依赖外部重型框架，可在任何常规 CPU 上独立复现。第一段代码演示不同分块粒度下的 BM25 计算、稠密余弦打分与加权 RRF 融合；第二段代码通过确定性状态机演示六道测试轨迹的分阶段截断。

```python
import math

paragraphs = [
    ("A1", "e42 means card payment failed", (0.8, 0.6), "A"),
    ("A2", "failed card payment refund deadline thirty days", (1.0, 0.1), "B"),
    ("B1", "e42 refund exception was superseded", (0.2, 0.98), ""),
    ("B2", "refund deadline seven days", (0.3, 0.95), ""),
    ("C1", "e24 card shipment failed", (0.5, 0.8), ""),
    ("C2", "shipment tracking delivery", (0.0, 1.0), ""),
]

def hybrid(size, alpha, k):
    chunks = []
    for i in range(0, len(paragraphs), size):
        parts = paragraphs[i:i+size]
        name = parts[0][0] if size == 1 else parts[0][0][0]
        words = sum((p[1].split() for p in parts), [])
        vec = tuple(sum(p[2][j] for p in parts) for j in range(2))
        facts = "".join(p[3] for p in parts)
        chunks.append(dict(name=name, words=words, vec=vec, facts=facts))
    n = len(chunks)
    avglen = sum(len(c["words"]) for c in chunks) / n
    for c in chunks:
        score = 0.0
        for term in ("e42", "refund", "deadline"):
            df = sum(term in d["words"] for d in chunks)
            tf = c["words"].count(term)
            idf = math.log(1 + (n - df + 0.5) / (df + 0.5))
            score += idf * tf * 2.2 / (tf + 1.2 * (0.25 + 0.75*len(c["words"])/avglen))
        c["bm25"] = score
        c["dense"] = c["vec"][0] / math.hypot(*c["vec"])
    def ranks(key):
        order = sorted(range(n), key=lambda i: (-chunks[i][key], i))
        return {i: rank + 1 for rank, i in enumerate(order)}
    sparse, dense = ranks("bm25"), ranks("dense")
    score = lambda i: (1-alpha)/(60+sparse[i]) + alpha/(60+dense[i])
    order = sorted(range(n), key=lambda i: (-score(i), i))[:k]
    return [chunks[i]["name"] for i in order], set("".join(chunks[i]["facts"] for i in order))

for size, alpha, k in ((1, 0, 2), (1, 0.5, 2), (1, 1, 2), (2, 0.5, 1)):
    names, facts = hybrid(size, alpha, k)
    print(f"每块{size}段 α={alpha:.1f} top-{k}={','.join(names)} 事实覆盖={len(facts)}/2")
```

**运行结果**

```text
每块1段 α=0.0 top-2=B2,B1 事实覆盖=0/2
每块1段 α=0.5 top-2=A2,B2 事实覆盖=1/2
每块1段 α=1.0 top-2=A2,A1 事实覆盖=2/2
每块2段 α=0.5 top-1=A 事实覆盖=2/2
```

```python
# 按检索顺序排列：R 是唯一标注证据，A–E 为干扰块。
traces = [
    ("Q1", 30, "RABCDE", dict(R=.6, A=.9, B=.3, C=.2, D=.1, E=.05)),
    ("Q2", 60, "ARBCDE", dict(R=.9, A=.3, B=.2, C=.1, D=.08, E=.05)),
    ("Q3", 90, "ABRCDE", dict(R=.5, A=.9, B=.8, C=.2, D=.1, E=.05)),
    ("Q4", 15, "ABCRDE", dict(R=.9, A=.5, B=.4, C=.3, D=.2, E=.1)),
    ("Q5", 45, "ABCDRE", dict(R=.8, A=.9, B=.5, C=.4, D=.3, E=.1)),
    ("Q6", 21, "ABCDER", dict(R=.8, A=.9, B=.5, C=.4, D=.3, E=.1)),
]
wrong_values = dict(A=7, B=9, C=11, D=13, E=17)

def diagnose(candidate_k, context_k, reader):
    summary = [0, 0, 0]
    for qid, gold, retrieval, scores in traces:
        candidates = list(retrieval[:candidate_k])
        ranked = sorted(candidates, key=lambda name: -scores[name])
        context = ranked[:context_k]
        passages = [(qid, gold) if name == "R" else ("other", wrong_values[name])
                    for name in context]
        answer = passages[0] if reader == "first" else next((p for p in passages if p[0] == qid), None)
        evidence_candidate = "R" in candidates
        evidence_context = "R" in context
        correct = answer is not None and answer[1] == gold
        summary = [a + int(b) for a, b in zip(summary, (evidence_candidate, evidence_context, correct))]
        print(f"{qid} 候选={''.join(candidates)} 上下文={''.join(context)} 答案={answer[1] if answer else '无'} 正确={int(correct)}")
    print(f"{reader}: 候选证据={summary[0]}/6 上下文证据={summary[1]}/6 答对={summary[2]}/6")

for reader in ("first", "matched"):
    diagnose(3, 2, reader)
```

## 5. 实战判断、迁移与前沿现状

**面向 Agent 与企业生产的落地闭环**：
在企业生产环境中，必须搭建全链路分布式追踪（Distributed Trace）系统。对每一次问答请求，从底层严格记录 Query 改写历史、BM25 与向量两路召回的原始切片 ID 与分值、RRF 融合结果、Cross-Encoder 重排得分、最终拼入 Prompt 的切片排布次序与 Token 消耗，以及大模型生成的答案与角标引用。
排查故障时务必按照优先级梯次推进：
1. **数据与切块层**：若源头切片由于硬切断裂导致语义缺失，优先调整切块边界或引入父子文档展开；
2. **召回层**：若金标准切片根本未进入候选池，排查意图改写、Embedding 表征与 BM25 词典分词；
3. **重排层**：若候选池已命中但未排进前排，优化重排模型、校准超长切片截断并适当放宽上下文候选数量；
4. **生成层**：若上下文已具备纯净证据但模型依然答错，重点调优提示词工程、控制干扰项密度并优化推理温度。

**2026 前沿现状**：
经典的“单次检索 + 单次生成”正在被更加动态的智能体范式迭代。生产系统普遍引入 Self-RAG、Corrective RAG（CRAG）等主动检索架构，使大模型具备自省能力：能够自主评估检索切片的相关度得分，在证据不足或相互冲突时自发触发二次 Query 改写甚至主动放弃回答（弃答机制）。评测框架层面，开源社区工具（如 Ragas、Ares）将上下文召回率、忠实度与语义相关度做了细粒度拆分，但在垂直领域落地时，仍然极度依赖人工校准的金标准测试集。支持超大窗口的模型带来了新的工程架构权衡，但基于企业数据安全、时效性快照、精准证据追溯以及推理成本的考量，RAG 的模块化架构依然是企业级落地的基石。

**迁移练习 1**：在包含 100 道复杂问答的测试集中，统计发现有 70 道题的已标注金标准证据切片成功进入了粗选候选集，55 道题的证据成功拼入了最终上下文，而大模型最终却答对了 75 道题。这一结果是否必然说明评测计算代码存在 Bug？

> **解答**：并不必然是计算错误。现实中的大模型在预训练与监督微调阶段已经沉淀了极其丰富的先验参数知识，部分常识性或通用性问题即便上下文未提供证据，模型亦可凭借自身权重准确作答；此外，知识库中可能存在未被人工标注的其他平行有效切片，且“最终答对”与“预设标注证据被命中”在概率上属于不同的关联事件。如果业务场景严格要求“答案必须百分之百有据可查、禁止依靠先验猜测”，则应另行统计“上下文具备有效证据且回答正确（有据且正确）”的交集题数，切忌直接把 75 题视作可靠溯源的系统能力。

**迁移练习 2**：在某次排查中，发现某道关键业务题的正确政策切片已经稳稳进入了粗排 Top-10 候选池，但系统最终拼入 Prompt 的 Top-3 上下文中却完全缺失了该切片。此时应当优先去调低大模型生成的 Temperature 参数吗？

> **解答**：绝对不应当。问题完全阻断在中间的“重排与上下文截断”阶段，此时调整下游生成模型的采样温度（Temperature）无济于事。正确的工程操作是：先固定粗排候选集，检查 Cross-Encoder 重排器打分与模型最大序列长度截断情况，排查是否存在近重复文档去重误删，或上下文 Token 预算被其他冗长切片挤占；同时可通过人工将该政策切片强行插入上下文首位进行反事实测试：若插入后模型能稳定答对，确证系统瓶颈位于重排选拔阶段，应集中精力调优重排器或放宽上下文输入预算。
