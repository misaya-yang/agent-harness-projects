# 8.3 工具调用与 Agent 架构

> **一句话核心直觉**：工具调用将语言模型从封闭的文本生成器，转变为向外部环境发出可执行动作的决策策略；而外部环境反馈的真实观测，反过来重塑下一步动作的输入历史。智能体全流程的成功率由工具选择、入参生成、环境执行与观测利用的联合条件概率共同决定。在多步复杂长链任务中，单步微小误差会呈指数级累积；引入校验与修复虽能挽回部分失败，却必须支付额外的调用与延迟成本；而多智能体协作方案，唯有在分工互补或多数票投票带来的确定性信息增益超越共因故障与通信交接损耗时，才具有工程合理性。
> **唤醒标签**：策略与环境 · 结构合法 ≠ 语义正确 · ReAct · 条件概率链 · 首错归因 · 检测 × 修复 · 规划的期望收益 · 共因错误 · 多数票与交接 · Agentic RL · 配对评测

前置：条件概率链式法则（→ 0.3）、语法约束解码（→ 7.1）与多轮强化学习（→ 2.6）。下一课探讨智能体上下文管理与长期记忆系统（→ 8.4）。

## 1. 痛点与钩子：为什么接入了工具，依然给出错误方案？

我们以一个贯穿本课的**离线行程助手**为例：用户提出需求：“11 月 23 日帮我规划从城市 A 到城市 B 的行程，避开我的日程会议，给出尚有空余座位的车次建议。”为保证实验环境确定可复现，行程助手仅连接离线沙箱数据：调用 `lookup_calendar(date)` 读取用户当天的离线会议日程，调用 `lookup_train(date, route)` 查询指定日期的列车班次与剩余座位；助手最终**仅生成拟定的建议方案，不执行任何真实的订票扣款操作**。

在线排查时，我们记录到模型生成了一段语法完全合法的工具调用参数：`lookup_train({"date":"2026-11-23","route":"A-B"})`。沙箱工具如实返回观测：“09:00 班次已售罄，13:00 班次尚有余票”；然而，模型在最终生成的回复中，却赫然向用户推荐了 09:00 班次。

这次任务失败，显然不是“模型没有接入工具”，而是**观测利用（Observation Utilization）失败**。更进一步，如果模型在入参中将日期错填成了 22 日，则属于**参数生成错误**；若工具服务查询了过期的本地数据快照，则属于**外部环境数据缺陷**。如果评测系统只粗暴地给出一个“最终任务失败”的 0 分，工程团队根本无法断定究竟是模型基底能力不足、提示词有误，还是底层工具 API 故障。

本课将围绕核心工程决策依次解构四个关键问题：
1. 模型究竟如何将自然语言转化为确定性动作？
2. 多步长链交互中，微小错误如何逐级指数级放大？
3. 规划反思（Reflection）与多 Agent 投票在何种数学边界下才真正具备正向收益？
4. 针对 Agentic RL 训练与线上评测，如何设计因果隔离实验定位系统瓶颈？

## 2. 第一性原理：一次工具调用的微观状态流转

### 2.1 动作、环境与部分可观测马尔可夫决策过程

我们将用户初始提问、多轮历史对话以及此前所有工具执行的返回结果统称为历史上下文 $h_t$。大型语言模型在这一语境下本质是一个决策策略（Policy）$\pi_\theta$，负责在当前时刻采样输出下一个动作 $a_t$：

$$
a_t \sim \pi_\theta(a\mid h_t),\qquad o_{t+1}\sim P_{\rm env}(o\mid h_t,a_t),\qquad h_{t+1}=(h_t,a_t,o_{t+1}).
$$

在 Agent 交互回路中：
- **动作 $a_t$**：既可以是一段直接面向用户的终局自然语言答复，也可以是一组包含**工具名称与结构化参数**（Function Call Schema）的调用指令；
- **观测 $o_{t+1}$**：由外部环境（API 服务、数据库或代码执行器）在运行时真正解析并执行动作 $a_t$ 后返回的物理结果；
- **新历史 $h_{t+1}$**：观测被格式化拼接入上下文，与之前的轨迹共同构成模型生成下一轮动作的全新条件输入。

外部环境既可以是确定性的离线静态数据，也可以带有现实网络中的延迟波动与临时异常。必须清醒认识到：**工具调用是一个典型的部分可观测过程（Partially Observable Process）**——语言模型所能感知的只有工具显式返回的观测字符串，它既不直接拥有物理世界的全部真实状态，也无法越过工具执行层直接篡改环境。

| 阶段 | 行程助手中发生的微观事件 | 独立受控评测指标 |
|---|---|---|
| **工具选择** | 根据当前上下文，判断应当调用日历工具还是查询班次工具 | 在明确需要外部工具的任务上，工具选取准确率 |
| **参数生成** | 依据用户意图抽取并填充日期、出发地、目的地等结构化字段 | 在选对工具的前提下，生成的 JSON 字段与用户约束一致率 |
| **环境观测** | 工具执行层实际向后端发起查询，返回余票数组或会议时段 | 在正确调用的前提下，工具返回数据的保鲜度、完整度与可解析率 |
| **观测利用** | 模型阅读工具返回的观测，正确剔除与会议冲突或售罄的班次 | 固定完全一致的正确观测，评测最终方案对观测的遵从利用率 |

大模型之所以具备工具调用能力，通常依赖监督微调（SFT）注入海量包含“工具 Schema 定义、模型调用动作、工具执行结果、后续思考”的高质量示范轨迹。训练的目标是对示范轨迹中**属于模型动作的 Token** 最大化条件对数似然。**环境返回的观测数据永远作为条件输入提供给上下文，模型绝不应当被训练去预测环境观测本身的 Token 分布**。早期研究如 Toolformer 探索了模型自发插入工具调用的标注学习，而 Gorilla 则深入系统化了大规模复杂 API 文档检索与参数匹配技术。

### 2.2 Schema 约束能保证什么，不能保证什么

基于上下文无关文法（CFG）或有限状态机（FSM）的语法引导约束解码技术（Grammar-guided Decoding，→ 7.1 §6），能够在模型生成每个 Token 时动态屏蔽掉不合法的词表候选，从而从数学上百分之百保证输出文本严格满足预设的 JSON Schema 或类型定义。

> [!WARNING]
> **结构合法绝不等于语义正确**。约束解码能够确保 `"date"` 字段必定是一个形如 `"YYYY-MM-DD"` 的合法日期字符串，但它完全无法阻止模型把用户明确要求的 23 日错误生成为 `"2026-11-22"`；同理，工具名拼写正确也无法保证模型没有选错工具。生成的参数是否契合用户真实意图、车次与会议是否真正发生冲突，必须依赖语义层面的逻辑核验与环境真实反馈。参数结构合法性、工具执行成功与全任务完成是三个完全独立的概率事件。

### 2.3 ReAct 范式：推理与行动的动态交替

传统的单次直接生成（Direct Prompting）强迫模型在没有任何外部中间证据的情况下，一次性凭空猜测出包含多个约束的最终答案。**ReAct（Reasoning + Acting）**架构的核心直觉，是将复杂的黑盒决策拆解为“思考（Thought）— 动作（Action）— 观测（Observation）”的闭环迭代：

1. **思考 1**：首先规划必须先核实用户的时间限制，触发动作 `lookup_calendar({"date":"2026-11-23"})`；
2. **观测 1**：环境返回“10:00–12:00 有部门周会”；
3. **思考 2**：已知 10:00–12:00 冲突，接下来查询 23 日 A 到 B 的可选车次，触发动作 `lookup_train({"date":"2026-11-23","route":"A-B"})`；
4. **观测 2**：环境返回“09:00 班次售罄，13:00 班次有票”；
5. **思考 3 & 答复**：综合两份外部观测，09:00 虽避开会议但无票，13:00 既在会议之后又尚有余票，最终输出推荐 13:00 车次的确定性方案。

在 ReAct 循环中，中间的思考过程将原本隐式的内部状态外化为可追溯、可审计的明文 Token 序列，**这无需假设模型公开了任何神秘的内部表征**。其关键价值在于使每一个后续决策都建立在真实外部世界返回的最新观测之上。此外，工具返回的文本本身可能包含非相关冗余、格式错误甚至注入指令，模型必须始终将其视为未经验证的“外部客观观测”，而绝不能将其作为不可违抗的最高系统指令盲从。

## 3. 承重墙推导：四段条件概率与首错归因

我们严格定义对应上述四个阶段的四个核心事件：
- $A_1$：在当前任务节点选对了正确的工具；
- $A_2$：在选对工具的前提下，生成的结构化参数完全正确；
- $A_3$：在调用合法的前提下，外部环境返回了新鲜、完整且正确的观测数据；
- $A_4$：在输入证据完整正确的前提下，模型最终正确利用了观测并给出无冲突的建议。

假设在当前的闭环任务中，全链路成功当且仅当这四个阶段均成功，不存在其他随机补偿机制。由**概率论乘法公式（无需任何独立性假设）**，端到端任务成功率可严格展开为条件概率连乘：

$$
P(\text{成功})=P(A_1)P(A_2\mid A_1)P(A_3\mid A_1,A_2)P(A_4\mid A_1,A_2,A_3).
$$

假设在一个经过评测标定的系统中，这四个按时序测得的**条件概率**依次为 $P(A_1)=0.90$、$P(A_2\mid A_1)=0.90$、$P(A_3\mid A_1,A_2)=0.95$ 以及 $P(A_4\mid A_1,A_2,A_3)=0.90$。则端到端整体任务成功率为：

$$
P(\text{成功}) = 0.90 \times 0.90 \times 0.95 \times 0.90 = 0.69255 \quad (\approx \mathbf{69.3\%}).
$$

总失败概率为 $1 - 0.69255 = 30.745\%$。沿着时间轴，我们可以严格按照“哪一个环节发生了首次崩溃（First-error Event）”，将这 30.745% 的失败样本互斥且完备地切分为四个子集：

| 首次失败归因阶段 | 占全体任务比例 | 严格数学计算展开 |
|---|---:|---|
| **工具选取错误** | 10.00% | $1 - P(A_1) = 1 - 0.90$ |
| **入参生成错误** | 9.00% | $P(A_1)[1 - P(A_2\mid A_1)] = 0.90 \times (1 - 0.90)$ |
| **环境观测有误** | 4.05% | $P(A_1)P(A_2\mid A_1)[1 - P(A_3\mid A_1,A_2)] = 0.90^2 \times (1 - 0.95)$ |
| **观测未被正确利用** | 7.695% | $P(A_1)P(A_2\mid A_1)P(A_3\mid A_1,A_2)[1 - P(A_4\mid \dots)] = 0.90^2 \times 0.95 \times (1 - 0.90)$ |

这四类互斥事件的概率相加恰好等于总失败率 30.745%。

> [!IMPORTANT]
> **首次失败发生的表面位置绝不等于系统的物理根因**。例如，如果用户在提问中使用了模糊或具有歧义的口语表达，既可能导致模型在第 2 步填错日期（表面为参数错误），也可能导致模型在第 4 步产生理解偏差（表面为利用错误）。如果脱离条件概率链条，把各阶段非受控的无条件边际准确率直接相乘，数学上完全不成立。

在工程诊断中，必须严格固定离线测试集与环境快照，采用**受控替换实验（Ablation）**进行因果归因：
- 给模型直接注入**标准工具名**，单独测量其参数生成能力；
- 给模型直接注入**标准参数与固定沙箱观测**，单独测量其观测理解与利用遵从率；
唯有逐一固定其他变量，才能清晰定位大模型的能力瓶颈所在。

## 4. 长链任务与反思修复：成功率收益与算力成本对齐

在复杂的自主 Agent 场景中，完成一项工作往往需要连续执行 $n$ 个**都必须全部成功**的关键步骤。若每一步在“前置步骤均成功”的条件下，首次执行成功率均为固定的条件概率 $p$，则不加任何干预的全链基线成功率为 $P_{\rm plain}=p^n$。随着步数 $n$ 增加，成功率将发生指数级衰减。

为对抗这种脆弱性，系统通常引入“自省检查（Self-Reflection）与重试机制”：对于任意单步首次失败的动作，假设系统有概率 $d$ 能够通过语法解析、静态规则或裁判模型检测出错误；在错误被检出的前提下，模型有概率 $q$ 能够通过重新生成一次性成功修复；同时假设原本已经成功的步骤绝不会被检测器误报破坏（无假阳性破坏）。

此时，单步成功的概率由两条互斥路径组成（首次成功，或首次失败后被检出并成功修复）：

$$
p_{\rm repair}=p+(1-p)dq,\qquad P_{\rm repair}=[p+(1-p)dq]^n.
$$

以 $p=0.90$、$d=0.80$、$q=0.70$ 且链路长度 $n=6$ 步为例进行复算：
- 经过检测与单次修复后，单步等效成功率从 90.0% 被抬升至 $0.90 + 0.10 \times 0.80 \times 0.70 = 0.956$（**95.6%**）；
- 六步全链任务的端到端成功率直接由原本的 $0.90^6 \approx \mathbf{53.1\%}$ 飞跃至 $0.956^6 \approx \mathbf{76.3\%}$。

然而，这种稳健性的提升绝非无代价的免费午餐：在每个步骤都必须执行的假设下，单步触发重试的概率为 $(1-p)d = 0.10 \times 0.80 = 0.08$；六步长链平均每轮需要额外付出 $6 \times 0.08 = 0.48$ 次工具调用重试与对应的验证 Token 消耗，且尚未计入检测器本身的前向计算延迟。[数值复算](#worked-example)


在交互实验中，深度探究长链任务中修复机制的数学边界：
- **调节参数**：拖动「必要步骤 n」（1～12 步）、「首次通过率 p」（0.70～0.99）、「失败被发现的概率 d」（0～1）以及「发现后修复成功的概率 q」（0～1）。
- **观察指标**：对比“不修复曲线”与“修复一次曲线”随步数 $n$ 的衰减走势，观察单步有效成功率、全链最终成功率以及期望额外重试次数的读数。
- **机制剖析**：当检测率 $d=0$ 时，即便修复能力 $q$ 再高，修复路径的激活概率 $(1-p)d$ 也彻底归零，系统完全退化为无修复的指数衰减基线。这从数学上阐明了反思规划的核心前提：**没有高保真的错误检测能力，盲目的自我反思毫无价值**。

工程上评估规划与反思的净收益准则极为明确：设引入规划后任务成功率由 $S_0$ 提升至 $S_1$，单次任务成功的商业价值为 $V$，而引入检测器与重试带来的新增 Token 与延迟成本为 $\Delta C$。唯有满足 $(S_1 - S_0)V > \Delta C$ 时，复杂反思架构才具备投入产出比。若脱离真实外部环境反馈，单纯依靠大模型对自身输出进行闭门反思，模型往往会极其自信地陷入对原先幻觉的二次辩解与死循环。开源研究 Reflexion 通过持久化记录外部环境执行失败的反馈文本，为后续重试提供上下文经验；但其成败依旧高度受限于外部反馈信号的精确度。

## 5. 多 Agent 架构：多数票机制解决不了共享的系统性偏见

在面对高难度决策时，一种直觉做法是引入多个独立的 Agent 协同投票。我们仍然以离线判断日历是否有空闲为例：部署 3 个完全平行的助手各自独立读取日程并给出结论，最终通过**多数票（Majority Voting）**裁定最终结果。

根据经典孔多塞陪审团定理（Condorcet's Jury Theorem）：在不存在共同系统性故障、且 3 个助手在给定任务下的判断**严格条件独立**时，设单人判断正确率为 $p$。只有恰好两人正确或三人全对时多数票生效：

$$
P_{\rm vote\mid no\ common}=\binom{3}{2}p^2(1-p)+p^3=3p^2-2p^3.
$$

然而在真实生产环境中，多个 Agent 往往共享同一套底层基础模型、同一套提示词模板或读取完全相同的外部知识库快照。设存在某种系统性漏洞（例如日历快照数据本身损坏、或提示词存在共性诱导偏见），以概率 $c$ 导致 3 个 Agent**必然全部做出同向错误判断（共因错误 Common-cause Failure）**。
此外，多智能体之间的信息传递需要协议通信，假设在表决完成后，结论还需要经过 2 次必要的跨智能体交接（Handoff），每次交接由于上下文压缩、信息提取或网络超时，各有概率 $h$ 独立地破坏一个原本正确的结论（且无法逆向纠错）。

此时，单智能体方案与三智能体协同团队的真实成功率分别为：

$$
P_{\rm single}=(1-c)p,\qquad
P_{\rm team}=(1-c)(3p^2-2p^3)(1-h)^2.
$$

代入工程经验参数：设 $p=0.8$、共因故障率 $c=0.1$、每次交接损耗率 $h=0.1$：
- **单 Agent 方案**：真实成功率为 $(1 - 0.1) \times 0.8 = \mathbf{72.0\%}$；
- **三 Agent 投票（交接前）**：在无共同故障时多数票高达 $3(0.8)^2 - 2(0.8)^3 = 89.6\%$，剔除共因故障后达 $(1 - 0.1) \times 0.896 = \mathbf{80.64\%}$；
- **三 Agent 投票（交接后）**：历经两次交接损耗（$(1-0.1)^2 = 0.81$）后，最终端到端胜率被直接腰斩至 $80.64\% \times 0.81 \approx \mathbf{65.32\%}$！

团队方案的最终表现竟然比单人方案还整整落后了 6.7 个百分点！数学推导表明，在此参数体系下，要让多 Agent 团队的端到端胜率勉强超过单 Agent，智能体间的交接损坏率 $h$ 必须严格控制在约 **5.51%** 以下（由 $(3p^2-2p^3)(1-h)^2 > p$ 求解而得）。

```academy-lab
8.3-team
```

在交互实验中，调控参数验证团队协作的脆弱边界：
- **调节参数**：调节「每人正确率 p」（0.5～1.0）、「共享假设导致全错的概率 c」（0～0.8）与「每次交接破坏正确结论的概率 h」（0～0.3）。
- **观察指标**：对比单人成功率、三人投票交接前成功率、以及两次交接后最终成功率三根条形柱的高低变动。
- **机制剖析**：多数票投票增益完全建立在“独立决策”这一虚妄假设之上。当共享假设缺陷 $c$ 很大时，投票机制对这部分错误彻底免疫；而如果智能体间的通信协议脆弱、上下游接口格式损耗严重（$h > 5.51\%$），多 Agent 的所谓“协作增益”会瞬间被通信熵增全盘吞噬。框架如 AutoGen 提供了强大的多智能体通信抽象，但在工程选型上，盲目堆叠 Agent 数量绝不可能自动提升系统正确率。

在做多 Agent 架构对比时，必须将参与人数、工具权限、共享数据快照以及总 Token/延迟预算严格固定：先看在同一证据下独立判断是否具备互补性，再单独隔离交接环节的传输损耗，否则一旦系统劣化，工程师根本无法分辨究竟是**共因认知盲区、提示词诱导、上下文截断损耗还是并发预算失控**。

## 6. 从提示到训练：优化整条轨迹的 Agentic RL

单纯依靠提示词工程（Prompt Engineering）与少样本示范（Few-shot），仅能微调动作条件概率 $\pi_\theta(a_t\mid h_t)$ 的局部先验，无法让模型真正学会应对由自身前期错误引发的新异常状态。**Agentic RL（智能体强化学习）**将整个工具交互闭环建模为策略与环境的强化学习序列：
- 动作 $a_t$ 涵盖模型自发生成的思考文本与结构化工具调用；
- 观测 $o_t$ 来源于沙箱工具执行的真实输出；
- 轨迹最终完成后，根据业务结果评估并赋予标量奖励回报 $R(\tau)$。

在环境转移概率 $P_{\rm env}$ 独立于模型参数 $\theta$ 的标准设定下，Agentic 策略梯度的基本形式如下：

$$
\nabla_\theta J=\mathbb{E}_{\tau\sim\pi_\theta}\!\left[\sum_t\nabla_\theta\log\pi_\theta(a_t\mid h_t)\,\bigl(R(\tau)-b(h_t)\bigr)\right].
$$

式中 $b(h_t)$ 为不依赖当前动作的基线估计器（Baseline），用于削减方差而不破坏无偏性。

> [!CAUTION]
> **策略梯度必须且只能在模型自身生成的动作 Token 上计算对数似然 $\nabla_\theta\log\pi_\theta(a_t\mid h_t)$**。环境返回的观测文本 $o_t$ 仅作为后续时间步的历史条件上下文注入，**绝对禁止对外部环境返回的观测 Token 强行计算梯度反向传播**（→ 2.6）。

在奖励函数设计上，必须平衡终局与过程的冲突：
- **终局回报（Outcome-based Reward）**：仅在任务终点对最终建议的合规性打分。信号真实稳健，但对于多步复杂长链而言，梯度信号极其稀疏，强化学习很难精准将功劳归因（Credit Assignment）给其中的某一次关键工具调用；
- **过程奖励（Process-based Reward）**：对每一个中间步骤的工具选择与参数结构进行密集打分。虽然梯度学习更迅速，但极易诱发严重的**奖励黑客（Reward Hacking）**——模型为了迎合过程奖励，疯狂生成格式完美的冗余工具调用，却彻底背离了最终解决用户问题的核心目标。

近期前沿研究（如 Search-R1 等）展示了在强化学习长程探索中自主学习动态检索决策的范式。在产业实践中，监督微调（SFT）用于初始化工具 Schema 的遵循基线，而在线强化学习（RL）则专门负责在复杂异常状态下优化闭环决策与自愈恢复策略。

**2. 严格分解首次失败归因并复算六步长链修复**

```python
from math import prod

stages = [0.90, 0.90, 0.95, 0.90]
prior = 1.0
first_fail = []
for probability in stages:
    first_fail.append(prior * (1 - probability))
    prior *= probability
print(f"四阶段成功率: {prod(stages):.5f}")
print("首错占比:", ", ".join(f"{x:.5f}" for x in first_fail))
print(f"首错占比之和: {sum(first_fail):.5f}")
p, d, q, n = 0.90, 0.80, 0.70, 6
fixed = p + (1 - p) * d * q
print(f"单步修复后: {fixed:.3f}")
print(f"六步不修复: {p**n:.5f}；修复后: {fixed**n:.5f}")
print(f"每步都执行时，期望额外重试: {n * (1-p) * d:.2f} 次")
```

**运行结果**

```text
四阶段成功率: 0.69255
首错占比: 0.10000, 0.09000, 0.04050, 0.07695
首错占比之和: 0.30745
单步修复后: 0.956
六步不修复: 0.53144；修复后: 0.76339
每步都执行时，期望额外重试: 0.48 次
```

**3. 复算多智能体多数票与交接损耗崩溃阈值**

```python
from math import sqrt

p, common, handoff = 0.80, 0.10, 0.10
vote = 3*p*p - 2*p**3
single = (1-common)*p
before = (1-common)*vote
after = before * (1-handoff)**2
threshold = 1 - sqrt(p / vote)
print(f"无共同故障时多数票: {vote:.4f}")
print(f"单人: {single:.4f}；团队交接前: {before:.4f}；交接后: {after:.4f}")
print(f"团队超过单人的交接错误率上界: {threshold:.4%}")
```

**运行结果**

```text
无共同故障时多数票: 0.8960
单人: 0.7200；团队交接前: 0.8064；交接后: 0.6532
团队超过单人的交接错误率上界: 5.5089%
```

## 8. 实战直觉、避坑与面试深挖

**与工程 / 应用的连接**
- **建立阶段隔离测试台**：固定离线测试集与沙箱环境，分别向模型注入“正确工具名”“正确入参”与“真实沙箱返回”，独立测量各个阶段的条件转化率，严禁仅用笼统的“调用成功次数”作为衡量指标；
- **严密记录全量成本账本**：在横向对比单 Agent、带反思 Agent 与多 Agent 方案时，必须同时拉齐最终任务成功率、总步骤耗时、Prompt/Completion Token 消耗、工具 API 吞吐与 P99 时延，基于成对数据进行严密假设检验（→ 5.4）；
- **过程合规绝不能掩盖结果失败**：Schema 校验 100% 通过与后端 API 状态码 200，绝不能等同于业务任务完成；必须将参数事实错误、无效死循环与超时全面纳入评测范围。

**常见误区 / 反直觉点**
1. **「API 调用成功 = 任务圆满完成」**：工具执行成功仅代表获得了外部客观观测，模型是否真正理解并基于观测调整决策，必须通过业务结果单独核验；
2. **「直接把各阶段准确率相乘计算整体成功率」**：乘法公式成立的绝对前提是“在上一阶段成功的条件概率”；盲目把非受控的无条件边际准确率相乘，严重背离概率论基本常识；
3. **「多轮反思或堆砌更多 Agent 必然更稳健」**：反思必须依赖高召回的错误检出能力；多 Agent 必须依赖低交接损耗与异构无偏性。共因偏见与接口信息损耗会轻易抹平协作增益；
4. **「首错位置必定是系统物理根因」**：表面的参数生成错误，根本诱因往往是前置用户 Prompt 歧义或工具 Schema 描述不清，必须通过受控替换做因果溯源。

**高频深挖题**
- **工具调用为什么兼具“语言生成问题”与“强化学习决策问题”的双重属性？**
  *答题路径*：语言模型前向计算生成动作 Token $\to$ 约束解码保证语法合法性 $\to$ 环境运行时返回物理观测并成为后续上下文 $\to$ 终局业务回报闭环驱动策略梯度的长期演进。
- **如何通过工程手段严格区分是“大模型不会使用工具”还是“工具本身返回质量低下”？**
  *答题路径*：固定基准任务集 $\to$ 受控注入黄金标准调用入参或标准数据快照 $\to$ 拆解条件概率链条 $\to$ 独立评估参数生成正确率与观测遵从率。
- **多 Agent 多数票表决的理论增益从何而来，工程落地中又在何时全面失效？**
  *答题路径*：孔多塞陪审团定理 $3p^2-2p^3 \to$ 关键假设为各主体在无共因故障下条件独立 $\to$ 现实中同质模型与共享数据导致共因错误 $c \to$ 智能体间协议交接损坏率 $h > 5.51\%$ 导致端到端表现劣于单 Agent。

## 9. 迁移练习（附解答）

**练习 1**　一个离线图书馆借阅助手必须顺序执行三个步骤：身份验证、图书检索与预约确认。在上一阶段成功的条件下，各步骤的首次执行成功率分别为 0.8、0.9 与 0.95。系统针对第三步单独增加了校验拦截：若第三步首次失败，有 0.5 的概率被检出；检出后重新修复的成功率为 0.8（假设通过的步骤不被误破坏）。引入该机制后，全流程任务的最终成功率提升了多少个百分点？

> **解答**：无修复时基线成功率为 $0.8 \times 0.9 \times 0.95 = 0.684$（68.4%）。第三步引入检测修复后，其等效条件成功率提升为 $0.95 + (1 - 0.95) \times 0.5 \times 0.8 = 0.97$（97.0%）。全流程端到端成功率变为 $0.8 \times 0.9 \times 0.97 = 0.6984$（69.84%），净提升了 **1.44 个百分点**。这属于严格的条件修复模型，尚未计入拦截检测器本身的 Token 开销。

**练习 2**　某电商系统部署了三个条件独立的离线库存核验智能体，各自在无共同系统故障下的独立判断正确率均为 0.7（假设不存在底层共因故障 $c=0$）。三者通过多数票表决出结论后，需要连续历经两次跨系统通信交接，每次交接有 0.1 的概率因格式截断破坏正确结论（且无法逆向修复）。请从数学上严密计算：该三智能体团队方案与无需交接的单智能体方案，究竟谁的最终决策质量更高？

> **解答**：三个独立 Agent 的多数票理论正确率为 $3(0.7)^2 - 2(0.7)^3 = 1.47 - 0.686 = 0.784$（78.4%）。然而，表决结论在经历两次通信交接后，最终保留下来的正确率仅为 $0.784 \times (1 - 0.1)^2 = 0.784 \times 0.81 = 0.63504$（约 63.50%）。这显著低于完全无需跨系统交接的单智能体基线（0.70，即 70%）。结论：尽管多数票带来了 8.4 个百分点的理论投票增益，但通信交接环节造成的累积信息损耗高达 14.9 个百分点，最终导致团队整体表现全面恶化。
