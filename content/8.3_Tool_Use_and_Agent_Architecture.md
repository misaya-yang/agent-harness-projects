# 8.3 工具调用与 Agent 架构

> **一句话核心直觉**：工具调用把语言模型的输出变成可执行的动作，环境返回的新观测再改变下一步决策；成功率由动作选择、参数、环境和观测利用的条件概率共同决定。多步任务的误差会累积，检测和修复可以挽回一部分，却要花额外成本；多个 Agent 只有在分工或投票带来的增益超过共享错误和通信损失时才划算。
> **唤醒标签**：策略与环境 · 结构合法 ≠ 语义正确 · ReAct · 条件概率链 · 首错归因 · 检测 × 修复 · 规划的期望收益 · 共因错误 · 多数票与交接 · Agentic RL · 配对评测

---

## 1. 问题：为什么会查工具，还是给错了方案？

用一位**虚构的行程助手**贯穿本课。用户说：「11 月 23 日从 A 到 B，避开我的日历会议，给出有空位的车次建议。」助手只能读取离线假数据：`lookup_calendar(date)` 给出会议时段，`lookup_train(date, route)` 给出班次与座位；最后**只给拟定方案，不真实订票**。

假设模型生成了合法的调用 `lookup_train({"date":"2026-11-23","route":"A-B"})`，但工具返回「09:00 满座、13:00 有座」，模型却建议 09:00。这次不是「没有接工具」，而是**观测利用失败**。若请求日期错了，则是参数错误；若工具查了过期快照，则是环境数据问题。只有结果分数，看不出是哪一层出错。

本课要回答四个问题：模型怎样生成动作？多步错误怎样累积？反思或多人协作什么时候真正有用？训练和评测怎样识别因果瓶颈？需要时回看 → 0.3 的条件概率、→ 7.1 的约束解码和 → 2.6 的多轮 RL。

## 2. 一次工具调用实际发生了什么

### 2.1 模型生成的是动作，不是工具结果

把用户请求、已有对话和已观察到的结果合称历史 $h_t$。模型策略输出下一个动作：

$$
a_t \sim \pi_\theta(a\mid h_t),\qquad o_{t+1}\sim P_{\rm env}(o\mid h_t,a_t),\qquad h_{t+1}=(h_t,a_t,o_{t+1}).
$$

动作可以是最终答复，也可以是**工具名 + 参数**。运行时解析并执行有效调用，工具返回的 $o_{t+1}$ 成为下一轮的观测；模型再据此产生动作。环境可以是确定性的离线表，也可以有随机延迟和失败。这是部分可观察过程：模型看到的是工具返回，不直接掌握世界的全部状态。

| 阶段 | 行程助手里发生什么 | 可单独测什么 |
|---|---|---|
| 选择 | 决定查日历还是查班次 | 在需要工具的任务上选对工具的比例 |
| 参数 | 输出日期、路线等结构化字段 | 给定选择正确，字段是否与用户意图一致 |
| 观测 | 运行时执行查询，返回空位 / 会议 | 给定正确调用，返回是否新鲜、完整、可解析 |
| 利用 | 根据观测排除冲突车次 | 固定同一份观测，看最终建议是否遵守它 |

函数调用能力可以用包含工具定义、调用和工具结果的示范轨迹做监督训练；目标是对示范中的模型动作 token 最大化条件对数似然。工具返回是**条件输入**，不是模型应预测并执行的动作。Toolformer（arXiv 2302.04761）探索了自动构造调用示范，Gorilla（arXiv 2305.15334）研究了 API 文档与调用的匹配。

### 2.2 Schema 约束保证什么

格式约束可以把不合法的下一个 token 屏蔽，使生成结果符合指定 JSON 或 schema（→ 7.1 §6）。但 `"date":"2026-11-22"` 可能格式完全合法，同时不符合用户说的 23 日；工具名合法也不代表选对了工具。日期与会议是否冲突、空位是否真实，仍要靠**语义检查和环境观测**判断。参数合法性、工具执行成功和任务完成是三个不同事件。

### 2.3 ReAct：行动与观测交替

ReAct（arXiv 2210.03629）的关键是交错产生中间决策、动作和观察，而不是一次性猜完全部答案。上面的轨迹可以是：

1. 选择查日历，得到 10:00–12:00 开会；
2. 查 23 日 A→B 的班次，得到 09:00 满座、13:00 有座；
3. 用两份观测筛选，输出「13:00 有座且不冲突」，注明这是离线数据上的拟定方案。

这里的中间决策可以写成简短的可审计计划，**无需假设模型公开内部推理**。闭环的价值是让后续动作依赖新信息：如果第 2 步只猜空位，即使文本看起来合理，也没有完成证据链。工具返回本身可能错误或包含无关文本，所以它也是观测，而不是自动可信的指令。

## 3. 四段乘法：先把错误分对地方

定义 $A_1,\ldots,A_4$ 为上表四个事件：选对工具、参数正确、观测正确、利用正确。假设本例任务成功当且仅当四者均成功，没有其他失败来源。**概率乘法公式无需独立假设**：

$$
P(\text{成功})=P(A_1)P(A_2\mid A_1)P(A_3\mid A_1,A_2)P(A_4\mid A_1,A_2,A_3).
$$

假设这四个按顺序测得的**条件**概率分别是 0.90、0.90、0.95、0.90，则任务成功率为 $0.90\times0.90\times0.95\times0.90=0.69255$，即 **69.3%**。总失败 30.745% 还可以按「首次出错」互斥地分解：

| 首次失败 | 占全部任务 | 计算 |
|---|---:|---|
| 工具选错 | 10.00% | $1-0.90$ |
| 参数错误 | 9.00% | $0.90(1-0.90)$ |
| 工具观测有误 | 4.05% | $0.90^2(1-0.95)$ |
| 观测未被正确利用 | 7.695% | $0.90^2\cdot0.95(1-0.90)$ |

这些类别按本例的必要条件定义，合起来正好是 30.745%；**首次失败位置不等于根本原因**：日期歧义、工具描述不清或不完整的日历数据可能同时影响多个阶段。若各值是无条件边际准确率，直接相乘一般不成立；上表也不代表所有真实任务都必须有且只有四步。

诊断时，保留同一离线任务集与工具快照，先查每一步的输入和输出；接着做替换实验：给模型**正确工具名**测试参数、再给**正确参数与固定工具返回**测试观测利用。分别换一处、其余保持一致，才能区分能力瓶颈；必要时把用户意图做成明确标注。失败轨迹中同一个会话可能有多个错误，先声明如何标注和处理修复。

## 4. 长链与修复：概率改善和成本一起看

现在把完成行程计划所需的查询、核对和整理抽象成 $n$ 个**都必须成功**的步骤。若每一步在此前成功的条件下首次成功率都是 $p$，则 $P_{\rm plain}=p^n$。不必假定样本边际独立，但必须假定每一步的相关条件概率都是 $p$；实际依赖状态、难度变化时，应逐步测量 $p_t$，用 $\prod_t p_t$。

对每个首次失败的步骤，假设检测到它的概率为 $d$，检测后一次修复成功的概率为 $q$；已成功步骤不会被误报破坏。单步成功的两条互斥路径是：首次成功，或首次失败后被发现并修复：

$$
p_{\rm repair}=p+(1-p)dq,\qquad P_{\rm repair}=[p+(1-p)dq]^n.
$$

例如 $p=0.90,d=0.80,q=0.70,n=6$，单步从 90.0% 升到 95.6%，全链从 **53.1% 升到 76.3%**。如果每步都执行且首次失败率始终相同，每步触发一次重试的概率是 $(1-p)d=0.08$，六步期望多重试 0.48 次；检测的时间和 token 还没算。若失败后立即终止，或修复会破坏原本正确的结果，成本与成功率都须另算。[数值复算](#worked-example)用独立 Python 验证。

```academy-lab
8.3
```

这也是规划和反思的判断方法：计划或额外检查如果能把成功率从 $S_0$ 提高到 $S_1$，一次成功的价值为 $V$、新增成本为 $\Delta C$，则在这些量可比、收益只取决于成功与否的简单模型中，只有 $(S_1-S_0)V>\Delta C$ 才值得。过度规划会拖长轨迹；自我反思没有外部反馈时也可能自信地重复同一个错误。Reflexion（arXiv 2303.11366）利用反馈产生可供后续尝试使用的文字经验；它不是对所有任务都免费有效的保证。

## 5. 多 Agent：多数票解决不了共享的错

仍然判断日历是否有空：三个助手先各自判断，用多数票汇总。设没有共同故障时，每人正确率 $p$，且三人的错误**在这个条件下独立**。恰有两人正确或三人均正确时多数票正确：

$$
P_{\rm vote\mid no\ common}=\binom{3}{2}p^2(1-p)+p^3=3p^2-2p^3.
$$

若错误的同一份日历快照以概率 $c$ 令三人**全部判断错误**，而两次必要交接各有概率 $h$ 独立地破坏一个原本正确的结论，且不能纠正原错，那么

$$
P_{\rm single}=(1-c)p,\qquad
P_{\rm team}=(1-c)(3p^2-2p^3)(1-h)^2.
$$

取 $p=0.8,c=0.1,h=0.1$：单人 **72.0%**，三人投票交接前 **80.6%**，交接后只剩 **65.3%**。固定其余假设，要让团队超过单人，交接错误率须低于约 **5.51%**。这是刻意简化的玩具模型：实际 Agent 可能共享同一模型、检索和提示，相关性不是单个 $c$ 所能完整描述；分工也可能解决单人根本做不了的问题。AutoGen（arXiv 2308.08155）展示了多 Agent 对话框架，并不意味着增加 Agent 数量必然提高准确率。

```academy-lab
8.3-team
```

把人数、每人可用工具、共同证据和 token / 延迟预算固定下来做对照：先用同一份证据看独立判断有无互补，再仅改变交接，最后改变共享证据。否则看到团队变差时，无法分辨是**共同盲点、信息压缩损失、交接错误还是预算不同**。

## 6. 从提示到训练：优化整条轨迹

提示和示范能改变 $\pi_\theta(a_t\mid h_t)$，但不能自动使模型学会处理自己造成的新状态。Agentic RL 把行程助手看成策略与环境的交互：动作是模型生成的文本和工具调用，观测来自日历和班次，完成任务后给回报 $R(\tau)$。若环境转移不依赖 $\theta$，策略梯度的基本形式是

$$
\nabla_\theta J=\mathbb{E}_{\tau\sim\pi_\theta}\!\left[\sum_t\nabla_\theta\log\pi_\theta(a_t\mid h_t)\,\bigl(R(\tau)-b(h_t)\bigr)\right].
$$

$b(h_t)$ 是不依赖当前动作的 baseline；该式写的是未折扣的终局回报，减少方差并不改变期望梯度。模型动作 token 参与策略梯度，环境返回的观测用于后续条件化，不能把观测当作模型动作求梯度（→ 2.6）。终局成功奖励能覆盖整条轨迹，但稀疏反馈难以定位是哪一步立了功；过程奖励更密，却可能奖励「形式正确的调用」而忽略最终建议错误。

Search-R1（arXiv 2503.09516）是把检索行为放进 RL 轨迹的研究例子。SFT、在线 RL、工具文档和执行环境可以结合；它们分别改变示范分布、交互策略、可用信息和反馈，并不能互相替代。离线示范无法覆盖所有执行结果，而在线 rollout 要负担查询、验证和多步采样成本。

**1. 一次实际可运行的离线调用**。即使 JSON 可解析，也要依据返回判断能否推荐；这不是票务 API。

```python
import json

action = json.loads('{"name":"lookup_train","arguments":{"date":"2026-11-23","route":"A-B"}}')
fixture = {("2026-11-23", "A-B"): [("09:00", 0), ("13:00", 2)]}
args = action["arguments"]
rows = fixture[(args["date"], args["route"])] if action["name"] == "lookup_train" else []
available = [time for time, seats in rows if seats > 0]
print("可推荐的有座班次:", ", ".join(available))
print("是否真实订票:", False)
```

```text

是否真实订票: False
```

**2. 分解首次失败并复算长链**。

```python
from math import prod

stages = [0.90, 0.90, 0.95, 0.90]
prior = 1.0
first_fail = []
for probability in stages:
    first_fail.append(prior * (1 - probability))
    prior *= probability
print(f"四阶段成功率: {prod(stages):.5f}")
print("首错占比:", ", ".join(f"{x:.5f}" for x in first_fail))
print(f"首错占比之和: {sum(first_fail):.5f}")
p, d, q, n = 0.90, 0.80, 0.70, 6
fixed = p + (1 - p) * d * q
print(f"单步修复后: {fixed:.3f}")
print(f"六步不修复: {p**n:.5f}；修复后: {fixed**n:.5f}")
print(f"每步都执行时，期望额外重试: {n * (1-p) * d:.2f} 次")
```

**运行结果**

```text
四阶段成功率: 0.69255
首错占比: 0.10000, 0.09000, 0.04050, 0.07695
首错占比之和: 0.30745
单步修复后: 0.956
六步不修复: 0.53144；修复后: 0.76339
每步都执行时，期望额外重试: 0.48 次
```

**3. 复算多数票与交接阈值**。

```python
from math import sqrt

p, common, handoff = 0.80, 0.10, 0.10
vote = 3*p*p - 2*p**3
single = (1-common)*p
before = (1-common)*vote
after = before * (1-handoff)**2
threshold = 1 - sqrt(p / vote)
print(f"无共同故障时多数票: {vote:.4f}")
print(f"单人: {single:.4f}；团队交接前: {before:.4f}；交接后: {after:.4f}")
print(f"团队超过单人的交接错误率上界: {threshold:.4%}")
```

**运行结果**

```text
无共同故障时多数票: 0.8960
单人: 0.7200；团队交接前: 0.8064；交接后: 0.6532
团队超过单人的交接错误率上界: 5.5089%
```

## 8. 实战直觉、避坑与面试深挖

**与工程 / 应用的连接**

- **先分阶段，再换一处验证**：固定任务、数据快照和模型采样设置，分别替换正确工具、参数与观测；报告任务成功率及各条件成功率，而非只报工具调用次数。
- **比较收益时记账**：比较单人、计划、复查和团队方案的最终成功率、步骤数、输入输出 token、工具次数与延迟；用相同题目配对比较，必要时按会话或任务来源重采样（→ 5.4）。
- **过程正确也要看最终结果**：schema 合法率和 API 执行率不能代替任务成功率；错误观测、不可完成任务和超时也要纳入评测。

**常见误区 / 反直觉点**

1. **「工具调用成功就是完成任务」**：工具只返回观测，最后是否据此答对还要单独测。
2. **「每步准确率乘起来总是成立」**：链式法则乘的是此前步骤成功条件下的概率；随意相乘边际准确率会忽略依赖。
3. **「多次反思或更多 Agent 一定更可靠」**：需要可检测的错误、能成功的修复，或真正互补的判断；共享错误与交接会抵消收益。
4. **「首错位置就是根因」**：相同的参数错误可能由用户意图歧义或模型解析失败造成，须受控替换证据。

**高频深挖题**

- 函数调用为什么既是生成问题又是决策问题？答题路径：策略生成结构化动作 → 约束解码只管合法性 → 环境观测改变下一步 → 任务奖励衡量动作后果。
- 如何区分模型不会用工具和工具本身不可靠？答题路径：固定任务集 → 注入正确动作或观测 → 比较条件成功率 → 检查数据快照和观测利用。
- 多 Agent 的独立投票增益从何而来，何时失效？答题路径：$3p^2-2p^3$ → 条件独立 → 共因错误 → 通信损失与额外成本。

## 9. 迁移练习（附解答）

**练习 1**　借阅助手必须依次完成身份验证、图书检索和预约确认。已走到每一步时，首次成功的概率依次为 0.8、0.9、0.95。只给第三步加一次补救：首次失败时有 0.5 的概率被发现，发现后有 0.8 的概率修好。假设已成功的步骤不受影响，整个任务的成功率能提高多少个百分点？

> **解答**：无修复为 $0.8\times0.9\times0.95=0.684$。第三步修复后为 $0.95+0.05\times0.5\times0.8=0.97$，全链为 $0.8\times0.9\times0.97=0.6984$，提高 **1.44 个百分点**。这是条件成功率模型，并未包括检测成本。

**练习 2**　三个条件独立的离线库存判断器，各自正确率 0.7，无共同故障。投票结论经过两次独立交接，每次以 0.1 的概率破坏正确结果，且无法纠错。团队和不需交接的单人谁更准？

> **解答**：多数票正确率为 $3(0.7)^2-2(0.7)^3=0.784$；两次交接后是 $0.784\times0.9^2=0.63504$，低于单人 0.7。投票本身有增益，但交接损失更大；还没有计入三个判断器的成本。
