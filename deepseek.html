EVENTS FIRST · RECOVERY BY DESIGN

一次 Agent 崩溃之后，系统凭什么敢继续？

从一个工程事故开始：模型已经发出工具调用，进程却在结果落盘前中断。接下来的 12 章，把“不丢输入、不乱序、能解释未知副作用”拆成可观察、可判断、可验证的机制。

  • 画出 Turn、Step、Request 与工具批次的完整事件轨迹
  • 判断模型看到的是原始日志、Surface 还是压缩后的视图
  • 定位工具拒绝、超时、乱序和重试分别由哪一层负责
  • 设计可冷恢复的子代理通信，并说明预算与安全边界

CHAPTER 01 · COMPOSITION

事故一：你改了“核心”，但真正生效的是另一棵插件树。

白话理解：dsh 没有一块不可替换的神秘内核。循环、模型、工具、会话和持久化都是容器里的服务行；先确定有效组合，才知道谁拥有行为。

MINI TRACE · BOOT

空配置 → bundle → profile patch → home patch → 命令行 patch → 挂载

Patch 按行标识替换整行配置，不做字段级深合并。Web 可实时重组装，短命的 headless、SDK 与 ACP 形态则只在启动时应用。

本章能力：遇到“配置明明改了却没生效”，先比较最终组合树，不先怀疑循环。

插件责任探针选择症状
OWNING PLUGIN

点击一个症状

查看首先应替换或检查的服务与证据。

判断法：三问找到拥有者

这是服务缺席、配置错误，还是服务运行失败？服务来自全局层还是 Agent 作用域？最近一层是否遮蔽了远层同名注册？回答完再决定改哪一行。

为什么值得学

“注册即效果”让每次挂载都自带回卷器，卸载时按逆序撤销。扩展不必改循环，但代价是装配顺序必须可导出、可检查。

CHECKPOINT · 2 MIN

练习：模型工具突然消失，你先查提示词、工具注册表，还是模型适配器？

查看判断标准

先看有效组合和当前 Agent 作用域中的工具注册表。若工具未注册或被限制，提示词与模型都只是下游现象。

本章小结

系统行为 = 插件行 + 作用域 + 事件。排障第一步是找拥有者，不是找最大的文件。

CHAPTER 02 · TURN / STEP / REQUEST

事故二：用户中途补充一句话，Agent 却提前宣布完成。

白话理解：Turn 是一个用户意图的完整闭环；Step 是一次模型请求及其工具批次；Request 是一次真实调用，失败重试会让同一 Step 出现多个 Request。

Turn / Step 事件步进机idle
  1. turn/start
  2. claim inbox
  3. step/start
  4. user/message
  5. request/header
  6. assistant/chunk*
  7. assistant/message
  8. tool/call → result
  9. step/end → turn/end

逐步观察“活的控制”怎样留下“持久事实”。

短 trace：插话不是抢占

steer 进入 next-step 并唤醒；followup 进入 next-turn 并唤醒；inject 进入 next-step 但不唤醒。循环在步边界领取消息，准备停止时还会重读收件箱。

判断法：看“欠下的工作”

模型不再调用工具并不自动等于结束。还要检查结论标记、粘滞的 max-tokens 状态与两条收件箱队列。终止由数据决定。

CHECKPOINT · TRACE

练习：同一 Step 的请求失败两次、第三次成功。应该有几个 Step，几个 Request？

查看答案

一个 Step、三个 Request。重试预算按 Step 计算；每次请求都从日志重新构造。

本章小结

相位负责“现在能不能跑”，日志负责“已经发生了什么”，收件箱负责“还欠什么”。

CHAPTER 03 · SESSION LOG & SURFACE

事故三：UI 显示成功，恢复后的模型却再次执行同一工具。

白话理解：日志保存所有已提交事实；Surface 只挑出模型此刻能看到的节点。UI、模型历史和遥测都是读者，没有谁可以反过来改写真相。

CRASH TAIL恢复时必须区分“没开始”和“结果未知”。没有已记录调用，模型可直接重试；调用已记录但结果缺失，只能在只读或幂等时重试，否则先检查外部状态。

短 trace：为什么 chunk 不等于消息

assistant/chunk 保存流式现场；完整或被中断的 assistant/message 才进入模型视图。压缩也不删除日志，只用 replace 节点遮蔽一段 Surface。

判断法：先找最后一个持久事实

若尾部只有工具调用而没有结果，不能相信 UI 的乐观状态。修补器会确定性补齐合成结果、步骤结束和 interrupted 回合结束。

CHECKPOINT · DECIDE

练习：一次“扣款”工具留下调用记录但没有结果。能否自动重试？

查看答案

不能。副作用结果未知，先查询外部账务状态或询问用户。

本章小结

日志是真相不代表日志永远完整；关键能力是让残缺也有类型、有修补顺序、有安全的下一步。

CHAPTER 04 · PROMPT & REQUEST

事故四：把每轮变化的状态塞进 System Prompt，缓存与审计一起失效。

白话理解：静态规则放稳定的提示词片段；沙箱、审批、委派等动态状态作为带“取代旧快照”说明的 user 消息进入历史。

SYSTEM具名片段 + 中央序位

相同输入得到相同字节，给前缀缓存稳定基础。

RUNTIME变化时追加快照

旧状态可审计、可被压缩。

SURFACE从事件折叠消息

请求不维护第二份易漂移的消息数组。

HEADER记录实际生效配置

Provider、模型、工具和提示词代际可重建。

系统提示拼装顺序台基线：两段 system

观察前部插入为何破坏稳定前缀，以及快照为什么不算进 system。

短 trace：一次请求的三层输入

装配 System 与 Tools → 比较并追加运行时快照 → 从 Surface 派生 Messages → 规范化并记录 Header → 发出冻结请求。

判断法：易变内容离前缀越远越好

身份进入稳定片段；会变的政策进入快照；用户与工具事实进入 Surface。缓存命中可能省钱，但不会缩短上下文窗口。

CHECKPOINT · CLASSIFY

练习：当前沙箱从只读变为可写，应该改 System Prompt 还是追加运行时快照？

查看答案

追加新的运行时快照，并明确取代此前快照。

本章小结

“模型看见什么”必须有可重放来源；“放在请求哪里”由稳定性和语义寿命决定。

CHAPTER 05 · TOOL PIPELINE

事故五：三个工具并行完成，结果却按完成速度乱序写回。

白话理解：工具可以并行执行，但模型对话必须保持调用顺序。dsh 把“跑得快”和“说得有序”拆成两件事。

工具失败定位器选择症状
FIRST EVIDENCE

选择一种失败

系统会指出最先查看的管线阶段。

  1. 记录调用：参数冻结，模型提出的内容先成为事实。
  2. 政策判断：pre-execute 只能 allow / deny / ask，不能偷改参数。
  3. 单调守卫：任何 guard 可拒绝，没有 guard 能替别的 guard 强放行。
  4. 执行与后处理：超时信号、工具体、post-execute 与结果 schema 依次收口。
  5. 顺序提交：并行派发，按模型调用顺序提交结果。

并发判断：默认独占

只有并发分类器精确返回 true 才进入滚动池；缺失、异常或模糊值都退回独占。默认池上限为 10。

取消判断：每个调用都要配对

取消时先排空已启动调用，未派发的调用补合成错误结果。调度器自身坏掉则不能伪造“已恢复”的结果。

CHECKPOINT · SCHEDULE

练习：调用 A 慢、B 快，二者都声明并发安全。结果先写谁？

查看答案

可以同时执行，但先提交 A，再提交 B。

本章小结

工具结果是下一步模型输入，所有政策、呈现与错误必须在唯一提交点前完成。

CHAPTER 06 · CAPABILITY SEAMS

事故六：换一个执行后端，却被迫改遍所有上层工具。

白话理解：真正可替换的能力需要三方同时成立——接口说“能做什么”，Provider 说“在哪里做”，Consumer 只说“为何要做”。

01 / DEFINITION

定义

给出窄接口、失败词汇与生命周期，不绑定实现位置。

02 / PROVIDER

提供

本地沙箱或远程运行时实现同一契约，并诚实广告能力。

03 / CONSUMER

消费

工具与表面只依赖接口，不出现后端名称分支。

Provider

FS、Bash、PTY、LSP 保持同一接口

判断法：能力先行广告

子代理 Provider 明确声明是否支持自定义选项、结构化输出、深度限制、工具过滤和 persona。调用方先比较“请求 × 能力”。

为什么远程不是“多一个 if”

远程边界会引入凭据剥离、工作目录解析、进程结算与诊断截断。差异收进 Provider，上层才不必重写失败分支。

CHECKPOINT · SEAM TEST

练习：怎样判断一个执行世界抽象真的切到位？

查看答案

替换 Provider 后，Consumer 不增加后端分支；不支持的能力在派发前暴露，而不是静默丢失。

本章小结

可替换性不是接口数量，而是差异是否被完整封在边界里。

练习：用户批准“写工作区外”，但当前模式仍是 workspace-write。能执行吗？

查看答案

不能。审批不改写沙箱策略，两条线都通过才可执行。

本章小结

每道安全边界都要准确声明防谁、不防谁、失败时做什么。

CHAPTER 08 · PROFILE / BUNDLE / PRESET

事故八：改了一个 Agent 的工具集，却意外影响所有会话。

白话理解：Profile 组装进程，bundle 提供能力集合，patch 覆盖插件行；Agent 作用域中的 preset 负责单个 Agent 的人格、工具限制与子组合。

组合层定位器选择变化
COMPOSITION OWNER

选择一种变化

查看应修改的层，以及它影响新进程还是新 Session。

判断法：先问生命周期

全进程共享能力放 Profile；运行表面差异放各自 bundle；用户覆盖走 patch；单个 Agent 的 persona 与工具限制落在 Agent 作用域。

设置为什么另有一套机制

运行时设置按“schema 默认 → 组合 base → 用户层”叠加，并用修订号控制并发。敏感字段只允许路径级修改，避免从脱敏视图写回时误删秘密。

CHECKPOINT · SCOPE

练习：只让研究子代理看见三个只读工具，应改全局 Profile 还是子 Agent 作用域？

查看答案

改子 Agent 作用域的工具 restriction。全局 Profile 会扩大影响面。

本章小结

配置层级就是影响半径。能说清何时生效、影响谁、如何回滚，才算选对层。

CHAPTER 09 · CONTEXT & COMPACTION

事故九：上下文越压越大，摘要反而挤爆窗口。

白话理解：压缩不是“删聊天”，而是一次带锁、选区、摘要、收缩门和替换提交的事务。原始事件仍在，只改变模型可见面。

  1. 测量：usage 锚点加 Surface 净位移，预测下一次请求压力。
  2. 先剪枝：先缩旧的大工具结果，仍超阈值才调用摘要模型。
  3. 选区：保留近期尾部，不切断工具调用与结果配对。
  4. 锁与摘要：记录 start，复用对话前缀，生成八节检查点。
  5. 双门验证：选区仍稳定，且新摘要确实更小、内容完整。
  6. 替换：summary 与 replace 相邻提交，end 释放持久锁。

三种触发不是一回事

压力触发在步边界，默认阈值是模型窗口的 0.8；溢出触发在请求错误链上；手动触发在空闲维护相位。

两级瘦身各守一段时间

spill 在新结果产生时外置超大文本；prune 在压力检查时缩旧结果。二者失败都不能把成功工具改判为失败。

CHECKPOINT · COMPACT

练习：摘要生成期间又来了新消息，能否直接提交旧摘要？

查看答案

自动路径要求整个 Surface 稳定；手动路径要求被选区间稳定。不满足就废弃本次摘要。

本章小结

压缩目标是用可追溯替换换取更小、仍可继续工作的模型视图。

CHAPTER 10 · EXTENSIONS & MULTI-AGENT

事故十：后台子代理还活着，宿主重启后却再也找不到它。

白话理解：一次性 run 只有结果；可续联 child 才拥有持久身份、自己的日志、FIFO 收件箱与冷恢复入口。Supervisor、Workflow 和 Team 都复用同一委派接缝。

ONE-SHOT一次性 run

失败折成停止原因，句柄结算后释放。

CONTINUABLE可续联 child

持久 descriptor + Session + Inbox，驻留实例可以丢。

WORKFLOW脚本 fan-out

Worker 线程负责并发与总量预算，不是安全边界。

TEAM V2星型团队

Lead 日志持久成员、任务与信箱，目标端按稳定 id 去重。

CURRENT BEHAVIOR · 49a606bc5b59Team 的 send_message 已统一 quiet 与 wakeup。目标 running 时在最近 Step 边界接收 steer；idle 时启动 Turn；inactive 时先冷恢复。团队消息事件为 version 2，并保持目标 mailbox 顺序。
SHORT TRACE · DURABLE TEAM MESSAGE

Lead 记录 queued → 目标接收入箱 → 目标日志 flush → Lead 记录 delivered

这是 at-least-once 交付：重启后未确认消息会重投，目标以稳定 id 去重。团队严格星型；普通子代理控制仍按父子谱系授权。

// 概念伪代码：表达顺序，不是可复制实现 queue(messageV2) if target.running → steerAtNextStep() else if target.idle → startTurn() else → restoreThenDeliver() flush(targetLog) ack(delivered)

三个控制工具就是状态机

list_agents 观察 running / idle / ready；send_message 只确认投递；interrupt_agent 只停当前回合并保留队列。ready 不是完成。

预算必须在协调者一侧

裸委派默认深度上限 3；Workflow 限并发、总子数、组合条目与同步时间；Team 限成员、任务、未达消息和消息尺寸。

CHECKPOINT · RECOVER

练习：一个 ready 子代理还能继续对话吗？应该调用什么？

查看答案

能。调用 send_message，续联管理器会冷恢复后再提交消息。

本章小结

驻留态可以丢，身份态必须可重建；消息可靠性来自日志、确认与去重。

CHAPTER 11 · EXECUTION SURFACES

事故十一：为新客户端复制一套循环，两个入口开始争写同一会话。

白话理解：Web、Headless、SDK、最小 SDK 与 ACP 是不同开机形态，不是五个内核。它们共享同一组 Agent、Session 与服务契约。

短 trace：Web 有两条通道

一次请求一次响应的方法走 HTTP；流式 token 走带心跳的 WebSocket 多路复用。连接级顺序不污染一问一答的类型契约。

判断法：入口不等于能力

谁能审批、谁接收流、谁负责退出由表面决定；真正可用的工具仍由有效插件树决定。

CHECKPOINT · CLIENT DESIGN

练习：新增 IDE 客户端，需要复制 Agent Loop 吗？

查看答案

不需要。新增薄协议表面，复用现有会话与循环服务。

本章小结

表面负责交互契约，Profile 负责组装能力，Session 负责唯一事实。

CHAPTER 12 · ERROR, RECOVERY & PRACTICE

最后一题：面对“Agent 又做了一遍”，怎样用证据而不是猜测排障？

把整门课压成一套诊断法：确定有效组合，找最后持久事实，区分控制状态与模型视图，按错误码路由，再用可推翻假设的最小实验验证。

01 / ROUTE

错误码决定处理者

限流、服务、超时、传输与空响应默认可重试；窗口溢出交给压缩；配额和凭据问题直接结束。

02 / CHECKPOINT

先持久，后副作用

模型计费前、工具体前与下一步前分别 flush，让崩溃后知道动作是否可能发生。

03 / REPLAY

恢复必须可重放

同一日志尾部得到同一修补；同一请求可从 Header 与 Surface 重建。

五步诊断卡

① 导出有效组合；② 确认 Agent 作用域和权限；③ 找日志最后一个已提交事件；④ 区分未开始、结果未知、可重试与终态；⑤ 写一个能让假设失败的最小回放或故障注入。

PROBLEM SET 01 · 副作用未知

进程在工具体执行后、结果落盘前崩溃。恢复系统应该自动标成功、自动重试，还是保留未知？

展开答题骨架

保留“结果未知”，补齐合法的工具结果与回合边界。自动标成功是在编造事实，自动重试可能重复副作用。

PROBLEM SET 02 · 重试设计

为什么重试要挂在 Step 边界，而不是包住底层流？

展开答题骨架

底层流可能已发出半截内容，直接重开会产生双份输出。Step 边界可以依据持久日志重建请求。

PROBLEM SET 03 · TEAM DELIVERY

Team 消息为什么需要 queued、目标 flush、delivered 三段？

展开答题骨架

三段把“计划发送、目标已持久接收、Lead 已确认”分开。重启时未确认消息可以重投，目标按稳定 id 去重。
