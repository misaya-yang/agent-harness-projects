KERNEL ATLAS · 7-COURSE PANORAMIC SYNTHESIS

七门课程全景：开源 Agent 架构对比与技术选型指南

横向打通 Codex (`codex-rs`)、Grok Build (`xai-org/grok-build`)、DeepSeek Harness (`deepseek-harness`)、Pi Agent (`pi-mono`)，以及新增的 OpenCode (`anomalyco/opencode`)、OpenClaw (`openclaw/openclaw`) 与 Hermes Agent (`NousResearch/hermes-agent`) 六大核心维度。选型结论是基于本地源码快照的教学归纳，不代表各上游项目的官方定位。

对比维度七门课程：各 Agent 架构实现与技术取舍核心特征
1. 会话与状态模型 Codex: Thread / Turn / Item 三层层级容器，状态由内存 Actor + 外部存储双重建模。
Grok Build: Tokio LocalSet 独立线程 Actor（`SessionActor` + `ChatStateActor`），追加持久化到 `updates.jsonl`。
DeepSeek: 纯追加型不可变 Session Log，由 `SurfaceManager` 实时投影出当前模型可见历史。
Pi Agent: 追加型 JSONL Session 树（`id` / `parentId`），通过移动叶节点指针实现非破坏性分支与回退。
OpenCode: 事件流投影进单文件 `opencode.db`，消息历史由最近一条摘要条目之后重建（`filterCompacted`），压缩对主循环完全透明。
OpenClaw: 双 SQLite 文件（全局 `state/openclaw.sqlite` + 每 agent `openclaw-agent.sqlite`），会话、transcript、standing intents 与记忆索引全落库；恢复靠状态已落库 + 事件重放。
Hermes: `~/.hermes/state.db` 以 `parent_session_id` 串起会话血统，外加压缩标记、压缩锁与 gateway 路由表；cron 任务单独持久化到 `jobs.json`。 State vs Tree
2. 通信协议与交互 Codex: App Server 双向 JSON-RPC 协议，规范化 Request 与 started / delta / completed 通知。
Grok Build: 采用 Agent Client Protocol (ACP) 标准协议，扩展 XAI 专有事件（`rewind`, `compaction`）。
DeepSeek: 面向自动化与工具管线的 JSON-RPC stdio / NDJSON 协议，流式提交 committed assistant 消息。
Pi Agent: LF-only JSONL Coding-Agent RPC 与 4 字节大端前缀 + 定长 CBOR 独立 Server Protocol 双协议面。
OpenCode: 单一本地 HTTP 服务器承载内核：`POST /session/:id/message` 是唯一喂脑入口，`GET /event`（SSE）是唯一广播出口；TUI、IDE、GitHub、CI 全是同构客户端。
OpenClaw: Gateway 统一接入模型、工具、消息通道与 macOS/iOS/Android/Wear 伴生应用；Telegram/Discord 等通道经 `src/channels/*` 抽象路由。
Hermes: 单个 Python 内核同时驱动 CLI、23+ 平台消息网关、TUI、Zed ACP、MCP server 与 Electron 桌面六面；`acp_adapter` 负责协议翻译。 JSON-RPC / ACP / SSE / CBOR
3. 沙箱与权限控制 Codex: `SandboxPolicy` (`ro`/`ww`/`dfa`) × `ApprovalPolicy` (`untrusted`/`on-request`/`never`) 正交二维决策矩阵。
Grok Build: `PermissionManager` (4种模式) × `SandboxProfile` (`workspace`/`read-only`/`strict`/`devbox`)，分层合并。
DeepSeek: 3 种文件效果模式 (`ro`/`ww`/`dfa`) × 独立审批通道，不可用时强制 fail-closed。
Pi Agent: 默认采用宿主进程全量权限；`Project Trust` 控制配置加载，真正安全隔离依托外部 Docker/VM。
OpenCode: 无 OS 级沙箱；按工具 × pattern 匹配 allow / ask / deny 规则，待审批以 `deferred` 终止原因表达——审批是循环的输入而非旁路。
OpenClaw: `beforeToolCall` / `afterToolCall` 钩子 + 网关审批（exec-approval-manager）；审批不通过时工具调用被替换为失败结果，模型只见结果不见例外。
Hermes: `tools/approval.py` 分级：hardline 直接拒绝、危险操作询问、cron/gateway 非交互场景各自降级；记忆写入另有 `write_approval` 闸门。 Sandbox × Approval
4. 上下文工程与压缩 Codex: 达到预算阈值触发 CompactionSummary 折叠，保留关键目标与 Diff 事实。
Grok Build: 85% 上下文压力触发全量替换压缩，专用 Sampler 生成摘要并记录 `CompactionCheckpoint`。
DeepSeek: `compaction/start` 耐久锁机制，在稳定日志区间生成摘要并通过 Surface Replacement 原子替换。
Pi Agent: `firstKeptEntryId` 动态截断点选择，后向搜索绝不切断 toolResult，单回合支持超长前缀摘要。
OpenCode: `isOverflow` 触发后把 compaction 摘要作为普通输入自喂进下一轮循环（compact then continue），`finish` 语义防御 provider 谎报。
OpenClaw: 溢出路径与阈值路径双路触发 `runAutoCompaction`；context-engine 以能力面（bootstrap / assemble-before-prompt / compact）可插拔。
Hermes: “Prompt 缓存神圣”宪法——缓存标记边界只有压缩可合法击穿；micro-compaction 与 `trajectory_compressor` 分别服务在线回合与离线轨迹。 Compaction & Summary
5. 执行世界抽象 Codex: Local / Git Worktree / Cloud 容器 / 远程宿主多环境适配。
Grok Build: `WorkspaceSession` 统一封装 FS、PTY、ProcessManager、VCS 与检查点，解耦上层调用。
DeepSeek: 严格三元解耦（Service Definition / Provider / Consumer），支持 Local、Sandbox 与 E2B 云沙箱热插拔。
Pi Agent: 原生 Node.js 宿主接口，支持 Gondolin 微虚拟机路由与 OpenShell 容器化封装。
OpenCode: 工具清单按模型 / agent / 权限三层过滤后交给 LLM；执行发生在 server 宿主侧，子代理以子 session 形式派生。
OpenClaw: 内核与宿主通过 `packages/agent-core` 能力接口解耦；run 落在 gateway 所在设备，伴生应用只是表面而非第二执行世界。
Hermes: 七个执行后端（local、Docker、Termux、Daytona、Modal 等）共享同一窄腰工具层，文件同步有独立通道，后端切换不动 loop。 Workspace Seam
6. 扩展体系与生态 Codex: 定制六边形（AGENTS.md、Memories、Skills、MCP、Hooks、Subagents）。
Grok Build: 规则文件、Skills、MCP 服务、Plugins 分发包、生命周期 Hooks 与跨会话 Memory。
DeepSeek: Cordis 插件树、Profile 继承、Agent Presets 作用域与 Dynamic Cordis 内存自修改运行时。
Pi Agent: Jiti 动态加载 TypeScript 模块（`ExtensionAPI`）、ResourceLoader 与统一 Provider 适配器。
OpenCode: 插件 hooks、自定义 commands、Skills、agents（子代理定义）与 MCP 统一汇入 tool registry 与权限管线。
OpenClaw: 约 150 个 `extensions/` 目录、SKILL.md 技能、SOUL.md 人格与 automations 工具，都以网关插件身份组合进单一 Gateway 进程。
Hermes: 学习闭环让 Agent 自创自改 SKILL.md、写回 MEMORY.md；与 OpenClaw 共享 SOUL.md / MEMORY.md / SKILL.md 文件族谱系并有双向迁移器（§ 条目是 Hermes 侧约定，OpenClaw 搬运不解析）。 Extension Hexagon
DEEPSEEK 适用 极致插件化与执行环境热插拔

追求“Everything is a Plugin”架构，需通过 Cordis IoC 容器无缝切换本地执行、E2B 云沙箱与自修改运行时的场景。

CODEX 适用 企业级多端与富客户端集成

需要严密 App Server 双向协议、细粒度正交权限矩阵与 Thread/Turn/Item 完整生命周期的生产级开发平台。

GROK 适用 高性能 Rust 终端与深度版本控制

追求极致终端响应速度、全屏 TUI 交互、ACP 标准支持以及原子级 Git Workspace Checkpoint / Rewind 恢复能力。

PI AGENT 适用 轻量嵌入式与非线性分支探索

需要极简轻量 TypeScript 内核、非破坏性 JSONL 树形分支探索（`/tree`）与 CSI 2026 同步差分渲染的应用。

OPENCODE 适用 服务器即内核的多客户端平台嵌入

需要一个本地 HTTP 服务器承载 Agent 内核，让 TUI、IDE、CI、GitHub 成为同构客户端；事件投影进单文件 SQLite，会话历史与计费统计最容易被平台接管。

OPENCLAW 适用 跨天存活的通用个人助理

“活着”不靠无限循环：有界 run 预算 + 双 SQLite 持久状态 + automations / standing intents 唤醒 + 凌晨记忆固化，多通道贯通你的设备。

HERMES 适用 单机 Python 的自演化内核

学习闭环接入 agent loop 一等公民（回合 nudge → 后台自省 → 技能/记忆写回），同一内核从 Termux 手机到 GPU 集群六面部署，并与 OpenClaw 共享两代格式谱系。

CHAPTER 01 · CORDIS COMPOSITION

先看插件树：运行时不是一个不可替换的“大循环”。

DeepSeek Harness 把模型适配器、Prompt、Tools、Session、持久化和 Agent Loop 都挂到 Cordis Context。扩展行为优先新增或替换插件，而不是修改 Loop。

四处源码分别回答“配置怎样变成树、谁驱动任务、历史写在哪里、工具怎样执行”。

为什么让 Loop 不可改

如果 Loop 直接 import 模型适配器与工具实现，那么换 Provider、加工具、改持久化都要动调度代码，每个改动都牵动全部消费者。Cordis 把这组依赖反转成服务接口：Loop 只认 ctx.llm、ctx.sessions，变化全部收进插件树。注册本身也是可撤销的：ctx.effect(() => ctx.agents.setFactory(this)) 随 Fiber dispose 逆向回收（packages/core/agent-loop/src/index.ts:350）。

失败推演：把 if (provider === 'e2b') 这类执行世界分支写进 Loop。下一次换沙箱就再写一个分支；三次之后，没有任何实现能同时跑通全部 Provider，Session 回放也会被 Provider 细节污染。

兄弟 harness 怎么摆这块

Pi 把宿主进程本身当执行世界，换环境等于换宿主；Codex 有一个特权协议核心，App Server 是唯一入口。DeepSeek Harness 连 boot() 都只是常规挂载（packages/boot/app-boot/src/index.ts:757），树外没有第二套真相。

组合规则也刻意简单：Bundle 与 Patch 逐层叠加，命中的行按 id 整行替换（packages/boot/app-boot/src/profile.ts:413）。配置可读出唯一有效树，这是所有排障的第一步。

INTERVIEW · 30 SECONDS

“换掉模型 Provider，最小改动是什么？这题在考什么？”

展开模范答案

Loop 零改动。新增或替换一个 LlmAdapter 插件条目，Loop 仍经 ctx.llm 发起流式调用；变化停在 Provider 边界，不扩散到会话与模型层。

考察点是区分“走扩展点”与“拉代码分叉”。回答“在 Loop 里加判断”即出局——那说明把运行时理解成了单体。

边界

依赖方向是单向的：插件知道 Loop，Loop 不知道插件。当你发现新特性需要在 Loop 里解释自己，就已经越界了。

CHAPTER 02 · TURN / STEP LOOP

一个 Step 是一次模型请求和它触发的工具；一个 Turn 可以有多个 Step。

输入进入持久 Inbox，Loop 先记录 Turn，再组装 Prompt、读取日志、发起流式请求、执行工具并回注结果；只有没有欠下的工作时 Turn 才结束。

Turn / Step 事件步进机idle
  1. turn/start
  2. claim inbox
  3. step/start
  4. user/message
  5. request/header
  6. assistant/chunk*
  7. assistant/message
  8. tool/call → result
  9. step/end → turn/end

逐步观察“活的控制”怎样留下“持久事实”。

Inbox 为什么必须耐久

Turn 是否结束，取决于“还有没有欠下的工作”；工具回注的 next-step 输入也在队列里。队列若只在内存，重启后已承诺的输入永远没喂给模型，Turn 要么悬挂要么丢工。Inbox.splice() 先 append agent/inbox/spliced 事件、再改内存队列（packages/core/agent/src/inbox.ts:139），重建时从 seed 之后重放——队列顺序因此成为可重放事实。

失败推演：取消路径若丢了 splice 事实，重建出的 Agent 看到的是“半个承诺”。这比显式失败危险，因为它没有错误可查。

兄弟 harness 如何接插话

Pi 把 steering / follow-up 放内存队列，在 Turn 结束点裁决优先级；Codex 用独立线程 Actor 串行接收。DeepSeek Harness 不区分“插话”与“排队输入”：一律 splice 进 Inbox，统一在 turn() 认领（packages/core/agent-loop/src/agent.ts:246），随后 preStep() 组装本轮 Prompt（packages/core/agent-loop/src/agent.ts:225）。差异不在谁更快，而在插话是否留下了可恢复的证据。

INTERVIEW · 30 SECONDS

“Turn 和 Step 的区别？模型一次返回 3 个 tool call 会发生什么？”

展开模范答案

Step 是一次模型请求及其触发的工具批次；Turn 是一整段用户工作，可以含多个 Step。3 个调用按 execution mode 分组，parallel body 可重叠，但结果按模型顺序写回日志；exclusive call 形成 barrier。

考察点是“调度顺序”与“日志顺序”是不是两件事。答“并行就会乱序，所以要禁用并行”说明两者混了。

边界

Turn 的结束由“是否还有欠下的工作”决定，不由 finish_reason 决定。Inbox 里还有一条 next-step 输入，turn 就不许关。

为什么 chunk 不进模型历史

assistant/chunk 是流式证据：服务回放、取消 prefix 保存与调试。模型只需要 committed 消息；chunk 若进历史，token 无意义膨胀，live 请求与 replay 请求还会漂移。deriveEventMessage() 的 switch 刻意写成非穷举——只有 user/message、非空 assistant/message、tool/result 投影为消息（packages/core/session/src/surface.ts:83），“哪些事件算历史”是显式契约，不是副作用。

对照：三种“历史”的存法

OpenCode 把事件投影进单文件 SQLite，历史从最近一条摘要之后重建；Pi 存 id / parentId 树，分支靠移动叶指针。DeepSeek Harness 的特点是 replacement 带 provenance：摘要消息必须引用更早的完整事件才能落地，因此“当前视图被改写”这件事本身也可审计。UI 文本永远不是真相源——它有乐观更新，也会被 replacement 过滤。

INTERVIEW · 30 SECONDS

“崩溃时日志结尾只有一个 tool/call。谁来闭合？修的是 UI 还是模型输入？”

展开模范答案

加载时、Session 发布前修：interruptedTurnClosers() 补 synthetic tool/result、step/end、interrupted turn/end（packages/core/session/src/repair.ts:27）；已有 call 无结果标为 outcome unknown。UI 和模型都只见修复后的投影，永远不见裸尾部。

核心判断句：日志是唯一事实，但事实可以残缺；残缺由谁在何时补齐，必须是契约。

为什么每个 Step 重拼 Prompt

sections、工具 schema、变量都随插件树变化。若缓存一份 Prompt 复用，重组后的树与模型实际所见就会脱节。SystemPrompt.assemble() 每步收集分层、按 order / 名称排序、再跑 system-prompt/assemble waterfall（packages/core/system-prompt/src/index.ts:467）。重拼不等于不稳定：稳定来自排序规则，而非缓存。

缓存边界由此而来：harness identity 固定在 order -100，persona 固定在 0（packages/core/system-prompt/src/index.ts:131）。新 section 用靠后的 order 追加、不插队，Provider 的前缀缓存就一直有效；一旦插到前部，其后全部失效。runtime context 干脆不进 system——pre-step 时以 user-role 快照加入，前缀天然不动。

失败推演与对照

把 cwd、git branch、时间戳塞进 system prompt：每一步前缀缓存失效，成本立刻翻倍，还谈不了重建。而任何不写事件的输入连回放都做不到——buildRequest() 先落 request/header 与 request/context，再从 deriveMessages() 构造请求（packages/core/agent-loop/src/agent.ts:426），可见性与可重建性被绑成同一件事。

同一条判断在其他 harness 也成立：Hermes 把它写成“Prompt 缓存神圣”，只有压缩可越界；Pi 干脆把动态内容放进消息流的 user turn。做法不同，理由相同——易变内容离稳定前缀越远越好。

边界

模型可见即可重放。没有对应 Session 事件的输入，不允许进入请求；没有排序契约的 section，不允许插进稳定前缀。

CHAPTER 05 · TOOL PIPELINE

模型只提出调用；工具结果要穿过有序策略后才成为权威事实。

调用先记录 tool/call，再经过 pre-execute、审批与 monotonic guard、execute、工具 body、post-execute、内容收口，最后同步通知并记录唯一 model-facing result。

为什么结果要穿过管线才算事实

模型只提出调用；真正写进日志的是 ToolRuntime.execute() 走完 pre-execute、审批与 monotonic guard、execute、post-execute、内容收口之后的唯一 model-facing result（packages/core/tools/src/index.ts:1342）。每一层只有一个落点，排障才等于“找第一处写出不一致事实的层”。

失败推演：把工具返回值直接回注、事后才补日志。取消发生在两者之间时，日志与模型上下文分叉——回放会凭空造出一个从未执行过的成功结果。

对照：审批住在哪

OpenCode 把待审批表达为 deferred 终止原因——审批是循环的输入。OpenClaw 不批则把调用替换为失败结果——模型只见结果不见例外。DeepSeek Harness 把审批放在 pre-execute 之后、body 之前，作为 one-shot seam 穿过 waterfall；三种设计回答同一个问题：被拒绝的调用留下什么证据。

INTERVIEW · 30 SECONDS

“工具确实改了文件，模型却说这次调用失败。日志能证明谁对吗？”

展开模范答案

能。body 的副作用发生在 tools/execute 内，而模型看到的内容在 post-execute 与内容收口之后才落为唯一 result。逐层比对 tool/call、原始 result、post replacement 与最终 content，第一处不一致的层就是责任层。

关键认知：tool result 不是函数返回值，是下一 Step 的模型上下文与可重放的耐久事实，两者允许且必须分层核对。

ORDERING

并发安全的 tool body 可以重叠执行，但结果仍按模型顺序提交；exclusive call 形成 barrier。并行是调度策略，不改变日志顺序。

三角色为什么必须同句出现

只声明接口、只写实现，都不构成能力缝。若 tool-fs 直接 import 本地实现（它实际只消费 ctx.fs，packages/fs/tool-fs/src/index.ts:54），接口就是摆设。FileSystem 把路径解析为带稳定 targetKey 的目标（packages/fs/fs/src/index.ts:86），Bash、PTY、LSP 才能对“在哪里执行”零感知。

失败推演：在工具 body 里写 Provider 分支。换一次执行世界就要分叉每个上层工具；FS 与 Bash 各自实现检查，还会得到两套不一致的 containment 判定。

换世界不等于换一切

E2B 被源码明确标注为实验性 provider-composition POC（packages/e2b/README.md:5）：搬的是文件与进程的执行世界，不搬 Harness 进程、Agent / Session、持久化与 SDK buffer；凭据也不随迁移泄漏，父环境按名称剔除后才交给子进程。对照：Pi 以宿主全权为默认，隔离交给外部 Docker / VM；Codex 用策略 × 沙箱正交矩阵。三种取舍，问题相同：换执行环境的最小改动面在哪。

边界

一个缝能不能被称为能力缝，看 Consumer 是否零分叉。凡需要改上层工具才换得掉的 Provider，说明缝还没切到位。

CHAPTER 08 · PROFILE / BUNDLE / PRESET

Profile 组合进程；Preset 组合一个 Agent 的能力面。

Profile 把 Bundle、用户 Patch 与启动 Patch 叠成全局插件树；Preset 在 Agent scope 下挂载 per-session 组合。已有输出的 Agent 不能随意 recompose，否则日志中的旧工具可能失去解释。

整行替换与禁止中途换树，防的是同一件事

Patch 命中一行就替换整行 config，不做深合并。深合并的有效配置无法从任何单个文件复现，排障退化成猜叠放顺序；整行替换让 dump-config 成为唯一答案。Preset 也守同一原则：Agent 一旦产出内容就不允许 recompose（packages/preset/agent-presets/src/index.ts:458），否则日志里的旧工具 schema 在当前树中失去解释。

Preset 的边界是组成边界

Preset 只是挂到 Agent scope 的 agent.cordis.yml 目录，子 Agent 经 composeFrom() 复用父代组合、不重读变更后的文件（packages/preset/agent-presets/src/index.ts:316）。发布 process-global Service 的行会被 invariant 直接拒绝（packages/preset/agent-presets/src/invariant.ts:39）。所以“给只读研究 Agent 收紧 sandbox”是错误需求：preset 能改工具集，不能改安全档位——安全档位属于 Profile。

边界

Profile 影响新进程，Preset 影响新 Agent；两者都无权改写已开始 Session 的历史。想让变化生效，先问它该落在哪一层。

CHAPTER 09 · CONTEXT & COMPACTION

Compaction 是带锁、校验和 Surface Replacement 的事务。

系统先在稳定日志上选区与生成摘要，再验证选区未被异步工作改变，最后用有 provenance 的 replacement 落地；原始事件仍留在日志中。

  1. 触发：pre-step 压力或 canonical context overflow。
  2. 锁定：append compaction/start，阻止同范围重入。
  3. 选区：保留近期 tail，不切断 tool call / result 配对。
  4. 摘要：复用 request system/tools，生成 text-only checkpoint。
  5. 验证：whole-surface 或 selected-span 必须仍稳定。
  6. 替换：追加 summary 与 replacement，再 compaction/end。

锁为什么是事件、验证为什么在摘要之后

Compaction 的锁不是 mutex，而是同步追加的 compaction/start 事件（packages/compaction/compaction-basic/src/region.ts:189）。进程会崩、异步任务会被取消；内存锁在重启后无法解释“为什么这里没有 end”，unmatched start 却是可检测状态。摘要生成期间日志仍在 append，异步完成后必须复查选区是否仍稳定——whole-surface 或 selected-span 任一被改动就放弃本次替换（packages/compaction/compaction-basic/src/region.ts:387），宁可重来，不把过期摘要强加到已变化的历史上。

对照：四种“历史太长”的答案

Grok 在 85% 压力点做全量替换并记 checkpoint；Pi 用 firstKeptEntryId 动态截断、绝不切断 tool 配对；Hermes 只在缓存边界被压缩击穿时动手；DeepSeek Harness 走区间事务：选区保留 recent tail 且不切断 call / result 配对（packages/compaction/compaction-basic/src/region.ts:98），原始事件留在日志。四家共享一条底线：截断决策必须留下可解释的证据。

INTERVIEW · 30 SECONDS

“Compaction 是不是删除聊天历史？”

展开模范答案

不是。在稳定区间上生成 summary，以带 provenance 的 surface replacement 落地；日志仍 append-only，原事件都在。变的是模型投影：更早的节点被一条引用它们的摘要取代，重放仍可复现整个替换过程。

加分点：说清异步摘要完成后还要重选区验证——这是它区别于“简单截断数组”的关键。

DO NOT SAY “DELETE CHAT”

Tool-result pruning 同样通过 shadow price 与 Surface replacement 降低模型成本；它没有从 append-only log 中抹掉原始结果。

SOURCE-ALIGNED TEACHING SKELETON · DYNAMIC CORDIS HOST RUNNER

Dynamic Cordis 内存自修改沙箱运行器 (`DynamicCordisRunner`)

下面是根据 `packages/extensions/cordis-host-runner` 与 `tool-cordis` 整理的教学骨架，不是上游源码复制。真实实现通过 `sandbox.ts` 的 Node API traps、`createSandbox()` / `evaluateHostCode()` 与 Cordis 生命周期共同完成，而且明确不是恶意代码隔离边界。

// packages/extensions/cordis-host-runner/src/index.ts import { Context, Service } from "cordis"; import * as vm from "node:vm"; export interface PackageDefinition { id: string; version: number; code: string; declaredServices: string[]; } export class DynamicCordisRunner extends Service { private packages = new Map<string, PackageDefinition>(); private activePackageId: string | null = null; private activeDisposer: (() => void) | null = null; constructor(ctx: Context) { super(ctx, "dynamicCordis", true); } /// 步骤 1: 注册动态包（语法解析校验与版本递增注册） public definePackage(id: string, code: string, declaredServices: string[] = []): { success: boolean; error?: string } { try { new vm.Script(code, { filename: `dynamic-cordis://${id}.js` }); const version = (this.packages.get(id)?.version ?? 0) + 1; this.packages.set(id, { id, version, code, declaredServices }); return { success: true }; } catch (err: any) { return { success: false, error: err.message }; } } /// 步骤 2: 激活动态包（创建白名单 Façade，执行并热挂载 Cordis Plugin 作用域） public async activatePackage(id: string): Promise<{ success: boolean; error?: string }> { const pkg = this.packages.get(id); if (!pkg) throw new Error(`Package ${id} not found`); // 白名单 Façade：隔离 Node 全局危险对象，仅受控暴露 Cordis 服务 const sandboxFaçade = { console, ctx: { on: this.ctx.on.bind(this.ctx), get: (name: string) => (this.ctx as any)[name], provide: (name: string, impl: any) => this.ctx.provide(name, impl), }, harness: { registerTool: (toolDef: any) => (this.ctx as any).tools?.register(toolDef), }, }; const vmContext = vm.createContext(sandboxFaçade); const script = new vm.Script(`(function(ctx, harness) { ${pkg.code}\n })`); try { const entryFn = script.runInContext(vmContext, { timeout: 1000 }); // 原子热替换：注销旧 Fork，挂载新 Plugin 作用域 if (this.activeDisposer) { this.activeDisposer(); this.activeDisposer = null; } const fork = this.ctx.plugin((subCtx: Context) => { entryFn(subCtx, sandboxFaçade.harness); }); this.activeDisposer = () => fork.dispose(); this.activePackageId = id; return { success: true }; } catch (err: any) { return { success: false, error: `Activation failed: ${err.message}` }; } } }

架构精要：Dynamic Cordis 允许 Agent 在运行时自主编写并加载 Cordis 插件，但 `node:vm` 仅提供独立上下文而非恶意代码防御边界；动态包只存在于当前进程内存，重启自动销毁。

为什么一个内核、多个表面

Session 只有一个权威写入者。若每个入口自带一套循环，同一日志会出现两个“当前状态”，崩溃修复与审批契约同时失效。所以表面被刻意做薄：headless 不发明私有协议，只提交一条普通 user message、等待 idle（packages/bundle/headless/README.md:5）；ACP 是 automation-only，审批按其机器策略回答（packages/acp/acp/src/index.ts:121）；SDK server 是一条 line-delimited JSON-RPC 插件（packages/sdk/server/src/index.ts:46）。表面证明自己是消费者，不是宿主。

对照 OpenCode：server 即内核，TUI / IDE / CI 都是同一 HTTP 面的客户端。两种路线回答同一问题——新入口接入时，改动必须停在表面层。

边界

表面选择决定交互契约——谁能审批、谁收流式更新、谁一次性退出；能力上限仍由有效插件树决定。别用入口推断能力。

PROBLEM SET 01 · 架构设计题

“为什么说 DeepSeek Harness 的核心是 Everything is a Plugin？如何将底层执行环境无缝迁移至 E2B 云端沙箱？”

展开答题骨架与解耦推演

【场景定义】 团队需要将原本运行在本地开发机上的 DeepSeek Harness 运行时迁移至远程 E2B 云端安全隔离沙箱中，要求上层数十个模型工具（文件读写、Bash 命令、PTY 终端、LSP 诊断）代码零改动、零分叉。

【归属层/故障机理分析】 属于 Cordis 插件树组合（`Chapter 01: Cordis Composition`）与能力缝架构（`Chapter 06: Capability Seams`）。核心机理在于通过 IoC（控制反转）与依赖注入，将能力严格拆分为三元组：Service Definition（`ctx.fs`, `ctx.subprocess`）、Service Provider（`fs-local` vs `fs-e2b`）与 Tool Consumer（`tool-fs`, `tool-bash`）。上层工具只面向抽象 Service 契约编程。

【关键证据链/判定条件】
1. 定义抽象：`FileSystem` 接口固定标准路径规范与操作签名。
2. 配置热插拔：在 Profile Patch 文件（`cordis.patch.yml`）中将 `packages/fs/fs-local` 替换为 `packages/e2b/fs-e2b`。
3. 消费者透明：`tool-fs` 在执行 `ctx.fs.readFile()` 时自动路由至 E2B 容器，Agent Loop 与工具逻辑完全无感。

【解决方案与系统级防线】
• 坚持纯粹的 Provider 隔离设计，禁止在 Agent Loop 或具体工具内部编写针对特定执行环境的 `if-else` 分支。
• 进程启动时由 Cordis Bundle 解析有效插件树，保证执行世界的替换只发生在 Provider 边界，不扩散至会话与模型层。

PROBLEM SET 02 · 故障排查题

“宿主进程崩溃重启后，Session Log 加载恢复的会话为什么与 UI 呈现不一致并出现重复工具调用？”

展开答题骨架与修复管线

【场景定义】 宿主进程执行耗时测试时意外断电或被 OOM 杀掉，重启后加载持久化日志，发现 UI 上显示最后一步工具执行成功，但模型在下一轮对话时却重新发起了一模一样的工具调用。

【归属层/故障机理分析】 属于事件日志投影与崩溃修复机制（`Chapter 03: Session Event Log` & 崩溃尾部修复）。故障机理为：进程崩溃时物理日志中仅写入了 `tool/call` 事件，尚未写入对应的 `tool/result`，形成了悬空的未闭合 Crash Tail；恢复引擎若未执行合成修复，将导致 `SurfaceManager.deriveMessages()` 无法正确派生模型历史。

【关键证据链/判定条件】
1. 查阅 Session Log 尾部：定位到孤立的 `tool/call` 事件，其后缺失 `tool/result`。
2. 检查 `interruptedTurnClosers()`：恢复引擎应自动为悬空工具合成 `synthetic tool/result { error: "interrupted" }` 并闭合 `turn/end`。
3. 检查模型输入投影：确认修补后的事件日志是否正确投影为包含失败标记的历史节点。

【解决方案与系统级防线】
• 牢记“UI 不是真相源，Session Log 才是唯一事实源”。
• 严格执行崩溃恢复管线（Repair Pipeline），对未确认结果的工具调用显式注入合成失败标记，禁止未闭合的悬空状态进入模型推理。

PROBLEM SET 03 · 安全攻防题

“Dynamic Cordis 自修改机制带来了哪些严重安全隐患？为什么不能将其作为恶意代码防御边界？”

展开答题骨架与安全边界

【场景定义】 允许 Agent 在运行时使用 `cordis_define` 和 `cordis_run` 自主编写并安装新插件，以动态扩展当前任务所需的能力。

【归属层/故障机理分析】 属于自修改运行时与扩展安全边界（`Chapter 10: Extension Runtime`）。核心事实：Dynamic Cordis 基于 Node.js `node:vm` 构建，而 Node 官方明确声明 `node:vm` 仅提供独立的全局对象和作用域，**不是针对恶意不可信代码的安全沙箱**。

【关键证据链/判定条件】
1. 原型链逃逸：在 `node:vm` 内可通过 `this.constructor.constructor("return process")()` 轻易获取宿主 `process` 对象并越权执行。
2. 内存常驻与提权：动态加载的包直接运行在宿主主进程内，能够直接调用注入的 `ctx.provide()` 覆盖核心系统服务。
3. 策略绕过：未受审批的动态包可静默注册具备网络外联或文件破坏能力的未受限工具。

【解决方案与系统级防线】
• Dynamic Cordis 必须设定为显式 Opt-in 特性，严禁在多租户或不可信输入环境下默认启用。
• 动态插件的挂载必须接入 `UserApproval` 一次性人工审批通道，且动态包仅保留在内存中，进程重启自动销毁。
