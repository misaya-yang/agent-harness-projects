KERNEL ATLAS · 7-COURSE PANORAMIC SYNTHESIS

七门课程全景：开源 Agent 架构对比与技术选型指南

横向打通 Codex (`codex-rs`)、Grok Build (`xai-org/grok-build`)、DeepSeek Harness (`deepseek-harness`)、Pi Agent (`pi-mono`)，以及新增的 OpenCode (`anomalyco/opencode`)、OpenClaw (`openclaw/openclaw`) 与 Hermes Agent (`NousResearch/hermes-agent`) 六大核心维度。选型结论是基于本地源码快照的教学归纳，不代表各上游项目的官方定位。

对比维度七门课程：各 Agent 架构实现与技术取舍核心特征
1. 会话与状态模型 Codex: Thread / Turn / Item 三层层级容器，状态由内存 Actor + 外部存储双重建模。
Grok Build: Tokio LocalSet 独立线程 Actor（`SessionActor` + `ChatStateActor`），追加持久化到 `updates.jsonl`。
DeepSeek: 纯追加型不可变 Session Log，由 `SurfaceManager` 实时投影出当前模型可见历史。
Pi Agent: 追加型 JSONL Session 树（`id` / `parentId`），通过移动叶节点指针实现非破坏性分支与回退。
OpenCode: 事件流投影进单文件 `opencode.db`，消息历史由最近一条摘要条目之后重建（`filterCompacted`），压缩对主循环完全透明。
OpenClaw: 双 SQLite 文件（全局 `state/openclaw.sqlite` + 每 agent `openclaw-agent.sqlite`），会话、transcript、standing intents 与记忆索引全落库；恢复靠状态已落库 + 事件重放。
Hermes: `~/.hermes/state.db` 以 `parent_session_id` 串起会话血统，外加压缩标记、压缩锁与 gateway 路由表；cron 任务单独持久化到 `jobs.json`。 State vs Tree
2. 通信协议与交互 Codex: App Server 双向 JSON-RPC 协议，规范化 Request 与 started / delta / completed 通知。
Grok Build: 采用 Agent Client Protocol (ACP) 标准协议，扩展 XAI 专有事件（`rewind`, `compaction`）。
DeepSeek: 面向自动化与工具管线的 JSON-RPC stdio / NDJSON 协议，流式提交 committed assistant 消息。
Pi Agent: LF-only JSONL Coding-Agent RPC 与 4 字节大端前缀 + 定长 CBOR 独立 Server Protocol 双协议面。
OpenCode: 单一本地 HTTP 服务器承载内核：`POST /session/:id/message` 是唯一喂脑入口，`GET /event`（SSE）是唯一广播出口；TUI、IDE、GitHub、CI 全是同构客户端。
OpenClaw: Gateway 统一接入模型、工具、消息通道与 macOS/iOS/Android/Wear 伴生应用；Telegram/Discord 等通道经 `src/channels/*` 抽象路由。
Hermes: 单个 Python 内核同时驱动 CLI、23+ 平台消息网关、TUI、Zed ACP、MCP server 与 Electron 桌面六面；`acp_adapter` 负责协议翻译。 JSON-RPC / ACP / SSE / CBOR
3. 沙箱与权限控制 Codex: `SandboxPolicy` (`ro`/`ww`/`dfa`) × `ApprovalPolicy` (`untrusted`/`on-request`/`never`) 正交二维决策矩阵。
Grok Build: `PermissionManager` (4种模式) × `SandboxProfile` (`workspace`/`read-only`/`strict`/`devbox`)，分层合并。
DeepSeek: 3 种文件效果模式 (`ro`/`ww`/`dfa`) × 独立审批通道，不可用时强制 fail-closed。
Pi Agent: 默认采用宿主进程全量权限；`Project Trust` 控制配置加载，真正安全隔离依托外部 Docker/VM。
OpenCode: 无 OS 级沙箱；按工具 × pattern 匹配 allow / ask / deny 规则，待审批以 `deferred` 终止原因表达——审批是循环的输入而非旁路。
OpenClaw: `beforeToolCall` / `afterToolCall` 钩子 + 网关审批（exec-approval-manager）；审批不通过时工具调用被替换为失败结果，模型只见结果不见例外。
Hermes: `tools/approval.py` 分级：hardline 直接拒绝、危险操作询问、cron/gateway 非交互场景各自降级；记忆写入另有 `write_approval` 闸门。 Sandbox × Approval
4. 上下文工程与压缩 Codex: 达到预算阈值触发 CompactionSummary 折叠，保留关键目标与 Diff 事实。
Grok Build: 85% 上下文压力触发全量替换压缩，专用 Sampler 生成摘要并记录 `CompactionCheckpoint`。
DeepSeek: `compaction/start` 耐久锁机制，在稳定日志区间生成摘要并通过 Surface Replacement 原子替换。
Pi Agent: `firstKeptEntryId` 动态截断点选择，后向搜索绝不切断 toolResult，单回合支持超长前缀摘要。
OpenCode: `isOverflow` 触发后把 compaction 摘要作为普通输入自喂进下一轮循环（compact then continue），`finish` 语义防御 provider 谎报。
OpenClaw: 溢出路径与阈值路径双路触发 `runAutoCompaction`；context-engine 以能力面（bootstrap / assemble-before-prompt / compact）可插拔。
Hermes: “Prompt 缓存神圣”宪法——缓存标记边界只有压缩可合法击穿；micro-compaction 与 `trajectory_compressor` 分别服务在线回合与离线轨迹。 Compaction & Summary
5. 执行世界抽象 Codex: Local / Git Worktree / Cloud 容器 / 远程宿主多环境适配。
Grok Build: `WorkspaceSession` 统一封装 FS、PTY、ProcessManager、VCS 与检查点，解耦上层调用。
DeepSeek: 严格三元解耦（Service Definition / Provider / Consumer），支持 Local、Sandbox 与 E2B 云沙箱热插拔。
Pi Agent: 原生 Node.js 宿主接口，支持 Gondolin 微虚拟机路由与 OpenShell 容器化封装。
OpenCode: 工具清单按模型 / agent / 权限三层过滤后交给 LLM；执行发生在 server 宿主侧，子代理以子 session 形式派生。
OpenClaw: 内核与宿主通过 `packages/agent-core` 能力接口解耦；run 落在 gateway 所在设备，伴生应用只是表面而非第二执行世界。
Hermes: 七个执行后端（local、Docker、Termux、Daytona、Modal 等）共享同一窄腰工具层，文件同步有独立通道，后端切换不动 loop。 Workspace Seam
6. 扩展体系与生态 Codex: 定制六边形（AGENTS.md、Memories、Skills、MCP、Hooks、Subagents）。
Grok Build: 规则文件、Skills、MCP 服务、Plugins 分发包、生命周期 Hooks 与跨会话 Memory。
DeepSeek: Cordis 插件树、Profile 继承、Agent Presets 作用域与 Dynamic Cordis 内存自修改运行时。
Pi Agent: Jiti 动态加载 TypeScript 模块（`ExtensionAPI`）、ResourceLoader 与统一 Provider 适配器。
OpenCode: 插件 hooks、自定义 commands、Skills、agents（子代理定义）与 MCP 统一汇入 tool registry 与权限管线。
OpenClaw: 约 150 个 `extensions/` 目录、SKILL.md 技能、SOUL.md 人格与 automations 工具，都以网关插件身份组合进单一 Gateway 进程。
Hermes: 学习闭环让 Agent 自创自改 SKILL.md、写回 MEMORY.md；与 OpenClaw 共享 SOUL.md / MEMORY.md / SKILL.md 文件族谱系并有双向迁移器（§ 条目是 Hermes 侧约定，OpenClaw 搬运不解析）。 Extension Hexagon
DEEPSEEK 适用 极致插件化与执行环境热插拔

追求“Everything is a Plugin”架构，需通过 Cordis IoC 容器无缝切换本地执行、E2B 云沙箱与自修改运行时的场景。

CODEX 适用 企业级多端与富客户端集成

需要严密 App Server 双向协议、细粒度正交权限矩阵与 Thread/Turn/Item 完整生命周期的生产级开发平台。

GROK 适用 高性能 Rust 终端与深度版本控制

追求极致终端响应速度、全屏 TUI 交互、ACP 标准支持以及原子级 Git Workspace Checkpoint / Rewind 恢复能力。

PI AGENT 适用 轻量嵌入式与非线性分支探索

需要极简轻量 TypeScript 内核、非破坏性 JSONL 树形分支探索（`/tree`）与 CSI 2026 同步差分渲染的应用。

OPENCODE 适用 服务器即内核的多客户端平台嵌入

需要一个本地 HTTP 服务器承载 Agent 内核，让 TUI、IDE、CI、GitHub 成为同构客户端；事件投影进单文件 SQLite，会话历史与计费统计最容易被平台接管。

OPENCLAW 适用 跨天存活的通用个人助理

“活着”不靠无限循环：有界 run 预算 + 双 SQLite 持久状态 + automations / standing intents 唤醒 + 凌晨记忆固化，多通道贯通你的设备。

HERMES 适用 单机 Python 的自演化内核

学习闭环接入 agent loop 一等公民（回合 nudge → 后台自省 → 技能/记忆写回），同一内核从 Termux 手机到 GPU 集群六面部署，并与 OpenClaw 共享两代格式谱系。

用一个“测试失败”，找出每层真正负责什么。

假设模型已经给出工具调用，但测试迟迟没有结果。本章沿输入、会话状态、可观察事件与工作区副作用逐层追踪，建立第一条可用于调试的源码路线。

SOURCE ROUTE · GROK BUILD 07b2f71

先读四个入口，再用架构责任探针做定位。

这四处源码把“收到任务、保存状态、呈现进度、执行副作用”分给不同拥有者。

  1. crates/codegen/xai-grok-shell/src/session/acp_session.rsSessionActor 接收请求并编排一次会话工作。
  2. crates/codegen/xai-chat-state/src/actor/mod.rsChatStateActor 持有 conversation、token 与 prompt index。
  3. crates/codegen/xai-grok-pager/src/acp/tracker.rsAcpUpdateTracker 把 SessionUpdate 变成用户看到的进度。
  4. crates/codegen/xai-grok-workspace/src/session/mod.rsWorkspaceSession 拥有文件、进程与可回退检查点。

学完本章你能：面对“模型结束但测试没返回”，先判断状态、事件还是副作用链路断了，而不是笼统归因于模型。

五个责任层

Pager 负责全屏终端与交互；Shell 承载 Session、采样和持久化；Agent 组装模型、工具与系统提示；Tools 管注册、schema、通知和实现；Workspace 拥有文件系统、VCS、进程、权限与检查点。

ROOT-CAUSE LENS

显示错位查 Pager；回合卡住查 Shell；工具不存在查 Agent/Registry；命令状态错查 Workspace。分层的价值，是让故障有唯一首要归属。

  1. xai-grok-pager：scrollback、prompt、modal 与渲染。
  2. xai-grok-shell：Session host、sampling、compaction、events。
  3. xai-grok-agent/tools：提示词、工具能力与调用桥。
  4. xai-grok-workspace：真实世界副作用与恢复点。

CHAPTER 02 · TURN RUNTIME

一次回合，是 Actor、采样与工具执行反复咬合。

每个 Session 运行在独立线程的 Tokio LocalSet 上：SessionActor 负责编排，ChatStateActor 持有 conversation、token 与 prompt index，Persistence actor 异步落盘。模型若返回 tool call，循环执行并回注，直到 stop reason 收敛。

循环中的控制点

每次采样前，系统可能注入项目规则、Skills、Memory 与系统提醒；采样过程中发出消息 chunk、thinking 与 tool call；工具完成后结果进入下一次采样。取消、steer、compact 都在安全间隙改变循环，而不是任意撕开状态。

  1. 接收 prompt，写入 Session history。
  2. 构造 Agent 能力与采样请求。
  3. 流式接收消息、思考与工具调用。
  4. 执行工具并回注，判断继续或结束。

CHAPTER 04 · TOOL REGISTRY

工具不是函数集合，而是动态裁剪后的能力视图。

AgentBuilder 选择工具，ToolRegistry 保存定义与实现，ToolBridge 把模型调用转换为受控执行；schema 校验、名称映射、通知、重试与输出归一化分属不同责任。

从定义到结果

模型看见的是 schema 和模型侧名称；运行时保留 canonical identity。调用先验证参数和可见性，再经过 ToolCallContext、权限与实现，流式输出被归一化为可持久化、可展示、可回注的结果。

FAILURE ORDER

未发现 → 查 allowlist/denylist；参数错 → 查 schema；执行错 → 查实现与 Workspace；UI 不更新 → 查 ToolNotification；模型误判 → 查归一化后的结果。

  1. Registry：工具身份、定义、实现与索引。
  2. Bridge：把采样返回的调用接入运行时。
  3. Context：call ID、session、取消与执行元数据。
  4. Output：流式片段、错误类型与截断策略。

SOURCE-ALIGNED TEACHING SKELETON · RUST WORKSPACE VCS

VCS Checkpoint 检查点捕获与原子回滚算法 (`WorkspaceSession`)

下面是根据 `xai-grok-workspace`、hunk tracker 与 rewind checkpoint 数据结构整理的教学骨架，不是上游源码复制，也不承诺可独立编译；真实恢复还包含持久化、路径校验、hunk/git 状态与失败处理。

// crates/codegen/xai-grok-workspace/src/session/mod.rs use std::collections::HashMap; use std::path::{Path, PathBuf}; /// 文件修改前快照 #[derive(Clone, Debug)] pub struct FileSnapshot { pub path: PathBuf, pub original_content: Option<String>, pub git_head_sha: Option<String>, } /// 绑定到特定 Prompt 索引的压缩/回滚检查点 #[derive(Clone, Debug)] pub struct CompactionCheckpoint { pub prompt_index: usize, pub update_seq: u64, pub snapshots: HashMap<PathBuf, FileSnapshot>, } pub struct WorkspaceSession { pub root_dir: PathBuf, pub checkpoints: Vec<CompactionCheckpoint>, } impl WorkspaceSession { pub fn new(root_dir: PathBuf) -> Self { Self { root_dir, checkpoints: Vec::new() } } /// 步骤 1: 在执行可能产生破坏性文件修改的工具前捕获 Checkpoint pub fn create_checkpoint( &mut self, prompt_index: usize, update_seq: u64, touched_paths: &[PathBuf], ) -> std::io::Result<()> { let mut snapshots = HashMap::new(); for path in touched_paths { let full_path = self.root_dir.join(path); let content = if full_path.exists() { Some(std::fs::read_to_string(&full_path)?) } else { None // 新建文件在回滚时对应删除操作 }; snapshots.insert(path.clone(), FileSnapshot { path: path.clone(), original_content: content, git_head_sha: None, }); } self.checkpoints.push(CompactionCheckpoint { prompt_index, update_seq, snapshots }); Ok(()) } /// 步骤 2: 将工作区文件系统原子回退到指定的 Prompt Checkpoint pub fn rewind_to_checkpoint( &mut self, target_prompt_index: usize, ) -> std::io::Result<Vec<PathBuf>> { let cp_idx = self.checkpoints.iter().position(|cp| cp.prompt_index == target_prompt_index) .ok_or_else(|| std::io::Error::new(std::io::ErrorKind::NotFound, "Checkpoint not found"))?; let checkpoint = &self.checkpoints[cp_idx]; let mut restored_files = Vec::new(); for (rel_path, snapshot) in &checkpoint.snapshots { let full_path = self.root_dir.join(rel_path); match &snapshot.original_content { Some(content) => { std::fs::write(&full_path, content)?; } None => { if full_path.exists() { std::fs::remove_file(&full_path)?; } } } restored_files.push(rel_path.clone()); } // 截断目标检查点之后的所有历史检查点 self.checkpoints.truncate(cp_idx + 1); Ok(restored_files) } }

架构精要：Grok 的 `rewind` 绝非简单的丢弃聊天气泡，而是由 `WorkspaceSession` 将文件内容、删除状态与 Git Hunk 实施物理还原，再由 `SessionActor` 向客户端广播 `RewindMarker` 同步刷新视图。

CHAPTER 08 · CONTEXT & COMPACTION

压缩不是删聊天，而是 full-replace 一份可继续工作的状态。

CHAPTER 10 · AGENT BUILDER & SUBAGENTS

Agent 是可移植的能力包，子代理是派生 Session。

AgentBuilder 发现 Skills、裁剪工具、注入 Memory/Plan/Task 能力并渲染 prompt。`task` 默认后台运行，状态由单写者 coordinator 管理；当前默认最大嵌套深度为 1，隔离可选 shared workspace 或 worktree。

定义的四个旋钮

promptMode 决定扩展基础模板还是完全接管；tools/disallowedTools 决定能力面；permissionMode 决定授权交互；completionRequirement 让编排 worker 必须显式提交完成。

DISCOVERY

CHAPTER 12 · PRACTICE & INTERVIEW

用“边界、事件、证据”回答系统设计题。

真正掌握 Grok Build，不是记住 crate 名，而是能从症状定位拥有层、从事件重建状态、从安全边界解释为什么某次行动被允许或拒绝。

五步诊断法

先复现并标记 Session/turn 边界；再判断是入口、Shell、Agent、Tool 还是 Workspace；沿 ACP/XAI update 与 ToolNotification 找最后一个可靠事实；核对权限、沙箱与取消状态；最后用最小测试锁住 owning layer。

PROBLEM SET 01 · 架构设计题

“如何设计支持全屏 TUI、IDE 插件与自动化 CI 共享的 Grok Rust Agent 运行时？”

展开答题骨架与深度推演

【场景定义】 构建一套高性能企业级 Agent 运行时，要求既能在终端提供 60fps 全屏交互式 TUI，又能作为子进程服务于 VSCode/Cursor 等现代编辑器（通过 ACP 协议），还能在 CI 环境下执行无人值守的 headless 批处理重构脚本。

【归属层/故障机理分析】 属于 Rust 架构分层（`Chapter 01: Rust Architecture`）与运行表面解耦层（`Chapter 11: Execution Surfaces`）。核心机理在于将会话状态、事件驱动与交互呈现彻底解耦：`SessionActor` 运行于独立的 Tokio LocalSet 线程维持纯粹状态机，`WorkspaceSession` 封装全部真实世界副作用，上层各 Surface 仅作为输入适配器与 `SessionUpdate` 事件消费者。

【关键证据链/判定条件】
1. TUI 模式：`xai-grok-pager` 订阅 `SessionUpdate` 流并驱动局部差分终端重绘，UI 崩溃不影响会话。
2. IDE 模式：`xai-grok-shell` 暴露标准 ACP stdio 传输层，双向收发 `PromptRequest` 与 `SessionUpdate`。
3. CI 模式：`grok -p` 以 Headless 模式运行，配置非交互式授权（如 `acceptEdits` 或受限 `dontAsk`），完成时直接输出结构化 NDJSON。

【解决方案与系统级防线】
• 严格遵循单一事实源原则：UI 呈现层严禁维护任何会话业务状态，所有变更均通过规范化事件总线广播。
• `WorkspaceSession` 封装底层文件读写、PTY 命令与 VCS 快照，保证无论从哪个表面触发，底层副作用与恢复语义严格一致。

PROBLEM SET 02 · 故障排查题

“自动上下文压缩（Auto-Compaction）后，Agent 为什么丢失了先前的代码修改记忆并出现重复修改？”

展开答题骨架与排查路径

【场景定义】 在长时间的多轮代码重构任务中，会话达到 85% 上下文阈值触发自动压缩，随后 Agent 开始重复修改已经修复过的文件，甚至否定之前的架构设计决策。

【归属层/故障机理分析】 属于上下文压缩机制（`Chapter 08: Context & Compaction`）与会话持久化层（`Chapter 07: Session State`）。故障机理为：专用 Sampler 在生成摘要 Prompt 时未强制提取 `Workspace.diff_summary` 与已修改文件清单，且 `ChatStateActor` 在全量替换历史时将包含关键事实的 `ToolResult` 彻底丢弃，导致代码不变量事实断裂。

【关键证据链/判定条件】
1. 查阅 `updates.jsonl`：定位 `CompactionCheckpoint` 事件及其包含的摘要文本。
2. 检查摘要生成 Prompt：确认是否遗漏了 `Workspace.diff_summary` 与已修改文件列表。
3. 检查后续采样的 `conversation` 消息：确认是否仅包含模糊的语义泛化描述而丢失了精确的文件路径与修改哈希。

【解决方案与系统级防线】
• 压缩摘要生成器必须强制包含 `Modified Files & Invariants` 结构化必填段落，将文件状态固化为显式上下文。
• 引入两阶段增量压缩机制，在替换会话前与 `WorkspaceSession` 当前文件真实状态进行对齐校验。

PROBLEM SET 03 · 安全攻防题

“在 `--yolo`（全自动审批）模式下，如何防止恶意或越权脚本破坏开发宿主机？”

展开答题骨架与防御体系

【场景定义】 开发者在本地开启全自动批准模式执行批量任务，模型生成的构建脚本中意外包含了恶意命令（如 `rm -rf /` 或覆写系统 `.bashrc` / `.ssh` 目录）。

【归属层/故障机理分析】 属于权限与沙箱边界层（`Chapter 06: Permissions & Sandbox`）。核心认知：`--yolo` / `dontAsk` 仅改变 `PermissionManager` 的交互询问策略，绝不等于关闭底层操作系统 Sandbox。

【关键证据链/判定条件】
1. 权限流转：`PermissionManager` 在 `dontAsk` 或自动放行模式下跳过交互弹窗。
2. 底层沙箱拦截：观察 `SandboxProfile`（如 `workspace` 或 `strict`）。底层沙箱依然拦截跨根目录的 `unlinkat` / `rename` 系统调用并返回 `EPERM`。
3. 恢复点验证：检查在破坏性命令执行前是否触发了 `WorkspaceSession.create_checkpoint`。

【解决方案与系统级防线】
• 在 `WorkspaceSession` 建立双重断路器：上层策略放行后，底层依然执行基于 OS 命名空间/特权级的路径约束。
• 关键文件修改前自动捕获 VCS Checkpoint，支持通过 `RewindMarker` 一键无损回滚工作区文件与会话状态。
