CHAPTER 01 · OWNERSHIP BEFORE DEBUGGING

场景：界面显示“完成”，测试进程却还在跑。先查哪里？

先定位状态拥有者。一个生产级 Agent 把承载、会话、工具和执行世界分开，症状出现在哪一层，不等于根因属于哪一层。

为什么先找“拥有者”

同一个会话内核可以被终端、stdio、leader 和 headless 承载。展示只消费事件；会话 actor 决定控制流；工具运行时把结构化提议变成调用；workspace 才拥有文件、进程与 VCS 副作用。

MINI TRACE

界面完成 → 会话是否收到终态？→ 工具是否发出 terminal 结果？→ 子进程是否真的退出？最后一个可靠事实在哪，责任边界就从哪继续向下查。

  1. 承载层：输入、展示与连接生命周期。
  2. 会话层：单写者状态、队列与 turn 裁决。
  3. 工具层：schema、权限、派发与结果。
  4. 执行层：文件、进程、VCS 与远端代理。

CHAPTER 02 · THREE NESTED LOOPS

场景：模型已经不再调用工具，为什么任务仍没结束？

模型本次没有发出工具调用，只表明当前采样步结束。Session 事件循环、prompt 级 round 和采样步各有自己的续跑与终止责任。

把一次工作拆成三种尺度

Session actor 串行接纳输入；round 决定 goal 或 Stop hook 是否让同一 prompt 再跑一轮；采样步 完成一次模型流与一批工具。自然结束、取消、步数耗尽和 stationarity 硬停必须是不同终态。

DECISION TRACE

Response → 有工具：执行并回填 → 无工具：查 todo-gate → 排空插话 → 返回 TurnOutcome → round 再决定是否继续。

  1. 输入只经权威 FIFO 进入会话。
  2. 采样前先查重复动作与容量。
  3. 工具完成后结果必须回到历史。
  4. 终态类型决定外层能否续跑。

CHAPTER 03 · PROTOCOL AS EVIDENCE

场景：用户按了取消，稍后却收到一条“成功完成”。哪一个状态尚未正式提交？

流式输出与可回卷状态并发时，“看见文本”不等于“响应已提交”。协议层要给每次请求一个可验证的结束边界。

01 / ACCEPT

请求进入谁的队列

标准 ACP 负责会话动作；扩展方法把插话、回卷和压缩也做成协议能力。

02 / STREAM

事件是否被消费

增量与工具状态先被消费，drain barrier 收到终端确认后才能提交响应。

03 / REVOKE

取消是否撤销所有权

cancel 或 rewind 撤销在途响应的提交权，旧成功不能写回恢复后的 turn。

CHAPTER 04 · TOOL GATES

场景：模型同批调用三个工具，第二个被拒，第三个还能仍会被执行吗？

不能。工具调用是串行准备、并行执行、逐个配对回填的受控管线。

先建立三段式管线

准备依次做 JSON/schema、hook、计划模式和权限判断；出现终局拒绝后，剩余调用都得到取消结果。批准项才进入并行执行，写同一路径的动作再用资源锁串行。结果按完成顺序回填，靠 call id 配对。

NEW MECHANISMS

StructuredOutput 被建模为合成工具，校验失败沿 tool_result 自纠；MCP 工具通过 search_tool → use_tool 延迟发现，避免工具数组变化破坏缓存。

  1. 解析、hook、权限：有序准备。
  2. 批准调用：并行执行。
  3. 同资源写操作：局部串行。
  4. 每个 tool_use：必有 tool_result。

CHAPTER 05 · SIDE-EFFECT BOUNDARY

场景：工具结果写着“成功”，文件却没变。成功到底是谁的事实？

工具结果是模型可见的叙述，workspace 才是副作用的拥有者。验证必须落到执行世界。

文件与 VCS

读写、状态和差异必须来自实际工作区，而不是模型的完成宣告。

进程与终端

命令的退出、被杀原因和输出终帧，才构成进程完成证据。

本地与代理

同一窄接口可在本机执行，也可通过类型化 RPC 交给远端 workspace。

调用方超时

代理客户端不替所有场景强加 deadline；等待预算由知道任务语义的一层拥有。

两道门，三个失败方向

应用权限门先把 bash 拆成可判断动作；无法分解就转人工。OS 沙箱在启动时施加；配置明确要求保护却无法生效时拒绝启动。Linux 子进程网络再用 per-spawn 过滤器收紧，因为 Agent 本身要联网、shell 子进程未必应该联网。

SECURITY TRACE

  2. 策略命中：明确拒绝。
  3. 保护无法施加：拒绝启动。
  4. 获批后仍受内核能力上限约束。

CHAPTER 07 · RECOVERABLE SESSION

场景：崩溃发生在“写入成功”和“收到确认”之间，能安全重放吗？

只有把“不确定”建成一等状态，调用方才能做对。会话由单写者 actor 串行演进，关键追加用 generation 幂等和三态提交描述崩溃边界。

三态比 success / failure 更诚实

NotCommitted 可安全重放；Committed 表示内容已落盘但确认链失败；Indeterminate 表示结果未知。普通历史以 append-only JSONL 保存，加载时隔离坏行并修复悬空、重复的工具结果。

RECOVERY TRACE

锁 → generation 查重 → 追加 → 同步内容与目录项 → 返回三态。恢复时先修复对话不变量，再允许下一次请求。

  1. 未提交：可以重放。
  2. 已提交：不可重复执行。
  3. 不确定：先对账，再决定。
  4. 坏行隔离，成对性修复。

CHAPTER 08 · CONTEXT ECONOMICS

场景：压缩成功了，Agent 却忘了约束、重复做事。摘要哪里不够？

Compaction 是替换历史后重建一个仍能工作的现场。真正困难的是：什么必须逐字保留、什么可以总结、什么运行态要重新注入。

源码更新 · 按配置启用的 Memory V2

新版记忆不再沿用旧文件树。

源码中的 V2 是隔离管线：使用独立目录、观察收件箱、主题文件和生成的汇总记忆。会话捕获与后续整理由不同阶段负责；是否启用由配置解析，不能把 V2 写成所有安装的默认行为。

CHAPTER 09 · EXTENSION TRUST

场景：项目新加一个扩展，为什么 Agent 看见了能力却不执行？

“被发现”“对模型可见”“可被派发”“被目录信任”是四件事。扩展类型决定它做什么，来源决定它是否可信。

六类扩展，各改一层

Rules 给约束；Skills 给工作流；MCP 给外部工具；Plugins 打包多种能力；Hooks 做确定性裁决；Memory 提供跨会话证据。项目来源统一经过 folder trust，托管策略来源不可被用户静默禁用。

DISCOVERY TRACE

发现来源 → 目录信任 → 优先级去重 → 模型可见性 → 注册/延迟检索 → 权限执行。任一步失败都不应统称为“插件坏了”。

  1. Rules / Skills：改变判断与流程。
  2. MCP：增加可调用能力。
  3. Plugins：组合与分发。
  4. Hooks：在明确时点拦截。

CHAPTER 10 · MULTI-AGENT GOVERNANCE

场景：子代理已经完成，父代理为什么既没收到结果，也没被重新唤醒？

后台完成不是一个返回值，而是带取消、已消费、可见性与父会话状态的事件。单写者协调 actor 管理整棵子任务树。

子代理是完整子会话

孩子复用同一会话引擎，拥有独立循环、历史和可选 worktree。父默认只收最终报告与 turns、tool calls、duration、tokens 等元数据。深度达到限制后直接剥掉 task 工具；并发默认每 session 32，超限排队或明确拒绝。

WAKE TRACE

child complete → coordinator → 是否后台？是否取消？是否已等待消费？goal 是否占用？父通道是否开放？→ 合成 prompt 唤醒 / 留待下个边界。

  1. New：干净子上下文，强隔离。
  2. Resume：复制已完成 transcript 续做。
  3. 完成：轮询面 + 事件面双通道。
  4. 血统：统一取消、计费与可见性。

CHAPTER 11 · ONE CORE, FOUR CARRIERS

场景：升级 CLI 后，旧后台进程仍在服务。谁应该退出？

同一 ACP 内核可以进程内嵌、走 stdio、共享 leader，或通过 headless relay 连接远端。共享守护进程还必须解决锁、就绪、身份和单向版本收敛。

承载不同，状态机不能分叉

内嵌适合强沙箱边界；stdio 跟随父进程死亡；leader 让多个客户端共享后台内核；headless relay 用 ping 和 liveness 超时治理半开连接。只有“客户端严格更新”才驱逐旧 leader，避免版本抖动。另有 Computer Hub 反向把本地工具供给可信远端。

DAEMON TRACE

锁 → pid/socket 核验 → 有界登录 → ready → client_id|request_id 路由 → keepalive → 新版本单向驱逐。每个跨进程等待都必须有上限。

  1. In-process：边界随当前进程。
  2. stdio：IDE 子进程承载。
  3. Leader：本机多客户端复用。
  4. Headless relay：远端连接与重连。

CHAPTER 12 · FAILURE BUDGETS & ENGINEERING

综合场景：同样是“请求太大”，为什么有时剥图，有时必须压缩？

恢复动作会改写请求，也可能损失信息。可靠系统先按“谁能修、要改什么”分类，再让每层消耗自己的预算。

五步故障判断法

① 找最后可靠事实；② 判断是模型可修、harness 可修还是必须交给用户；③ 区分瞬态与确定性；④ 选择不扩大损失的恢复动作；⑤ 用线级真实测试锁住协议、事件和用户所见。

ERROR TRACE

字节级超限 → 剥图一次；token 超窗 → compaction；429 + Retry-After → 按服务器节奏退避；已有流式输出 → 禁止透明重放；未知状态 → 不做破坏性恢复。

  1. 传输重试：独立预算。
  2. 生成循环重采样：独立预算。
  3. 截断续写：独立预算。
  4. 子代理等待限流：独立预算。

LAB 01 · 循环诊断

模型连续 8 次读取同一份内容，应该在哪一层止损？

展开判断骨架

先看动作签名：将工具名与规范化、排序后的参数组成签名。只读重复先提醒，达到阈值后返回不可被外层续跑的 stationarity 终态。

验证：相同调用乱序后仍应被识别；硬停后 goal 与 Stop hook 不应重新点火。

LAB 02 · 压缩诊断

压缩后规则还在，但 Agent 忘了后台子任务。缺了哪条链？

展开判断骨架

项目规则应逐字重插；后台任务属于运行态，应由 compaction 后的状态 reminder 重建。摘要负责较早语义历史，不承担全部现场恢复。

LAB 03 · 多代理诊断

用户刚取消父任务，后台孩子完成了。要自动唤醒父会话吗？

展开判断骨架

不要唤醒：取消或显式 kill 是唤醒闸门的否决条件。结果仍可持久化和查询，但不能在用户刚停止后重新启动模型。

TurnOutcome
把自然结束、取消、预算耗尽与防循环硬停分开的终态词汇。
Stationarity
按规范化工具签名检测“动作没有进展”。
Full-replace
摘要旧历史，再显式重建约束、意图与运行态。
