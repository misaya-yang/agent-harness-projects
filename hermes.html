CHAPTER 12 · PRACTICE & INTERVIEW

诊断一个 Hermes 症状，先问三个问题：缓存坏没坏、nudge 到没到、锁在哪一层。

五步诊断法 + 三套面试题（架构、故障、谱系对比），把前十一章变成可操作的手感。docs/ 下有现成 RCA 样本可作教材：docs/rca-ssl-cacert-post-git-pull.md、session-lifecycle.md、micro-compaction.md。

五步诊断法（Hermes 症状通用）

  1. 表面定位：症状在哪个表面？先分清是 cli.py、gateway/run.py 还是 tui_gateway/server.py 的进程——session key 是跨表面串线索的缰绳。
  2. 缓存检查：成本/延迟异常先查 prompt cache 边界（prompt_caching.py markers、stable 前缀是否被中途重建），合法破例只有压缩。
  3. 状态检查：~/.hermes/state.db 里 sessions 的 active/compacted 位、parent_session_id 血统、compression_locks、gateway_routing；cron 单独看 jobs.json 的 claim 字段。
  4. 门控检查：工具不见 → check_fn TTL/last-good；命令被拒 → tools/approval.py 分级（hardline 拒 / 危险 ask / cron·gateway 非交互降级不同，approval.py:96/:293/:252）；记忆没写 → write_approval.py 闸门。
  5. 后台线程检查：学习没发生 → nudge 计数与 _spawn_background_review 是否触发、review agent 是否被 nudge 清零逻辑短路；cron 没跑 → tick 是否活着、mark_running_jobs_interrupted 是否有遗留。

PROBLEM SET 01 · 架构设计题

“只用一个进程内对象图描述 Hermes：AIAgent、SessionDB、ToolRegistry、BaseEnvironment、GatewayRunner 各自职责与依赖方向；为什么核心循环是同步的而网关是 asyncio？”

展开答题骨架与解耦推演

【场景定义】 面试者需要在白板上画出 Hermes 的进程内对象图，并论证同步内核 + asyncio 外围这一反直觉组合的合理性。

【组合关系/依赖方向】 AIAgent（run_agent.py:421）组合而非继承——tools 来自 registry.get_definitions，持久化委托 SessionDB（:4045），执行后端工厂化（terminal_tool.py:1816）；依赖全部指向 agent/ 子模块：god-file 是门面不是泥球，agent/ 目录正是被反向提取出来的模块群。

【关键证据链】 ① 循环同步换来工作线程中断模型（chat_completion_helpers.py:1335 的 owner_tid socket-abort 设计）——比 asyncio 嵌套回调更容易做 interrupt/redirect；② asyncio 留给 I/O 密集的网关适配器层；③ session key（gateway/session.py:1090）是唯一跨面坐标，六个表面经它汇入同一 state.db——“narrow waist” 在状态层的投影。

【反方追问/代价】 这种设计的坏处：多进程共享 sqlite 需要 WAL fallback 与修复锁（hermes_state.py:1077/:1751）；TUI dispatch 的慢 handler 要单独线程池，否则一格卡满屏。

PROBLEM SET 02 · 故障排查题

“用户报告：Telegram 上的 agent 突然不认识上周教它的技能了，而且这周 API 费用翻倍。给出两个症状的独立根因假设与排查路径。”

展开答题骨架与排查路径

【场景定义】 同一用户、同一 gateway 会话上出现“能力退化 + 成本飙升”双症状，要求先拆分独立假设再谈关联。

【技能消失假设】 skill_manage 写路径守卫拒绝过更新（security scan / pinned / quarantine）？还是 skills 属 volatile 层、focus 模式降级为 name-only（system_prompt.py:535）导致模型“看不见”正文？

【费用翻倍假设】 gateway 侧某处每轮重建工具集破缓存（宪法禁止，AGENTS.md:24-29）；或用户切换 provider 触发 _redecorate_prompt_cache_for_provider（conversation_loop.py:1607，正常但短痛）；或 compression.micro_compact 被打开（docs/micro-compaction.md 明示每回合重写历史会破前缀）。

【同源假设与证伪命令】 两症状可同源：一次失败的 compaction 留下 compression_locks 半状态，fork 出的子会话丢了 skills volatile 段重建——先查 messages.active/compacted 位。每个假设配一条证伪命令：hermes doctor / state.db SQL / cache_stats 字段（transports 的 extract_cache_stats）。

PROBLEM SET 03 · 两代演化对比题

“Hermes 与 OpenClaw 双向都能迁移对方数据。作为架构师，解释为什么迁移协议是文件目录而不是 API；并评估两代共享文件格式的策略对第三代意味着什么。”

展开答题骨架与谱系推演

【场景定义】 openclaw migrate apply hermes 与 hermes claw migrate 互为反向导入器；要求从协议设计层面解释这一现象。

【资产分层论】 个人助理的内核状态天然分层——人格（SOUL.md）/ 记忆（§ 条目，Hermes 侧约定）/ 技能（SKILL.md）是“用户资产”，sessions / plugins / logs 是“运行时私有”；两侧文档都按这条线划 import 与 archive-only（openclaw migrating-hermes.md 与 claw.py 导入清单一致）。文件目录即用户可审计、可备份、可 hand-edit 的接口，API 反而要求两代进程同时活着。

【同族认领论】 迁移器做的恰恰是翻译与搬运：openclaw→hermes 方向把源条目译成 Markdown 后按 Hermes 自己的 § 约定落目标 store，hermes→openclaw 方向原样拷贝文件族——openclaw 侧从不解析 §。真正能自证谱系的是 SOUL.md / MEMORY.md / SKILL.md 文件族 + 双向迁移脚本这对组合：格式先于产品稳定，是 agentskills.io 这种开放标准策略的延续。

【第三代与追问】 第三代要么兼容这族文件格式才能吃到存量用户，要么自带第三个迁移器；Hermes 连 .clawdbot / .moltbot 旧目录名都认（claw.py:56），说明“认历史”本身就是竞争策略。反追问：哪些东西刻意不迁移？——Hermes-only 的 cron claim、Honcho 凭据、plugins；不迁移清单即产品差异化清单。
