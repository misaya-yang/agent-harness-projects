CHAPTER 01 · ONE TURN

用户只补充一句话，不该因此杀掉正在写文件的工具。

这是回合设计的第一道考题。Hermes 把一条用户输入拆成序章、循环、尾声，并把运行中消息分成四种干预；判断依据不是“消息有多急”，而是已经完成的工作能不能安全丢。

INCIDENT → PLAIN LANGUAGE

三段式回合把一次性工作和重复工作分开。

序章恢复会话、预检压缩、冻结本轮上下文；循环重复“问模型—执行工具—回填结果”；尾声持久化、生成预算耗尽摘要并触发后台复盘。模型不再请求工具时正常结束；预算、护栏、中断和持久化失败都是带原因的出口。

短 trace：build → model → tools → model → finalize

STEER补充方向

不取消任何工作，把指引附到下一条工具结果。适合“另外也检查测试”。

REDIRECT更换目标

只取消正在生成的模型请求，保留已经完成的前缀；工具在跑时退化为 steer。

INTERRUPT立即硬停

传播到工具线程与活动子树，给每个悬挂调用补上终止结果。

QUEUE下回合再说

当前回合完整收尾后，再把消息作为一个新回合处理。

回合生命周期步进机idle
  1. run_conversation()
  2. _restore_or_build_system_prompt()
  3. should_compress()
  4. while(api_calls<max && budget>0)
  5. interruptible_streaming_api_call()

逐步观察一个回合怎样在“无 tool_calls”处正常终结。

CHAPTER CHECK

判断题：模型正在执行数据库迁移，用户说“完成后再跑一次检查”。选 steer，不杀副作用；若用户说“迁移目标错了，立刻停”，才选 interrupt。

CHAPTER 02 · MODEL & FAILURE

同一个 429，不一定该做同一件事；先分类，再恢复。

Hermes 把供应商方言归一后交给同一回合引擎。所有 API 异常先进入集中分类器，得到“可否重试、是否压缩、是否轮换凭据、是否切备用端点”四个动作位；外层循环消费结果，SDK 自带重试关闭。

01 / INCIDENT

双重重试风暴

SDK 退避一次，外层循环又退避一次；两个层都不知道对方已经花了多少预算。单一重试权威消除叠加。

02 / TRACE

集中分类

error → reason → action bits → one retry owner。请求形状修复只改本次 API 副本，不回写规范转录。

03 / EXIT

错误去哪里

机器能修的静默自愈；模型能修的作为工具结果回填；只有用户能决定的才送到界面，并带层级和是否可重试。

凭据冷却
按失败语义定时长，不只看状态码；歧义会被单独标为“未确认”。
备用链
按真实后端身份去重，避免“名字不同、其实还是同一坏端点”。
成本守卫
长上下文出现确定性空响应时，缩短昂贵重试，不让每次沉默都重新付整段输入。
CHAPTER CHECK

你能做什么：为新 provider 错误补一个分类和恢复动作，而不是在调用点再堆一段字符串判断；还能解释为什么修复历史必须 copy-on-write。

CHAPTER 03 · TOOL EXECUTION

模型一次发来六个正确调用和一个空工具名，不该整批作废。

工具进入执行器前会先去重、纠正常见参数形状、标记非法调用，再按资源冲突切成并行段和屏障段。合法调用继续执行；非法项得到自己的错误结果，保证每个调用 id 恰好对应一个结果。

  1. 目录发现：工具按注册元数据进入统一注册表；发现结果可缓存，动态 schema 在给模型展示时才求值。
  2. 渐进披露：外围目录过大时，只先展示搜索、描述、调用三个桥接入口；核心和桌面必需工具保持直接可见。
  3. 冲突调度：读—读可以并行；任何重叠写会切断当前并行段，按原顺序落到下一段。
  4. 结果治理：大结果保留预览并溢写，重复大结果变引用桩，未信任的网页与外部工具结果加语义边界。

CHAPTER 04 · EXECUTION BOUNDARY

本地能执行命令，不等于本地有操作系统沙箱。

Hermes 用同一执行环境接口服务 local、容器、远程主机与按需沙箱。每次调用启动新 shell，工作目录和环境由会话快照恢复。真正的安全边界按部署拼装；未启用的隔离层不能算作已有能力。

SECRET先拿走秘密

子进程环境剥离模型供应商凭据；启用出口代理时，执行侧只见短期 token，由出口换回真凭据。

DAMAGE再限制破坏

危险命令走审批，不可逆自毁操作有不可绕过的硬底线；写入还要过路径和自仓库守卫。

POLICY最后保护规则

关键模式在导入期冻结，会话归属走上下文作用域；进程内插件仍被视为可信代码，而不是沙箱。

CHAPTER 05 · TRANSCRIPT & RECOVERY

工具刚落盘，进程就崩了：恢复时既不能重做，也不能假装没发生。

规范转录负责“发生过什么”，API sidecar 负责“当时实际发了什么”，会话库存储血缘与可搜索原文。副作用工具在执行前先持久化调用块；写失败直接熔断，不允许副作用跑在不可恢复状态上。

01 / CANONICAL

干净转录

保留用户、assistant、tool 的规范顺序。临时记忆和中断脚手架不应污染这里。

02 / SIDECAR

精确重放

每条消息可保存 API 视图副本。内容一旦被压缩或改写，旧副本必须丢弃，避免发送过期注入。

03 / RECOVERY

按副作用清尾

纯读调用可以安全丢弃；未知、插件、外部和写类调用默认可能有副作用，恢复时保守保留。

CHAPTER 06 · MEMORY LOOP

“记住这条经验”不能阻塞用户当前的回答。

Hermes 把会话内冻结快照、磁盘活状态和外部记忆 provider 分开。回合尾的后台复盘 fork 继承必要上下文，只保留受限工具；写记忆失败、整合失败或被安全扫描拦截，都不能让主回复卡住。

FROZEN会话内快照

系统提示看到的是本轮冻结版本，避免每次记忆写入都击穿缓存；活状态要等重建边界才进入提示词。

PREFETCH回合级召回

外部 provider 的召回内容进入 user 消息 API 副本，并带“素材而非新指令”的边界。

REVIEW后台自审

独立 fork 只拿记忆、技能管理和必要只读工具，不写主会话转录。

DRIFT写入防漂移

读取失败不能当空文件；外部修改无法往返时拒绝覆盖，并留下可恢复副本。

CHAPTER 07 · EXTENSION SYSTEM

能观察发生了什么，不等于有权改变将要发生什么。

Hermes 把扩展权力分成三档：skill 是按需加载的知识包；observer hook 汇报生命周期；middleware 才能改写请求或包住执行。进程内 Python 插件明确不是沙箱，因此能力默认关闭、用户同意绑定能力集合哈希。

Skill
先把名字和摘要放进索引，正文用到时再读；适合可复用的操作知识，不占常驻上下文。
Observer
记录或轻量回应事件。坏插件不能拖垮错误分类，多个观察者可以依次运行。
Middleware
真正改变请求或执行，仅保留少数强制入口；输入先复制，避免共享可变对象被污染。
Capability
每项声明必须对应已经存在的强制 gate；升级新增能力后重新征得同意。

CHAPTER 08 · CACHE & COMPACTION

压缩后消息变少，不代表这次压缩有效。

系统提示按 stable、context、volatile 三层组装；回合级变化走 API sidecar，避免改写已发送前缀。真正接近窗口时，自动 compaction 在多个时点检查，但只有 provider 回报的真实输入用量降到线下，才算成功。

CACHE保护已发送字节

stable 前缀是缓存资产；时间、记忆与插件上下文不应在每回合重写它。

MEASURE粗估配真实回执

发送前用统一粗估，响应后用真实 token 校准；中文和 reasoning 重放不再提前触发压缩。

GATES三道闸门

摘要失败 cooldown、结构上无内容时 no-op、连续无收益时 anti-thrash；观察期探针允许系统重新尝试。

TXN提交像事务

会话锁、提交栅栏、防增长守卫和软归档共同保证“压坏了就不发布”。

SHORT TRACE

一次安全压缩的最短心智模型

pressure? → checkpoint → keep head/tail → summarize middle → validate size → commit or rollback

摘要失败也要分类：认证、网络、空内容或截断时保全原文；普通失败才允许确定性兜底。压缩结果保留用户原话、关键锚点和检索提示，让丢失变成延迟检索。

CHAPTER CHECK

你能做什么：拒绝“每回合都重写摘要”的便宜方案，因为它会持续击穿前缀缓存；并用真实 prompt 用量而非消息条数衡量收益。

CHAPTER 09 · MULTI-HOST

CLI、桌面、消息网关可以长得不同，但不能各自拥有一套回合语义。

Hermes 只有一个会话内核。宿主负责输入仲裁、事件展示和会话写租约；模型调用、工具循环、压缩和恢复都留在内核。新增前端时接协议与工具面，不复制主循环。

01 / INPUT

输入仲裁器

回合忙时，宿主根据 steer、redirect、interrupt、queue 的语义路由新消息。

02 / OUTPUT

事件多路复用

流式 token、步骤和工具生命周期通过同一事件面送往终端、WebSocket 或镜像观察者。

03 / WRITE

写锁持有者

多个路由键可能命中同一会话；按会话 id 的代际租约防两个对象交错写同一转录。

传输失败
只把明确的“对端已死”当正常断开；本机磁盘、序列化等错误必须进入崩溃诊断。
工具面门控
只有能应答桌面操作的宿主才向模型展示桌面工具，从源头消灭不存在的调用。
配置恢复
进程内配置解析失败沿用上次成功值；新进程没有这份内存快照，只能回退默认。
CHAPTER CHECK

练习：为一个新 IDE 宿主画接线图：它只需要会话 RPC、事件消费和能力门控；若方案里出现第二个 while 工具循环，边界已经错了。

CHAPTER 10 · ASYNC DELIVERY

后台任务完成时，父代理还在说话：结果不能硬塞进当前消息序列。

Hermes 把子代理结果、代理间回复与后台进程完成统一放进 completion queue，等目标会话空闲时铸成新回合。这样同时保住角色交替、前缀缓存和崩溃恢复。

DISPATCH立即给句柄

后台工作不阻塞当前回合；若目标没有耐久消费者，则降级为同步，不发一个永远没人收的句柄。

CLAIM先认领再投递

耐久账本记录派发、完成和投递状态，claim 租约防两个进程重复交付。

REPLAY有界重放

重启后可恢复新鲜结果；交付次数和结果年龄都有上限，避免僵尸任务永久回灌。

CHAPTER 11 · DELEGATION

多代理最难的不是“并发跑”，而是只把值得保留的内容带回来。

子代理是同进程内 fork 的第二个会话内核：全新转录、独立预算与终端会话，继承父工具集后减去敏感能力。父只看到任务与最终摘要，子过程不会把父窗口淹没。

CAPABILITY能力来自配置

默认委派树扁平；是否能继续 spawn 由深度上限和 orchestrator 开关推导，不接受模型自称角色来提权。

CONTROL实时 list / steer / stop

归属同时检查对象身份链与耐久会话血缘；公共 id 只是查找提示，不是授权。

BUDGET摘要聚合预算

每份摘要按父剩余窗口均分；超限保留头尾并溢写全文，避免 N 份合格摘要一起撑爆父窗口。

LIVENESS心跳与 stale 分档

空闲等待和长工具执行使用不同阈值；判定者停止续命，由既有超时机制负责处决。

PROOF自我报告不是证据

子说“已部署”只能算摘要；父必须用 URL、ID、提交或其他句柄亲自核验外部副作用。

SHORT TRACE

委派的完整闭环

validate → fork → work in isolated transcript → summarize → budget → queue → new parent turn → verify

并行写文件时可选独立 worktree；检查失败必须报告 UNKNOWN，不能把探针失败洗成“干净、零提交”。

CHAPTER CHECK

你能做什么：为子代理写一个自足任务，明确目标、上下文、输出契约和验证句柄；同时说明为什么不能把整段子转录拼回父历史。

CHAPTER 12 · OPERATING JUDGMENT

排查 Agent，不要先猜模块；先判断哪一层还有能力修复。

最终练习把前十一章压成五个问题：回合在哪一段？消息该走哪条干预通道？失败应交给机器、模型还是用户？状态是否已耐久？新结果能否在不改写前缀的情况下进入下一回合？

五步事故诊断

  1. 定范围：是单次模型请求、工具执行、整回合，还是宿主路由？先别把所有“卡住”都叫网络问题。
  2. 看退出原因：区分预算耗尽、中断、护栏、持久化失败、provider 失败与真正的正常回答。
  3. 查耐久边界：工具副作用发生前，调用块是否已经可恢复？后台完成是否已进入耐久账本？
  4. 核对缓存边界：谁改写了已发送前缀？易变内容是否错误地进入系统提示或规范转录？
  5. 验证恢复动作：重试是否只有一个 owner？压缩是否真的降到阈值下？子代理的完成是否有父侧验证句柄？

PROBLEM SET 01 · 干预选择

模型正在生成解释，用户改了最终输出格式；模型正在执行不可逆命令，用户说目标错了。两次分别选什么？

展开判断

前者用 redirect：取消在途模型请求并保留已经完成的上下文。后者用 interrupt：副作用目标错误，继续执行的代价更高。若工具正在做安全的长读且用户只是补充范围，用 steer。

PROBLEM SET 02 · 压缩设计

摘要后消息少了一半，但下一次真实输入仍高于阈值。算成功吗？下一步怎么做？

展开判断

不算。不可压的系统提示和工具 schema 可能占据地板。应记录无收益，进入 anti-thrash，避免每回合重复烧摘要；到观察期再探测，或先降低不可压固定成本。

PROBLEM SET 03 · 委派信任

三个子代理都说“修复完成”，父代理能直接向用户宣布成功吗？

展开判断

不能。摘要是自我报告。父应检查可核验句柄，运行与声明同等级的测试，并区分 implemented、tested、published 和 deployed。探针失败就报告 UNKNOWN。

回合
从一条用户输入进入，到尾声发布状态的完整单位；一次模型调用只是迭代。
sidecar
随消息持久化的 API 视图副本，不改规范正文。
checkpoint
压缩或副作用前确认外部状态可恢复的检查点。
completion queue
后台结果等待会话空闲并开启新回合的共享交付轨。
FailoverReason
把供应商异常归一为恢复动作的失败分类。
