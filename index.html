KERNEL ATLAS · 4-AGENT PANORAMIC SYNTHESIS

四大主流开源 Agent 全景架构对比与技术选型指南

横向打通 Codex (`codex-rs`)、Grok Build (`xai-org/grok-build`)、DeepSeek Harness (`deepseek-harness`) 与 Pi Agent (`pi-mono`) 六大核心维度。选型结论是基于本地源码快照的教学归纳，不代表各上游项目的官方定位。

对比维度四大主流 Agent 架构实现与技术取舍核心特征
1. 会话与状态模型 Codex: Thread / Turn / Item 三层层级容器，状态由内存 Actor + 外部存储双重建模。
Grok Build: Tokio LocalSet 独立线程 Actor（`SessionActor` + `ChatStateActor`），追加持久化到 `updates.jsonl`。
DeepSeek: 纯追加型不可变 Session Log，由 `SurfaceManager` 实时投影出当前模型可见历史。
Pi Agent: 追加型 JSONL Session 树（`id` / `parentId`），通过移动叶节点指针实现非破坏性分支与回退。 State vs Tree
2. 通信协议与交互 Codex: App Server 双向 JSON-RPC 协议，规范化 Request 与 started / delta / completed 通知。
Grok Build: 采用 Agent Client Protocol (ACP) 标准协议，扩展 XAI 专有事件（`rewind`, `compaction`）。
DeepSeek: 面向自动化与工具管线的 JSON-RPC stdio / NDJSON 协议，流式提交 committed assistant 消息。
Pi Agent: LF-only JSONL Coding-Agent RPC 与 4 字节大端前缀 + 定长 CBOR 独立 Server Protocol 双协议面。 JSON-RPC / ACP / CBOR
3. 沙箱与权限控制 Codex: `SandboxPolicy` (`ro`/`ww`/`dfa`) × `ApprovalPolicy` (`untrusted`/`on-request`/`never`) 正交二维决策矩阵。
Grok Build: `PermissionManager` (4种模式) × `SandboxProfile` (`workspace`/`read-only`/`strict`/`devbox`)，分层合并。
DeepSeek: 3 种文件效果模式 (`ro`/`ww`/`dfa`) × 独立审批通道，不可用时强制 fail-closed。
Pi Agent: 默认采用宿主进程全量权限；`Project Trust` 控制配置加载，真正安全隔离依托外部 Docker/VM。 Sandbox × Approval
4. 上下文工程与压缩 Codex: 达到预算阈值触发 CompactionSummary 折叠，保留关键目标与 Diff 事实。
Grok Build: 85% 上下文压力触发全量替换压缩，专用 Sampler 生成摘要并记录 `CompactionCheckpoint`。
DeepSeek: `compaction/start` 耐久锁机制，在稳定日志区间生成摘要并通过 Surface Replacement 原子替换。
Pi Agent: `firstKeptEntryId` 动态截断点选择，后向搜索绝不切断 toolResult，单回合支持超长前缀摘要。 Compaction & Summary
5. 执行世界抽象 Codex: Local / Git Worktree / Cloud 容器 / 远程宿主多环境适配。
Grok Build: `WorkspaceSession` 统一封装 FS、PTY、ProcessManager、VCS 与检查点，解耦上层调用。
DeepSeek: 严格三元解耦（Service Definition / Provider / Consumer），支持 Local、Sandbox 与 E2B 云沙箱热插拔。
Pi Agent: 原生 Node.js 宿主接口，支持 Gondolin 微虚拟机路由与 OpenShell 容器化封装。 Workspace Seam
6. 扩展体系与生态 Codex: 定制六边形（AGENTS.md、Memories、Skills、MCP、Hooks、Subagents）。
Grok Build: 规则文件、Skills、MCP 服务、Plugins 分发包、生命周期 Hooks 与跨会话 Memory。
DeepSeek: Cordis 插件树、Profile 继承、Agent Presets 作用域与 Dynamic Cordis 内存自修改运行时。
Pi Agent: Jiti 动态加载 TypeScript 模块（`ExtensionAPI`）、ResourceLoader 与统一 Provider 适配器。 Extension Hexagon
CODEX 适用 企业级多端与富客户端集成

需要严密 App Server 双向协议、细粒度正交权限矩阵与 Thread/Turn/Item 完整生命周期的生产级开发平台。

GROK 适用 高性能 Rust 终端与深度版本控制

追求极致终端响应速度、全屏 TUI 交互、ACP 标准支持以及原子级 Git Workspace Checkpoint / Rewind 恢复能力。

DEEPSEEK 适用 极致插件化与执行环境热插拔

追求“Everything is a Plugin”架构，需通过 Cordis IoC 容器无缝切换本地执行、E2B 云沙箱与自修改运行时的场景。

PI AGENT 适用 轻量嵌入式与非线性分支探索

需要极简轻量 TypeScript 内核、非破坏性 JSONL 树形分支探索（`/tree`）与 CSI 2026 同步差分渲染的应用。

心智模型

一次回合不是一次模型调用。它从用户输入入队开始，经过上下文组装、流式响应、工具判定、受控执行与结果回注，直到模型不再请求工具才收敛。

ROOT-CAUSE LENS

把故障归到拥有它的层：模型选错工具、策略拒绝权限、执行环境失败、还是结果没有正确回注。不要把所有失败都叫作“模型不行”。

  1. 提交：输入变成可追踪的操作。
  2. 推理：模型读取上下文并选择下一步。
  3. 行动：工具在权限与沙箱边界内执行。
  4. 回注：结果进入历史，驱动下一次判断。

CHAPTER 02 · APP SERVER PROTOCOL

把 UI 与内核之间的对话，读成一条事件河流。

当前 App Server 以双向 JSON-RPC 为协议骨架：客户端发起 Thread/Turn 请求，服务端用 thread/*、turn/* 与 item/* 通知流式报告事实。

请求与通知

向内的是请求，向外的是证据。连接先完成 initialize/initialized 握手，再 start、resume 或 fork Thread；Turn 可被 steer 或 interrupt，Item 则承载消息、命令、文件变更和工具调用。

CLI、IDE 与自定义客户端因此可以共享同一运行时，同时拥有不同的呈现、持久化和审批界面。

  1. Request：thread/start、turn/start、审批决定与中断。
  2. Notification：item/started、delta、item/completed 与 turn/completed。
  3. 可恢复性：状态从持久化 Thread 与事件重建，而不是从 UI 猜测。

CHAPTER 03 · TOOL LIFECYCLE

工具不是插件列表，而是一条受控执行管线。

模型只提出结构化调用；系统负责发现、校验、授权、执行、截断输出与回注。每个环节都有自己的失败模式。

六个检查点

先确认工具是否对当前回合可见，再校验参数；之后权限策略与沙箱共同决定能否执行。执行结果需要保留退出码、标准输出与标准错误，最后包装成模型能继续推理的结果。

DEBUG ORDER

工具未出现 → 查注册与能力；调用参数错 → 查 schema；执行被拒 → 查审批与沙箱；命令成功但回答错 → 查输出截断和结果回注。

  1. 发现：当前身份与作用域可见哪些工具。
  2. 校验：参数是否符合结构化契约。
  3. 授权：能力与策略是否允许。
  4. 执行：在限定环境中启动并采集结果。
  5. 归一化：保留诊断，控制体积。
  6. 回注：让模型基于事实继续。

    CHAPTER 05 · CONTEXT ENGINEERING

    上下文不是“聊天记录”，而是一份有预算的工作集。

    系统指令、项目规则、用户输入、工具输出与摘要争夺同一个窗口。真正的工程问题是：留下什么、压缩什么、何时让缓存前缀保持稳定。

    预算与信息密度

    窗口越大，不等于每个 token 都同样有用。长日志、重复工具输出和过期分支会稀释关键约束。压缩的目标也不是“变短”，而是保留下一步决策所需的状态、证据与未完成工作。

    1. 长期规则、当前目标、关键决定、验证证据。
    2. 已完成步骤、重复输出、可从文件重读的细节。
    3. 无关分支、过期假设、没有影响后续的噪声。

    CHAPTER 07 · THREAD / TURN / ITEM

    真正的状态骨架，是三层而不是一条消息链。

    Thread 是可持久化的对话容器，Turn 是一次用户请求及其后续工作，Item 是消息、命令、文件变更或工具调用等最小输入输出单元。

    01

    Thread

    拥有身份、历史与运行状态；可 start、resume、fork、archive，并包含多个 Turn。

    02

    Turn

    一次请求与 Agent 工作；可 steer、interrupt，完成时发出明确 final status。

    03

    Item

    最小可观察单元；拥有 started / completed 生命周期并承载增量更新。

    CHAPTER 08 · EXTENSION BUS

    扩展能力不是一个“插件”按钮，而是多条不同信任边界。

    内建命令与文件变更、MCP、Apps、动态工具和 Skills 都能进入 Turn，但它们的发现方式、执行位置、审批语义与生命周期并不相同。

    先问四个问题

    能力从哪里被发现？谁执行？返回什么 Item？哪类副作用必须审批？只有把这四个问题答清，工具系统才真正可审计。

    MCP 还能在 Turn 中发起表单或 URL elicitation；动态工具则通过客户端回调执行，目前属于实验性协议。

    1. Built-in：命令、文件变更、权限请求。
    2. MCP：工具、资源、认证与 elicitation。
    3. Apps：经过产品与策略封装的连接器能力。
    4. Dynamic：Thread 启动时注入、由客户端回调执行。

    SOURCE-ALIGNED TEACHING SKELETON · MCP ELICITATION

    MCP 交互式表单提示与参数补全运行时 (`CodexTurnElicitationHandler`)

    下面是帮助理解控制流的教学骨架，不是上游源码复制，也不能直接用于生产。真实入口请查 `codex-rs/core/src/session/mcp.rs` 的 `request_mcp_server_elicitation()` / `resolve_elicitation()`，以及 `codex-rs/app-server/tests/suite/v2/mcp_server_elicitation.rs`。

    架构精要：MCP Elicitation 允许在模型运行回合中安全发起结构化人机交互，通过 `oneshot::channel` 保持异步 Turn 不中断，表单数据提交后直接回注工具上下文而无需重置整个会话。

    CHAPTER 09 · CUSTOMIZATION SYSTEM

    把“这个 Agent 怎么工作”拆成五种互补机制。

    AGENTS.md 约束仓库行为，Memories 保留跨对话上下文，Skills 封装流程，MCP 连接外部系统，Subagents 负责有边界的专业委派；Hooks 则提供确定性生命周期扩展。

    GUIDEAGENTS.md

    随代码库传播的持久指导；适合命令、约定、评审标准和目录级规则。

    REMEMBERMemories

    把仍会影响后续工作的事实带到新对话；不是完整聊天记录，也不是模型参数。

    REUSESkills

    按需加载的流程与领域知识；可声明工具、环境变量或 MCP 依赖。

    CONNECTMCP

    把外部工具与共享系统接入 Codex；连接不等于自动授权。

    DELEGATESubagents

    独立上下文与工具配置的专业执行者；并行不应扩大原任务授权。

    ENFORCEHooks

    在 Session、Turn 和工具生命周期运行确定性脚本，用于校验、日志和安全控制。

    CHOOSING THE MECHANISM

    需要模型“知道”规则 → AGENTS；需要复用判断流程 → Skill；需要访问系统 → MCP；需要硬性执行 → Hook；需要隔离并行工作 → Subagent；需要跨对话保留局部事实 → Memory。

    环境不是实现细节

    本地项目、Git Worktree、云端隔离环境和远程宿主会改变文件寿命、网络可达性与并行方式。诊断前先确认“这轮到底跑在哪里”。

    CHAPTER 12 · PRACTICE & INTERVIEW

    把架构知识变成诊断顺序。

    真正有用的掌握，不是能背组件名，而是面对失败时知道先看哪一条证据、归属哪一层、做哪一个最小实验。

    五步诊断

    1. 定位容器：Thread、Turn 还是 Item 出了问题？
    2. 读事件：事实停在 started、approval、delta 还是 completed？
    3. 查边界：工具可见性、权限、沙箱、网络还是环境？
    4. 查上下文：规则、历史、Skill 和结果回注是否完整？
    5. 最小验证：设计一个能推翻当前假设的检查。
    PROBLEM SET 01 · 架构设计题

    “如何设计企业级高可用 Codex App Server 双向 JSON-RPC 会话管理体系？”

    展开答题骨架与解耦推演

    【场景定义】 为支持数千名开发者同时在 Web IDE、桌面客户端与命令行中使用 Codex，需要构建一套高并发、支持长连接热迁移与流式双向通信的 App Server 架构。

    【归属层/故障机理分析】 属于协议与服务解耦层（`Chapter 07: Thread / Turn / Item` & `Chapter 11: Client Surfaces`）。核心机理在于：Codex 状态模型严格拆分为 Thread（持久化状态容器）、Turn（执行生命周期）与 Item（最小可观察更新粒度）。App Server 采用双向 JSON-RPC 协议，将长连接管理与无状态执行引擎分离，实现流式通知与增量事件广播。

    【关键证据链/判定条件】
    1. 握手与协商：客户端连接后必须通过 `initialize` / `initialized` 交换协议版本与 capability 集合。
    2. 三层生命周期映射：`thread/start` $\to$ `turn/start` $\to$ `item/agentMessage/delta` $\to$ `item/completed` $\to$ `turn/completed`。
    3. 中断与恢复：支持通过 `turn/interrupt` 触发取消令牌，后续通过 `turn/start` 增量续跑，不丢失已提交的 Item。

    【解决方案与系统级防线】
    • 客户端严禁私自维护业务状态镜像，所有 UI 渲染与进度推进均以 App Server 推送的 `item/*` 事件为准。
    • 在 App Server 外围构建平台租约（Lease）与签名验权，实现会话多租户安全隔离与横向负载均衡。

    PROBLEM SET 02 · 故障排查题

    “Turn 执行中收到 `mcp_elicitation_request` 后，为什么下游工具无法获取参数并发生超时？”

    展开答题骨架与排查路径

    【场景定义】 模型调用外部 MCP 数据库迁移工具，该工具触发结构化密码填写表单，但用户在前端输入并提交后，后端工具迟迟没有恢复执行，最终因 30s 超时报错中断。

    【归属层/故障机理分析】 属于 MCP 交互式表单总线（`Chapter 08: Extension Bus`）。故障机理为：App Server 内部维护的 `pending_elicitations` 回调映射表在多工作线程环境下发生竞争，或客户端在调用 `submit_elicitation_response` 时提交了错误的 `elicitation_id`，导致 `oneshot::Sender` 无法成功唤醒挂起工具。

    【关键证据链/判定条件】
    1. 协议抓包：检查 App Server 是否成功广播了包含 `elicitation_id` 的 `item/mcp_elicitation_request`。
    2. 回包匹配：检查客户端提交响应时附带的 `elicitation_id` 与注册表键值是否完全一致。
    3. 唤醒通道状态：检查 `oneshot::channel` 是否在提交前已被异常 drop 或由于超时提前关闭。

    【解决方案与系统级防线】
    • 使用带线程安全锁的 `Arc>>` 严格保护未决请求映射。
    • 为交互式 Elicitation 设置独立的长超时策略（如 300s），并支持客户端显式取消（Cancel）优雅退出。

    PROBLEM SET 03 · 安全攻防题

    “在正交权限矩阵中，`SandboxPolicy::WorkspaceWrite` 与 `ApprovalPolicy::OnRequest` 发生冲突时如何判定？”

    展开答题骨架与权限决策

    【场景定义】 用户设置了允许工作区写（`WorkspaceWrite`），但命令审批策略配置为按需询问（`OnRequest`）。模型发起了跨越工作区根目录的编辑操作（如修改 `/etc/hosts` 或用户全局配置文件）。

    【归属层/故障机理分析】 属于权限与沙箱正交决策体系（`Chapter 04: Permissions & Sandboxing`）。核心认知：`SandboxPolicy`（沙箱物理能力）与 `ApprovalPolicy`（人机交互策略）是正交独立的二维矩阵。物理越权必须在沙箱层被绝对拦截，即使审批策略设置为自动放行也无法越界。

    【关键证据链/判定条件】
    1. 审批判定：`ApprovalPolicy` 评估目标动作是否需要发起人机交互审批弹窗。
    2. 沙箱判定：`SandboxPolicy` 评估该路径是否在可写根目录允许列表中。
    3. 冲突决议：若动作超出 `WorkspaceWrite` 范围，系统直接拒绝执行或降级报错，绝不因用户点击批准而静默关闭底层沙箱隔离。

    【解决方案与系统级防线】
    • 坚守“最小特权原则”：沙箱层负责硬性物理隔离（OS 命名空间 / Landlock / Seatbelt），审批层仅负责策略偏好。
    • 任何需要突破当前沙箱边界的临时越权操作，必须通过显式重新配置沙箱 Profile 完成，禁止隐式动态提权。

    速查术语

    Thread
    包含多个 Turn 的对话与持久状态容器。
    Turn
    一次用户请求及 Agent 随后完成的全部工作。
    Item
    消息、命令、文件变更或工具调用等最小输入输出单元。
    SandboxPolicy
    命令实际可访问的文件系统与网络边界。
    ApprovalPolicy
    何时暂停并请求越界授权的交互策略。
    Compaction
    把旧历史折叠成保留关键状态的摘要。
    Elicitation
    MCP 在 Turn 中请求结构化表单输入或 URL 流程的机制。
    Hook
    在 Codex 生命周期节点运行的确定性脚本。
