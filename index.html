CHAPTER 01 · TURN LOOP

从“测试失败”开始，跟踪一次完整回合。

假设你让 Codex 修复一个失败测试。本章不先背概念，而是追踪任务从协议入口、模型判断、工具执行到完成事件的全过程。

INCIDENT 01 · TEST PASSED, TURN STILL RUNNING

命令成功，只说明一个 Item 完成；它不代表整个 Turn 已收束。

把一次任务分成三层就不容易误判：提交循环接收操作，Turn 循环决定是否继续，单次采样 step 负责一次模型请求。模型还想调用工具、或队列里还有 steer / mailbox 输入，都会进入下一步。

  1. 看到命令退出码 0：只确认这次执行成功。
  2. 看到 tool output 回注：模型现在才拿到执行事实。
  3. 看到仍需跟进：模型或排队输入要求再跑一个 step。
  4. 看到 turn completed：整轮才真正结束。

学完本章你能：解释为什么“命令退出码为 0”不等于“Turn 已完成”，并指出该去查哪一类事件。

心智模型

一次回合不是一次模型调用。它从用户输入入队开始，经过上下文组装、流式响应、工具判定、受控执行与结果回注，直到模型不再请求工具、也没有排队输入才收敛。

Steer 不抢断当前 token 流，而是在下一个 step 边界进入历史；Interrupt 才会取消活动任务，先给约 100ms 的优雅收尾窗口，必要时硬终止，并留下“本轮被打断”的历史事实。

ROOT-CAUSE LENS

把故障归到拥有它的层：模型选错工具、策略拒绝权限、执行环境失败、还是结果没有正确回注。不要把所有失败都叫作“模型不行”。

  1. 提交：输入变成可追踪的操作。
  2. 推理：模型读取上下文并选择下一步。
  3. 行动：工具在权限与沙箱边界内执行。
  4. 回注：结果进入历史，驱动下一次判断。

CHAPTER 02 · APP SERVER PROTOCOL

断线重连后，UI 凭什么知道刚才发生了什么？

本章把协议当成事实流水：客户端发请求，服务端发通知，也会反向发起审批或 elicitation。学完后你能判断“界面没显示”究竟是内核没做，还是客户端漏投影。

向内是意图，向外是事实

短 trace：initialize → thread/start → turn/start → item/started → delta → item/completed → turn/completed。连接先握手；Thread 承载可恢复状态；Turn 表示一次工作；Item 是流式可观察单元。

它必须是双向协议，因为服务端不只“播事件”，还可能要求客户端做决定，例如命令审批、结构化表单或客户端执行的动态工具。UI 不应猜测业务状态，而应把通知折叠成可重建的投影。

内部会话用提交队列与回复通道通信，跨进程边界才用请求 id 关联。两套协议职责不同：一个服务并发与任务控制，一个服务客户端互通。

  1. Request：表达“请开始、转向、中断或回答”。
  2. Notification：报告“已经开始、变化、完成或失败”。
  3. 反向请求：服务端需要客户端给出审批、表单或工具结果。
  4. 恢复原则：持久化记录与事件是事实源，界面只是投影。

CHAPTER 03 · TOOL LIFECYCLE

模型“会用工具”，为什么还是调用不到？

因为工具调用不是一个按钮，而是发现、校验、授权、执行、归一化与回注六个检查点。本章教你按顺序排除，而不是把任何失败都归咎于模型。

六个检查点，一条定位顺序

短 trace：可见？ → 参数对？ → 允许？ → 执行了？ → 输出完整？ → 回到历史？。先找第一个“否”，不要跨层猜原因。

DEBUG ORDER

工具未出现 → 查本 step 的可见工具；参数错 → 查 schema；执行被拒 → 查审批、规则与沙箱；命令成功但回答错 → 查输出截断和回注。

当前机制会在每个 step 重建工具路由，因此 MCP、项目规则和动态工具的变化最迟下一步生效。工具还分直接、延迟、仅模型调用、仅 code mode 与隐藏等暴露方式；列表太大时由 tool_search 按需发现。取消也不能让调用凭空消失：每个已派发调用都必须得到真实或合成回执，历史才可重放。

另一个容易混淆的新变化：同步用户提问会挂起等待；异步用户提问或消息会立即返回“已接受”，答案以后续输入到达。看到“工具成功”时，先确认它承诺的是完成，还是仅仅送达。

  1. 发现：这个 step 里模型是否看得见。
  2. 校验：参数是否符合结构化契约。
  3. 授权：策略、规则与权限是否允许。
  4. 执行：在限定环境中启动并采集结果。
  5. 归一化：保留头尾诊断并声明截断。
  6. 回注：让模型基于事实继续。

“工具返回 accepted，是否代表用户已经回答？”

展开判断与答案
不一定。异步消息工具立即返回 accepted，只表示消息已送出；用户回答会作为后续输入到达。同步提问才会在当前工具调用中等待应答。排障时必须先分清送达语义与完成语义。

本章小结：工具系统的核心不是“有多少工具”，而是每一步是否有确定输入、可观察输出和失败归属。

CHAPTER 04 · SAFETY BOUNDARIES

用户点了允许，为什么命令仍然被拒绝？

因为安全不是一个开关。审批策略决定“要不要问”，权限画像决定“能碰什么”，命令规则决定“这类动作如何分类”，最后还要由系统沙箱强制执行。

    把一次拒绝拆成三问

    短 trace：命令规则分类 → 是否允许询问 → 权限画像与沙箱执行。规则可给出允许、询问或禁止；Granular 还能分别开关沙箱升级、规则询问、Skill 脚本、权限申请和 MCP elicitation，关掉某类意味着自动拒绝，不是静默放行。

    当自动审查被启用且路由条件满足时，Guardian 可以代替用户裁决；它超时、执行失败或格式错误时都 fail-closed。受管网络还可以把出口收敛到代理，启用凭据 broker 时，沙箱进程只看到占位值，真实凭据在出口注入。

    判断法：先问“谁拒绝”，再问“这个拒绝能否通过审批改变”。沙箱硬边界、企业约束和禁止规则不是点一下按钮就会消失。

    “审批策略设成 never，是不是就没有安全边界了？”

    展开判断与答案
    不是。never 只表示系统绝不向用户升级询问，沙箱、权限画像与禁止规则仍然生效；越界结果会直接回给模型。审批是交互策略，沙箱才是执行强制。
    BOUNDARY

    实验台展示常见沙箱与审批组合；实际裁决还可能叠加 Granular 分类、企业 requirements、Guardian 与受管网络。不要从一个开关推断整条安全链。

    本章小结：审批通过仍失败时，按“规则 → 询问策略 → 权限画像 → OS 沙箱”逐层找第一个收紧点。

    CHAPTER 05 · CONTEXT ENGINEERING

    项目规则刚改，为什么模型下一步能看到、又不会重读全部历史？

    答案不是“更长的 system prompt”，而是分层：基础指令、动态世界状态、对话历史和工具面各走各的通道。本章教你判断模型究竟漏了哪一层。

    先分层，再谈压缩

    短 trace：本 step 状态快照 → 与上一步比较 → 只注入变化 → 从历史派生模型请求。动态环境被拆成具名区块；前态可能是未出现、已知或未知。未知时宁可全量重发，也不假装模型已经知道。

    单条工具输出在写入历史时就会按预算保留头尾并声明截断；整段历史到达窗口阈值后才进入 compaction。当前实现并存本地摘要、两种远端压缩和直接开启新窗口四条路径，触发原因还包括窗口限制、压缩兼容变化、模型降档与用户手动请求。

    最关键的分账：compaction 改的是模型工作记忆，不是用户授权证据。原始审查转录与少量已验证回答另行保留；回滚才会同时撤销工作历史与对应证据。

    1. 保留：目标、约束、关键决定、验证证据与未完成工作。
    2. 差分：项目指令、权限与环境只发送变化。
    3. 压缩：已完成步骤与长历史进入摘要或新窗口。
    4. 分账：授权证据不随模型摘要一起消失。

    “上下文快满了，先压缩历史还是先截断工具输出？”

    展开判断与答案
    两者不在同一个时点竞争：单条输出入档时先截断，整个工作集到阈值后再压缩。更重要的是，压缩只改模型历史，不应清掉授权证据。先问“丢的是哪本账”，再判断是否符合预期。
    TEACHING SCALE

    100k 窗口和 86% 自动压缩阈值只用于让变化可视化；真实窗口、压缩触发与缓存行为随模型和 Codex 版本变化。

    本章小结：遇到“模型忘了”时，先区分未注入、被截断、被压缩、被回滚四种原因；它们的修复手段完全不同。

    CHAPTER 06 · HARNESS ARCHITECTURE

    终端、IDE 和远程客户端，怎样共用一套行为而不各自漂移？

    Codex 把会话能力放在内核库里，把多端接入收口到 App Server 协议面。学完本章，你能判断一项平台需求应该进入内核、协议、客户端还是外围服务。

    MENTAL MODEL内核拥有会话 actor、Turn 循环、工具与历史语义。协议拥有请求顺序、双向交互、类型生成与多种传输。

    一个内核，两套协议，两种部署形态

    短 trace：客户端 → App Server → 会话 actor → 工具与模型 → 事件返回客户端。进程内提交用操作队列和回复通道；跨进程接入用双向 JSON-RPC。Rust 类型单向生成客户端类型与 schema，减少多端接口漂移。

    TUI 可以内嵌 App Server，也可以通过 stdio、Unix socket 或 WebSocket 接入常驻服务。远程控制、daemon 和不同前端改变的是部署与传输，不改变 Thread / Turn / Item 的核心语义。

    判断所有权时问一句：这项逻辑是否影响“任何客户端都必须遵守的事实”？是，就放进内核或协议；只是呈现、租户接入或产品工作流，则留在外层。

    CHAPTER 07 · THREAD / TURN / ITEM

    进程在半轮任务中重启，哪些状态必须回来？

    Thread、Turn、Item 不是三种命名，而是三种寿命。学完本章，你能解释恢复、分叉、中断和回滚分别作用在哪一层。

    01

    Thread

    拥有身份、历史与运行状态；可 start、resume、fork、archive，并包含多个 Turn。

    02

    Turn

    一次请求与 Agent 工作；可 steer、interrupt，完成时发出明确 final status。

    03

    Item

    最小可观察单元；拥有 started / completed 生命周期并承载增量更新。

    三层对应三种恢复问题

    短 trace：Thread 持有历史 → Turn 持有本次任务 → Item 记录可观察事实。Thread 可恢复、分叉与归档；Turn 可转向、中断并明确收尾；Item 则必须保持调用与输出配对。

    会话记录采用追加日志与替换历史检查点。恢复时从日志尾部向前找到最近检查点，再正向重放尾部；回滚写成新的事实，而不是删除曾经发生的记录。这样在线视图与恢复视图可以由同一套重放语义生成。

    如果只保存消息列表，“命令已经执行但最终回答还没完成”就无法准确表达。三层模型能保住已提交 Item，同时把未完成 Turn 标成中断，而不是假装它从未发生。

    CHAPTER 08 · EXTENSION BUS

    一个能力到底在哪里执行，谁为副作用负责？

    扩展不是同一种“插件”。内建工具、MCP、Apps、动态工具、Hooks 与 Subagents 分别跨越不同信任边界。本章给你一套不靠背名词的判断法。

    每个扩展先回答四问

    短 trace：从哪里发现？ → 在哪一侧执行？ → 产生什么回执？ → 谁批准副作用？。这四问答不清，就不要接入生产。

    MCP 可以在 Turn 中发起结构化表单或 URL elicitation；动态工具则由客户端回调执行。二者都可能表现为服务端发起的反向请求，因此“服务端通知了”不等于“服务端执行了”。

    Hooks 是确定性生命周期拦截，可阻断或改写；AGENTS 与 Skills 影响模型判断；Subagents 创建独立会话并共享工作区。它们的控制强度、执行位置和资源账本完全不同。

    1. Built-in：内核管理执行、取消与回执。
    2. MCP / Apps：外部能力经协议、认证与审批接入。
    3. Dynamic：能力在客户端侧，服务端反向调用。
    4. Subagents：独立会话协作，权限不能超过根任务。

    INCIDENT 08 · FORM SUBMITTED, TOOL STILL WAITING

    把 elicitation 当作一笔“有请求键的未决应答”。

    服务端发出结构化请求并登记等待项；客户端展示表单；用户提交时必须带回同一请求键；应答命中等待项后，工具才继续。如果连接断开、请求键错误或等待项被取消，就必须得到明确拒绝或中止结果，不能永久悬挂。

    1. REQUEST：服务端登记等待项并发送表单定义。
    2. DISPLAY：客户端展示输入，不擅自改写字段语义。
    3. RESOLVE：响应携带原请求键，命中对应等待者。
    4. CONTINUE：答案成为工具结果的一部分，Turn 继续。

    判断练习：用户已点击提交但工具没继续，先核对请求键与等待项是否仍存活，再查超时或取消；不要先怀疑模型。

    边界

    扩展面成熟度不齐：dynamic tools、elicitation 与部分环境参数仍带实验性标记，hooks 事件集也会演化。生产接入要以运行时能力协商为准，不能只凭课程中的名字做兼容承诺。

    CHAPTER 09 · CUSTOMIZATION SYSTEM

    一条新规则，应该写进 AGENTS、Skill、Hook，还是交给 Subagent？

    选错机制会制造重复提示、越权或不可复现。本章从“规则要让谁知道、由谁执行、要不要跨会话”三个问题出发，建立清晰的定制分工。

    GUIDEAGENTS.md

    随代码库传播的持久指导；适合命令、约定、评审标准和目录级规则。

    REMEMBERMemories

    把仍会影响后续工作的事实带到新对话；不是完整聊天记录，也不是模型参数。

    REUSESkills

    按需加载的流程与领域知识；可声明工具、环境变量或 MCP 依赖。

    CONNECTMCP

    把外部工具与共享系统接入 Codex；连接不等于自动授权。

    DELEGATESubagents

    独立上下文与工具配置的专业执行者；并行不应扩大原任务授权。

    ENFORCEHooks

    在 Session、Turn 和工具生命周期运行确定性脚本，用于校验、日志和安全控制。

    CHOOSING THE MECHANISM

    让模型知道仓库规则 → AGENTS；复用一套判断流程 → Skill；访问外部系统 → MCP；确定性拦截或强制 → Hook；隔离并行工作 → Subagent；跨对话保留局部事实 → Memory。

    两条容易记反的规则

    配置是覆盖，项目指令是拼接。配置层有明确优先级：打包默认、设备管理、系统、企业、用户、项目、会话参数逐层合并，遗留托管层仍可能拥有更高优先级；企业 requirements 还能直接拒绝越界值。项目指令则从项目根到当前目录逐层收集，局部 override 只替换同目录主文件，总量还受字节预算限制。

    Subagent 不是“多开一次模型调用”，而是独立会话：可选择继承全部、最近若干轮或不继承父历史；历史会洗掉推理过程和工具噪声，只保留适合交接的内容。消息可只排队，也可唤醒目标；最终答案会沿父子关系回传。资源还分别受并发、驻留与整棵树预算约束，权限只能收紧不能扩大。

    CHAPTER 10 · CONFIG & ENVIRONMENTS

    “我明明改了配置”，为什么这一轮还是没生效？

    生效值来自配置覆盖、企业约束、step 快照与执行宿主的共同结果。本章教你沿来源追踪有效配置，而不是只盯着手边那一个文件。

    先问“谁赢”，再问“在哪里执行”

    短 trace：读取各配置层 → 高优先级覆盖 → 企业约束校验 → 本 step 冻结快照 → 交给执行宿主强制。会话参数通常能覆盖项目与用户值，但受管要求可以拒绝越界配置。

    本地项目、Git Worktree、云端隔离环境和远程宿主会改变文件寿命、网络可达性与并行方式。远程执行时，沙箱在宿主侧落地；本机看到的配置只是请求意图。环境参数还可能区分“未指定”“明确不提供环境”“指定候选环境”，不能把空值都当默认值。

    判断法：先记录有效模型、权限画像、审批策略、网络与宿主，再复现实验。把本地结论直接搬到云端或远程宿主，是最常见的错层排障。

    1. Local：直接作用于当前机器的项目边界。
    2. Worktree：隔离 Git 工作树，适合并行改动。
    3. Cloud：受托管环境模板和网络策略约束。
    4. Remote host：客户端发意图，宿主负责真正执行与强制。

      CHAPTER 11 · CLIENT SURFACES

      同一个任务，什么时候用交互客户端，什么时候用批处理？

      不同表面共享核心能力，却拥有不同的等待、审批与恢复契约。本章让你按工作流选入口，而不是按“哪个看起来更高级”选。

      客户端表面交换台choose by contract
      契约
      最适合
      连接方式

      按交互契约选，不按功能清单选

      短 trace：需要持续呈现 Item、接收反向审批、断线恢复 → App Server；需要人直接协作 → CLI 或 IDE；需要程序控制任务 → SDK；需要一次进出与明确退出码 → 非交互入口或自动化集成。

      App Server 可内嵌，也可经 stdio、Unix socket 或 WebSocket 连接；MCP server 的方向相反，它把 Codex 暴露成其他 Agent 能调用的能力。两者都叫“server”，但调用方向和所有权完全不同。

      无人值守环境没有随时可回答的用户，因此任何可能反向询问的能力都要提前给出明确策略：自动拒绝、自动审查，或根本不在这类流程中使用。

      CHECK YOUR MODEL

      “CI 里为什么通常不直接复刻 App Server 富客户端？”

      展开判断与答案
      CI 的核心契约是一次进出、可重试、退出码清晰；它通常没有审批人，也不需要维护复杂 UI 投影。只有确实需要双向审批、历史恢复与细粒度流事件时，才值得接入完整 App Server。
      BOUNDARY

      表面可以不同，事实源不能分叉。无论 CLI、IDE 还是自定义客户端，都不应另造一套 Turn 或 Item 语义。

      本章小结：先写清“是否有人在场、是否需要流式投影、是否需要恢复、失败如何返回”，入口选择通常就会自然收敛。

      CHAPTER 12 · PRACTICE & INTERVIEW

      面对真实故障，先看哪条证据？

      最后一章把前面的机制压缩成可执行顺序：定位容器、找到最后事实、检查边界、核对上下文，再设计一个能推翻假设的最小实验。

      五步诊断

      1. 定位容器：Thread、Turn 还是 Item 出了问题？
      2. 读事件：事实停在 started、approval、delta 还是 completed？
      3. 查边界：工具可见性、权限、沙箱、网络还是环境？
      4. 查上下文：规则、历史、Skill 和结果回注是否完整？
      5. 最小验证：设计一个能推翻当前假设的检查。
      PROBLEM SET 01 · 架构设计题

      “流在工具执行后断开，重试为什么可能制造重复副作用？”

      展开答题骨架与解耦推演

      【先定位】 工具 Item 已执行，但模型流没有自然完成。重试粒度通常是重新发送从历史派生的请求，不是从断开的字节位置继续。

      【关键风险】 如果模型不知道调用已经执行，就可能再次触发同一命令。系统会记录已尝试调用并在重建请求时附回；这是“告诉模型事实”，不是事务回滚。

      【最小验证】 检查第一次调用是否有稳定 call id、执行记录是否完整、重试请求是否带回已执行事实，以及外部动作本身能否设计为幂等。

      【答题结论】 Agent 重试的底线不是“绝不重复”，而是“重复前拥有足够事实，并让副作用尽量幂等”。

      PROBLEM SET 02 · 故障排查题

      “用户提交了 MCP 表单，为什么工具仍然超时？”

      展开答题骨架与排查路径

      【先定位】 这是反向请求的应答关联问题，不是模型生成问题。先确认请求已发出、客户端已展示、响应已返回、等待项已命中四个事实。

      【关键证据】 请求键是否一致？等待项在响应前是否被取消或清理？连接断开后有没有明确的中止结果？

      【避免误判】 不要在没有证据时断言“多线程竞争”或随意延长超时。先找最后一个已确认事件，再修拥有断点的那一层。

      PROBLEM SET 03 · 安全攻防题

      “WorkspaceWrite 与 OnRequest 同时存在，跨工作区写入该怎么判？”

      展开答题骨架与权限决策

      【先分轴】 WorkspaceWrite 描述当前可写边界，OnRequest 描述何时允许询问。命令规则与企业约束还可能进一步收紧。

      【判断顺序】 先看规则是否禁止或要求询问，再看策略是否允许展示询问，最后由权限画像与系统沙箱执行。某些模式可在明确批准后尝试升级执行，但绝不能把“用户点了同意”直接等同于“沙箱已被关闭”。

      【答题结论】 三轴是组合关系，不是二选一。要回答谁能放行，必须先指出当前拒绝来自哪一轴。

      边界

      课程事实边界为快照 498d40b29f60。实验性能力、事件名和默认配置会继续变化；生产集成应以运行版本的能力协商与生成 schema 为准。能说出结论的失效条件，才算真正掌握。

      毕业检查：任选一个失败，能否在 60 秒内说清“最后事实、拥有它的层、一个可证伪假设、最小验证动作”？能做到，就已经把课程从知识变成了工程能力。

      速查术语

      Thread
      包含多个 Turn 的对话与持久状态容器。
      Turn
      一次用户请求及 Agent 随后完成的全部工作。
      Item
      消息、命令、文件变更或工具调用等最小输入输出单元。
      SandboxPolicy
      命令实际可访问的文件系统与网络边界。
      ApprovalPolicy
      何时暂停并请求越界授权的交互策略。
      Compaction
      把旧历史折叠成保留关键状态的摘要。
      Elicitation
      MCP 在 Turn 中请求结构化表单输入或 URL 流程的机制。
      Hook
      在 Codex 生命周期节点运行的确定性脚本。
