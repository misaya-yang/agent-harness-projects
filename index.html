01 / CONTROL FLOW运行循环一个任务为何继续、转向或结束？

学完能画出用户输入、模型请求、工具批次和回合结束之间的控制关系。

任务现场

测试进程还在跑，模型已经输出“完成”。你先检查模型文本、工具回执，还是 Turn 的收束事件？

  1. 用户提交请求，宿主创建运行中的 Turn。
  2. 模型提出工具调用；工具完成后，结果进入下一步模型输入。
  3. 只有循环的终止条件满足，宿主才宣布回合结束。

继续追问用户插话在什么边界进入？工具失败应继续让模型修复，还是终止整个 Turn？

跨项目对照Codex 把提交、采样和工具结算分层；Pi 的循环更薄。比较时先写清每套系统把终止权交给谁。

迁移练习为“测试失败后修复一次，再验证”写出最多两轮的停止条件与事件轨迹。

面试自测：如何设计不会误判完成的 Agent Loop？

回答要包含 Turn 与模型 step 的区别、工具调用与回执配对、明确的终止判据，以及中途插话如何改变下一步。

02 / STATE状态协议UI、模型和日志看到的状态为何不同？

学完能区分持久事实、模型当前视图和客户端投影，并从最后一个已提交事件定位故障。

任务现场

UI 显示工具成功，进程重启后模型又执行了一次。哪一层的“成功”没有成为持久事实？

  1. 调用先成为可追踪事件。
  2. 工具结果回写后，模型视图和 UI 各自从事件投影。
  3. 恢复从持久边界重建；缺失结果必须保持“未知”。

继续追问流式 chunk 算正式消息吗？断线后应相信旧 UI 状态还是重新读取快照？

跨项目对照DeepSeek 从事件日志投影模型 Surface；Codex 从 rollout 与 checkpoint 恢复工作历史。两者都要求重建时有唯一的事实来源。

迁移练习设计“工具调用已落盘、结果未落盘”的恢复判定表。

面试自测：为什么原始日志不等于模型上下文？

回答要区分追加事实、当前模型可见投影和客户端视图；恢复应从持久边界重建，不能依赖断线前的 UI 状态。

03 / TOOLS工具系统并行执行怎样保持结果有序、可取消？

学完能设计工具的发现、参数校验、派发、执行和回注管线。

任务现场

同一批次的 B 比 A 先完成。下一步模型输入应该按完成顺序，还是按模型发起顺序？

  1. 按当前 step 的可见工具集解析调用。
  2. 满足并发条件的调用可以同时执行。
  3. 每个 call id 都有结果，模型历史按调用顺序配对。

继续追问参数错误是可修复结果还是致命异常？取消时尚未启动的调用如何结算？

跨项目对照Pi 强调源序回填；DeepSeek 在并行前要求明确分类，并把失败收口到唯一提交点。两者都不能按完成速度改写对话顺序。

迁移练习为两个并行读和一个写操作给出安全调度与回注顺序。

面试自测：工具并行完成，怎样保持历史正确？

回答要分开发现、授权、执行和提交；允许安全并行，但用 call id 配对结果，并保证下一次模型请求看到合法顺序。

DeepSeek · 工具管线 ↗Pi · 源序回填 ↗Codex · 工具路由 ↗
04 / EFFECTS副作用安全用户批准后，为什么命令仍可能被拒？

学完能分开审批、权限规则与实际执行隔离，并说明每一道门由谁强制。

任务现场

一次写工作区外的操作获得批准，进程却仍被沙箱挡住。批准改变了什么？

  1. 模型提出动作；规则识别目标和风险。
  2. 审批决定是否允许这次越界请求。
  3. 执行宿主施加实际文件、进程和网络边界。

继续追问沙箱不可用时能否降级裸执行？“never ask”应该放行还是明确拒绝？

跨项目对照Codex 将策略审批与 OS 沙箱分层；DeepSeek 的能力缺失走明确拒绝。比较应写清每层保护的资源与失败行为。

迁移练习列出一次危险 shell 操作从提议到进程启动的所有裁决点。

面试自测：审批和沙箱分别防什么？

审批处理是否获得这次越界授权；沙箱限制进程实际能力。还应说明规则分类、执行宿主与保护失效时的拒绝路径。

Codex · 审批与沙箱 ↗DeepSeek · 失败关闭 ↗OpenClaw · 多道防线 ↗
05 / MODEL INPUT提示词与上下文下一次请求究竟给模型发了什么？

学完能拆出基础指令、动态环境、活跃历史、工具定义和输出约束，并识别缓存失效来源。

任务现场

项目规则刚修改。下一步模型需要看到变化，但不该把完整转录重新塞进窗口。

  1. 宿主读取基础指令和当前环境。
  2. 对动态状态做快照或差分，派生模型可见历史。
  3. 连同当前工具 schema 组装这一次请求。

继续追问工具定义算历史消息吗？压缩会改写基础指令或授权证据吗？

跨项目对照Codex 每步组装指令、动态状态、历史和工具；Hermes 特别处理稳定前缀与易变补丁。缓存优化不能改变事实来源。

迁移练习为一条模型请求标出稳定前缀与每步变化的输入。

面试自测：Agent 每个 step 发给模型什么？

回答应写出基础指令、动态上下文、活跃历史、工具 schema 与输出约束，并说明它们的寿命和缓存影响。

Codex · Prompt 分层 ↗DeepSeek · 请求装配 ↗Hermes · 前缀缓存 ↗
06 / CONTINUITY记忆与恢复会话日志、摘要和长期记忆各管什么？

学完能为“继续当前任务、恢复进程、跨会话记住偏好”选对状态层。

任务现场

上下文压缩后模型看不到早期细节；磁盘转录还在。下一次请求是否仍会自动读完整转录？

  1. 每个会话追加自己的事实记录。
  2. 压缩用有界工作集替换模型活跃历史。
  3. 恢复重放持久边界，长期记忆另行提取和检索。

继续追问摘要会不会无限增长？已批准的操作证据是否跟着摘要消失？

跨项目对照Codex 把活跃历史、rollout、审查证据和长期记忆分账；Grok 的 V2 再把观察与整理分开。它们回答不同寿命的问题。

迁移练习画出同一 Thread 两次压缩后的日志、checkpoint 和当前模型请求。

面试自测：压缩后 transcript 与模型上下文怎样变化？

原始事实继续追加，当前活跃历史被有界 checkpoint 替换；恢复与长期记忆使用不同读取路径，摘要不会无条件串接增长。

Codex · 五套记忆 ↗Grok Build · 压缩与记忆 ↗OpenClaw · 长期状态 ↗
07 / EXTENSION扩展机制规则、工作流、工具和钩子放在哪里？

学完能按作用域、执行权力和生命周期选择扩展点，而不是把所有要求写入提示词。

任务现场

团队要在每次文件写入前做确定性检查。它该是一条 Skill，还是执行前的强制钩子？

  1. 明确能力是知识、模型可见工具，还是宿主强制动作。
  2. 确定生效范围和是否可以被模型跳过。
  3. 用最窄的扩展点接入并测试卸载。

继续追问插件被发现就等于可调用吗？模型请求钩子能修改什么？

跨项目对照DeepSeek 用插件组合替换服务；Hermes 区分知识、观察与改写权；Codex 的 Skills 与受信宿主钩子权力不同。

迁移练习把项目规范、外部数据库查询和写前检查分别放到合适的机制。

面试自测：何时选 Skill、MCP 或 Hook？

从模型是否需要知识、是否需要新工具、是否必须由宿主确定性强制三点回答，再说明信任与卸载范围。

Codex · 定制与扩展 ↗DeepSeek · 插件组合 ↗Hermes · 扩展权力 ↗
08 / DELEGATION多代理编排子任务完成后，结果怎样安全回到父任务？

学完能设计子任务的历史继承、权限收紧、结果回传、取消与资源上限。

任务现场

子代理返回 accepted，父代理却立即宣布完成。真正结果还没到，谁负责唤醒父会话？

  1. 父任务声明目标、上下文和输出契约。
  2. 子任务独立运行并受预算与权限约束。
  3. 结果通过受控消息或新回合回到父任务。

继续追问父历史应继承多少？谁有权取消后代任务？

跨项目对照Codex 的子代理在树内共享控制面；OpenClaw 的异步任务强调交付与当前控制权；Hermes 在会话空闲时回注完成消息。

迁移练习为并行研究和最终综合写出任务树、交付点与取消规则。

面试自测：子代理怎样回报、取消和控制成本？

回答要分开创建与完成，说明历史继承、独立预算、消息交付、当前控制权和根用户授权。

Codex · Rooted Tree ↗OpenClaw · 异步回流 ↗Hermes · 委派 ↗
09 / PRODUCT SURFACE客户端与宿主多个入口如何共享一套运行语义？

学完能区分内核、协议服务、执行宿主和 UI 投影，为新客户端接入画出边界。

任务现场

CLI 与 Web 同时打开一个会话。谁可以写入，谁只能看投影？断线后由谁恢复？

  1. 客户端提交命令并消费事件。
  2. 共享内核决定会话控制与状态变更。
  3. 执行宿主承担真实文件和进程效果。

继续追问前端能否自建第二个工具循环？不同宿主的权限是否天然相同？

跨项目对照Codex 分 Core 与 App Server；OpenCode 让 Server 成为共享入口；Hermes 多宿主共用会话内核。比较谁拥有会话写入权。

迁移练习为一个 IDE 客户端写出最小接线图，不复制内核循环。

面试自测：同一 harness 如何支持多个客户端？

内核拥有会话与工具语义，协议层连接客户端，客户端消费事件，执行宿主承担真实副作用与权限。

Codex · Core / App Server ↗OpenCode · Server 内核 ↗Hermes · 多宿主 ↗
10 / OPERATIONS可靠性工程失败发生后，哪一层还有权重试？

学完能按最后已提交事实、失败类型和副作用状态决定继续、重试、恢复或交还用户。

任务现场

工具已写入文件，模型流随后断开。重新发送整个请求可能重复副作用；应该先核对什么？

  1. 找最后一个持久事件和可能已发生的副作用。
  2. 把失败归给工具、模型、传输或宿主。
  3. 只由拥有该失败的层使用有界恢复预算。

继续追问HTTP 200 证明任务成功了吗？恢复测试为何必须验证调用与结果成对？

跨项目对照Pi 将可修复工具错误回给模型；DeepSeek 以持久事件处理残缺尾部；Codex 区分工具自救与致命失败。重试必须由拥有者决定。

迁移练习为“工具成功、传输断开、进程重启”写一张不重复执行的恢复表。

面试自测：如何避免多层重试放大一次故障？

先按失败类别和副作用状态确定 owner；每层只有自己的有界预算，并以持久事件、回执成对和端到端结果验证恢复。

Codex · 失败收口 ↗Pi · 错误分诊 ↗DeepSeek · 日志恢复 ↗
