BOUNDED RUNS · PERSISTENT STATE · SOURCE-LED

看懂 OpenClaw 如何用一连串有界的短 run，活过很多天。

它的内核循环与 Pi 几乎同构、本身无界；跨天存活靠的是外层工程：run 重试预算、双 SQLite 账本、automations / heartbeat / standing intents 三类唤醒源，以及凌晨 3 点的记忆固化。本课程沿三层循环向外逐层拆解。

Pi / Grok Build / OpenClaw：三种续跑答案

同一门系列里，Pi 把循环做到极简，Grok Build 用熔断器家族守住编码会话，OpenClaw 则把“活着”拆成有界 run 与唤醒源的组合。对照结论基于本地源码快照的教学归纳，不代表各上游项目的官方定位。

CHAPTER 01 · THE LOOP STACK

一次对话不是一条大循环，而是三层各有职责的小循环嵌套。

会话层管“要不要再跑一轮”，内核管“这一轮里模型和工具怎么咬合”，run 外层管“这个 run 失败了还有几次命”。

CHAPTER 02 · SETTLED OR CONTINUE

“跑完了吗”由三股力量裁决：模型 stopReason、Harness 队列、宿主移交。

内核自然停（无 tool call 且队列空）只是必要条件；会话层还会因重试、压缩、排队消息强行续跑，或因 turn handoff 把控制权交给外部投递。

handlePostAgentRun（agent-session-prompting.ts:53）的决策序即短路序：handoff→settled（:58-61）；aborted / 无消息→settled（:62-64）；isRetryableError && prepareRetry→continue（:66-68）；checkCompaction→continue（:81）；hasQueuedMessages()→continue，否则 settled（:85）[源码确认]。运行中注入走 steer()（agent.ts:337），跑完注入走 followUp()（:342），abort() 在 :373。非 handoff 结束时 finally 里 emit agent_settled（:47-48）——失败与中止也要收束，唯一例外是 handoff 把后续 run 控制权移交外部投递。

RETRY IS NARROWER THAN YOU THINK

isRetryableError 只认 overloaded / rate-limit / server error——上下文溢出不重试，交给 compaction（agent-session-execution.ts:18-21 注释）。会话级自动重试走指数退避 baseDelayMs * 2 ** (retryCount - 1)，并与 provider 的 Retry-After 取 max（:53/:59）；成功响应即清零 retryCount（agent-session-base.ts:450-456），开关与 maxRetries 上限在 willRetryAfterAgentEnd（:462-464）。

工具侧还有一条终止语义：shouldTerminateToolBatch（agent-loop.ts:1202）要求全批工具 terminate:true 才终止内层循环 [源码确认]——一个工具喊停不算数。

CHAPTER 06 · BUDGET NOT COUNTERS

防失控不靠“最多跑 N 轮”，靠一整排分层断路器。

内核无 maxTurns；真正的限量在外层：run 重试预算、48h 墙钟、空闲 5 连击、compaction 后同参同果窗口 3、以及默认关闭的工具循环检测。

预算公式 clamp(24 + 8×profile数, 32, 160)（run/helpers.ts:120-132），耗尽走 handleRetryLimitExhaustion（run-loop.ts:331）；recordRunRetry 对 progress_continuation 不计费（实现上先扣后退：计费照常 +1，随后把 attemptsCounted 减回一，retry-budget.ts:35-38）——有进展的续跑不吃预算。同模型 rate-limit 原地重试 ≤3 次、线性退避步长 10s（10/20/30s，run/helpers.ts:48-51），超出才进 profile 轮换。纯推理重试 2 / 空回复重试 1（run/incomplete-turn-recovery.ts:32-33，run-loop.ts:190-191 消费）[源码确认]。

  1. 墙钟：默认 48h、0 = 不限 sentinel（src/agents/timeout.ts:13/:21-24）。
  2. 空闲断路器：MAX_CONSECUTIVE_IDLE_TIMEOUTS_BEFORE_OUTPUT = 5（run/idle-timeout-breaker.ts:16）。
  3. 压缩后守卫：DEFAULT_WINDOW_SIZE = 3、违规抛 PostCompactionLoopPersistedError（post-compaction-loop-guard.ts:14/:166）。
  4. 耗尽 ≠ 直接报错：有 fallback_model 决策时抛 FailoverError 切模型继续，否则产出用户可见失败载荷 "Request failed after repeated internal retries"（run/retry-limit.ts:29-43）。
DEFAULT-OFF FEATURE工具循环检测默认关闭。tool-loop-detection.ts:53-54 enabled:false，warn 10 / critical 20 / circuit 30（:49-52）是配置默认值而非在跑的行为；opt-in 前没有“重复工具调用”断路器。不得表述为“OpenClaw 有内置循环检测在跑”。

SOURCE-ALIGNED TEACHING SKELETON · RUN-RETRY-BUDGET

run 重试预算教学骨架（RunRetryBudget / recordRunRetry / resolveMaxRunRetryIterations）

下面是与 src/agents/embedded-agent-runner/run/helpers.ts、run/retry-budget.ts、run-loop.ts 结构对齐的教学简化，命名与真实源码对齐，非上游源码复制。真实实现在 idle 断路器与 48h 墙钟上并行生效。

// teaching-skeleton: run-retry-budget.ts —— 与 run/helpers.ts、run/retry-budget.ts、run-loop.ts 结构对齐 type RunRetryKind = "progress_continuation" | "recovery"; // 同 retry-budget.ts:1 const BASE_RUN_RETRY_ITERATIONS = 24; // helpers.ts:120 const RUN_RETRY_ITERATIONS_PER_PROFILE = 8; // helpers.ts:121 const MIN_RUN_RETRY_ITERATIONS = 32; // helpers.ts:122 const MAX_RUN_RETRY_ITERATIONS = 160; // helpers.ts:123 export function resolveMaxRunRetryIterations(profileCandidateCount: number): number { const scaled = BASE_RUN_RETRY_ITERATIONS + Math.max(1, profileCandidateCount) * RUN_RETRY_ITERATIONS_PER_PROFILE; return Math.min(MAX_RUN_RETRY_ITERATIONS, Math.max(MIN_RUN_RETRY_ITERATIONS, scaled)); } export interface RunRetryBudget { max: number; used: number } export function createRunRetryBudget(max: number): RunRetryBudget { return { max, used: 0 }; } // 关键语义：有进展的续跑不吃预算——先扣后退（真实实现：attempt 起点 +1，recordRunRetry 只退回，retry-budget.ts:35-38） export function recordRunRetry(budget: RunRetryBudget, kind: RunRetryKind): void { budget.used += 1; // 先计费 if (kind === "progress_continuation") budget.used = Math.max(0, budget.used - 1); // 有进展则退回 } export function isRunRetryBudgetExhausted(budget: RunRetryBudget): boolean { return budget.used >= budget.max; } // 外层 run 循环骨架（对应 runPreparedEmbeddedLoop 的 while(true)，run-loop.ts:315） export async function runPreparedEmbeddedLoopTeaching( attempt: (budget: RunRetryBudget) => Promise<{ outcome: "done" | "retry"; kind: RunRetryKind }>, profiles: number, onExhausted: (budget: RunRetryBudget) => Promise<{ outcome: "done" }>, ): Promise<{ outcome: "done" }> { const budget = createRunRetryBudget(resolveMaxRunRetryIterations(profiles)); while (true) { if (isRunRetryBudgetExhausted(budget)) return onExhausted(budget); // 真实源码此处 failover/报错（run-loop.ts:317-331） const result = await attempt(budget); // beginRunAttempt ≈ run-loop.ts:351 if (result.outcome === "done") return result; recordRunRetry(budget, result.kind); // idle 断路器 / 48h 墙钟在真实实现里并行生效 } }

架构精要：预算只给“失败与 recovery”定价，有进展就免费——这是 OpenClaw“分层治理”的最小样本：限量不靠一条 maxTurns，而靠每个机制各管一段红线。

CHAPTER 07 · TWO PATHS, ONE PLUG

溢出是事故，超阈值是保养——compaction 有两条路径，且引擎可整体换掉。

checkCompaction 区分“模型报错了被动压”与“到水位了主动压”；被动压缩带自动重试且有次数上限；更外层，context-engine 是一个七能力面的可插拔接口。

两路径定义见注释与实现（src/agents/sessions/agent-session-compaction.ts:283-284）：溢出路径 :335-353 自动重试，上限 MAX_OVERFLOW_COMPACTION_ATTEMPTS = 3（src/agents/agent-compaction-constants.ts:14）；阈值路径 :377 压缩后不自动重试（:284 注释）[源码确认]。

CHAPTER 09 · ONE GATEWAY, MANY SURFACES

一个长驻 Gateway 拥有所有通道连接，其它一切都是它的 WS 客户端。

WhatsApp / Telegram / Slack / Discord / Signal / iMessage 通道各自只有一个宿主；CLI、Web Control UI、macOS 应用、automations 都以 WS 角色接入同一个 Gateway，设备节点（node）再声明自己的 caps。

架构文档：单 Gateway、WS on 127.0.0.1:18789、node 以 role: node 同端口接入、emit 面 agent/chat/presence/health/heartbeat/cron、客户端订阅面含 tick/shutdown（docs/concepts/architecture.md:31/:37——tick 是订阅节奏，不是 emit 事件名）[文档声明+源码确认]。通道实现为扩展：extensions/telegram（grammY）、whatsapp（Baileys）、discord、slack、signal、imessage、msteams、googlechat、matrix、irc、nostr、sms、zoom-meetings 等；协议与帧校验在 packages/gateway-protocol（frame-guards.ts）。内嵌场景（TUI/单进程）用 in-process-gateway.ts / embedded-gateway-stub.ts 复用同一网关契约——工具不感知自己面对的是进程内还是远程 Gateway [源码确认，合理推断（双实现同接口）]。

node 暴露设备能力命令（camera.*、screen.record、location.get，macOS app 加 canvas.*），配对为设备级、审批存于 device pairing store [文档声明]；相关表 session_members、device_pairing_join_codes、operator_approvals 在 src/state/ schema 常量中可见 [源码确认]。

CHAPTER 12 · PRACTICE & INTERVIEW

把前十一章倒过来用：从症状走回源码。

五步诊断法 + 三套面试题（架构 / 故障 / 安全），全部答案可落回课程定位。

五步诊断法

第一步定层：症状发生在哪层？唤醒（cron / heartbeat / 通道）→ run 预算（run-loop）→ 会话续跑（runAgentPrompt）→ 内核（runLoop / 工具）→ 状态（SQLite）。第二步看事件：agent_start / turn_start / turn_end / agent_end / agent_settled / auto_retry_end 哪个缺失或重复——事件即分层探针（agent-loop.ts:228/:523、agent-session-prompting.ts:47）。第三步查预算：run 重试 used/max、会话 retryCount、溢出压缩 overflowRecoveryAttempts(≤3)、idle 连击(≤5) 四个计数器各查各的，勿混为一谈。第四步读账本：agent SQLite 的 transcript_events 与 sessions 是唯一事实源，崩溃恢复问题先问“最后一条落库事件是什么”。第五步验证唤醒：跨天不动 = 唤醒源问题——automations 定义是否持久化、timer 是否 arm、heartbeat 是否在 active hours、standing intent 是否已 3 连发 / 过期。

PROBLEM SET 01 · 架构题

“OpenClaw 如何让助理‘活着’而不烧 token？”

展开答题骨架

【结论】 不靠长驻循环，靠有界 run + 持久状态 + 事件唤醒 + 记忆注入。

【机制】 三层循环（预算 / 会话 / 内核）；run 结束即在 finally 里 emit agent_settled 落库休眠；automations / heartbeat / 通道消息再把下一次 run 点火。

【源码定位】 run-loop.ts:71、agent-session-prompting.ts:28/:47、timer-scheduler.ts:50、heartbeat-runner-scheduler.ts:62。

【反例追问】 agent_settled 为什么在 finally 里？——失败 / 中止也要收束，唯一例外是 handoff 把后续 run 控制权移交外部投递。

PROBLEM SET 02 · 故障题

“一个 cron 任务每天凌晨都失败重跑，怎么查？”

展开答题骨架

【结论】 先在“定层”里分清是 run 失败预算耗尽、agentTurn 60min 安全阀、还是 dreaming / 任务本身报错。

【机制】 预算只计 recovery；“到点重跑”多为"上次没跑完 + 定义持久化 + 明早再 arm"，不是同一次 run 在续命。

【源码定位】 helpers.ts:120-132、retry-budget.ts:35、timeout-policy.ts:16、retry-limit.ts:43 的失败载荷、transcript_events。

【反例追问】 为什么“有进展的续跑”不扣预算反而可能烧更多钱？——预算防失控不防长任务，48h 墙钟与 idle 5 才是另两条红线。

PROBLEM SET 03 · 安全题

“助理要在 Telegram 里执行一条危险 shell，链路上有哪几道闸？”

展开答题骨架

【结论】 审批模式 → ExecApprovalManager 集中裁决 → 审批转发到通道等批复；未批的调用以失败结果回填，模型只见结果不见豁免。

【机制】 ask: off|on-miss|always 三态 + askFallback: deny|allowlist|full；DM 不可信输入与 pairing；beforeToolCall 可阻断。

【源码定位】 exec-approvals-config.ts:123-125/:257-259、exec-approval-manager.ts:231、types.ts:49（beforeToolCall）、README 安全段。

【反例追问】 Gateway 的 WS 为什么默认只绑 127.0.0.1？——信任边界：控制面在本机，远程必须走 SSH / Tailscale 隧道，防止任何能连端口的人驱动你的设备。
