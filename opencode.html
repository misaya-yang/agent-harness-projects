ACCIDENT-DRIVEN · SNAPSHOT B578B72

一个失控的 Agent，怎样靠持久状态重新站起来。

一条普通指令可能卡在审批、重复调用工具、塞满上下文，或在重启后留下半截调用。本课把事故串成一条可推演的链：输入怎样成为轮次，状态怎样决定续停，失败怎样重新变成下一步。

CHAPTER 01 · WHY WON'T IT STOP?

模型已经说“完成”，Agent 却又跑了一轮。

当前 v1 CLI 不只听模型口头说“停”。每轮重读持久历史，再检查回复结论、工具痕迹和父子消息关系；三项同时成立才退出。

SHORT TRACE · CURRENT CLI V1

把循环压成六步

重读历史 → 判断续停 → 组装上下文与工具 → 调模型 → 结算工具与用量 → 再读历史。用户插话只是新增一条用户消息，下一轮自然改变“最后问题”。

while (true) { history = readDurableHistory() if (finishedNormally(history) && !hasLocalToolPart(history) && answersLatestUser(history)) break persistEverySettledPart(yield runOneModelStep(history)) }

判断法：先问“持久历史现在长什么样”，不要先问内存 finished 标志。

CHAPTER 02 · ONE BRAIN, MANY SURFACES

TUI 正常，Web 却看见另一份状态。

终端、Web、桌面、IDE 与 SDK 经过同一张 HTTP/事件契约；本地嵌入只是把网络 fetch 换成进程内或线程内 fetch。

  1. 最短 trace：客户端 → 统一路由 → 按目录实例 → 会话循环 → 事件流 → 客户端。
  2. 实例边界：一个进程服务多个目录；首次并发加载合并成一次，销毁时广播。
  3. 实时边界：会话事件走 SSE；交互终端字节流才走 WebSocket。
  4. 安全边界：开启局域网发现会扩大绑定面，未配置认证时应视为暴露风险。

CHAPTER 03 · WHAT SURVIVES A CRASH?

进程重启后，半截工具调用让下一次请求非法。

v1 以消息与 part 表作为循环判据；v2 把 durable 事件当权威、查询表当投影。两代都守一条底线：恢复后的历史必须仍是合法对话。

CHAPTER 04 · THE TOOL THAT DISAPPEARED

工具明明注册了，模型却根本看不见。

v1 汇入内建、自定义、插件与 MCP 工具，再按模型、agent 与权限生成当轮视图；v2 正升级为带版本身份的 materialize 快照。

CHAPTER 05 · APPROVAL WITHOUT FREEZING

工具等待批准，整个 Agent 看起来像死机。

工具识别真实资源后主动 ask 并挂起。v1 的等待与 always 授权主要活在进程内；v2 把 asked/replied 与保存规则做成 durable 状态。

审批裁决矩阵选择四个维度
01 · permission
02 · agent
03 · 规则位置
04 · reply
等待选择
  1. 选择资源、agent、规则位置与回复。
  1. 短 trace：识别资源 → findLast → ask → 挂起 → reply → 结算/停止。
  2. always 会放行同会话已排队且被新规则覆盖的请求；reject 可携带修正反馈。
  3. 默认拒绝停循环，避免模型在人明确说“不”后绕路。
  4. 规则不是沙箱：获批的 shell 仍以宿主用户能力运行。
小结 · 事故判断

asked 无 replied 时先找应答者。练习：调整规则顺序验证“后写规则赢”。

CHAPTER 06 · THE PROMPT CHANGED OVERNIGHT

日期或规则一变，长会话缓存全部失效。

v1 每次请求按稳定顺序组装 system；v2 把固定 agent 指令与环境基线分开，用 context epoch 让大多数变化只追加尾部补丁。

V1 · BASE固定指令

按模型选择底稿；agent 指令可替换基础段。

V1 · CONTEXT变化分片

环境、项目规则、MCP、技能清单按稳定顺序装配，常态不超过两条 system。

V2 · EPOCH类型化源

每个源定义 baseline、update、removed，并区分“暂时不可观察”与“不存在”。

V2 · PATCH三分支

未变复用；兼容变化追加；不兼容或压缩越界才换代。

CHAPTER 07 · MEMORY WITHOUT AMNESIA

上下文装不下；删完历史，Agent 也忘了目标。

compaction 保语义，prune 只减工具输出体积，溢写保原文。三种“遗忘”解决不同问题。

  1. 短 trace：超限 → 摘要旧历史 → 保留近期原文 → 重建合法消息 → 继续。
  2. 五段锚点：目标、细节、工作状态、下一步、相关对象；旧摘要滚动合并。
  3. v1 当前：按 turn 保留约 25% 可用预算（2k–15k），可 prune，并可能注入“继续”消息。
  4. v2 方向：请求前估算加 20k 缓冲，默认保留 8k recent；prune 尚未接线。
  5. 一次恢复：压缩后仍 overflow 就硬停，不能无限递归压缩。
小结 · 设计练习

标出必须逐字留、可以摘要、只留检索句柄的三类数据。工具配对和当前阻塞项不能只靠自由摘要。

CHAPTER 08 · THE CHILD THAT NEVER REPORTED BACK

父 Agent 等子任务卡死，兄弟还在重复工作。

当前 v1 把子代理实现成 task 工具创建的普通子会话：不共享父 transcript，没有 swarm 或横向通信，只回一条文本结果与状态信封。

CHAPTER 09 · TWO GENERATIONS, TWO RETRY OWNERS

一次瞬时错误，触发了十几次请求。

SDK、HTTP 和会话层若都重试，次数会相乘。OpenCode 关闭通用 SDK 自动重试，再让不同层只处理自己拥有的失败。

DO NOT BLEND迁移未完成

v2 尚缺 task、多来源工具完整接入、prune 等能力。

  1. 错误三去向：回模型自纠、抛用户、自动重试但对 UI 可见。
  2. 整轮风险：流中途失败后重跑可能重复已执行写操作；当前未见复用已完成结果的守卫。
  3. 中断不重试：用户取消是控制信号，不能被重试器复活。

CHAPTER 10 · EXTENSIONS WITHOUT A BACKDOOR

插件改得了请求，却绕开了对外契约。

插件拿普通生成客户端访问同一服务器契约；技能正文按需加载；工具开关应同步改变 schema。

KNOWLEDGESkills

PROTOCOLSDK / MCP / ACP

  1. 短 trace：声明 → 兼容门禁 → 注册 → 权限过滤 → 统一客户端 → 事件观察。
  2. 配置判断：多来源后加载者覆盖前者，企业托管层最终兜底。
  3. 代际边界：v2 远程 skill 防护更严格，不代表 v1 完全等价。
  4. 实验边界：受限解释器限制脚本环境，不把被调用工具变成 OS 沙箱。
小结 · 扩展审查

回答：模型何时看见？谁能调用？异常去哪？开关关闭时 schema 是否消失？

CHAPTER 11 · WHEN SELF-CORRECTION LOOPS

模型连续三次用同一参数撞同一堵墙。

自纠是能力，重复自纠是失控。步数、重复检测、审批、输出预算和取消共同治理，但没有覆盖一切的全局计时器。

  1. 短 trace：失败回模型 → 重写 → 再调用 → 同名同参三次 → doom_loop 审批。
  2. 步数墙：v1 主要靠 assistant 预填收尾；v2 同时摘除工具并设 toolChoice:none。
  3. 资源墙：默认子代理深度 1、工具输出限额、会话可取消；没有任务树总预算。
  4. 路径墙：词法与真实路径双查防符号链接逃逸，但仍非系统隔离。
  5. 观测墙：重试、结算、审批、会话状态都应可见。
KNOWN RISK整轮流级重试可能重复副作用。写工具仍需幂等键、执行记录或事务，不能只靠退避。
小结 · 故障演练

模拟第三次相同调用：展示什么证据？放行多大范围？拒绝后能否绕路？把答案写进产品。

CHAPTER 12 · DIAGNOSE FROM STATE

“Agent 卡住了”不是诊断，只是症状。

先看会话状态，再看最后合法历史，再看工具结算与审批，最后检查预算、重试和 v1/v2 边界。

五步诊断法

① 状态：idle、busy、retry，还是事件断线？② 历史：最后问题是谁，回复是否属于它，是否有本地工具 part？③ 结算：每个 tool use 是否完成、失败或补成 interrupted？④ 闸门：是否有未回复审批、retry-after、步数或深度限制？⑤ 代际：解释的是当前 v1 还是迁移中的 v2？

课程事实边界

静态快照能证明实现关系，不能代替线上运行证据；未来版本需要重新核对。

PROBLEM SET 01 · 主循环题

“provider 返回 stop，为什么 Agent 仍继续？”

展开答题骨架

finish reason 与工具事实可能不一致。v1 同时检查正常 finish、没有本地工具 part、回复属于最新用户；任一不成立就续。判据来自持久历史，崩溃恢复和插话可复用。

PROBLEM SET 02 · 长会话题

“规则变化，怎样兼顾新鲜度与缓存？”

展开答题骨架

先分版本：v1 稳定重组 system；v2 才有 context epoch。再答未变复用、兼容变化追加、不兼容才换代，以及快照和序号窗口的成本。

PROBLEM SET 03 · 可靠性题

“如何保证崩溃后还能继续工具会话？”

展开答题骨架

守住每个 tool use 必有 result：退出结算、重放补洞、重启清账。先验证消息合法，再验证副作用幂等；进程启动成功不算完成。

step
一次模型采样；是否再采样由外层循环决定。
steer
运行中插话，在下一轮边界进入历史；v2 将其显式持久化。
settle
工具从 pending/running 到 success/error 的生命周期。
materialize
生成当轮模型真正可见的工具快照。

毕业练习

任选症状，用四句话回答：事故、短 trace、持久判据、失败路径验证。能答完，你学到的是可迁移的 Harness 思考法。
