KERNEL ATLAS · 4-AGENT PANORAMIC SYNTHESIS

四大主流开源 Agent 全景架构对比与技术选型指南

横向打通 Codex (`codex-rs`)、Grok Build (`xai-org/grok-build`)、DeepSeek Harness (`deepseek-harness`) 与 Pi Agent (`pi-mono`) 六大核心维度。选型结论是基于本地源码快照的教学归纳，不代表各上游项目的官方定位。

对比维度四大主流 Agent 架构实现与技术取舍核心特征
1. 会话与状态模型 Codex: Thread / Turn / Item 三层层级容器，状态由内存 Actor + 外部存储双重建模。
Grok Build: Tokio LocalSet 独立线程 Actor（`SessionActor` + `ChatStateActor`），追加持久化到 `updates.jsonl`。
DeepSeek: 纯追加型不可变 Session Log，由 `SurfaceManager` 实时投影出当前模型可见历史。
Pi Agent: 追加型 JSONL Session 树（`id` / `parentId`），通过移动叶节点指针实现非破坏性分支与回退。 State vs Tree
2. 通信协议与交互 Codex: App Server 双向 JSON-RPC 协议，规范化 Request 与 started / delta / completed 通知。
Grok Build: 采用 Agent Client Protocol (ACP) 标准协议，扩展 XAI 专有事件（`rewind`, `compaction`）。
DeepSeek: 面向自动化与工具管线的 JSON-RPC stdio / NDJSON 协议，流式提交 committed assistant 消息。
Pi Agent: LF-only JSONL Coding-Agent RPC 与 4 字节大端前缀 + 定长 CBOR 独立 Server Protocol 双协议面。 JSON-RPC / ACP / CBOR
3. 沙箱与权限控制 Codex: `SandboxPolicy` (`ro`/`ww`/`dfa`) × `ApprovalPolicy` (`untrusted`/`on-request`/`never`) 正交二维决策矩阵。
Grok Build: `PermissionManager` (4种模式) × `SandboxProfile` (`workspace`/`read-only`/`strict`/`devbox`)，分层合并。
DeepSeek: 3 种文件效果模式 (`ro`/`ww`/`dfa`) × 独立审批通道，不可用时强制 fail-closed。
Pi Agent: 默认采用宿主进程全量权限；`Project Trust` 控制配置加载，真正安全隔离依托外部 Docker/VM。 Sandbox × Approval
4. 上下文工程与压缩 Codex: 达到预算阈值触发 CompactionSummary 折叠，保留关键目标与 Diff 事实。
Grok Build: 85% 上下文压力触发全量替换压缩，专用 Sampler 生成摘要并记录 `CompactionCheckpoint`。
DeepSeek: `compaction/start` 耐久锁机制，在稳定日志区间生成摘要并通过 Surface Replacement 原子替换。
Pi Agent: `firstKeptEntryId` 动态截断点选择，后向搜索绝不切断 toolResult，单回合支持超长前缀摘要。 Compaction & Summary
5. 执行世界抽象 Codex: Local / Git Worktree / Cloud 容器 / 远程宿主多环境适配。
Grok Build: `WorkspaceSession` 统一封装 FS、PTY、ProcessManager、VCS 与检查点，解耦上层调用。
DeepSeek: 严格三元解耦（Service Definition / Provider / Consumer），支持 Local、Sandbox 与 E2B 云沙箱热插拔。
Pi Agent: 原生 Node.js 宿主接口，支持 Gondolin 微虚拟机路由与 OpenShell 容器化封装。 Workspace Seam
6. 扩展体系与生态 Codex: 定制六边形（AGENTS.md、Memories、Skills、MCP、Hooks、Subagents）。
Grok Build: 规则文件、Skills、MCP 服务、Plugins 分发包、生命周期 Hooks 与跨会话 Memory。
DeepSeek: Cordis 插件树、Profile 继承、Agent Presets 作用域与 Dynamic Cordis 内存自修改运行时。
Pi Agent: Jiti 动态加载 TypeScript 模块（`ExtensionAPI`）、ResourceLoader 与统一 Provider 适配器。 Extension Hexagon
PI AGENT 适用 轻量嵌入式与非线性分支探索

需要极简轻量 TypeScript 内核、非破坏性 JSONL 树形分支探索（`/tree`）与 CSI 2026 同步差分渲染的应用。

CODEX 适用 企业级多端与富客户端集成

需要严密 App Server 双向协议、细粒度正交权限矩阵与 Thread/Turn/Item 完整生命周期的生产级开发平台。

GROK 适用 高性能 Rust 终端与深度版本控制

追求极致终端响应速度、全屏 TUI 交互、ACP 标准支持以及原子级 Git Workspace Checkpoint / Rewind 恢复能力。

DEEPSEEK 适用 极致插件化与执行环境热插拔

追求“Everything is a Plugin”架构，需通过 Cordis IoC 容器无缝切换本地执行、E2B 云沙箱与自修改运行时的场景。

CHAPTER 08 · COMPACTION & BRANCH SUMMARY

Compaction 改变 Context Projection，不擦除旧 Entry。

当前 coding-agent 源码用 firstKeptEntryId 指向保留边界；cut point 不落在 toolResult 上，超大单 Turn 会拆出 prefix summary。Branch summary 则把离开的路径带到新分支。

  1. 判断压力：contextTokens 超过 window - reserveTokens。
  2. 选择边界：从后向前保留近期内容，不切断 tool result。
  3. 序列化：Tool result 在摘要请求中截断，原 JSONL 不变。
  4. 生成摘要：独立 routing/session id，禁用 tools 与 cache retention。
  5. 追加 Entry：summary、firstKeptEntryId、tokensBefore 与 file details。
SOURCE WINS不要把另一套 Harness 格式混进来。仓内部分文档提到 retainedTail，但当前 coding-agent CompactionEntry 与 buildContextEntries() 以 firstKeptEntryId 为实现事实。

SOURCE-ALIGNED TEACHING SKELETON · ANSI CSI 2026 TUI

ANSI CSI 2026 同步差分终端重绘算法 (`DifferentialTuiRenderer`)

下面是根据 `packages/tui/src/tui-main-screen.ts` 整理的教学骨架，不是上游源码复制。真实实现还处理 viewport、Kitty image、cursor、scrollback、resize 与 full redraw 条件。

// packages/tui/src/differential-renderer.ts export class DifferentialTuiRenderer { private previousLines: string[] = []; private outputStream: NodeJS.WriteStream; constructor(stream: NodeJS.WriteStream = process.stdout) { this.outputStream = stream; } /// 差分渲染：仅输出发生变更的行，并使用 CSI ?2026h/l 消除屏幕撕裂 public render(nextLines: string[]): void { let buffer = "\x1b[?2026h"; // 开启 ANSI CSI 2026 同步输出锁 const maxRows = Math.max(this.previousLines.length, nextLines.length); for (let row = 0; row < maxRows; row++) { const prev = this.previousLines[row] ?? ""; const next = nextLines[row] ?? ""; if (prev !== next) { // 光标跳转到特定行（1-indexed）并清空行内容后覆写 buffer += `\x1b[${row + 1};1H\x1b[2K${next}`; } } buffer += "\x1b[?2026l"; // 关闭 ANSI CSI 2026 同步输出锁，触发终端原子绘制 this.outputStream.write(buffer); this.previousLines = [...nextLines]; } }

架构精要：Pi TUI 坚持将“呈现”与“状态”彻底分离，`render()` 不修改任何 Agent 运行时模型；`\x1b[?2026h` 确保现代终端在接收完整差分帧前不刷新显存，杜绝高频流式输出下的终端闪烁。

SOURCE-ALIGNED TEACHING SKELETON · CBOR PROTOCOL FRAMING

4 字节大端定长 CBOR 协议帧打包与流式解码 (`PiProtocolFraming`)

下面是协议两层组合后的教学骨架，不是上游源码复制：`packages/protocol/src/framing.ts` 只负责带 16 MiB 默认上限的 4-byte big-endian `Uint8Array` 分帧，CBOR 编解码属于 `packages/protocol/src/cbor/`。

// packages/protocol/src/framing.ts import * as cbor from "cbor-x"; export class PiProtocolFraming { /// 编码：[4-Byte Big-Endian Length] + [CBOR Payload] public static encodeFrame(message: unknown): Buffer { const payload = Buffer.from(cbor.encode(message)); const header = Buffer.alloc(4); header.writeUInt32BE(payload.length, 0); return Buffer.concat([header, payload]); } /// 解码：处理 TCP / WebSocket 流式粘包与半包分片 public static decodeFrames(incomingBuffer: Buffer): { messages: unknown[]; remaining: Buffer } { const messages: unknown[] = []; let offset = 0; while (offset + 4 <= incomingBuffer.length) { const frameLength = incomingBuffer.readUInt32BE(offset); if (offset + 4 + frameLength > incomingBuffer.length) { break; // 半包等待后续字节到达 } const framePayload = incomingBuffer.subarray(offset + 4, offset + 4 + frameLength); messages.push(cbor.decode(framePayload)); offset += 4 + frameLength; } return { messages, remaining: incomingBuffer.subarray(offset), }; } }

架构精要：Pi 独立 Server Protocol 采用基于大端长度头与定长 CBOR 的二进制打包方案，支持高吞吐远程会话租赁（Session Lease），与基于 stdin/stdout 的 LF-only JSONL RPC 形成清晰的双协议面。

CHAPTER 12 · SECURITY & PRACTICE

Pi 默认拥有启动用户的全部权限；Project Trust 不是 Sandbox。

内建 Read、Write、Edit、Bash 和 Extensions 都运行在 Pi 进程权限内。处理不可信仓库或无人值守任务时，真正边界必须来自 Container、VM、Micro-VM 或 Policy-controlled Sandbox。

机制实际控制什么不保证什么
Project Trust项目级设置、Packages、Extensions 与资源是否加载不限制已加载工具
--tools allowlist模型看见哪些 Built-in Tools不是进程权限
Gondolin Extension把 Built-in Tools 与 ! commands 路由到 Micro-VM其他 Extensions 仍可能在 Host
Docker / OpenShell隔离整个 Pi 进程及其工具Bind mount 仍可改 Host

五步诊断法

先确定入口模式和当前 Session；再沿 agent/turn/message/tool events 找最后一个事实；区分 Agent conversion 与 Provider adaptation；核对 active tools 与 Extensions；最后确认需要的是 Project Trust、工具配置还是外部隔离。

PROBLEM SET 01 · 架构设计题

“如何利用 Pi 的 JSONL Session Tree 实现低成本的探索性任务分支与多路径假设验证？”

展开答题骨架与树形推演

【场景定义】 开发者需要对一个复杂的重构任务探索方案 A（重写接口）与方案 B（向后兼容补丁），希望能够在不同思路间自由切换，既保留每条分支完整的上下文事实，又不在磁盘上复制巨大的对话历史。

【归属层/故障机理分析】 属于会话树形持久化层（`Chapter 07: JSONL Session Tree`）。核心机理在于：Pi 抛弃了传统 Agent 线性数组或全局覆写的历史记录方式，将会话建模为 Append-Only 的有向无环图（DAG）。每个 Entry 均包含 `id` 与 `parentId`，分支切换仅需移动当前会话的 `leafId` 指针，即可通过反向遍历即时投影出目标分支的全部祖先消息。

【关键证据链/判定条件】
1. 单文件多分支：单个 `.jsonl` 文件同时记录多条互不干扰的演化路径，无惧并发写冲突。
2. 无损分支：创建新分支不需要对已有历史做任何 `UPDATE` 或 `DELETE` 操作，杜绝数据损坏风险。
3. 上下文投影：调用 `buildContextEntries()` 时仅提取从当前 `leafId` 向上回溯到根节点的活跃链路。

【解决方案与系统级防线】
• 使用 `SessionManager.branch(entryId)` 实施非破坏性回退，在分叉点开启新探索。
• 注意认知边界：Session Tree 只切换对话上下文，不负责文件系统状态回滚。文件级变更需配合 Git 提交或工作区分支进行隔离。

PROBLEM SET 02 · 故障排查题

“并行工具调用（Parallel Tool Batch）执行时，为什么工具完成日志乱序但最终 Transcript 顺序依然严格对齐？”

展开答题骨架与排序机制

【场景定义】 模型单次回合返回了 `[fetch_doc, grep_symbol, read_file]` 三个工具调用并开启并发执行，控制台日志显示耗时最短的 `grep_symbol` 最先完成，但最终发送给模型的上下文与 Transcript 顺序依然严格保持为原调用顺序。

【归属层/故障机理分析】 属于工具批次调度与事件生命周期（`Chapter 06: Tool Batch`）。机理分析：Pi 区分了执行完成事件（`tool_execution_end`，按物理实际完成时序发出，供 TUI 实时更新进度）与会话提交顺序（`toolResult` 消息，必须严格按照模型在 `AssistantMessage` 中声明的 Source Order 插入）。

【关键证据链/判定条件】
1. 调度执行：`runToolCalls()` 使用 `Promise.all` 并发触发，各 Promise 解决时立即广播局部进度事件。
2. 槽位预留：内部预先分配与声明顺序一致的 `resultsArray[index]` 槽位。
3. 消息生成：所有并发任务完成后，按索引顺序依次生成 `ToolResultMessage` 并追加到 Transcript。

【解决方案与系统级防线】
• 绝不可将实时的流式完成通知直接当作上下文提交顺序，避免破坏大模型关于多工具调用依赖的上下文假设。
• 若任一工具在定义中声明了 `sequential: true`，整批调用立即安全降级为严格串行流水线。

PROBLEM SET 03 · 安全攻防题

“Pi 默认以宿主全量权限运行，为什么说 Project Trust 不是 Sandbox？如何为企业构建真实防御边界？”

展开答题骨架与防御纵深

【场景定义】 用户克隆了一个公开的第三方开源项目并用 Pi 打开，项目目录内包含了恶意的 `.pi/extensions/auto-run.ts` 扩展脚本，试图在启动时窃取本地环境变量与 SSH 私钥。

【归属层/故障机理分析】 属于供应链安全与执行隔离边界（`Chapter 09: Extensions` & `Chapter 12: Security`）。核心认知：`Project Trust` 只是一个资源加载的准入门禁（Gate），用于决定是否执行该目录下的配置文件与扩展，它绝不是操作系统级别的安全沙箱。一旦用户点击了“Trust”，所有已加载的代码均在宿主 Node 进程内以当前操作系统用户身份全权运行。

【关键证据链/判定条件】
1. 未受信任状态（Untrusted）：Pi 拒绝加载 `.pi/` 下的项目级扩展与 prompt 模板，有效阻断恶意脚本初次加载。
2. 受信任状态（Trusted）：Jiti 将直接在主进程内求值 TypeScript 扩展，拥有完整的 `fs`, `child_process` 与 `net` 访问权限。
3. 权限继承：内建的 `bash`、`edit` 工具同样不具备任何内建特权降级或 chroot 隔离。

【解决方案与系统级防线】
• 生产与 CI 环境下必须将整个 Pi 进程置于容器（如 Docker、OpenShell）或 Micro-VM（如 Firecracker、Gondolin）中运行。
• 宿主与容器间仅允许受限挂载目标工作区，严禁挂载 `~/.ssh`、`~/.aws` 或根文件系统。
