CHAPTER 01 · FIND THE OWNER

场景：终端显示“完成”，会话里却没有最终消息。先定位状态拥有者。

同一个任务横跨模型适配、循环、会话壳和呈现层。只有找到“谁持有这份事实”，你才知道该查哪一种证据。

四层职责与事实拥有者

Pi AI 翻译各家模型请求；Agent Core 运行 turn、工具与队列；AgentSession 持久化、压缩、重试并托管扩展；TUI / RPC 只呈现或传输。屏幕结束，只能证明最后一层画完了。

SHORT TRACE

user → stream → message_end → session entry → render

若 message_end 已有而 entry 缺失，查会话壳；entry 已有而屏幕没更新，查呈现；stream 直接以 error 收口，问题更靠近模型适配。

先认 owner，再选择事件、会话条目或屏幕证据。

学习检验：给你“屏幕完成但记录缺失”，你会先查完成事件与会话条目，而不是笼统重跑。

partial 是草稿，message_end 才是已提交消息；agent_end 发出后，等待型监听器还可能尚未结算。

事件与状态的关系

message_start/update 更新 streamingMessage，不会不断追加 transcript；message_end 才把完成消息推入公开状态。监听器按顺序等待，因此“结束事件发出”和“run 已闲置”不是同一时刻。

判断法

三种读点，三种承诺

画字读 partial；取最终答案读完成消息；安全开启下一项工作等 idle。不要在应用层再造一份“当前助手消息”。

学习检验：连续点击更新与结束，能说出哪一步只改变草稿、哪一步才增加消息数。

CHAPTER 03 · ONE PROMPT, MANY TURNS

场景：用户只问一次，日志却出现五次模型请求。它不一定失控。

一次 prompt 可以包含多个 turn；每个 turn 是“一次助手响应 + 紧随其后的工具批次”。工具结果回填后，模型需要再开一轮才能继续推理。

  6. assistant message_end
  7. tool execution
  8. toolResult messages
  9. next turn / stop
  10. agent_end

先看事件顺序，再谈“任务完成”。

循环的四类终止条件

遇到 error/aborted 立即停；一批工具全部要求 terminate 才停；宿主的 finishTurn 在回合结算边界决定是否结束；工具、插话和续跑队列都空才自然停。低层循环没有内建轮数上限，预算必须由宿主接入。

SHORT TRACE

toolUse → result → toolUse → result → stop

这是一条 prompt、三次 turn。看到 agent_end 只说明循环已停，不说明业务目标已达成。

学习检验：能把“模型请求次数”与“用户输入次数”分开，并指出缺少预算回调的失控风险。

CHAPTER 04 · STEER / FOLLOW-UP / ABORT

场景：工具正在写文件，用户说“停，改另一个方案”。消息该插在哪里？

Steer 纠正当前任务，Follow-up 排下一件事；二者都不会插进 tool call 与 tool result 之间。Abort 只是协作式信号，不能撤销已发生的副作用。

消息干预先保证协议配对

Steer 默认一次取最早一条，在当前批次落定后、下次模型调用前进入；Follow-up 只有任务自然收口后才续跑。Abort 会传给模型流、钩子和工具，但是否及时停止取决于执行体是否响应信号。

练习

开始工具 → Steer → Follow-up → 结束 Turn

预期先消耗 Steer，Follow-up 仍排队。若先 Abort，只能断言信号发出，不能断言副作用回滚。

学习检验：能区分 Steer、Follow-up、Abort，并为 Abort 写出“工具必须配合”的验收条件。

缓存与思考档位也要可诊断

兼容模型会用稳定前缀、延迟工具与工具引用降低缓存重付；兼容的 Anthropic 模型还能记录实际 provider thinking level。它们是 Provider 能力，不是全局承诺。

学习检验：跨模型重放失败时，会先判断是通用消息投影还是目标 Provider 约束，而不是修改主循环。

CHAPTER 06 · TOOL BATCH

场景：快工具先完成，为什么不能先把它的结果塞回会话？

执行可以并行，历史必须确定。Pi 把一批工具拆成“按源序预备 → 并发执行 → 按源序回填”。

工具批次排序实验parallel

只要一个工具要求 sequential，整批都串行。

并行进度与源序提交

tool_execution_end 按真实完成先后发，UI 立即反馈；tool result 按模型原始调用顺序写入，确保重放、缓存与测试稳定。两者混用才会让结果对不上调用。

两道安全题

残缺参数与副作用冲突

助手因 length 被截断时整批不执行，只回喂错误让模型重发。参数校验与调用前钩子先串行完成；同文件修改也应串行化。

动态工具

结果可声明 addedToolNames。兼容 Provider 随后以延迟定义或 tool_reference 按需出现新工具；不支持时退回立即声明。

学习检验：运行并行实验后，能解释为何 fast 先结束，而 transcript 仍先写 slow 的结果。

CHAPTER 07 · APPEND-ONLY SESSION TREE

场景：回到旧消息试另一条路，原分支会不会被覆盖？文件改动会不会一起回滚？

当前 Coding Agent 使用 v3 追加式条目树；移动 leaf 就能从历史点续写，旧分支仍在。但这是对话历史，不是工作区快照。

源码更新 · 规范上下文

历史保留，模型视图仍可以修订。

SessionManager 已成为后续模型请求上下文的权威来源。新的 context_edit 作为追加条目，可省略或替换一条消息在未来请求中的内容，却不改写原始会话树和 UI 历史。

CHAPTER 08 · CONTEXT COMPACTION

场景：上下文快满了，直接删最老消息却把 tool call 与 result 拆开。

当前压缩不删历史，只追加摘要与 firstKeptEntryId；下一次请求看到“摘要 + 近期路径”。切点必须让位于工具配对完整性。

  1. 判压力：provider usage 为权威，新增内容保守估算；超过 window − reserve 才自动触发。

  3. 生成摘要：旧对话转纯文本，合并上一摘要；残缺摘要不落盘。
  4. 追加边界：原条目仍在树中，只有模型投影改变。

压缩改变模型视图，保留历史事实

旧事实仍可供人回读，但摘要会丢细节。溢出时先移除工作状态里的失败响应，压缩并只重试一次；时间戳、模型一致性与闩锁共同防止恢复风暴。

两代协议别混

当前 firstKeptEntryId；在建 retainedTail

新 Harness 的纯压缩函数能产出 retainedTail，但驱动层尚未把它接入完整任务。交互台模拟当前 v3 路径。

学习检验：能回答“旧消息去哪了”：存储没动，模型视图换成摘要和近期路径。

CHAPTER 09 · EXTENSIONS & DELEGATION

场景：把项目设为 Trusted 后，扩展仍能读取宿主凭证。为什么？

Project Trust 决定是否加载项目资源，不是加载后的 OS 权限。扩展在主进程内运行；子代理只是示例扩展启动的一次性进程，并非核心编排器。

源码更新 · 未发布扩展事件

Provider 原始流与规范化事件之间也有观察点。

当前 Unreleased 版本加入 provider_stream_event，让扩展观察解析后、规范化前的供应商事件。它是诊断入口；不要据此推断扩展能够任意改写最终会话事实。

CHAPTER 10 · TUI IS A PROJECTION

场景：终端看起来卡住，实际只是没有变化的行无需重绘。

TUI 比较前后行，只更新变化区间，并用同步输出降低流式闪烁。它展示状态，但不拥有 Agent 的运行事实。

差分帧对比台等待帧

高亮行是本帧真正重写的内容；宽度变化会完整重绘。

TUI 只投影运行状态

流式文本只改一行就不重画整屏；窗口宽度变了，旧换行假设失效，必须完整重绘。组件产出超宽行时，差分路径宁可报错也不悄悄错位。

判断法

状态证据不要取自截图

自动化应读完成事件、会话上下文或 RPC 状态。截图不能证明监听器已结算、消息已落盘或业务目标已满足。

学习检验：依次点击流式、工具和 resize，能解释差分与全量重绘的边界。

底层能力与可运行产品的边界

新会话格式能表达共享树、多 lane、操作记录与可恢复状态；折叠器拒绝 12 类不可能日志，SQLite 租约以 fencing token 挡旧写者复活。但驱动遇到恢复或运行操作会显式拒绝。

协议判断题

progress 能不能当权威状态？

不能。远程栈以带 revision 的完整 snapshot 为准，progress 只是提示；断线后必须以新快照覆盖本地推断。stdio JSONL 还必须独占 stdout，避免普通日志撕碎帧。

学习检验：看到“有类、有类型、有后端测试”，仍会追问哪个入口真正调用它、能否完成 prompt→tool→resume 闭环。

CHAPTER 12 · TRIAGE & BUILD YOUR OWN

综合场景：模型重试、压缩重试和用户处理同时发生，成本开始失控。

按“模型能否修复”和“证据是否仍新鲜”分诊。工具错误回喂模型，瞬态网络错误退避，配额与未知错误交给用户；溢出单独走一次性压缩恢复。

看到什么正确出路验收证据
参数错 / 工具抛错写成 isError 结果，带现场与下一步动作下一轮能自纠
429 / 5xx / 断流只对白名单瞬态模式做可取消退避重试事件 + 终态
quota / billing / 未知不盲重试，交回用户无恢复风暴
context overflow排除普通重试；压缩后仅允许一次恢复尝试新边界 + 闩锁
用户 Abort终止不重试；检查执行体是否响应副作用实际停止

五步判断法

  1. 标入口：SDK、交互、print/json、RPC 或实验远程栈。
  2. 找最后一个已提交事实：终态消息、工具结果、会话条目或 snapshot。
  3. 按 owner 分层：Provider、Loop、Session、Extension、UI。
  4. 检查恢复：类型匹配吗？证据晚于最近压缩吗？预算只允许几次？
  5. 验证目标，不把 HTTP 成功、进程退出或截图当成任务完成。
BUILD CHECK

自己的 Agent 至少写下六条合同

事件何时提交；工具如何排序；截断参数是否执行；队列在哪里注入；失败去往模型、重试还是用户；持久历史怎样重建上下文。每条都要有反例测试。

FINAL EXERCISE

“两个并行工具完成顺序相反，随后上下文溢出。写出不破坏历史的 trace。”

展开参考答案

执行：按声明顺序预备，并发执行；进度按完成顺序发，结果按声明顺序回填。

恢复：确认溢出来自当前模型且晚于最近压缩；移除工作上下文里的失败助手消息，追加压缩边界，再 continue 一次。原始条目不删除，第二次仍溢出就交用户。

验收：工具调用与结果配对完整；历史保留场景，模型下一轮看不到失败残骸；恢复不超过一次。

课程边界会读事件，也会怀疑“已实现”。当前 AgentSession 可运行；示例子代理可用但非核心；远程栈实验；新 Harness 地基已实现、驱动未接线。越过这条边界，都要新的端到端证据。

课程完成：你现在可以从短 trace 判断 owner、顺序、恢复和证据等级，并把机制迁移成可测试合同。
