KERNEL ATLAS · 7-COURSE PANORAMIC SYNTHESIS

七门课程全景：开源 Agent 架构对比与技术选型指南

横向打通 Codex (`codex-rs`)、Grok Build (`xai-org/grok-build`)、DeepSeek Harness (`deepseek-harness`)、Pi Agent (`pi-mono`)，以及新增的 OpenCode (`anomalyco/opencode`)、OpenClaw (`openclaw/openclaw`) 与 Hermes Agent (`NousResearch/hermes-agent`) 六大核心维度。选型结论是基于本地源码快照的教学归纳，不代表各上游项目的官方定位。

对比维度七门课程：各 Agent 架构实现与技术取舍核心特征
1. 会话与状态模型 Codex: Thread / Turn / Item 三层层级容器，状态由内存 Actor + 外部存储双重建模。
Grok Build: Tokio LocalSet 独立线程 Actor（`SessionActor` + `ChatStateActor`），追加持久化到 `updates.jsonl`。
DeepSeek: 纯追加型不可变 Session Log，由 `SurfaceManager` 实时投影出当前模型可见历史。
Pi Agent: 追加型 JSONL Session 树（`id` / `parentId`），通过移动叶节点指针实现非破坏性分支与回退。
OpenCode: 事件流投影进单文件 `opencode.db`，消息历史由最近一条摘要条目之后重建（`filterCompacted`），压缩对主循环完全透明。
OpenClaw: 双 SQLite 文件（全局 `state/openclaw.sqlite` + 每 agent `openclaw-agent.sqlite`），会话、transcript、standing intents 与记忆索引全落库；恢复靠状态已落库 + 事件重放。
Hermes: `~/.hermes/state.db` 以 `parent_session_id` 串起会话血统，外加压缩标记、压缩锁与 gateway 路由表；cron 任务单独持久化到 `jobs.json`。 State vs Tree
2. 通信协议与交互 Codex: App Server 双向 JSON-RPC 协议，规范化 Request 与 started / delta / completed 通知。
Grok Build: 采用 Agent Client Protocol (ACP) 标准协议，扩展 XAI 专有事件（`rewind`, `compaction`）。
DeepSeek: 面向自动化与工具管线的 JSON-RPC stdio / NDJSON 协议，流式提交 committed assistant 消息。
Pi Agent: LF-only JSONL Coding-Agent RPC 与 4 字节大端前缀 + 定长 CBOR 独立 Server Protocol 双协议面。
OpenCode: 单一本地 HTTP 服务器承载内核：`POST /session/:id/message` 是唯一喂脑入口，`GET /event`（SSE）是唯一广播出口；TUI、IDE、GitHub、CI 全是同构客户端。
OpenClaw: Gateway 统一接入模型、工具、消息通道与 macOS/iOS/Android/Wear 伴生应用；Telegram/Discord 等通道经 `src/channels/*` 抽象路由。
Hermes: 单个 Python 内核同时驱动 CLI、23+ 平台消息网关、TUI、Zed ACP、MCP server 与 Electron 桌面六面；`acp_adapter` 负责协议翻译。 JSON-RPC / ACP / SSE / CBOR
3. 沙箱与权限控制 Codex: `SandboxPolicy` (`ro`/`ww`/`dfa`) × `ApprovalPolicy` (`untrusted`/`on-request`/`never`) 正交二维决策矩阵。
Grok Build: `PermissionManager` (4种模式) × `SandboxProfile` (`workspace`/`read-only`/`strict`/`devbox`)，分层合并。
DeepSeek: 3 种文件效果模式 (`ro`/`ww`/`dfa`) × 独立审批通道，不可用时强制 fail-closed。
Pi Agent: 默认采用宿主进程全量权限；`Project Trust` 控制配置加载，真正安全隔离依托外部 Docker/VM。
OpenCode: 无 OS 级沙箱；按工具 × pattern 匹配 allow / ask / deny 规则，待审批以 `deferred` 终止原因表达——审批是循环的输入而非旁路。
OpenClaw: `beforeToolCall` / `afterToolCall` 钩子 + 网关审批（exec-approval-manager）；审批不通过时工具调用被替换为失败结果，模型只见结果不见例外。
Hermes: `tools/approval.py` 分级：hardline 直接拒绝、危险操作询问、cron/gateway 非交互场景各自降级；记忆写入另有 `write_approval` 闸门。 Sandbox × Approval
4. 上下文工程与压缩 Codex: 达到预算阈值触发 CompactionSummary 折叠，保留关键目标与 Diff 事实。
Grok Build: 85% 上下文压力触发全量替换压缩，专用 Sampler 生成摘要并记录 `CompactionCheckpoint`。
DeepSeek: `compaction/start` 耐久锁机制，在稳定日志区间生成摘要并通过 Surface Replacement 原子替换。
Pi Agent: `firstKeptEntryId` 动态截断点选择，后向搜索绝不切断 toolResult，单回合支持超长前缀摘要。
OpenCode: `isOverflow` 触发后把 compaction 摘要作为普通输入自喂进下一轮循环（compact then continue），`finish` 语义防御 provider 谎报。
OpenClaw: 溢出路径与阈值路径双路触发 `runAutoCompaction`；context-engine 以能力面（bootstrap / assemble-before-prompt / compact）可插拔。
Hermes: “Prompt 缓存神圣”宪法——缓存标记边界只有压缩可合法击穿；micro-compaction 与 `trajectory_compressor` 分别服务在线回合与离线轨迹。 Compaction & Summary
5. 执行世界抽象 Codex: Local / Git Worktree / Cloud 容器 / 远程宿主多环境适配。
Grok Build: `WorkspaceSession` 统一封装 FS、PTY、ProcessManager、VCS 与检查点，解耦上层调用。
DeepSeek: 严格三元解耦（Service Definition / Provider / Consumer），支持 Local、Sandbox 与 E2B 云沙箱热插拔。
Pi Agent: 原生 Node.js 宿主接口，支持 Gondolin 微虚拟机路由与 OpenShell 容器化封装。
OpenCode: 工具清单按模型 / agent / 权限三层过滤后交给 LLM；执行发生在 server 宿主侧，子代理以子 session 形式派生。
OpenClaw: 内核与宿主通过 `packages/agent-core` 能力接口解耦；run 落在 gateway 所在设备，伴生应用只是表面而非第二执行世界。
Hermes: 七个执行后端（local、Docker、Termux、Daytona、Modal 等）共享同一窄腰工具层，文件同步有独立通道，后端切换不动 loop。 Workspace Seam
6. 扩展体系与生态 Codex: 定制六边形（AGENTS.md、Memories、Skills、MCP、Hooks、Subagents）。
Grok Build: 规则文件、Skills、MCP 服务、Plugins 分发包、生命周期 Hooks 与跨会话 Memory。
DeepSeek: Cordis 插件树、Profile 继承、Agent Presets 作用域与 Dynamic Cordis 内存自修改运行时。
Pi Agent: Jiti 动态加载 TypeScript 模块（`ExtensionAPI`）、ResourceLoader 与统一 Provider 适配器。
OpenCode: 插件 hooks、自定义 commands、Skills、agents（子代理定义）与 MCP 统一汇入 tool registry 与权限管线。
OpenClaw: 约 150 个 `extensions/` 目录、SKILL.md 技能、SOUL.md 人格与 automations 工具，都以网关插件身份组合进单一 Gateway 进程。
Hermes: 学习闭环让 Agent 自创自改 SKILL.md、写回 MEMORY.md；与 OpenClaw 共享 SOUL.md / MEMORY.md / SKILL.md 文件族谱系并有双向迁移器（§ 条目是 Hermes 侧约定，OpenClaw 搬运不解析）。 Extension Hexagon
DEEPSEEK 适用 极致插件化与执行环境热插拔

追求“Everything is a Plugin”架构，需通过 Cordis IoC 容器无缝切换本地执行、E2B 云沙箱与自修改运行时的场景。

CODEX 适用 企业级多端与富客户端集成

需要严密 App Server 双向协议、细粒度正交权限矩阵与 Thread/Turn/Item 完整生命周期的生产级开发平台。

GROK 适用 高性能 Rust 终端与深度版本控制

追求极致终端响应速度、全屏 TUI 交互、ACP 标准支持以及原子级 Git Workspace Checkpoint / Rewind 恢复能力。

PI AGENT 适用 轻量嵌入式与非线性分支探索

需要极简轻量 TypeScript 内核、非破坏性 JSONL 树形分支探索（`/tree`）与 CSI 2026 同步差分渲染的应用。

OPENCODE 适用 服务器即内核的多客户端平台嵌入

需要一个本地 HTTP 服务器承载 Agent 内核，让 TUI、IDE、CI、GitHub 成为同构客户端；事件投影进单文件 SQLite，会话历史与计费统计最容易被平台接管。

OPENCLAW 适用 跨天存活的通用个人助理

“活着”不靠无限循环：有界 run 预算 + 双 SQLite 持久状态 + automations / standing intents 唤醒 + 凌晨记忆固化，多通道贯通你的设备。

HERMES 适用 单机 Python 的自演化内核

学习闭环接入 agent loop 一等公民（回合 nudge → 后台自省 → 技能/记忆写回），同一内核从 Termux 手机到 GPU 集群六面部署，并与 OpenClaw 共享两代格式谱系。

CHAPTER 01 · LAYER MAP

先分清 Pi AI、Agent Core、Coding Agent 与 TUI。

Pi 不是一个单体 CLI：统一模型 API 负责 Provider，Agent Core 负责状态与工具循环，Coding Agent 负责 Session、资源与入口，TUI 只负责终端呈现。

SOURCE ROUTE · PI a470b121b

先读四个入口，再用责任探针定位问题。

它们分别回答“谁拥有活状态、谁驱动一次 run、谁组合产品能力、谁保存可分支历史”。

  1. packages/agent/src/agent.tsAgent 拥有 transcript、streaming state、queues、listeners 与 abort controller。
  2. packages/agent/src/agent-loop.tsagentLoop / runLoop 产生 turn、message 与 tool lifecycle events。
  3. packages/coding-agent/src/core/agent-session.tsAgentSession 组合模型、工具、SessionManager、资源和 Extensions。
  4. packages/coding-agent/src/core/session-manager.tsSessionManager 把 entry 写入 append-only JSONL tree，并投影当前 branch。

学完本章你能：先找拥有状态的层，再决定读 Provider event、Agent event、Session entry 还是 UI snapshot。

四层各持有一份可变事实

分层不是为了目录整洁：Pi AI 拥有事件语义，Agent Core 拥有活状态（packages/agent/src/agent.ts:173），Coding Agent 拥有持久历史（packages/coding-agent/src/core/session-manager.ts:855），TUI 只拥有像素（packages/tui/src/tui-main-screen.ts:180）。换 Provider 不动 Loop，换 UI 不动状态；基础 Agent 刻意不碰磁盘，持久化整层留在 CLI 侧。

跨层 bug 都以“某层证据缺失”的形式出现：UI 显示完成但 message_end 从未发出，或 Session 里有 toolResult 而 Agent state 里没有。定位时先问哪层缺证据，再进那层的源码，比通读仓库快一个量级。

边界

判断症状归属看谁持有那份可变事实，不看代码在哪个包。活状态在 Agent，历史在 SessionManager，像素在 TUI；找错 owner 层，修的都是症状不是原因。

Low-level agentLoop() 的 stream 是观察接口；需要 listener barrier、public state 与 idle settlement 时，使用 Agent。

为什么 run 拿的是启动快照

每次 run 开始前，Agent 把 messages 与 tools 复制成一份 context 快照（packages/agent/src/agent.ts:437），请求期间不再看可变 state。不这样做的话：应用中途向 transcript 直接 push，正在飞的 provider 请求与落盘历史会分叉成两个版本。快照的代价是 run 中改 tools 要到下一轮才生效——这是设计要你看见的延迟，不是 bug。

写回 public state 的入口只有一个：message_end 之后由 processEvents（packages/agent/src/agent.ts:544）追加完成消息。streaming 期间外界能读到的 partial 只有 streamingMessage；在应用层另存一份“当前 assistant 消息”，就是给撕裂状态开门。

面试考点 · STATE OWNERSHIP

“收到 agent_end 事件时，能立刻把 Agent state 当最终态读吗？”

展开 30 秒模范答案

不能无条件读。agent_end 是事件不是承诺：等待型 listener 仍属于 settlement 阶段，subscribe 按注册顺序 await listener（packages/agent/src/agent.ts:250），安全读点在 listener 链走完或 waitForIdle() resolve 之后。

加分点：说清三条读法的时间差——partial 读 streamingMessage、最终消息读 state.messages、跨层证据读 Session entry。把三者混为一谈是这题最常见的挂点。

CHAPTER 03 · EVENT LOOP

一次 prompt run 可以包含多个 Turn；这里的 Turn 是一次模型调用加工具批次。

Provider stream 先形成 committed assistant message；如果其中有 tool calls，执行结果成为 toolResult messages，再开启下一个 Turn。

Prompt 事件步进机idle
  1. agent_start
  2. turn_start
  3. user message
  4. transform → convert
  5. provider stream
  6. assistant message_end
  7. tool execution
  8. toolResult messages
  9. next turn / stop
  10. agent_end

观察 Provider event 怎样被提升为 Agent lifecycle。

Turn 的数量由模型决定，不由用户决定

Provider 无状态，所谓“记忆”全是 transcript 重放。Pi 把一次模型调用连同它引发的工具批次定义为一个 Turn（packages/agent/src/agent-loop.ts:155）；一次 prompt 的 turn 数从 1 到几十都有可能，取决于模型是否还在发 tool call。committed assistant message 是批次 preflight 的 barrier（packages/agent/src/agent-loop.ts:281）：参数没流完整，绝不执行。

两个失败推演：若 toolResult 按物理完成顺序即时回流，模型看到的结果与它声明调用的顺序对不上，配对假设断裂；若 stopReason 为 length 的截断消息照常执行 tool call，半个 JSON 参数就可能落盘。后者的处置是整批改判为 error result（packages/agent/src/agent-loop.ts:381）——宁可让模型重试一个干净回合。

边界

循环的终止权在 stopReason，不在事件计数。看到 agent_end 只能证明 loop 停了，证明不了任务做完了。

CHAPTER 04 · STEER / FOLLOW-UP / ABORT

Steer 早于 Follow-up，但不会撕开正在运行的工具批次。

Steer 在当前 assistant turn 的工具完成后注入；只有没有 tool call 和 steering 时才检查 Follow-up。Abort 只触发 signal，Provider 与 Tool 必须主动尊重它。

为什么 steer 不撕开正在运行的工具批次

工具是带副作用的原子操作：bash 跑了一半、edit 落了一半，比让用户多等三秒危险得多。所以 Pi 把注入点钉死在批次边界——入队的 steer（packages/agent/src/agent.ts:283）要等当前 turn 的工具全部处理完、到达 drain 点才被取出（packages/agent/src/agent-loop.ts:259）；follow-up 再低一级，只有没有 tool call 也没有 steering 时才检查。

Abort 是另一种诚实：packages/agent/src/agent.ts:319 只拉下 AbortController，不伪造一条“正常结束”的 assistant 消息。Provider 不检查 signal 就继续流 token 计费，工具不检查 signal 就把副作用跑完。对照 Codex 的审批模型：打断的同样是“下一条要执行的事”，不回收已发生的副作用。

边界

队列只保证注入时机，不保证中止时机。steer 是批次边界的确定性语义，abort 是协作式 signal——两者可靠性不在一个量级，验收 abort 要看 Provider 与工具是否真的响应 signal。

统一语义，故意不统一 wire

Pi AI 统一的是三样：模型查找、auth 合并（packages/ai/src/models.ts:636）、事件收口语义——一切失败都落成 StopReason 的 error 或 aborted（packages/ai/src/types.ts:405）。故意不统一的是 wire payload：system 消息的位置、thinking 签名、tool-call id 规则是各家的私有事实，抹平它们只会得到谁都不像的最小公倍数。

最容易碎的场景是跨模型重放历史：thinking 签名不可重放、tool id 长度规则不同、孤立的 tool call 会被 provider 直接拒收。Pi 把这类修复集中在共享中间层 transformMessages（packages/ai/src/api/transform-messages.ts:64），为孤立调用补 synthetic result，adapter 只负责最后的 payload。把这两层合并成一个“大转换器”，是这类架构最常见的腐化点。

边界

错误不 reject 是合同不是风格：StreamFunction 必须把失败装进最终 AssistantMessage、以 error event 收口。调用方因此永远只有一条消费路径——在 Pi 里用 try/catch 捕 provider 错误是错的。

CHAPTER 06 · TOOL BATCH

并行 body 可以乱序完成，Transcript 仍按模型声明顺序写入。

Preflight 按 source order 校验并执行 beforeToolCall；parallel 模式并发真正的 execute，tool_execution_end 跟随完成顺序，最终 toolResult messages 则回到 source order。

工具批次排序实验parallel

任一目标 Tool 标记 sequential，整批都会退化为串行。

TRUNCATION SAFETY

如果 assistant stopReason 是 length，Pi 不执行其中任何 tool call，而是为每个调用生成解释性 error result。

两种顺序都对，错的是混用

tool_execution_end 跟物理完成顺序走（packages/agent/src/agent-loop.ts:489），TUI 进度靠它实时；toolResult 写 transcript 跟模型声明顺序走，重放一致性靠它。拿实时事件当提交顺序，上下文里会出现结果先于调用；反过来为保顺序憋住进度事件，人就以为卡死了。

真正的坑在副作用：两个并行 edit 改同一文件，各自读-改-写，后写覆盖前写。Pi 的解法不是禁用并行，而是给同文件变更挂串行队列 withFileMutationQueue（packages/coding-agent/src/core/tools/file-mutation-queue.ts:32）；兜底规则是任一目标工具声明 sequential，整批立即退化串行（packages/agent/src/agent-loop.ts:422）。

NOT A FILE CHECKPOINTBranch 不会回滚工作区。JSONL tree 记录对话路径；文件回退必须由 Git、扩展或外部 Sandbox 单独负责。

树把回退成本降成移动指针

线性日志加 undo 的每一次回退都在改历史；Pi 的 branch()（packages/coding-agent/src/core/session-manager.ts:1360）只移动 leaf，旧分支一行不动。探索性任务的本质是多条假设共存：树让 /tree 在任意历史点续写的成本是 O(1)，也让任意分支随时可以回放审计。

模型看到的不是文件，是投影：buildContextEntries()（packages/coding-agent/src/core/session-manager.ts:418）从当前 leaf 回溯路径，再把最近 compaction 之前的段替换为 summary。同一个 v3 JSONL（CURRENT_SESSION_VERSION = 3），UI 读全量、LLM 读精简，两个视图互不篡改。

边界

branch 改变的是“接下来从哪里续写”，不是“刚才发生过什么”：它不回滚文件，也不删除任何 entry。把分支当成时间机器用，是 Session Tree 的第一号误读。

CHAPTER 08 · COMPACTION & BRANCH SUMMARY

Compaction 改变 Context Projection，不擦除旧 Entry。

当前 coding-agent 源码用 firstKeptEntryId 指向保留边界；cut point 不落在 toolResult 上，超大单 Turn 会拆出 prefix summary。Branch summary 则把离开的路径带到新分支。

三个必须记住的设计点

触发是减法不是百分比：contextTokens > window − reserveTokens（packages/coding-agent/src/core/compaction/compaction.ts:237），默认预留 16384。窗口越小、预留越多，压缩来得越早——长输出场景常调大 reserve 防溢出。

cut point 只落在 user 或 assistant 上，绝不切断 toolResult（packages/coding-agent/src/core/compaction/compaction.ts:403）：call 与 result 拆散，下一次请求会被 provider 直接拒收。所以“保留约 20000 token”是近似值，边界必须让位于配对完整性。

摘要请求自身也要防爆：进摘要的单个 tool result 先截到 2000 字符（packages/coding-agent/src/core/compaction/utils.ts:89），摘要调用走独立会话、禁 tool、禁 cache retention——压缩不能反过来把上下文炸掉。

“压缩之后，旧消息去哪了？”

展开 30 秒模范答案

哪都没去。Compaction 只向 JSONL 追加一条 compaction entry，带 summary 与 firstKeptEntryId；被“丢弃”的只是 context 投影——buildContextEntries() 把保留段之前的路径换成 summary。能说出“投影变了、存储没动”这组词，这题就过关。

CHAPTER 10 · TUI & CLI MODES

TUI 是差分渲染器，不是 Agent 状态机。

Regular 模式使用主屏与 terminal scrollback；实验性 Fullscreen 使用 alternate screen 与自有 viewport。两者都比较前后行，只重画变化区域并用 synchronized output 降低闪烁。

差分帧对比台等待帧

高亮行 = 本帧真正重写的行；其余行只活在 previousLines 的比较里。

差分的前提是一条宽度合同

主屏模式下 scrollback 归用户，Pi 只能改自己视口内的行：doRender（packages/tui/src/tui-main-screen.ts:180）比较 previousLines，只重写 firstChanged 到 lastChanged，整段输出包在 CSI 2026 同步锁里（packages/tui/src/tui-main-screen.ts:212）——终端收到完整帧前不刷新显存，高频流式才不闪。

差分的隐藏合同是组件每行不得超宽：超宽在差分路径上直接抛错，而不是悄悄画歪，宁可崩也不错位。宽度变化则放弃比较、整屏重画——差分省的是重绘量，不省例外分支。

SOURCE-ALIGNED TEACHING SKELETON · ANSI CSI 2026 TUI

ANSI CSI 2026 同步差分终端重绘算法 (`DifferentialTuiRenderer`)

下面是根据 `packages/tui/src/tui-main-screen.ts` 整理的教学骨架，不是上游源码复制。真实实现还处理 viewport、Kitty image、cursor、scrollback、resize 与 full redraw 条件。

// packages/tui/src/differential-renderer.ts export class DifferentialTuiRenderer { private previousLines: string[] = []; private outputStream: NodeJS.WriteStream; constructor(stream: NodeJS.WriteStream = process.stdout) { this.outputStream = stream; } /// 差分渲染：仅输出发生变更的行，并使用 CSI ?2026h/l 消除屏幕撕裂 public render(nextLines: string[]): void { let buffer = "\x1b[?2026h"; // 开启 ANSI CSI 2026 同步输出锁 const maxRows = Math.max(this.previousLines.length, nextLines.length); for (let row = 0; row < maxRows; row++) { const prev = this.previousLines[row] ?? ""; const next = nextLines[row] ?? ""; if (prev !== next) { // 光标跳转到特定行（1-indexed）并清空行内容后覆写 buffer += `\x1b[${row + 1};1H\x1b[2K${next}`; } } buffer += "\x1b[?2026l"; // 关闭 ANSI CSI 2026 同步输出锁，触发终端原子绘制 this.outputStream.write(buffer); this.previousLines = [...nextLines]; } }

架构精要：Pi TUI 坚持将“呈现”与“状态”彻底分离，`render()` 不修改任何 Agent 运行时模型；`\x1b[?2026h` 确保现代终端在接收完整差分帧前不刷新显存，杜绝高频流式输出下的终端闪烁。

CHAPTER 11 · RPC / PROTOCOL / CLIENT

Pi 有两类不同协议：Coding Agent RPC 与实验性 Server Protocol。

RPC 是 stdin/stdout JSONL 命令事件流；独立 Protocol 使用 4-byte length + CBOR，Server Snapshot 是权威状态，Progress 只是临时提示，认证由 Transport Listener 负责。

消费者
选择一种集成方式
权威状态
由各自的 message/session snapshot 定义

两个协议面，两种失败模型

Coding Agent RPC 给人调试、给 IDE 嵌子进程：LF-only JSONL，肉眼可读、jq 可切。它刻意不用 Node readline（packages/coding-agent/src/modes/rpc/jsonl.ts:21）——readline 把 U+2028/U+2029 也当换行，而它们在 JSON 字符串内合法，一条合法消息可能被切成两帧。Server Protocol 给远程多客户端：4 字节大端长度 + 定长 CBOR（packages/protocol/src/framing.ts:28），半包、粘包、超限帧都在解码层拦下。

语义层面两边同一条铁律：snapshot 是权威，progress 是提示。PiClient 的会话租约从 acquire 开始（packages/client/src/client.ts:151），最后一个 lease 释放才 detach，断线不自动重连。把 TranscriptProgress 当状态存下来的实现，会在重连后永久错位。

边界

协议包不欠你认证：transport 拿到字节之前完成 authn/authz 是 listener 的责任。把 CBOR 帧直接暴露到公网，不是“用了 Pi 协议”，是给没上锁的门换了更精致的门牌。

面试考点 · FRAMING

“JSONL 分帧为什么坚持手工按 \n 切，不用 readline？”

展开 30 秒模范答案

因为 JSON 字符串内可以合法出现 U+2028/U+2029。Node readline 把它们当行分隔符，会把一条合法 JSONL 消息切成两行；协议层只能按 \n 分帧、容忍可选 \r，才能保证帧边界与 JSON 语法互不污染。

延伸：再对比 CBOR 面的 4 字节长度前缀——定长头让半包判断是 O(1)。两种 framing 回答的是同一个问题：流的边界不能靠内容推断。这是所有流协议面试的通用底题。

SOURCE-ALIGNED TEACHING SKELETON · CBOR PROTOCOL FRAMING

4 字节大端定长 CBOR 协议帧打包与流式解码 (`PiProtocolFraming`)

下面是协议两层组合后的教学骨架，不是上游源码复制：`packages/protocol/src/framing.ts` 只负责带 16 MiB 默认上限的 4-byte big-endian `Uint8Array` 分帧，CBOR 编解码属于 `packages/protocol/src/cbor/`。

// packages/protocol/src/framing.ts import * as cbor from "cbor-x"; export class PiProtocolFraming { /// 编码：[4-Byte Big-Endian Length] + [CBOR Payload] public static encodeFrame(message: unknown): Buffer { const payload = Buffer.from(cbor.encode(message)); const header = Buffer.alloc(4); header.writeUInt32BE(payload.length, 0); return Buffer.concat([header, payload]); } /// 解码：处理 TCP / WebSocket 流式粘包与半包分片 public static decodeFrames(incomingBuffer: Buffer): { messages: unknown[]; remaining: Buffer } { const messages: unknown[] = []; let offset = 0; while (offset + 4 <= incomingBuffer.length) { const frameLength = incomingBuffer.readUInt32BE(offset); if (offset + 4 + frameLength > incomingBuffer.length) { break; // 半包等待后续字节到达 } const framePayload = incomingBuffer.subarray(offset + 4, offset + 4 + frameLength); messages.push(cbor.decode(framePayload)); offset += 4 + frameLength; } return { messages, remaining: incomingBuffer.subarray(offset), }; } }

架构精要：Pi 独立 Server Protocol 采用基于大端长度头与定长 CBOR 的二进制打包方案，支持高吞吐远程会话租赁（Session Lease），与基于 stdin/stdout 的 LF-only JSONL RPC 形成清晰的双协议面。

CHAPTER 12 · SECURITY & PRACTICE

Pi 默认拥有启动用户的全部权限；Project Trust 不是 Sandbox。

内建 Read、Write、Edit、Bash 和 Extensions 都运行在 Pi 进程权限内。处理不可信仓库或无人值守任务时，真正边界必须来自 Container、VM、Micro-VM 或 Policy-controlled Sandbox。

PROBLEM SET 01 · 架构设计题

“如何利用 Pi 的 JSONL Session Tree 实现低成本的探索性任务分支与多路径假设验证？”

展开答题骨架与树形推演

【场景定义】 开发者需要对一个复杂的重构任务探索方案 A（重写接口）与方案 B（向后兼容补丁），希望能够在不同思路间自由切换，既保留每条分支完整的上下文事实，又不在磁盘上复制巨大的对话历史。

【归属层/故障机理分析】 属于会话树形持久化层（`Chapter 07: JSONL Session Tree`）。核心机理在于：Pi 抛弃了传统 Agent 线性数组或全局覆写的历史记录方式，将会话建模为 Append-Only 的有向无环图（DAG）。每个 Entry 均包含 `id` 与 `parentId`，分支切换仅需移动当前会话的 `leafId` 指针，即可通过反向遍历即时投影出目标分支的全部祖先消息。

【关键证据链/判定条件】
1. 单文件多分支：单个 `.jsonl` 文件同时记录多条互不干扰的演化路径，无惧并发写冲突。
2. 无损分支：创建新分支不需要对已有历史做任何 `UPDATE` 或 `DELETE` 操作，杜绝数据损坏风险。
3. 上下文投影：调用 `buildContextEntries()` 时仅提取从当前 `leafId` 向上回溯到根节点的活跃链路。

【解决方案与系统级防线】
• 使用 `SessionManager.branch(entryId)` 实施非破坏性回退，在分叉点开启新探索。
• 注意认知边界：Session Tree 只切换对话上下文，不负责文件系统状态回滚。文件级变更需配合 Git 提交或工作区分支进行隔离。

PROBLEM SET 02 · 故障排查题

“并行工具调用（Parallel Tool Batch）执行时，为什么工具完成日志乱序但最终 Transcript 顺序依然严格对齐？”

展开答题骨架与排序机制

【场景定义】 模型单次回合返回了 `[fetch_doc, grep_symbol, read_file]` 三个工具调用并开启并发执行，控制台日志显示耗时最短的 `grep_symbol` 最先完成，但最终发送给模型的上下文与 Transcript 顺序依然严格保持为原调用顺序。

【归属层/故障机理分析】 属于工具批次调度与事件生命周期（`Chapter 06: Tool Batch`）。机理分析：Pi 区分了执行完成事件（`tool_execution_end`，按物理实际完成时序发出，供 TUI 实时更新进度）与会话提交顺序（`toolResult` 消息，必须严格按照模型在 `AssistantMessage` 中声明的 Source Order 插入）。

【关键证据链/判定条件】
1. 调度执行：`runToolCalls()` 使用 `Promise.all` 并发触发，各 Promise 解决时立即广播局部进度事件。
2. 槽位预留：内部预先分配与声明顺序一致的 `resultsArray[index]` 槽位。
3. 消息生成：所有并发任务完成后，按索引顺序依次生成 `ToolResultMessage` 并追加到 Transcript。

【解决方案与系统级防线】
• 绝不可将实时的流式完成通知直接当作上下文提交顺序，避免破坏大模型关于多工具调用依赖的上下文假设。
• 若任一工具在定义中声明了 `sequential: true`，整批调用立即安全降级为严格串行流水线。

PROBLEM SET 03 · 安全攻防题

“Pi 默认以宿主全量权限运行，为什么说 Project Trust 不是 Sandbox？如何为企业构建真实防御边界？”

展开答题骨架与防御纵深

【场景定义】 用户克隆了一个公开的第三方开源项目并用 Pi 打开，项目目录内包含了恶意的 `.pi/extensions/auto-run.ts` 扩展脚本，试图在启动时窃取本地环境变量与 SSH 私钥。

【归属层/故障机理分析】 属于供应链安全与执行隔离边界（`Chapter 09: Extensions` & `Chapter 12: Security`）。核心认知：`Project Trust` 只是一个资源加载的准入门禁（Gate），用于决定是否执行该目录下的配置文件与扩展，它绝不是操作系统级别的安全沙箱。一旦用户点击了“Trust”，所有已加载的代码均在宿主 Node 进程内以当前操作系统用户身份全权运行。

【关键证据链/判定条件】
1. 未受信任状态（Untrusted）：Pi 拒绝加载 `.pi/` 下的项目级扩展与 prompt 模板，有效阻断恶意脚本初次加载。
2. 受信任状态（Trusted）：Jiti 将直接在主进程内求值 TypeScript 扩展，拥有完整的 `fs`, `child_process` 与 `net` 访问权限。
3. 权限继承：内建的 `bash`、`edit` 工具同样不具备任何内建特权降级或 chroot 隔离。

【解决方案与系统级防线】
• 生产与 CI 环境下必须将整个 Pi 进程置于容器（如 Docker、OpenShell）或 Micro-VM（如 Firecracker、Gondolin）中运行。
• 宿主与容器间仅允许受限挂载目标工作区，严禁挂载 `~/.ssh`、`~/.aws` 或根文件系统。
